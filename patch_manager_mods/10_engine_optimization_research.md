## Findings so far (all also in the knowledge DB: `functions`, `name_map`, `candidates`, `lessons`)
1. **Allocator stack (Phase 0-4, Ghidra decompile).** The exe's CRT is VS2008, static. `__heap_init` 0x9270E0 does `_crtheap(0xA806C8) = HeapCreate(mt ? 0 : HEAP_NO_SERIALIZE, 0x1000, 0)` and sets `__active_heap`(0xA80DD8) = 1 (system heap) unconditionally, so the V6/SBH code (`_V6_HeapAlloc` 0x921597, `___sbh_*`) is dead. `_malloc` 0x9215E6, `_calloc`/`__calloc_impl` 0x920D6C/0x931AB0, `_realloc` 0x934311, `_free` 0x91C6B5, `__msize` 0x92AACB reduce to `HeapAlloc/HeapReAlloc/HeapFree/HeapSize(_crtheap, ...)`. `operator new` 0x919723 loops `_malloc` + `__callnewh` then throws `bad_alloc`. Only `__chsize_nolock` 0x93811D uses `Heap*` outside the family. `VirtualAlloc/VirtualFree` are used only by dead SBH code, so the address-space census (1b) must use `VirtualQuery`. Consequence: the 1a census can be IAT hooks on `HeapAlloc/ReAlloc/Free/Size` filtered by handle 0xA806C8, and candidate A is feasible at those entry points (value depends on Wine's heap, unmeasured).
2. **GlobalMemoryStatus users:** 0x478A20 (called every MainLoop iteration from 0x78262C; also busy-wait `FUN_00478a00`, dead because float 0xA309A8 is never written) and the `CExoResMan` constructor 0x711360.
3. **Bug (candidate J1): the resource-manager cache budget is always 16 MB.** `CExoResMan::Constructor` 0x711360 sets `[this+4] = [this+8] = max(dwTotalPhys/2, 16 MB)` but compares with `SAR ECX,1; CMP ECX,0x1000000; JLE` (signed, 0x71143A-0x711442). `dwTotalPhys` is clamped to `0xFFFFFFFF` on >= 4 GB machines (measured under Proton wine: `totalPhys=4294967295 availPhys=4294967295 totalVirt=4294836224`), so the shifted value is -1 and the 16 MB floor wins on every modern system (Windows clamps the same way). `CExoResMan::Malloc` 0x712F30 subtracts each resource size from `[this+8]` and calls `FreeChunk` 0x712160 (evicts unreferenced resources, up to 1 MB per pass) whenever the size exceeds what is left. So the engine's resource cache holds about 16 MB. Effect on load time/IO is **unmeasured**; the smallest fix would be a ctor post-hook or 3-byte edit (SAR->SHR, JLE->JBE) plus a chosen cap, but nothing is installed.
4. **Name transfer validated:** all 61 GOG `CExoResMan` rows land on one constant delta (+0xF66A0); 60/61 hit Steam function starts and `ret N` agrees with the GOG param size on the large majority. Stored in `name_map` (`high`: Constructor, Malloc, FreeChunk, AsyncLoad; the rest `medium`, or `low` where `ret N` disagrees). `AsyncLoad` 0x715C00 is the resman worker thread (wrapper 0x7112F0, suspends itself when idle).

## How a patch installs runtime hooks under KPM (verified against `load_hang_probe_src/LoadHangProbe.cpp`)
KPM injects the patch DLL into the game process (its `DllMain(DLL_PROCESS_ATTACH)` runs) and installs the `[[hooks]]` detours from the `.hooks.toml`, which call exported functions (e.g. `HangProbeMainLoop`, `__cdecl`, args from registers per `[[hooks.parameters]]`). Anything else (IAT patching of the exe's imports, `wglGetProcAddress` wrappers, helper threads) is done by the DLL itself: `DllMain` reads its flag file (`hangprobe_debug.txt` style; `perflab_debug.txt` here) and returns early when absent (inert), else logs and starts threads. IAT writes need only `VirtualProtect` on the exe's import table (no `LoadLibrary` in `DllMain`, loader-lock safe). Detours run at function entry and cannot see return values, hence IAT hooks for the allocation census.
