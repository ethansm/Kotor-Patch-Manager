# U1 - NWScript virtual machine (Steam swkotor2.exe, sha256 6a522e71...)

## Summary (5 lines)
1. CONFIRMED runaway guard: instruction counter `[VM+0x24]` trips at `CMP dword ptr [ECX + 0x24],0x20000` (0x6FFA6D) -> returns -0x5d (0xFFFFFFA3); nesting limit is 8 (`CMP ... < 8` in ReadScriptFile 0x701FD0, error -0x5e). Neither was hit in runA as far as static code can tell (no counter exists; hook H4 below).
2. CONFIRMED partial leak: when the target-object lookup fails, ActionDoCommand (0x6699D0) never frees the popped script situation at all, and DelayCommand/AssignCommand (0x670370 / 0x66D9F0) free only the 0x28-byte struct with a bare `free` (0x9196FD), leaking its NCS code copy + saved-stack object/arrays (code copy avg ~45 KB per runA RT 2010 = 6662362 B / 149 loads). Frequency SPECULATIVE (needs invalid OBJECT_SELF / AssignCommand target).
3. CONFIRMED data-triggered crash path: ExecuteCommand (0x668FD0) bounds-checks the command id with a SIGNED `JGE`, and the id is read with `MOVSX word` (0x700275), so NCS command ids 0x8000-0xFFFF index the handler table at negative offsets (table = `malloc(0xDB4)` = 877 entries, 0x665F59).
4. CONFIRMED per-run churn: every RunScript does malloc+memcpy of the WHOLE NCS (0x6FF8A0) and every DelayCommand/AssignCommand/ActionDoCommand does a SECOND malloc+memcpy of it (0x703140), and the save path serialises that code blob per pending situation (0x703370 "CodeSize"/code) -> save size and heap scale with pending delayed commands x NCS size. The VM stack grows linearly (+0x100 entries, 5 B each) with unchecked mallocs (0x6FE460), freed at the end of every top-level run.
5. Pending DelayCommand events live in one sorted singly-walked list (node 0x18 B, insert is an O(n) scan, 0x51E220), drained per server tick by 0x51D790 (frame loop 0x407920 -> 0x51C470 -> 0x533830 -> 0x51D790 -> 0x5221B0 -> 0x6FD930 -> 0x702590); freed on execute (0x702590), on dead-target (0x520CE0 case 1 -> DeleteScriptSituation), and en masse on module unload (0x51DFE0). Heartbeats = one RunScript per object per >=6000 ms, polled per object per tick.

### Axis 1 - leaks / unbounded growth

**B1.1 [CONFIRMED, leak on failed target lookup, frequency SPECULATIVE].** The situation returned by StackPopCommand (0x703140) owns: the 0x28 struct, a malloc'd code copy (`[sit+0x10]`, size `[sit+0x14]`), and a stack object (`[sit+0]`, two arrays). Its correct free is DeleteScriptSituation 0x7037C0 (`FUN_006ff6e0(); FUN_009196fd(param_1);`, where 0x6FF6E0 frees `[+0x10]` and the stack object). Three command handlers drop it on the failure path without that:
- ActionDoCommand 0x6699D0, no free at all: asm `00669a30 750c JNZ 0x00669a3e` jumps straight to `00669a3e 33c0 XOR EAX,EAX` when the object-exists byte differs (`CMP EAX,ECX` with `[0x0099447f]`). Success path `00669a39 CALL 0x005e1340` hands over ownership (0x5E1340 frees via 0x6FDBB0 when the object has no action list, `bVar1 = *(int *)(param_1 + 0xec) != 0; ... else { FUN_006fdbb0(param_2); }`).
- DelayCommand 0x670370: `0067045d 837df400 CMP [EBP-0xC],0 / 00670463 8b45f4 ... 0067046d CALL 0x009196fd` (and again at 0x67048e when `[impl+4] != 1`): frees ONLY the 0x28 struct -> code copy + stack object/arrays leak.
- AssignCommand 0x66D9F0: `else if (local_14 != 0) { FUN_009196fd(local_14); }`, same partial free.
Size per leak ~ one NCS (avg 6662362 / 149 = ~44.7 KB per RT 2010 in runA) + ~1.3 KB of stack arrays. Whether the path occurs in vanilla scripts is SPECULATIVE (AssignCommand on an already-destroyed object is the plausible case). Runtime counters: H7/H8.

**B1.2 VM stack growth / free [CONFIRMED].** Push helper 0x6FE460: `if (*param_1 == param_1[2]) { param_1[2] = param_1[2] + 0x100; _Dst = FUN_00919723(param_1[2]*4...); _Dst_00 = FUN_00919723(param_1[2]); if (*param_1 != 0) { _memcpy(_Dst,(void *)param_1[4],*param_1 << 2); _memcpy(_Dst_00,(void *)param_1[3],*param_1); }` -> 5 B per entry (1 type byte + 4 value), +0x100 entries per step, both mallocs unchecked (alloc_sites: `operator_new 006fe4a3 006fe460 var:ECX no`, `006fe4bb ... var:EDX no`), O(n) copy per step. Initial capacity 0 at ctor (`FUN_006fe440` clear) -> the first push allocates 256 entries (1024 + 256 B). Free: at top-level RunScript start and end, `007022e7 CMP dword ptr [ECX+0x28],-0x1 / JNZ` then `ADD ECX,0x1AC / CALL 0x006fe440` (clear -> `FUN_009196fd(param_1[3]); ... (param_1[4])`). Not freed at the end of RunScriptSituation (0x702590 only clears at its START `FUN_006fe440()` and frees the slot) -> the arrays of the last situation run stay allocated until the next run (bounded retention <= 5*(0x10000+0x10) B per slice, see clamp in 0x6FE8E0). Worst case growth bound = instruction cap: 0x20000 instructions x <=1 push each = ~655 KB, reached through ~512 reallocs with O(n) copies (~170 MB memcpy total in the pathological case, SPECULATIVE estimate from the +0x100 step).

**B1.3 Runaway guard (TMI) [CONFIRMED].** `006ffa58 MOV EDX,[ECX+0x24] / ADD EDX,1 / MOV [EAX+0x24],EDX / 006ffa6d CMP dword ptr [ECX+0x24],0x20000 / 006ffa74 JL 0x006ffa80 / 006ffa76 MOV EAX,0xffffffa3` = -0x5d, returned out of ExecuteCode. The counter is per VM and reset only when a top-level run starts (`007022e3 CMP [ECX+0x28],-1`; sets `*(param_1 + 0x24) = 0`) and unconditionally in RunScriptSituation (`*(undefined4 *)(param_1 + 0x24) = 0;` 0x702590): nested ExecuteScript shares the parent's budget. Trip effect: 0x702850 sees `local_18 < 0`, logs with the script name (`FUN_00734010`) and calls implementer vtbl slot +0x10 with `-local_18` (report text lives in vtbl 0x9940D0 slot 4, not dumped: SPECULATIVE that it prints "TMI"); the stack is trimmed back (`FUN_006ff450(local_14)`) and the script is abandoned - no crash. Nesting guard: 0x701FD0 `*(int *)(param_1 + 0x28) = *(int *)(param_1 + 0x28) + 1; if (*(int *)(param_1 + 0x28) < 8)` else `uVar1 = 0xffffffa2` (-0x5e); same in 0x7029F0 (`7 < depth` -> -0x5e). There is NO guard on the script's own stack depth (no max in 0x6FE460) other than the instruction cap, and none on the pending DelayCommand count (see B1.5).

### Axis 3 - crash / robustness
**B3.1 Negative command id [CONFIRMED by asm].** Opcode 5 reads the id as a sign-extended 16-bit value: `0070021a 0fbe540102 MOVSX EDX,byte ptr [ECX+EAX+2] / SHL EDX,8 / AND EDX,0xff00 ... In 0x668FD0: `00668fd9 817d086d030000 CMP dword ptr [EBP+8],0x36d / 00668fe0 7d30 JGE 0x00669012` (signed) then `CMP dword ptr [ECX+EDX*4],0` and `CALL EAX`. So ids 0x8000-0xFFFF (negative) pass the check and read `table[id]` up to 128 KB BEFORE the heap block (table is `malloc(0xDB4)`, 877 entries = `local_8 < 0x36d`); non-zero garbage there would be called. Ids in [0x36D, 0x7FFF] are rejected with 0xFFFFF82E (-2002). A mod NCS with a corrupt/large id (e.g. from a miscompiled or hex-edited script) is the trigger; vanilla scripts are unaffected (R: unimplemented ids inside range have a NULL slot and return -2002 without crash). Severity: low likelihood (needs a bad NCS), potentially hard crash.

**B3.2 Lower-bound-less code pointer [CONFIRMED, low].** ExecuteCode 0x6FF9F0: `if (*param_2 == -1) return 0; if (param_4 <= *param_2 + 1) return -0x6b;` with no `< 0` test; JMP/JSR with a large negative offset reads `code[neg]`. Only reachable by a malformed NCS / corrupted save (InstructionPtr is read from the save at 0x703530 and used directly).

**B3.3 Unchecked allocations [CONFIRMED].** `6fe460`, `6ff8a0`, `703140`, `51e220`, `703530` (save CodeSize) all memcpy into an unchecked malloc result (alloc_sites.tsv rows above). `0x703530`: `local_24 = FUN_00919723(*(undefined4 *)(*param_2 + 0x14))` uses a size read from the save file; a huge CodeSize in a corrupt save is passed straight to malloc then `FUN_00719640` (read bytes) with no cap.

**B3.4 Nested RunScriptSituation clears the shared VM stack [SPECULATIVE reachability].** 0x702590 begins with `ADD ECX,0x1AC / CALL 0x006FE440` (clear the whole VM stack) and sets `[+0x24]=0` unconditionally, without testing the depth `[+0x28]`. If a script ever triggers an event handler that runs a situation synchronously (callers of 0x6FD930: 0x61F170, 0x617B40, 0x56EFD0, 0x5F2FE0, 0x62C630, 0x5221B0, 0x557440, 0x6010B0, 0x62B8E0, 0x5D99D0), the outer script's stack would be wiped and its instruction budget reset. No evidence it happens in vanilla (timed events are queued and run from 0x51D790 at depth -1). Hook H9 detects it.
