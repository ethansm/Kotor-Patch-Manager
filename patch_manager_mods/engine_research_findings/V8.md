## 5-line summary
1. K3 (leading newline): NO BUG in K2. Every CSWSItem property builder (0x609110..0x610FC0, 0x615FF0) APPENDS `"\n"` (`acc = acc + "\n"`, asm `MOV ECX,[EBP+8]` = accumulator, the `"\n"` temp is the 2nd operand of `CALL 0x733df0`), the final description is `props + description` (0x607790, asm 0x6079db-0x6079de) and the journal entry is `"<planet>:\n" + body` (0x7fc4bb-0x7fc52c); nothing prefixes a newline and `SetText` 0x416E30 does not need to trim. Only 2 of 136,540 TLK strings start with `"\n"` (strref 124480 / 124904, "Droid Ion Blast" descriptions). One hypothetical empty line = 38 px at 3840x1600 (`fnt_d16x16b` fontheight 0.19 x fs 2.0).
2. Listbox client margin: K2 does the SAME as K1: `CSWGuiListBox::SetExtent` 0x41D710 always does `width -= [this+0x118]` (scrollbar width) and `left += it` under LEFTSCROLLBAR (asm 0x41d77e `2b 45 ec`, 0x41d775 `03 55 ec`). User's description boxes (inventory LB_DESCRIPTION 246 units, journal 232, upgrade LB_DESC 219) all carry a 16-unit scrollbar = 76.8 px (6.5 % of the box) at 3840 wide (800-unit GUI space x 4.8). The K2 PADDING validator 0x41E9D0 tests the OLD stored byte, not the new value (harmless; all 58 shipped/override listboxes have PADDING 0). Verdict NO BUG (by design).
3. Fonts: (a) `spacingR` is stored at font+0x10 by the TXI parser 0x424F60 and read by BOTH the breaker (0x47b223 etc., `spR*scale*100` px per glyph) and Draw (0x47c5aa, effectively `spR*texW*scale^2*1e4/W` px = 6.7 % of the breaker's value at 3840); all 15 stock font TXIs have spacingR = 0 except `fnt_console` (0.02), so no effect on this install. (b) NO hard-coded default overrides an authored FONT (0x4174d2/0x416a61 only fill a missing FONT), BUT the font-name resolver 0x413CE0 force-appends `b` to every authored name (a dead "Use Small Fonts" read is overwritten by `MOV byte ptr [EBP-2],2` at 0x413d35): `dialogfont10x10` renders as `dialogfont10x10b`, whose stock TXI fontheight is 0.16 = the 16x16 height. That explains K1's "10x10 renders as 16x16" mystery in K2 data terms (4 HUD controls). (c) Other glyph-advance truncations exist (first char of every line, break widths, Draw's [+0x40]==0 fallback) but each is a plain ftol, bounded by 1 px per occurrence.
4. CORRECTION to V3 F2/L4: with the real K2 TXI tables (spacingR 0, texturewidth 2.56 / 5.12) every stock glyph advance at fs 1.0/2.0/3.0 is within 0.0006 of an integer, so the vanilla `+0.25` was already exact (mean error 0.000 px; plain truncation would under-measure 46/95 and 58/95 ASCII glyphs by 1 px). The live `k2-wrap-measure-fix` (0x47B232 -> 0.5) changes 0 of 95 glyphs at fs 2.0 (3840x1600); it only changes results at fs 1.5 (2560 wide: 29 / 14 glyphs +1 px). It is a harmless no-op here, not the 0.25 px/char bug V3 modelled with uniform fractions.
5. No BUG verdict needs a new hook. Log-only probes with windows are given in (c): P1 0x416E43 (SetText leading bytes), P2 0x47AFAE (CAurFontInfo values used by the breaker), P3 0x413DC8 (authored -> resolved font name). None overlaps any of the 198 live hooks (+-8 bytes).

## (b) Findings

### F1. K3: how K2 builds item and journal descriptions (question 1)

**F1.1 The accumulator pattern is "append", not "prefix".** Every property function takes the output CExoString as its stack argument (`ret 4`, `[EBP+8]`) and does `acc = acc + piece` through `0x733df0` (CExoString::operator+ with ECX = lhs). Block header (0x60a990):
```
0060aab1  6808769900   PUSH 0x997608          ; ":\n"   (bytes 3a 0a 00 00 at 0x997608)
0060ab06  8b4d08       MOV ECX,dword ptr [EBP + 0x8]     ; ECX = acc (lhs)
0060ab09  e8e2921200   CALL 0x00733df0        ; tmp = acc + <strref 0x1cb5d>
0060ab27/0060ab2c  ... CALL 0x00733df0        ; tmp2 = tmp + ":\n"
0060ab54  8b4d08       MOV ECX,dword ptr [EBP + 0x8]
0060ab57  e8648c1200   CALL 0x007337c0        ; acc = tmp2
```
Block end (0x60a990, quoted decomp `FUN_00733570(&DAT_00986b2c); ... FUN_007337c0(uVar3);`):
```
0060b2b2  682c6b9800   PUSH 0x986b2c           ; "\n" (byte 0a 00 00 00 at 0x986b2c)
0060b2d4  8b4d08       MOV ECX,dword ptr [EBP + 0x8]     ; ECX = acc
0060b2d7  e8148b1200   CALL 0x00733df0         ; acc + "\n"
0060b2fc  e8bf841200   CALL 0x007337c0         ; acc = ...
```
The `"\n"` temp is always the SECOND operand. Whole-dump scan (every `PUSH 0x986b2c` in `decomp/*/*.asm`: 31 files; my script printed, for the item builders, the ECX source of the next `CALL 0x00733df0`): all 20 sites in 0x609110..0x610FC0 (excluding 0x60B6B0/0x60E0D0 below) have ECX = `[EBP+8]` (accumulator, 0x609110 x3, 0x609CB0 x2, 0x60A0D0 x2, 0x60A4F0 x2, 0x60A990 x2, 0x60B360 x2, 0x60D8E0, 0x60DA50, 0x60E6B0, 0x60EA50 x2, 0x60FEE0, 0x610FC0) or the equivalent local accumulator `[EBP-0x20]` (0x615FF0); 0x608F30 (GetSortedPropertyStrings) uses `MOV ECX,dword ptr [EBP + 0xc]` (its out/acc argument, asm `00609083`). 0x60B6B0 (damage, 1 site, 0x60c2a8) and 0x60E0D0 (1 site, 0x60e3bc) build the `"\n"` early and use it as the LAST operand of a left-folded chain starting at `MOV ECX,dword ptr [EBP + 0x8]` (0x60c342 / 0x60c474: `LEA EAX,[EBP + 0xfffffdc8]` pushed as rhs). Entry line formats are suffix-terminated: `%s: +%d\n` (0x99765C), `%s: %d\n` (0x997674), `%d-%d\n\n` (0x99763C), `%s: %dm\n` (0x997650), `%d%% %s, %d %s, %s %d\n` (0x9976A8), `%d/%d\n` (0x9976E0); strings dumped from the vanilla exe, referenced from `strings.tsv` (functions 0x60b6b0, 0x60d8e0, 0x60da50, 0x60e6b0, 0x60ea50, 0x610fc0).

**F1.2 Final assembly: properties FIRST, description after.** 0x607790 asm:
```
0060794d  05b0020000  ADD EAX,0x2b0               ; this+0x2b0 = description CExoLocString (identified branch)
00607972  e8d9791300  CALL 0x0073f350             ; language id (client app [0xa1b4a4]+4)
```

Result = `props + description` (decomp `FUN_00733df0(local_3c,local_24); FUN_007337c0(uVar3);`). The accumulator `[EBP-0x28]` starts as `FUN_00733540` (empty). So a leading `"\n"` can only come from the first emitted piece. The first piece of the first non-empty block is the header strref + `":\n"` (e.g. "Attributes Required:\n", strref 0x1CB5D read from `dialog.tlk`), or an entry line; none starts with `"\n"`. After the last block the accumulator ends with `"\n"` (blank separator line), then the description follows. K2 therefore shows `Header:\nline\nline\n` + `\n` + description, i.e. a BLANK LINE BETWEEN properties and description (by design), not a leading blank line.

**F1.3 Other consumers do not re-add a leading newline.** 0x8D9EE0 (workbench-style skill/item description, strings `base_skill`/`skillLevel`, strref 0x1C2E5 "Skill Required to Create: ") builds `X + "\n" + Y + "\n" + description`: asm `008da850  e89b95e5ff  CALL 0x00733df0` with `LEA ECX,[EBP + -0x7c]` (lhs = a non-empty label), `008da8a5 ... CALL 0x00733df0` (+ second `"\n"` temp pushed at 0x008da817 / 0x008da82b as rhs). 0x615FF0 (upgrade screen) appends (`006168e8..0061690d`, ECX = `[EBP-0x20]`). 0x8D50E0 has the same two `PUSH 0x986b2c` (0x8d5bcf / 0x8d5be3; ECX `[EBP-0x94]`), not read further (SPECULATIVE same shape).

**F1.4 Journal.** Selected quest entry (0x7FC390): decomp `FUN_00733570(&DAT_00997608); ... FUN_0071dee0(local_58,local_44); FUN_00733df0(local_68,local_60); uVar2 = FUN_00733df0(local_70,local_3c); FUN_007337c0(uVar2);` and asm `007fc4bb PUSH 0x997608`, `007fc503 CALL 0x00733df0` (lhs = TLK string from `[0xa1b4b0]`, ECX `[EBP+0xffffff6c]`), `007fc52c CALL 0x00733df0` (lhs = that + `":\n"`, rhs = entry body `[EBP-0x38]`), `007fc551 CALL 0x007337c0`, then `007fc61a CALL 0x00416e30`. Text = `"<planet name>:\n" + body`; header first, nothing prefixed. If the entry has no planet (`CMP dword ptr [EAX + 0x34],-0x1` at 0x7fc462) the body goes straight to SetText.

**F1.5 No setter trims, none needed for code-built text.** `0x416E30` (full asm quoted in (a)) is assign + `[+8] = -1` + forward to the string object (vtable +0x18) + `0x417800` relayout. A trim would belong after `00416e3e CALL 0x007337c0`.

**F1.6 Data side: leading `"\n"` exists in TLK.** Parsing `dialog.tlk` (136,540 entries, game dir): exactly 2 strings begin with `\n` or `\r`: strref 124480 (0x1E640) and 124904 (0x1E7E8) = `"\nCharges: Using this item consumes one charge. ... \n\nThe "Scrambler" was de..."`, neighbours 124479 / 124903 = "Droid Ion Blast Mark I". These are item descriptions; when the item has no property block (props = "") the description opens with one empty line. No other description or journal entry in vanilla `dialog.tlk` does. Mod items (UTI inline text) not scanned. Cost of an empty line: the breaker's newline branch (V3 F1, asm `0047b137 CMP EDX,0xa`) pushes a zero-width line; Draw line height = `fontheight * this+0x54 * 100`.

**F1.7 Empty-line height at 3840x1600 (fs 2.0).** fs = `1 + 0.5*floor((3840-1022)/1024)` = 2.0 (V3: `0x479AB0`). Stock TXI values (read from the TPC-embedded TXI in `swpc_tex_gui.erf`): `dialogfont16x16(b)` fontheight 0.16, `fnt_d16x16(b)` fontheight 0.19. The description listboxes (`inventory_p` LB_DESCRIPTION, `journal_p` LBL_ITEM_DESCRIPTION, `upgrade_p` LB_DESC, `abilities_p` LB_DESC) author PROTOITEM TEXT FONT `fnt_d16x16` (override GUI parsed with pykotor), resolved to `fnt_d16x16b` (F3b). One line = float32(0.19)*2.0*100 = 37.9999995 px (`GetFontPixelHeight` 0x47a510: +0.5 then ftol = 38). Box height: inventory LB_DESCRIPTION is 300 units x (1600/600) = 800 px; one empty line = 4.75 % of it. For `dialogfont16x16b` labels the line is 32 px (31.9999993 + 0.5 -> 32). Moot for code-built text; applies to the 2 Droid Ion Blast descriptions only when they have no properties. SPECULATIVE whether the user's override `dialogfont16x16b.tga` ships a different TXI (none on disk, see F3a).

### F2. Listbox client rect margin (question 2)

**F2.1 K2 does the same unconditional reservation.** `CSWGuiListBox::SetExtent` 0x41D710 (bridge row `0x41bf80 CSWGuiListBox::SetExtent -> 0x41d710 ret 4`; confirmed `ret 4`, callees 0x41ea50/0x41d810/0x414d80, and the K1-style 4-int rect store):
```
0041d758  8b9118010000  MOV EDX,dword ptr [ECX + 0x118]     ; scrollbar width (embedded control this+0x10C, +0xC = width)
0041d770  7409          JZ 0x0041d77b                       ; bit 4 of [this+0x2cc] = LEFTSCROLLBAR (set by 0x41d8e0)
0041d772  8b55f0        MOV EDX,dword ptr [EBP + -0x10]
0041d775  0355ec        ADD EDX,dword ptr [EBP + -0x14]     ; left += scrollbar width (LEFTSCROLLBAR only)
0041d77b  8b45f8        MOV EAX,dword ptr [EBP + -0x8]
0041d77e  2b45ec        SUB EAX,dword ptr [EBP + -0x14]     ; width -= scrollbar width, ALWAYS
0041d781  8945f8        MOV dword ptr [EBP + -0x8],EAX
```
Decomp: `local_c = *(int *)(param_1 + 0xc) - local_18;` and `if ((*(uint *)(param_1 + 0x2cc) >> 4 & 1) != 0) { local_14 = local_14 + local_18; }`. The result is stored through `0x414d80` into `this+0x29c..0x2a8` (client rect: x, y, w, h; `[+0x2a4]` w, `[+0x2a8]` h are what the organizers read: asm 0x41ec10 `MOV EAX,dword ptr [EDX + 0x2a8]`). `+0x118` is the width field of the embedded scrollbar control: `0x41d810` addresses it through `param_1[0x43]` (= this+0x10C, the vtable of the embedded scrollbar) and `(param_1[1] + param_1[3]) - local_c` for its left. The brief's "does K2 do the same" = YES. Whether the bar is actually drawn when content fits is not shown here (not needed: the reservation is in SetExtent, unconditional).

**F2.2 PADDING validator (K1 0x41C190).** K2 0x41E9D0 (`ret 4`, called by Load 0x41ffd0 and 0x41d430):
```
0041e9ea  0fb68ad0020000  MOVZX ECX,byte ptr [EDX + 0x2d0]   ; OLD stored padding
0041e9fa..0041e9ff        CDQ / SUB EAX,EDX / SAR EAX,1  ; [this+0x2a4] / 2   (client width / 2)
0041e9ff  3bc8            CMP ECX,EAX
0041ea01  7f1c            JG 0x0041ea1f                      ; reject -> skip store
0041ea06  0fb688d0020000  MOVZX ECX,byte ptr [EAX + 0x2d0]   ; OLD again vs [this+0x2a8] / 2 (0x41ea10..0x41ea1d)
0041ea24  8a4d08          MOV CL,byte ptr [EBP + 0x8]        ; the NEW value, only used here
0041ea27  8888d0020000    MOV byte ptr [EAX + 0x2d0],CL
```
Decomp: `if (((int)(uint)*(byte *)(param_1 + 0x2d0) <= *(int *)(param_1 + 0x2a4) / 2) && ((int)(uint)*(byte *)(param_1 + 0x2d0) <= *(int *)(param_1 + 0x2a8) / 2)) { *(undefined1 *)(param_1 + 0x2d0) = param_2; ...`. The test compares the PREVIOUS padding with half the client size; `param_2` (new value) is never compared. KMRP's text ("a value greater than half ... is rejected") is not what K2 does. Effect: a first assignment always passes (old = 0 <= anything, including the not-yet-set client rect 0 at Load time: Load calls it before the extent is applied, decomp order in 0x41ffd0 `... FUN_0041d8e0(uVar1); uVar3 = FUN_00718c80(... "PADDING" ...); FUN_0041e9d0(uVar3);`), so the guard is effectively inert and a "corrected" check against the NEW value would reject all nonzero authored PADDING at load (client rect 0). Not a bug worth fixing.
PADDING is read by the organizers as a row/inset constant (`0x41eaec`, `0x41ebfa`, 0x41f170 x7, 0x41f7f0 x4: e.g. decomp 0x41ea50 `local_18 = (uint)*(byte *)(param_1 + 0x2d0) + *(int *)(param_1 + 0x2c4);` = padding + item height) but every listbox in the user's setup has PADDING 0: scan of all `*.gui` in `Override/` (58 listboxes) and in `ultrawide_gui/originals/` (58): `PADDING {0: 58}`, scrollbar widths `{16: 56, 15: 1, 14: 1}`, 1 LEFTSCROLLBAR.
