# W5: SNDRI (Force Software apply kills sound) + NETOVF (net send ring overflow) -- patch-ready designs

Summary (5 lines):
1. SNDRI CONFIRMED: Options > Sound apply (0x7DB680 -> 0x70B9B0 -> Initialize 0x7051C0) takes the `[this+0xD4] != 0` teardown branch, stores `[+0xD4]=0` at 0x7054CE, and the common tail at 0x705559 then sees 0 and calls `AIL_quick_shutdown` (0x705562) and returns 0. The startup block (0x7054DA..0x705527) is never reached in the same call. Sound stays dead until a second apply (which takes the `+0xD4==0` startup branch at 0x70521A). `+0xD4` = Miles HDIGDRIVER (written by `_AIL_quick_handles` at 0x70550B).
2. SNDRI fix = 12-byte patch at 0x7054CE..0x7054D9: `FF 15 7C 65 98 00` (CALL [AIL_quick_shutdown]) + 6-byte NOP, which falls straight into the startup block at 0x7054DA. All register/flag state checked; no branch target inside the range (scan empty). The tail then runs the existing restore code (replay queue, `0x70CAA0`/`0x70DED0`) in the same call.
3. NETOVF CONFIRMED defect: after the overflow test at 0x7040F7 the log string is built into a CExoString that is never written anywhere (only destroyed at 0x704410) and the two memcpys still run (0x704428, 0x70444E). Heap overflow only when `idx + 4 + len > 0x20000` (len >= 65,534 worst case idx 0xFFFF; len >= 131,069 at idx 0). Observed max 14,035 B: not reachable by a single message in normal play.
4. NETOVF fix = two patches: (A) 0x704406..0x704414 (15 bytes) -> destroy string, `XOR EAX,EAX`, `JMP 0x70446D` (return 0 = same value as the peer-NULL path); (B) 0x7040EF `ADD EAX,0x10000` -> `MOV EAX,0x20000` so the branch fires only on a true heap overflow (the stock test is also a ring-lap test that does not account for writer wrap, see F7).
5. Verdicts: SNDRI `FIX 0x7054CE..0x7054D9 FF 15 7C 65 98 00 66 0F 1F 44 00 00` ; NETOVF `FIX 0x704406 (15 B) + 0x7040EF (5 B)`. Hook points for runtime proof are in section (c).

All addresses are Steam swkotor2.exe sha256 6a522e71 (vanilla_clean backup bytes were read read-only to verify every `original_bytes` below; they match the .asm dump).

**F2. What is `+0xD4`.** The only writer of a non-zero value is `_AIL_quick_handles(this+0xD4,0,0)` at 0x70550B (push `LEA EAX,[this+0xd4]` via `00705505 ADD EAX,0xd4 ; 0070550a PUSH EAX ; 0070550b CALL [0x00986578]`), i.e. **`+0xD4` is the HDIGDRIVER handle** (also `decompile: _AIL_quick_handles_12(param_1 + 0xd4,0,0);`). Complete list (exact scan `grep -rn -E "\+ 0xd4\]|ADD [A-Z]+,0xd4$" decomp/{62,63,70,71,72,73}/*.asm`):

- WRITE handle: 0x70550B (via pointer, `_AIL_quick_handles`)

**F3. Intended flow.** The function is a toggle: `+0xD4==0` means "not running -> start Miles then build everything", `+0xD4!=0` means "running -> tear down". Evidence that the author intended teardown+restart in ONE call: the teardown saves state that only the tail restores: 0x70DDE0 saves stream position `param_1[0x51] = _AIL_stream_position_4(*param_1)` after `_AIL_pause_stream_8(*param_1,1)`, and the tail (`0070caa0`, `0070ded0`, `0070ed50(1,1)`) re-opens and `_AIL_set_stream_position_8(*param_1,param_1[0x51])`. The decompile (see 0x7054CE) shows no shutdown before the startup block, and the common tail uses `+0xD4==0` as "startup failed" and returns 0, so a successful teardown is indistinguishable from a failed startup. GOG: `00634140 CExoSoundInternal Initialize 16`, `0063a950 CExoSound ReInitialize 8`; no separate "ReInitialize" exists on CExoSoundInternal in the GOG list, i.e. the single Initialize serves both roles in the shipped design (structure-based, SPECULATIVE on the original source). Second caller: only the CExoSound ctor 0x70B4E0 (`FUN_007051c0(param_2,param_3,param_4,param_5);` at 0x70B581), which runs once at startup with `+0xD4==0` (set by 0x704E8F). No caller re-initialises after a reapply (call list of 0x70B9B0: only 0x7DB680 at 0x7DB79A; `callgraph.tsv`: `007db680 007db79a 0070b9b0 CALL`). So the user must press apply a second time (the second call hits JZ 0x7054DA and restarts everything, replaying the saved sources) or restart the game.
Side finding: Force Software has no other effect in Initialize: arg3/arg4 are only touched by the dead pair `00705539 CMP dword ptr [EBP + 0x14],0x0 ; 0070553f MOV dword ptr [EBP + 0x10],0x0` and `imports.tsv` has no `_AIL_open_3D_provider`/`_AIL_set_preference` use in this function. The EAX/3D-provider selection was stripped from the Steam build (consistent with U2 Q1). The apply is therefore only ever useful as "reset Miles"; the fix restores that.

Ring layout (object = `new(0x2007c)`, U6): data bytes `[0 .. 0x1FFFF]` (64 KB ring `[0..0xFFFF]` + 64 KB slack), `+0x20000` READ idx (consumer), `+0x20004` WRITE idx, `+0x20008` owner, `+0x2000C` peer, `+0x20010` started flag, `+0x20060..0x20078` BN state (0x7045B0). The send writes into the PEER's data and indices (`[peer+0x20004]`). Record = `len(4) | payload | pad` with total `4 + len + (4 - len%4)` (1..4 pad bytes; an aligned len wastes 4).

Exact overflow limits:
- Heap overflow (buffer 0x20000 B, then `+0x20000` indices/owner/peer): bytes written = `[w, w+4+len)`; overflow iff `w + 4 + len > 0x20000`, `w` in `[0, 0xFFFF]` after the wrap on 0x7040B7. Worst case w = 0xFFFF: `len > 0x20000 - 4 - 0xFFFF = 65,533`, i.e. len >= 65,534 (`newW` exceeds by up to 4 pad). Best case w = 0: len >= 131,069.
- Stock "overflow" test (log/no-op today): `newW > r + 0x10000` (unsigned `JBE` skip). With a drained ring (`w==r`), that is `len + 8 > 0x10000` roughly, i.e. a single message with len > ~65,528 (minus pad) at w==r.

(4) Live registers/flags: `CMP [EBP-0x14],EAX` at 0x7040F4 rewrites EFLAGS before the JBE; EAX is dead after the CMP (`0070410c`.. loads reassign EAX/ECX/EDX; 0x704418 `LEA EAX,[EBP+0x10]`). MOV does not alter flags, and none are consumed between 0x7040EF and the CMP.

**F7. Reachability in single player.**
(i) Single message >= 65,534 B (heap overflow): SPECULATIVE-but-not-observed. All 9 callers: 0x647050 (server -> player, `0x50` + major + minor payloads from CSWSMessage composers; 128 call sites), 0x87A350 (client -> server `0x70` messages; `FUN_00704060(uVar1,puVar2,local_8,uVar3)`), 0x665280 (`0x53` + string), 0x884450 (`0x73` + string), 0x7045B0 and 0x883560/0x8FACA0 (BN "BNCSU" + <= 255-byte module string: `local_18 + 9`, local_1c is a byte), 0x704970, 0x812350 (`%c%s.%s` "Module" strings). The string senders are tiny. Large ones can only come from the 0x647050/0x87A350 composer buffers (area/object/inventory updates, DumpPlayer, save/load state). Runtime max seen 14,035 B (brief), 4.7x below the 65,534 worst-case bound, so the heap overflow was not observed in play. Can a single composer exceed 64 KB? Not decided statically (the composer buffer cap was not read): SPECULATIVE; mod-heavy saves or very large inventories are the only plausible sources.
(ii) Backlog/lap (stock log condition): the reader runs once per frame (client 0x781BE0 -> 0x703F30; server 0x533830, U6 F4/5.1). A burst of messages totalling > ~64 KB between two drains (e.g. a server module load sending many (area/object) messages while the client drain is blocked) would trigger the stock branch. Note the stock test only sees the case where the writer has not wrapped: `newW` is computed from the wrapped `w` (`0x7040B7 MOV [EBP-0x10],0`) but compared with the unwrapped `r + 0x10000`: after the writer wraps (w small) while the reader is still at e.g. r=0xF000, free space is `r - w`, yet the test allows up to `r + 0x10000 - w` => lap overwrite of unread data goes UNDETECTED (false negative, derived from the quoted instructions, not tested). So the stock branch is NOT a reliable ring-full detector and patch A on the unmodified condition would only catch the non-wrapped lap; this is why Patch B (heap-only) is the safe minimum.
(iii) Because the branch currently does nothing visible (no log written), a user cannot tell whether it fires today; the counter in (c) is required before deciding to also enforce lap protection.
