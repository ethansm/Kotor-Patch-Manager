# T4: H1/F1 -- can a movie during a load stop message pumping so WM_ACTIVATEAPP(TRUE) is never dispatched?

## 5-line summary
1. The literal H1 (PlayMovies stops pumping, activation lost in the queue) is REFUTED: the [EBP-0x20] cut-off is only set when `this+0x254==1`, and `this+0x254` is the "user confirmed Quit" flag (writer 0x796de6 in callback 0x796da0, registered by the WM_CLOSE handler 0x796ba0). Otherwise PlayMovies pumps every 501 spins with an unfiltered PeekMessage/GetMessage/Dispatch (0x4094F0); WM_ACTIVATEAPP is a SENT message and cannot be dropped by that drain.
2. The movie subsystem CAN still produce the exact hang signature (`[0xA1B4E0]==0`, never changes, startup toggles 0,1,0,1,0): the movie THREAD (0x40D430) ends a movie whose own window saw WM_ACTIVATEAPP(FALSE) by `PostMessageA(main, 0x1C, 0, 0)` (asm 0x40D69E) i.e. a SYNTHETIC deactivate that the OS never undoes, and it sets `[0xA1B76C]=1` (0x40D637), which makes 0x40BF40 skip its forced re-activation (`CMP [0xA1B76C],0; JNZ` at 0x40BF92). WndProc then runs 0x40BC40 -> `[0xA1B4E0]=0` (0x40BCE1). No further WM_ACTIVATEAPP(TRUE) is generated because the OS believes the app is already active.
3. Second, independent gate in the WndProc WM_ACTIVATEAPP(TRUE) branch (0x40B5E8..0x40B6CC): in fullscreen (`Aurora vtable+4 != 0`) activation is only honoured if `[0xA1B4BC]==0 && [0xA1B4D4]==0`, otherwise only if `GetTickCount()-[0xA1B6F4] < 1000` (0x40B6A9 `CMP EAX,0x3E8`). A deactivate that arrives while a movie is playing sets [0xA1B4BC]=1 (0x40B54B), so a late reactivation (> 1 s) is ignored. Also the whole case is skipped when `[0xA1B48C]==0` (0x40B4AD), which is true during window re-creation (0x409750 sets it to 0).
4. Only two writers of [0xA1B4E0] exist (0x40BCE1 =0 in 0x40BC40, 0x40BD04 =1 in 0x40BCF0; 0x40BC40/0x40BCF0 called from WndProc 0x40A750, 0x409750, 0x40BF40); PlayMovies only reads it (0x79886E, 0x798B39) and skips restoring the input flag if it changed during the movie.
5. Verdict: PARTIALLY -- the pump cut-off does not explain it; a movie-thread synthetic WM_ACTIVATEAPP(0) plus the a1b76c / 1000 ms / a1b4bc gates does (proven sufficient by code, occurrence unproven -> SPECULATIVE until probed). Probe list at the end (entry/exit of 0x798820, 0x40D637/0x40D692 in the movie thread, WndProc case entry 0x40B4AD, movie-window deactivate 0x40C6B3, writers 0x40BCE1/0x40BD04).

## Verdict
PARTIALLY. (a) The message-pump cut-off (`[EBP-0x20]`, `this+0x254==1`) cannot explain the hang: `+0x254` is the quit-confirmed flag, set only by 0x796DE6, and otherwise PlayMovies pumps every 501 spins; WM_ACTIVATEAPP is a sent message dispatched by any unfiltered PeekMessage/GetMessage (0x407E65/0x4094F0) and cannot be lost there. Static proof of sufficiency only; occurrence is SPECULATIVE until the probe log shows 0x40C6B3 / 0x40D692 hits in a hung launch.
