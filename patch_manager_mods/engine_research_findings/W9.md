### 3.3 Why the data path is safe (re-checked here, from the asm)

### 6.2 Shared shim and per-site retarget (VERIFIED bytes; all three sites: exe==asm True, interior targets none, start/end targets none, rel-branch = the CALL itself, which is the only thing rewritten)
Caller convention at every site (quoted above): `PUSH reg(situation)` / `CALL 0x9196FD` / `ADD ESP,4` (`83 C4 04`, verified at 0x670472, 0x670493, 0x66DAD1). The shim must be cdecl-shaped (callee leaves the caller's argument on the stack):
```
S+0  FF 74 24 04        push dword ptr [esp+4]      ; copy of the argument
S+4  E8 <rel32>         call <dispose>              ; ret 4 pops the copy;  rel32 field at S+5 = <dispose> - (S+9)
S+9  C3                 ret                         ; caller's ADD ESP,4 pops the original
```
**<dispose> must be 0x7037C0, not 0x6FDBB0**, or ECX must be loaded: `0x6FDBB0` is a thiscall method that dereferences its ECX: `006fdbb3 PUSH ECX / 006fdbb4 MOV [EBP-4],ECX / ... 006fdbbb MOV ECX,[EBP-4] / 006fdbbe 8b491c MOV ECX,dword ptr [ECX + 0x1c]` and only then calls 0x7037C0; all three engine callers set `MOV ECX,[0x00a1b4a8]` first (0x5E135F, 0x53E80D, 0x520E67). `0x7037C0` only stores ECX (`007037c6 MOV [EBP-0x18],ECX`, never read again; verified by reading the whole asm) and is `RET 4`, so it is ECX-independent and does exactly what 0x6FDBB0 does with the same argument. ECX at the three sites: 0x67046D and 0x66DACC load `MOV ECX,[EBP-0x18]` (= the situation pointer, non-null by the preceding `CMP/JZ`; `[ECX+0x1C]` is inside the 0x28-byte struct, readable) so the 0x6FDBB0 shim would not crash there by coincidence; at 0x67048E ECX is NOT set (`MOV EAX,[EBP-0x1c] / PUSH EAX`), so ECX is whatever 0x6FDB30/0x703140 left in it: not guaranteed readable. Therefore:
* Variant A (recommended, 10 bytes): `FF 74 24 04 E8 <0x7037C0 - (S+9)> C3`.
* Variant B (engine-faithful, 16 bytes): `8B 0D A8 B4 A1 00 / FF 74 24 04 / E8 <0x6FDBB0 - (S+15)> / C3` (`mov ecx,[0xA1B4A8]` = the VM, as at the engine's own call sites).
* The brief's literal form `FF 74 24 04 / E8 <rel32 to 0x6FDBB0> / C3` (shown for completeness): rel32 field = `0x6FDBB0 - (S+9)`. Not recommended (reason above).
Example with S = 0x10002000 (computed): variant A `FF 74 24 04 E8 B7 17 70 F0 C3` (rel32 0xF07017B7); variant B `8B 0D A8 B4 A1 00 FF 74 24 04 E8 A1 BB 6F F0 C3`; literal-0x6FDBB0 form `FF 74 24 04 E8 A7 BB 6F F0 C3`.
Per-site retarget: new rel32 = S - (site + 5), little-endian; bytes before/after (before = verified exe bytes; after for S = 0x10002000):
| site | function / branch | before (5 B) | after (5 B) | new rel32 (general) | nearest live hook |
|---|---|---|---|---|---|
| 0x67046D | DelayCommand, object lookup failed (0x6703FC -> 0x67045D) | `E8 8B 92 2A 00` (= 0x9196FD - 0x670472 = 0x002A928B) | `E8 8E 1B 99 0F` | S - 0x670472 | 247 to PerfLabDelayCommand 0x670370 (6 B) |
| 0x67048E | DelayCommand, `[this+4] != 1` (0x6703C1 -> 0x67047E) | `E8 6A 92 2A 00` (= 0x9196FD - 0x670493) | `E8 6D 1B 99 0F` | S - 0x670493 | 280 to PerfLabDelayCommand |
| 0x66DACC | AssignCommand, object lookup failed (0x66DA6D -> 0x66DABC) | `E8 2C BC 2A 00` (= 0x9196FD - 0x66DAD1) | `E8 2F 45 99 0F` | S - 0x66DAD1 | 4459 to level-up-override `LuoHold_66C95C` 0x66C95C |
The patch rewrites only the 4 rel32 bytes (the opcode `E8` stays); no instruction boundary changes; flags and registers after the CALL are not read (the next instructions are `ADD ESP,4` then stores of `[EBP-n],0`). S = a VirtualAlloc'd page (32-bit process: rel32 wraps, any S works), same pattern as `caveAlloc` in RobustnessFixes.cpp. Group name suggestion `dclk` (verifySite on all 3 sites before any write, default ON only after the drop-frequency counter has run); optional counter: `lock inc dword [dclk_free]` (`F0 FF 05 <abs32>`, 7 B) at the top of the shim (flags are dead there) distinguishes the three sites if three shims are used.

### 6.3 DEFECT in the installed k2-robustness-fixes 1.2.0 `vmlk` cave (same ECX problem; flag for the next KPM contributors / Opus gate)
`RobustnessFixes.cpp` `applyVmlk()` (lines ~423-440) emits on the missing-object path: replayed `movzx ecx,byte [0x0099447F]` (the exe byte at 0x99447F is `00`, read from the vanilla exe) / `cmp eax,ecx` / `jnz missing`, then at `missing`: `lock inc [g_vmlkFree]`, `push dword [ebp-0xC]`, `call 0x006FDBB0` with **ECX = 0** (the replayed MOVZX result; the branch is taken only when EAX != 0, ECX stays 0). `0x6FDBB0` then executes `MOV ECX,[ECX+0x1c]` = a read of address 0x1C = access violation. W8.md section 4 states "0x6FDBB0 ... no register inputs needed (0x7037C0 stores ECX but never reads it)": true for 0x7037C0, not for 0x6FDBB0 (asm quoted above). The installed DLL is 1.2.0 (`k2-robustness-fixes.dll` md5 294be99f646666a51b192f6cd34a1634, `vmlk` default ON per the header comment "missing keys default to 1, except movspin = 0"; the log still shows 1.1.0 loads: not launched since the 15:51 hot-swap). Effect: a leak that was benign becomes a crash IF the object-missing path ever fires (never observed: `adc_leak_upper = 0` in all 1,180 VM snapshots; max `adc_enter` 536). Fix (one constant, no extra bytes): `VmlkDeleteSituation = 0x006FDBB0` -> `0x007037C0` (the cave's `e.rel(0xE8, ...)` recomputes rel32), or add `8B 0D A8 B4 A1 00` (`mov ecx,[0xA1B4A8]`, +6 B; cave is 48 B, current use ~36 B). Why the harness did not catch it: `perf_lab_src/harness/smoke_robustness.cpp` stubs 0x6FDBB0 as `static void __stdcall fakeDelSit(void* sit)` (line ~216, comment `// 0x6FDBB0`), i.e. with no ECX use, so the vmlk test passes (`g_delsit == 1 && g_delArg == 0x5150`) while the real function would fault; a correct stub must read `[ecx+0x1c]` (e.g. run with ECX = 0 and a guard page at address 0, or declare it `__attribute__((thiscall))` and assert ecx != 0).
Verdict: DelayCommand/AssignCommand: FIX-AS-EXPERIMENT (shim variant A, 3 rel32 rewrites, counter first); VMLK cave: FIX NOW (ECX), low urgency by observed frequency, high by "a patch must not add a crash".
