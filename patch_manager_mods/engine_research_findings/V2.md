# V2: CSWGuiListBox row-height inflation on repopulate (K1 "K2" lead) checked against K2 Steam

Batch V2, static analysis only (swkotor2.exe Steam, sha256 6a522e71..., decomp/asm under ROOT; vtable slots read from the clean exe `backups/vanilla_clean/swkotor2.exe`, same sha prefix, read-only).

## Summary (5 lines)
1. The K1 building blocks exist in K2: `OrganizeControls 0x41EA50` writes an inflated row height (`+0x2C4` base + leftover/rows) into the rows via `SetExtent`, and `AddControls` saves each row's CURRENT rect into the saved-rect vector (`list+0x2B8`) that the next dirty pass restores from (0x41FD10-0x41FD3A); `ClearItems 0x41D290` restores the saved rect only when flag bit 2 is set.
2. The cycle closes only for a list that is non-owned + restore-bit clear + equal-height + whose row `SetExtent` stores the passed height + whose caller does not set the height itself. The only multi-row lists with the first three properties are the Abilities Powers/Feats lists (`0x8A3C60`, two calls `(0,0,0)`), and their chain-row class (vtable 0x9A6BAC) has a `SetExtent` (0x899CB0) that DISCARDS the passed height (`MOV [EBP-0x34],0x2c` at 0x899CDD) -> no growth.
3. Mod 6 path (`PopulateItemListBox 0x8A7BA0`, `CALL 0x41FC30` at 0x8A7E8C with args `(list, 0, 1, 0)`) = non-owned + restore=1, rows are persistent `CSWGuiInGameItemEntry` objects (pool `panel+0x24B0`); `ClearItems` restores their saved rects every refill, so Mod 6's sort/filter repopulation does NOT compound. The Mod 6 hooks (0x8A7E22, 0x8A7E76) do not touch flags, ClearItems or AddControls args.
4. All 28 callers of the single-control `AddControls 0x41FD90` (description labels) call text-height (`vtbl+8`) then `SetExtent` (`vtbl+4`) with an explicit height right before AddControls, so they re-seed the height each time; 14 more 0x41FC30 sites are non-owned+restore, 23 are owned (rows deleted each clear), 4 are `unequal` mode (no inflation).
5. Verdict: NO BUG on K2 (mechanism present structurally, cycle broken at three independent points for every call site seen); no live-hook overlap in the listbox code; no fix proposed. A log-only probe is specified in (c) in case the user ever sees a growing list.

### F1. Where the enlarged height is written (the K1 "two stores")
Dirty pass first measures, then lays out. `local_18/[EBP-0x14]` = pad + base, `[EBP-0x18]` = row count.
- Reset + measure (dirty only, bit3): asm `0041eb17  MOV dword ptr [EDX + 0x2c4],0x0`; per row `0041eb5c PUSH EAX` (saved rect `[this+0x2b8] + i*16`) then `0041eb68 CALL EDX` (= vtable `+4`, SetExtent: **restore from saved rect**), then `0041eb87 CALL EAX` (vtable `+0x34` = GetHeight), `0041eb92 CMP EDX,dword ptr [ECX + 0x2c4]` / `0041eba0 MOV dword ptr [EAX + 0x2c4],ECX`.
  Decomp: `(**(code **)(**(int **)(*(int *)(param_1 + 0x2ac) + local_10 * 4) + 4))(local_10 * 0x10 + *(int *)(param_1 + 0x2b8));` then `if (*(int *)(param_1 + 0x2c4) < iVar1) { *(int *)(param_1 + 0x2c4) = iVar1; }`.
- Leftover: `local_c = (*(int *)(param_1 + 0x2a8) - (uint)*(byte *)(param_1 + 0x2d0)) - *(short *)(param_1 + 0x2d4) * local_18;` then `local_24 = local_c / (int)*(short *)(param_1 + 0x2d4);` asm `0041ef4b 99 CDQ` / `0041ef4c f7f9 IDIV ECX` / `0041ef4e 8945e0 MOV [EBP-0x20],EAX` (quotient = extra px per row, NOT a row count; KMRP's "COUNT" wording in K1 notes does not match this K2 code) and remainder `0041ef64 894df8 MOV [EBP-0x8],ECX`.
- **Inflation store #1** (equal-height rows inside the window): decomp `local_8 = *(int *)(param_1 + 0x2c4) + local_24;` asm
  `0041f06e 8b91c4020000 MOV EDX,dword ptr [ECX + 0x2c4]` / `0041f074 0355e0 ADD EDX,dword ptr [EBP + -0x20]` / `0041f077 8955fc MOV dword ptr [EBP + -0x4],EDX`; used at `0041f0ad 8b45fc MOV EAX,[EBP-4]` / `0041f0b0 8945dc MOV [EBP-0x24],EAX` (rect height) then row `SetExtent`: `0041f0ec 8d45d0 LEA EAX,[EBP + -0x30]` / `0041f0ef 50 PUSH EAX` / `0041f0f8 8b4204 MOV EAX,[EDX+4]` / `0041f0fb ffd0 CALL EAX`.
- **Inflation store #2** (+1 px to the first `remainder` rows): decomp `local_28 = local_8 + 1;` asm `0041f0c8 8b45dc MOV EAX,[EBP-0x24]` / `0041f0cb 83c001 ADD EAX,0x1` / `0041f0ce 8945dc MOV [EBP-0x24],EAX`.
- Rows outside the window, before it (`0041effe..0041f025`) and after it (`0041f140..0041f167`), get the base: `0041efad 8b45b0 MOV EAX,[EBP-0x50]` (= `+0x2c4`, stored at `0041ef6a..0041ef70`) / `0041efb0 8945dc MOV [EBP-0x24],EAX`.
- K1 mapping: KMRP NOPs `add ebp,edx` (K1 0x41B507 = OrganizeControls+0x3C7) and changes `lea edx,[ebp+1]` (K1 0x41B52C). The K2 counterparts are `0x41F074` (`03 55 E0`) and `0x41F0CB` (`83 C0 01`). Non-dirty passes (scroll via `0x41E870`, which sets only bit 0x1000: `*(uint *)(param_1 + 0x2cc) \| 0x1000;`) recompute from `+0x2C4` and never read row heights, so they cannot compound.

### F2. Where the inflated height is READ BACK (closing the loop)
Only one read-back route exists: `GetHeight` (`[row+0x10]`) in the dirty pass, **after** `SetExtent(saved[i])`. So the base used by pass N+1 is the height that `row->SetExtent(saved[i])` leaves in the row, with `saved[i]` captured by `AddControls`:
- asm `0041fd10 8b45f0 MOV EAX,[EBP-0x10]` / `0041fd13 83c004 ADD EAX,0x4` / `0041fd16 83ec10 SUB ESP,0x10` ... `0041fd2b 8b400c MOV EAX,[EAX+0xc]` / `0041fd31 8b4de8 MOV ECX,[EBP-0x18]` / `0041fd34 81c1b8020000 ADD ECX,0x2b8` / `0041fd3a e8e1190000 CALL 0x00421720`.
  Decomp: `FUN_00421720(*(undefined4 *)(iVar2 + 4),*(undefined4 *)(iVar2 + 8),*(undefined4 *)(iVar2 + 0xc),*(undefined4 *)(iVar2 + 0x10));` = the row's CURRENT rect (including height).
- `ClearItems` is the first call of `AddControls` (`0041fc4c CALL 0x0041d290`). It restores `saved[i]` into each row first only if flag bit2: asm `0041d38c c1ea02 SHR EDX,0x2` / `0041d392 742f JZ 0x0041d3c3` / `0041d3ae..0041d3c1 (PUSH saved[i]; CALL [vtbl+4])`. Bit2 = AddControls arg 4 (`param_4 & 1) << 2`, asm `0041fc76 c1e002 SHL EAX,0x2`).
- **Loop-closure condition (all must hold):** (1) rows persist across repopulates (non-owned: owned rows are deleted by `0041d329 PUSH 1 ... CALL EDX` and re-created); (2) arg4 (restore) = 0; (3) equal-height normal path (not unequal 0x41F170, not oversized 0x41F7F0); (4) the row class's `SetExtent` stores the passed height; (5) the caller does not re-seed the height itself. Then `saved' = base + extra(+1)`, so pass N+1 has base' = base + floor(leftover/n) (+1), a ratchet that stops when `n*(base+pad)` reaches `clientH - pad` (hypothetical example, not measured: H=310, pad=0, base=100: n=3, leftover 10, extra 3, rem 1 -> row0 104; next n=2, leftover 102, extra 51 -> 155; next leftover 0 -> stable).

### F4. Why the Powers/Feats (class A) rows do not grow in K2
`0x8A3C60` branches on tab id `[0x73F750()+0xFC0]`: Skills `FUN_0041fc30(local_2c,0,1,0)` (restore=1), Powers `FUN_0041fc30(param_1 + 0x121d,0,0,0)` and Feats `FUN_0041fc30(param_1 + 0x1221,0,0,0)` (restore=0, rows persistent in `panel+0x4874/0x4884` vectors, destroyed only by `0x89A6E0` with `(**(code **)*puVar1)(1)`). These match the K1 symptom description (Skills fine, Powers/Feats grow).
The row is the chain-row class created by `0x89BED0` (`FUN_00919723(0x324)`, ctor `0x899930`, vtable `MOV dword ptr [EAX],0x9a6bac`). Its vtable (read from the exe): slot +4 = `0x899CB0`, slot +0x34 = `0x414BA0` (GetHeight). `0x899CB0` overwrites the incoming size:
- decomp: `local_3c = 0x106; local_38 = 0x2c;` ... `*(int *)(param_1 + 0xc) = local_3c; *(int *)(param_1 + 0x10) = local_38;` (the decompile's naming differs from the asm frame, the asm is authoritative)
- asm: `00899cd6 c745c806010000 MOV [EBP-0x38],0x106`, `00899cdd c745cc2c000000 MOV [EBP-0x34],0x2c`, `00899d56 db45cc FILD [EBP-0x34]` / `00899d59 d84de0 FMUL [EBP-0x20]` (= `FUN_00479ab0()`, a screen-width-derived scale) / `00899d5c CALL 0x0091c860` / `00899d61 894dcc MOV [EBP-0x34],EAX`, stores `00899fd4 8b55cc` / `00899fd7 89500c MOV [EAX+0xc],EDX`.
So `row+0x10` = `ftol(44 * FUN_00479ab0())`, independent of the rect passed by `OrganizeControls`: base `+0x2C4` is the same on every pass and the inflated height is never stored. (Constant `_DAT_0098c014` inside `FUN_00479ab0` and the scale's absolute value on this install were not read; irrelevant to the verdict because the result is input-independent.)

### F5. Mod 6 path (same fields? growth?)
- `PopulateItemListBox 0x8A7BA0` builds the vector with `CreateItemEntry 0x8A75F0` per item and finalises: asm `008a7e76 6a00 PUSH 0` / `008a7e78 6a01 PUSH 1` / `008a7e7a 6a00 PUSH 0` / `008a7e7c 8d45d4 LEA EAX,[EBP-0x2c]` / `008a7e86 ADD ECX,0x588` / `008a7e8c CALL 0x0041fc30` = `AddControls(vec, owned 0, restore 1, unequal 0)` on the embedded `LB_ITEMS` list (panel+0x588), class C.
- Rows are PERSISTENT: `if (*param_3 == *(int *)(param_1 + 0x24b4))` -> `FUN_00919723(0x3b4,...)` + `FUN_0083ea60` append to `panel+0x24B0`, else `local_18 = *(int **)(*(int *)(param_1 + 0x24b0) + *param_3 * 4);` (reuse). New rows get `Initialize` once (`(**(code **)(*local_b8 + 0xa0))(...)`, width `list+0x2A4 - 2*pad`); reuse never calls `SetExtent`.
- Row class `CSWGuiInGameItemEntry` (vtable 0x9A76C4, ctor `0x8B0A60`) `SetExtent 0x8B0C30` DOES store the passed height (asm `008b0c63 894a0c MOV [EDX+0xc],ECX`; guard `008b0c3c CMP [EAX+8],0x24` / `008b0c40 JG`), so growth would occur if restore were 0. It is 1: each refill's `ClearItems` runs `SetExtent(saved[i])` on every row of the previous population (`0041d3b5 PUSH ECX ... 0041d3c1 ffd0 CALL EAX`), then AddControls saves pristine rects. Sorting/filtering only changes the ORDER and SUBSET in which pool rows are appended; each row that was in the list is restored at the next ClearItems. Rows not in the current list were restored at the previous clear, so they are pristine.
- Mod 6 hooks: `0x008A7E22 (79 B)` replaces "reselect check + push args + CALL CreateItemEntry" (`8B 55 E8 ... E8 7F F7 FF FF`), `0x008A7E76 (22 B)` runs before the original `6A 00 6A 01 6A 00 8D 45 D4 50 8B 8D 7C FF FF FF 81 C1 88 05 00 00` then the original `CALL 0x41FC30`. Same flags, same ClearItems, same fields as vanilla; `InventorySortFilter.cpp` contains no `SetExtent`/`AddControls`/`0x41D290` calls (grep). Mod 6 users therefore see exactly vanilla behaviour: no growth.
- Live-hook overlap (live_hooks_2026-09-30g.tsv, +-8 bytes): only the two Mod 6 hooks above fall in `0x41D290..0x420380`, `0x899CB0`, `0x8B0C30`, `0x8A75F0..0x8A7ED0`, `0x8A3C60`; none touches OrganizeControls/ClearItems/AddControls/SetExtent.

## (c) Runtime measurements (log-only, perf-lab style; only needed if a list is ever seen to grow)
1.
