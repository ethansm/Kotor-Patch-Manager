## 5-line summary
1. K2 `WrapStrings` 0x47AF30 has the SAME mis-targeted progress check as K1 (cursor backs up one char, then compares to the STRING start `[this+0x14]` not the LINE start `[ebp-0x14]`; asm 0x47b321), so a line whose first two glyphs do not fit restarts at the same spot forever. BUT K2 bounds it with a 100-pass cap (asm 0x47b0e8 `MOV [EBP-0x20],0x64`, 0x47b109 `CMP ECX,[EBP-0x20]`): no hang, no OOM (about 200 ints, 8 small allocs); the result is silent text loss (`return` with zero lines when it happens on the first line; a few junk lines otherwise). Hang/OOM verdict: NO BUG. Side effect: any single paragraph wrapping to more than 100 lines is truncated at line 100.
2. Per-glyph advance in the breaker is `ftol(((u1-u0)*texW + spacingR)*scale*100.0 + 0.25)` (asm 0x47b1f1-0x47b238, `FADD double ptr [0x0098c1d8]` = 0.25) with `_ftol2_sse` = CVTTSD2SI TRUNCATION, i.e. mean under-measure 0.25 px/char; Draw advances with exact float (asm 0x47c5aa-0x47c5f9), so wrapped lines can be wider than the box by ~0.25 px x chars. First-char widths and break-width subtractions truncate with no bias at all. Verdict L4: BUG (cosmetic). Fix = re-point the 4-byte operand at 0x47b234 to the existing 0.5 double at 0x987f08.
3. Draw 0x47B500 drops lines from the top with no "keep the last line" guard, in both vertical-centre (0x47b6cb loop) and bottom (0x47b7cb loop) alignment: single-line text vanishes when box height < font line height (centre), any text vanishes when box height < one line (bottom). Verdict K5-style vanishing: BUG (latent). Under assumptions flagged SPECULATIVE (font height 0.16, GUI px/unit = H/600) it is NOT triggered by vanilla GUI labels at 800x600..3840x1600, but IS triggered for the 18-unit-high labels (character_p LBL_EXPERIENCE_STAT etc.) at 5120x1440, because the font scale at 0x479AB0 grows with display WIDTH only (1.0/1.5/2.0/2.0/3.0 at 1920/2560/3440/3840/5120 wide).
4. Hook feasibility: L4 is a pure data patch (no hook); K5 needs two small caves (9-byte window 0x47b7db, 11-byte window 0x47b6d4, each ends with a rel32 Jcc that is re-emitted); no live hook within +-8 bytes of any site (nearest live hooks 0x478A20, 0x4A715E, 0x4160BD).
5. Reachability of the L3 non-advance on this install is low (needs a text label narrower than two glyphs holding >= 3 chars; no vanilla GUI label has that, mod-created labels might); the cap path and the "first line returns empty" path are both observable with the log-only counters in section (c).

### F1. (a) Breaker: the K1 progress-check mistake is present in K2, but bounded by a 100-line cap

Algorithm as read from the asm (my Python transcription is in the scratchpad, `scratchpad/v3/sim.py`, not part of the repo):
- Entry reset: `0047af7a MOV dword ptr [EAX+0x40],0x0` / `0047af84 MOV dword ptr [ECX+0x4c],0x0` (decomp `*(undefined4 *)(param_1 + 0x40) = 0; *(undefined4 *)(param_1 + 0x4c) = 0;`), so both arrays are rebuilt per call (capacity kept).
- Per-pass counter: `0047b0e1 MOV dword ptr [EBP-0x8],0x0`, `0047b0e8 MOV dword ptr [EBP-0x20],0x64`, per outer iteration `0047b100 ADD EAX,1`, `0047b109 CMP ECX,[EBP-0x20]`, `0047b10c JLE 0x0047b12a`. Decomp: `local_c = local_c + 1; if (100 < local_c) { FUN_00733570(*(undefined4 *)(param_1 + 0x14)); FUN_00733780(); return; }`. One outer iteration emits exactly one wrapped line, so this is a 100-LINE cap, not a retry cap. On the 101st pass it builds and destroys a CExoString copy of the text (asm `0047b118 CALL 0x00733570`, `0047b120 CALL 0x00733780`; looks like a stripped log/assert, no output) and returns WITHOUT clearing the arrays.
- Line scan: `0047b178 CMP [EBP-0x2c],EDX / JGE 0x0047b261` (decomp `while (local_30 < local_28)`); break candidates: space (asm `0047b18b CMP ECX,0x20`) or '-' between two letters (asm `0047b196 CMP EAX,0x2d`, `0047b1a3 CALL 0x0091f4e0` = _isalpha on `[ECX-0x1]`, `0047b1b7 CALL 0x0091f4e0` on `[EAX+1]`). When the first char of the string is '-', `[ECX-0x1]` reads one byte BEFORE the string buffer (harmless read, quoted for completeness: `0047b19e MOVZX EDX,byte ptr [ECX+-0x1]`).
- No-break-opportunity branch (the K1 case), asm 0x47b2b0: `CMP dword ptr [EBP-0x28],0x0 / JNZ 0x0047b406` (no break recorded) then:
  - `0047b312 SUB EDX,0x1` / `0047b318 MOV [EBP-0xc],EDX` = cursor backed up one char (decomp `local_10 = local_10 + -1;`)
  - progress check: `0047b31b MOV EAX,[EBP-0x60]` / `0047b321 CMP ECX,dword ptr [EAX+0x14]` / `0047b324 JNZ 0x0047b33f` (decomp `if (local_10 == *(byte **)(param_1 + 0x14)) { *(undefined4 *)(param_1 + 0x40) = 0; *(undefined4 *)(param_1 + 0x4c) = 0; return; }`). `[EAX+0x14]` = whole-string start. The LINE start is `[EBP-0x14]` (`local_18`), never compared. Same defect as K1.
  - append: line length `0047b3e0 MOV EAX,[EBP-0xc]; SUB EAX,[EBP-0x14]; NEG EAX; PUSH EAX; ... ADD ECX,0x48; CALL 0x004491c0` (decomp `FUN_004491c0(-((int)local_10 - (int)local_18));`) and width `0047b3f1 MOVSX ECX,word ptr [EBP-0x4]; PUSH ECX; ... ADD ECX,0x3c; CALL 0x004491c0`.
  - next pass start: `0047b4a1 MOV EAX,[EBP-0xc]; MOV [EBP-0x14],EAX` (line start := cursor) and `0047b4e7 MOV dword ptr [EBP-0x2c],EAX; JMP 0x0047b0ef` (running width := width of the first char at the cursor). Decomp `local_18 = local_10; local_30 = FUN_0091c860(...)`.
- Why it does not advance (arithmetic): let L = line start, P = string start, oc = overflow position. If the first two chars of the line (L, L+1) do not fit and there is no space/hyphen, the scan stops with cursor oc = L+1; backing up gives cur = L; L != P so the check passes; appended length is `-(cur-L)` = 0; next pass starts at L again with the identical state `(L, cur=L, w = width(first char))`. It repeats until the cap. If L == P the check fires and the function returns with count 0 (text vanishes). A single char wider than the box behaves the same (`cur` goes to L-1, length +1, then oscillates at L-1).
- Simulation (my transcription of the asm with synthetic integer metrics: u=8.4, spacing 1.0 giving a=8, b=9, c=9; NOT real font data): `"a 12345"` at box width 12 returns state CAP100 with 100 line entries `[1,0,0,0,...]`; at widths 20/30 it terminates normally with hyphenated lines (`[1,-1,-1,-1,2]`, `[1,-2,3]`); `"999"` at width 14 returns empty (first-line return); `"12"` at width 10 trips the guard. `"word "*500` at width 200 returns CAP100 with the remainder dropped.
- The two K1 "guards" exist in K2 too: `0047b0a2 CMP EAX,0x1 / JNZ / ... CMP ECX,EDX / JGE 0x0047b0ba / JMP 0x0047b4ef` (strlen==1 and box width < width('o') incl. spacing = `MOV EDX,0x6f; IMUL EDX,EDX,0xc` at 0x47b04b..) and `0047b0c9 CMP EAX,0x2 / JA ... SHL EAX,0x1 / CMP EDX,EAX / JGE / JMP 0x0047b4ef` (strlen <= 2 and box < 2*width('o')): text of 1-2 chars in a box narrower than one/two 'o' is blanked.
- What each pass appends: one int to `+0x3c` and one int to `+0x48` (pairs), so the cap bounds the arrays to <= ~200 ints; growth is 16 -> 32 -> 64 -> 128 per array (`0x4491c0`: `local_c = 0x10` then `param_1[2] << 1`), i.e. 4 `new[]` + 4 `delete[]` per array in the worst case.
- Allocation failure: `0x449320` -> `0x91d288` -> operator new 0x919723, which per R5 never returns NULL: `__CxxThrowException_8` (std::bad_alloc), uncaught -> process death. Not reachable from the capped loop (about 1.6 KB total). Uncapped growth exists only in the newline branch: `while (*local_10 == 10)` at asm `0047b137 CMP EDX,0xa / JNZ` pushes two zeros per '\n' (`0047b14b PUSH 0x0 ... ADD ECX,0x3c; CALL 0x004491c0`, `0047b158 PUSH 0x0 ... ADD ECX,0x48`) without touching the pass counter: memory linear in the number of consecutive newlines, no hang. SPECULATIVE whether any content produces millions of them (no).
- Consequence of the cap for real text: more than 100 wrapped lines in one string are cut at line 100 (arrays keep lines 1-100, the rest is never drawn). 100 lines is >= 2.5 kB of ordinary prose at ~35-40 chars/line (my estimate; font data unavailable), so only unusually long mod descriptions could hit it.

Verdict F1: hang/OOM = NO BUG (cap); the underlying K1 progress-check defect is present (BUG in logic) but its only observable effect is blank/truncated text, covered by F3-style "vanish" behaviour.

### F2. (b) Glyph advance: +0.25 then truncate in the breaker; exact float in Draw

Breaker, per-char advance inside the scan loop (asm 0x47b1f1-0x47b240):
```
0047b1f4 MOVZX ECX,byte ptr [EAX]  ; IMUL ECX,ECX,0xc ; ADD ECX,[EDX+0x24]   ; &glyphLR[c]
0047b206 FLD float ptr [EAX]                  ; u1
0047b217 FSUB float ptr [ECX+EDX*1]           ; - u0 (table +0x18)
0047b21d FMUL float ptr [EDX+0xc]             ; * texturewidth
0047b223 FADD float ptr [EAX+0x10]            ; + spacingR
0047b229 FMUL float ptr [ECX+0x54]            ; * this+0x54 (text scale)
0047b22c FMUL double ptr [0x0098ba38]         ; * 100.0
0047b232 FADD double ptr [0x0098c1d8]         ; + 0.25
0047b238 CALL 0x0091c860                      ; _ftol2_sse = CVTTSD2SI, truncation
0047b23d ADD EAX,dword ptr [EBP+-0x2c]        ; running width += int
```
Decomp: `iVar5 = FUN_0091c860(); ... local_30 = iVar5 + local_30;`. Constants read from .rdata (vanilla_clean exe): 0x98ba38 = 100.0, **0x98c1d8 = 0.25 (bytes 00 00 00 00 00 00 d0 3f)**, 0x987f08 = 0.5 (bytes 00 00 00 00 00 00 e0 3f, a double already used by `FADD double ptr [0x00987f08]` at 0x420cf4, 0x420dea, 0x436439), 0x98c014 = 0.5f (resolution scalar step), 0x987490 = 2.0, 0x986b38 = 0.0, 0x986b50 = 1.0, 0x9884a0 = 255.0. For fractional part f uniform in [0,1): `trunc(x+0.25) = floor(x) + (f >= 0.75)`, so the error `x - measured` has mean `0.5 - 0.25 = +0.25 px` (computed numerically 0.2495). The breaker UNDER-measures by 0.25 px/char on average (range -0.25 .. +0.75).
Other widths are truncated with no bias: first char of every line `0047afe8..0047b020` and `0047b4a7..0047b4e7` (`FMUL double [0x98ba38]; CALL 0x91c860`, no FADD, no spacing, mean -0.5 px) and the break-width bookkeeping `0047b2c8..0047b3d3`, `0047b411..0047b46b` (ftol of `(u1-u0)*texW+spacingR`, no bias).
Draw advance, exact float, per glyph (asm 0x47c5aa-0x47c5f9; Ghidra marks the surrounding switch as removed but this is the executed path):
```
0047c5aa FLD float ptr [ECX+0x10]      ; spacingR
0047c5b3 FMUL float ptr [EDX+0x54] ; 0047c5b6 FMUL double [0x98ba38] ; FIDIV [display W]
0047c5df FADD float ptr [EDX]          ; + u1
0047c5f0 FSUB float ptr [EAX+ECX*1]    ; - u0
0047c5f3 FMUL float ptr [EBP+-0x2c]    ; * (texW*scale*100/W)
0047c5f6 FADD float ptr [EBP+-0x24]    ; x += ...
```
Decomp: `local_28 = (((*(float *)(local_24 + 0x10) * *(float *)(param_1 + 0x54) * (float)_DAT_0098ba38) / (float)(int)*(short *)(...) + *local_12c) - *(float *)(...)) * local_30 + local_28;` where `local_30 = (texW * scale * 100) / W` (asm 0x47b5b8-0x47b5e7). Draw works in normalised x (divide by display width `DAT_00a309cc` table), the breaker in pixels (`this+0xc` box px, set by 0x47a1d0/0x47a7a0). So the same glyph is `int(x+0.25)` px wide in the breaker and exactly `x` px in Draw. A 40-char line is under-measured by ~10 px on average, so a line that "just fits" is drawn up to ~10 px over `this+0xc`; Draw never clips horizontally (no scissor in the function; SPECULATIVE for clipping done by callers/GL state). Note a second inconsistency visible in the same decompile: Draw multiplies the spacingR term by `local_30` (the whole `(sp*s*100/W + u1) - u0` is scaled), the breaker does not; harmless if spacingR = 0 (K1 TXI sample) but SPECULATIVE for K2 fonts (K1's font-scaling.md says the renderer ignores spacingR there; K2 reads it in both places).
Verdict L4: BUG, cosmetic (under-measure 0.25 px/char mean; unbiased rounding would be `+0.5`).

### F3. (c) Draw drops lines from the top, including the only line (K5-style vanishing)

Vertical alignment is `this+0x5a & 0x38`: 0x10 centre, 0x20 bottom, otherwise top (no dropping). Line pixel height `h = fontheight(+4) * this+0x54 * 100.0`.
Centre (asm 0x47b678-0x47b78d):
```
0047b67e FILD [ECX+0x10] (box H) ; 0047b687 FILD [EDX+0x4c] (n lines) ; FLD [EAX+4]; FMUL [ECX+0x54]; FMUL 100.0
0047b69f FMULP ; 0047b6a1 FSUBP                      ; B - n*h
0047b6c0 FMUL double ptr [0x00987490] ; FDIVP        ; / (H_display * 2.0)  -> local_50 (EBP-0x4c)
0047b6cb FLD [EBP-0x4c] ; 0047b6ce FCOMP double [0x00986b38] (0.0) ; 0047b6d4 FNSTSW AX ; 0047b6d6 TEST AH,5 ; 0047b6d9 JP 0x0047b784
        loop body: local_50 += h/H_display (0x47b6e2-0x47b714); skip |len[local_8]| chars (0x47b71d-0x47b73d); local_8++ (0x47b776-0x47b77c); JMP 0x47b6cb
0047b784 FLD [EBP-0x18] ; FADD [EBP-0x4c]            ; y += (negative) local_50
```
Decomp: `while (local_50 < (float)_DAT_00986b38) { local_50 = h/H + local_50; ... local_14 = local_14 + iVar4; ... local_8 = local_8 + 1; }`. No test of `local_8 < this+0x4c`. Drop count k = ceil((n*h - B)/(2h)) for n*h > B. For n = 1 and B < h: k = 1 = n, nothing is drawn (the drawing loop is `for (; local_8 < *(int *)(param_1 + 0x4c); ...)`). For n >= 2, k <= ceil(n/2) < n, the last line always survives. So in centre alignment only a SINGLE-line text vanishes, when box height B < h.
Bottom (asm 0x47b792-0x47b89b):
```
0047b7ae FILD [EAX+0x4c] ; FLD [ECX+4]; FMUL [EDX+0x54]; FMUL 100.0 ; FMULP ; 0047b7c8 FSTP [EBP-0x50]   ; n*h
0047b7d1 FILD [EAX+0x10] (box H) ; 0047b7d4 FLD [EBP-0x50] ; 0047b7d7 FCOMPP ; 0047b7d9 FNSTSW AX ; 0047b7db TEST AH,0x41 ; 0047b7de JNZ 0x0047b86c   ; exit if n*h <= B
        body: 0047b7e4 MOV ECX,[EBP-0x20]; FLD [ECX+4] ... 0047b7f9 FSUBR [EBP-0x50] ; FSTP [EBP-0x50]   ; n*h -= h ; skip line chars; local_8++ ; JMP 0x47b7cb
0047b86c FILD [EDX+0x10] ; FSUB [EBP-0x50] ; ... FIDIV [H] ; FADD [EBP-0x18]                          ; y offset = (B - remaining)/H
```
Decomp: `while ((float)*(int *)(param_1 + 0x10) < local_54) { local_54 = local_54 - h; ... local_8 = local_8 + 1; }`. Drop count k = n - floor(B/h): if B < h every line (all n) is dropped, text fully vanishes; if B >= h at least one line stays. Again no `local_8 < n` check. (Float accumulation could make `n*h - n*h` slightly > 0 when B == 0 and read `len[n]` past the array: SPECULATIVE, B == 0 labels are excluded earlier by the width/height nonzero test in 0x417800 for rect-built labels.)
After the loops `local_8` = lines skipped; the glyph loop starts at line `local_8`, so skipped lines are never drawn. With the fix (keep the last line) the single remaining line is drawn with a negative y offset, i.e. overflowing the box (SPECULATIVE whether a parent scissor clips it).

### Hook feasibility for the BUG verdicts

**L4 (advance bias): data patch, no cave.**
- window: 0x0047B232, 6 bytes `dc 05 d8 c1 98 00` (`FADD double ptr [0x0098c1d8]`); absolute operand, no relative branch, no branch target inside (fallthrough only; loop head 0x47b178 is elsewhere).

**K5-style (keep the last line): two caves, both end in a re-emitted rel32 Jcc.**

The JNZ is the stolen relative branch; the cave re-emits `jnz 0x0047b86c`. No branch target inside (loop head is 0x47b7cb; body starts 0x47b7e4 = return address).
