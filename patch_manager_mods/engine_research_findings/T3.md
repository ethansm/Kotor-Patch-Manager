# T3 - remaining save paths + resman speculative bugs (Steam swkotor2.exe, sha256 6a522e71...)

## Summary (5 lines)
1. CONFIRMED leak: `0x8529E0` (autosave-slot restore, strings "AUTOSAVE"/"SAVEGAME"/"GAMEINPROGRESS:") does `new(0xD0)` (CERFFile, alloc 0x852B9B) and never frees it (no `0x720C20`/`0x9196FD` in its callees, only 4 uses of the slot `[EBP-0x24]`); per restore it leaks 0xD0 B + all entry lists built by `0x720FC0` (0xC+0x18+0xC per ERF entry + list nodes); every other save/load path audited (0x55B830, 0x534600, 0x53AF20 tail, 0x7D1940, 0x855F30, 0x7216C0, 0x55CC70, 0x5FB1A0, 0x655010) is balanced. `0x55D7F0` leaks a 4-byte CResStruct but is dead (`DAT_00a7d88c` has no writer).
2. Screenshot = `0x52F610 -> 0x401B90 -> 0x4289D0`: one full-viewport `glReadPixels` (w padded to x4, h, 3 bpp, ~15-18 MB at ultrawide) + a scaled 256x256 copy, all freed (new[] 0x91D288 / delete[] 0x91C6AA); NO GL/GDI objects created. Crash triggers: `0x482BD0` `_fopen(...,"wb")` result never NULL-tested (`0x482C30`), `0x4289D0` derefs NULL if `FindObject("camera")` fails (`0x428B24`), and if padded width <= height the output dims `[EBP-0xC]/[EBP-8]` are uninitialised (`0x428AE5 JLE 0x428B17`).
3. Q3 CONFIRMED (narrow): only `0x714300` Update and `0x715A60` read resman+0x28; `0x711A30` CancelRequest clears +0x28/+0x2c only under `count==0 && flag&0x10` (JZ at `0x711A9B`), so a queue head whose async Service returned 0 (flag 0x10 never set: 0-byte override file, fopen fail, Malloc NULL) that is cancelled and deleted leaves `[resman+0x28]` dangling; next Update derefs it (`CMP [ECX+8],-1` at `0x714346`). Also CONFIRMED: Cancel of an in-flight (0x10) CRes never clears flag 0x10 nor frees the buffer (permanent leak, CRes shared by name so a later Demand returns the raw unparsed buffer at `0x711D0D`).
4. Q4 REFUTED as stated: `RemoveKeyTable 0x7131D0 -> DestroyTable 0x726350` never deletes CRes objects and unlinks/frees refcount-0 ones from the evict list via `0x711230 -> 0x711E60 -> 0x711FE0` (which searches the list and `FUN_0064dde0` removes the node). Real defect found instead: the "still in demand" branch (`0x726496`) leaves CRes+0x14 pointing into the freed key array, and `0x713010` later does `MOV [ECX+0x10],0` (`0x71306C`) through it = 4-byte zero write into freed heap (CONFIRMED path; frequency SPECULATIVE; the save-list UI `0x854A00` swaps SAVEGAME.sav tables while a "screen" TGA texture is still held).
5. Q5 CONFIRMED: failed sync Service (short read `0x714216 CMP EAX,[EBP-8]`, or OnResourceServiced==0 -> flag 4 cleared) returns 0 with the Malloc'd buffer still in CRes+0x10; nothing frees it (FreeChunk needs list membership, 0x711E60 needs flag 4|0x10) and the next Demand re-enters `0x712F30` which overwrites `[CRes+0x10]` with a new Malloc (`0x712FC3/0x712FE0`) = first buffer leaked, budget `[resman+8]` decremented twice. Q6: unchecked fwrite/ferror everywhere (save silently truncated on disk full), NULL-safe on fopen failure except `0x482BD0`.

### F3 (Q3). CancelRequest and resman+0x28
Readers of `[resman+0x28]` (grep of decomp `+ 0x28` in 71/*.c plus every .asm that loads `[0xa1b490]`; other hits (`0x52F610`, `0x5582F0`, `0x5E9EE0`, `0x781BE0`, ...) are other objects): ONLY

- `0x715A60` ServiceCurrentAsyncRes: `iVar1 = FUN_00712d70(*(undefined4 *)(param_1 + 0x28));` and later `... FUN_007f2a90(); *(undefined4 *)(param_1 + 0x28) = 0;`.
Writers: Update (set), 0x715A60 (clear), CancelRequest (clear) only.

Cancel logic (asm): `00711a92 MOV EAX,[EBP+8]; 00711a95 MOV ECX,[EAX+0xC]; 00711a98 AND ECX,0x10; 00711a9b JZ 0x00711b9f` - the clear of +0x28/+0x2c (0x711B..) is inside the flag-0x10 block; the fallthrough (0x711B9F) only removes the queue node (`if (local_8 == param_2) { if (*(short *)(param_2 + 6) == 0) FUN_0064dde0(local_10); break; }`).

Stale-pointer path (CONFIRMED statically):
1. Update sets +0x28 = head H every pass where +0x28==0, and sets flag 0x10 only `if ((local_8 != 0) && (flag & 4) == 0)`.
2. `Service*(H,1)` returns 0 when: 0x7133A0 async with 0-byte / unopenable file (`if (local_24 == 0) { ... FUN_00739880(); FUN_009196fd(iVar3); ... return 0; }`, `if (local_1c == 0) ... return 0;`), any async Malloc NULL (0x712F30 returns 0), or no table match (fall off the `while (local_14 != 0)` loop -> 0). Then H stays head, +0x28 = H, retried every frame.
3. Owner cancels/deletes H (helper dtor 0x93D200: `FUN_007111c0(); FUN_00713010(...)` then delete): CancelRequest takes the flag-0x10-clear path, removes H from the queue but leaves +0x28 = H.
4. Next Update: `+0x28 != 0` so no re-fetch; reads `*(H+8)` from freed memory (0x714346). Depending on heap reuse: reads garbage flags -> `Service*(garbage,1)` or `FUN_007F2A90()` (RemoveHead of an unrelated queued request). Also the queue behind H is stalled the whole time.

### F4 (Q4). RemoveKeyTable and the evict list
Chain: `0x7131D0` -> `FUN_00726350()` (DestroyTable) -> `FUN_0064dde0(local_10)` (unlink table node) -> `FUN_00722ff0()` (free key array via `0x723190(3)`: `_eh_vector_destructor_iterator_(param_1,0x24,...); FUN_009196fd((int)param_1 + -4)`) -> `FUN_009196fd(table)`.

CRes objects are never deleted here (owners delete them via 0x93D200 -> 0x713010). A refcount-0 CRes therefore cannot stay on the evict list past table removal (it is unlinked in 0x711FE0), and refcount>0 CRes are never on the list (`0x7130B0` adds on the 1->0 transition only).

Residual issues found:

## (d) Open questions
1. Which caller re-Demands a rejected resource repeatedly (Aurora texture retry?) - decides whether F5 leaks once (mod-broken file) or per frame. M2 during a session with a deliberately corrupt override TGA answers it.
2. Does the Wine/Proton CRT abort on `_fwrite(NULL)`? (`0x482BD0` unchecked fopen) - needs a read-only SAVES dir test; static only shows no guard.
3. Does DestroyTable's "still in demand" branch actually fire during save-list browsing (M4b)? If yes, F4b is a routine UAF write whose visible symptom depends on heap reuse of the freed 0x24-stride array.
4. Which requesters produce a 0-byte/unopenable async Service (mods with empty override files) - only then does F3 step 2 occur; M3/M3b will show.
5. `0x8529E0` exit path was not audited for exceptions: SEH unwind (0x9605xx tables) may free nothing either way; the leak stands regardless.
6. 0x53AF20 sub-savers not audited in depth: 0x53C680 (AUTOSAVEPARAMS), 0x53D540, 0x5F..: only checked that no new GFF/CERFFile allocation sits in their alloc_sites rows (0x53AF20 closure allocs at depth 1-2 are CExoString helpers, GUI pump singletons guarded by `if (*(int *)(param_1 + 0x80) == 0)` in 0x411B20, and the balanced sites above).
