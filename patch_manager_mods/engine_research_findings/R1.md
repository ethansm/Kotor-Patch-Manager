# R1 - CExoResMan resource lifetime (Steam swkotor2.exe, sha256 6a522e71...)

## Summary (5 lines)
1. The ~195 MB (a2 0x712fb7) is the `size+10` branch of Malloc (CRes+0x24 != 0), which only CResTPC (ctor 0x945ce0) and CResTGA (ctor 0x9452c0) set: those 73 blocks are texture file buffers; Aurora keeps a pointer into them and drops the ref only in its free callback (0x93ea10 -> Release 0x7130b0), so they are pinned (refcount>0), not cache.
2. Refcounts: CRes+4 (u16) = data refcount (Demand++ / Release--), CRes+6 (u16) = async-request count (Request++ / CancelRequest--), CRes+0x1c = object refcount (ReleaseResObject). Release to zero only sets flag 0x100 and pushes the CRes on the eviction list (resman+0x20) with AddHead; data is freed only by FreeChunk (0x712160) via FreeResourceData 0x7120c0 (or 0x711fe0 via ReleaseResObject/dtor).
3. J1 confirmed and sharpened: budget `[this+8]` = TotalPhys/2 with a SIGNED compare (0x711438 SAR/CMP/JLE); for LAA exe (installed swkotor2.exe Characteristics=0x123, LAA set) dwTotalPhys saturates >= 0x80000000 -> negative -> 16 MB floor; with 195 MB outstanding the budget is hugely negative so EVERY Malloc calls FreeChunk and evicts ALL refcount-0 entries (cache ~0 MB). Eviction order is newest-released-first (AddHead + walk from head).
4. C2: Demand's `while(!FUN_00739a10()) Sleep(1)` polls `DAT_00a7ea98` (FUN_0073de00 just returns it); that global has NO writer anywhere in the decompiled corpus, so the async path is either dead on PC or written outside the corpus (measure, do not assume). Loop entered only for a CRes with flag 0x10 (in flight) and resman+0x2c != 0.
5. Leaks/UAF: on short-read / OnResourceServiced failure the Malloc'd buffer stays attached to the CRes with flag 4 clear (not in eviction list, dtor path 0x711e60 requires flag 4|0x10) -> permanent leak + budget under-count; CancelRequest does not clear resman+0x28 unless flag 0x10 is set -> possible stale head pointer in Update (speculative). Hook addresses in section (c).

Flags (+0xC): 0x04 loaded/serviced (set by Service*/0x715a60), 0x10 async in flight (set 0x714300, blocks eviction: `if ((local_8[3] & 0x10U) == 0)` in FreeChunk), 0x100 present in evict list (set Release, cleared FreeChunk/Demand/0x711fe0), 0x08/0x200 deferred-delete marker (0x713010 `& 0xfffffdff | 0x200` when flag 8).

## (b) Findings

### F1 Refcount / flag rules (Q1)
- Increment +4: only Demand: loaded-hit `00711cdc..ce7: MOVZX/ADD AX,1 -> [ECX+4]`; cold `*(short *)(param_2 + 4) = *(short *)(param_2 + 4) + 1;` (after Service* ok); async-complete branch 0x711d47 same. Nothing else increments +4 (checked: only Demand writes `+4` upwards; CRes ctor zeroes it).
- Decrement +4: only Release 0x7130b0: `*(ushort*)(p+4) >= 2 -> --`, `==1 -> =0 (0x713141 XOR EAX,EAX / MOV [ECX+4],AX)`, `==0 -> return -1` (double release is detected, no underflow).
- On reaching 0 (0x713153..): if flag 0x100 clear -> `FUN_0054aa10(p)` (AddHead on resman+0x20) then flag |= 0x100 (asm 0x713176, 0x71318c `AND EAX,0xfffffeff` then OR). If 0x100 already set -> `FUN_00711e60(p,0)` frees immediately (rare: 0x100 is normally cleared by Demand on re-ref).
- Release also does for source type 1: `(**(code **)(*(int *)**(undefined4 **)(iVar2 + 0x30) + 0x14))()` = close image file.
- +6 request count: Request (0x713310) ++ (first time AddTail on queue resman+0x24, `0x713372 CALL 0x0054aa30`); CancelRequest (0x711a30) --; queue node removed at 0.
- +0x1C object refcount: SetResObject sets 1; ReleaseResObject (0x713010) decrements; at <2 and data refcount 0 unlinks key entry and calls `FUN_00711230(1)` (frees data if refcount 0). The CRes object itself is deleted by the caller: `if (FUN_00713010(res)==0) (**(code**)*res)(1)` (e.g. 0x93d200, 0x93d2b0).
- Who frees data buffers: (1) FreeChunk 0x712160 (LRU-less scan, above), (2) 0x711fe0 (via 0x711e60 from Release-with-0x100-set, ReleaseResObject via 0x711230, CRes dtor 0x7111a0), (3) 0x722a30 (another caller of 0x7120c0, not analysed). All funnel into 0x7120c0 (`FUN_009196fd`). Data pointer is never freed elsewhere except the error paths in F6.
- Eviction ORDER: AddHead (0x739da0: `*param_1 = (int)local_18` makes the new node the head) and FreeChunk starts with `FUN_007a1720()` (head) then GetNext (node[1] = older). => newest-released-first (MRU) eviction: the entry released last is freed first. Speculative whether intended; effect: recently released textures are the first dropped.

### F2 Cache budget / J1 (Q4 hook context)
- `0x711438 MOV ECX,[EAX]; SAR ECX,1; CMP ECX,0x1000000; JLE 0x71145f` (signed). `[this]` = MEMORYSTATUS.dwTotalPhys (`GlobalMemoryStatus(&local_34)`, [ebp-0x28]). If TotalPhys>>1 (arith) > 16 MB then `[this+4]=[this+8]=TotalPhys>>1` else both = 0x1000000.
- Installed exe PE Characteristics = 0x123 (read from ~/.local/share/Steam/steamapps/common/Knights of the Old Republic II/swkotor2.exe): LAA set. GlobalMemoryStatus (DWORD) saturates at 0xFFFFFFFF for >=4 GB RAM (also 2-4 GB gives >=0x80000000) -> as signed int negative -> SAR stays negative -> JLE -> **budget = 16 MB**. (Wine detail, i.e. that Proton does not return a value < 0x80000000 for LAA exes, is speculative; measure `[resman+4]` at first Malloc hook.)
- Malloc (0x712f30): `while (size <= budget) break; else FUN_00712160()` -> `budget -= size` -> alloc; budget can go arbitrarily negative (nothing clamps): with 195 MB pinned, budget ~ -180 MB.
  Consequence (static): every Malloc while over budget calls FreeChunk repeatedly (each pass <=1 MB freed, loop `while (iVar1 != 0)` continues) until the evict list is exhausted, so every refcount-0 resource is dropped on the very next Malloc. Effective cache for unreferenced resources ~ 0; every re-Demand of a Release'd resource re-reads from BIF/dir. Predicted signal: Demand cold-path count >> hit count for re-requested ids.

### F3 The big blocks (Q2)
Census key = a2 (return address). Verified against Malloc asm:
- a2 0x712fb7 (194.8 MB, 73 blocks, avg 2.7 MB) = return of `new` at 0x712fb2, i.e. branch `CMP [EAX+0x24],0` -> size+10 (asm 0x712f9f..0x712fb7). The only CRes ctors setting +0x24=1: CResTPC 0x945ce0 (`param_1[9] = 1`, vtbl 0x9b9708) and CResTGA 0x9452c0 (vtbl 0x9b96f0). Caller of Malloc is NOT recoverable from this row (a1=0x73dc11 is a stale stack value inside FUN_0073dba0 file-size code). ### F4 Async / C2 (Q5)
- Demand (0x711c20): `else if ((flag & 0x10)!=0) { if (this+0x2c == 0) return data; else { while ((iVar2 = FUN_00739a10()) == 0) Sleep(1); iVar2 = FUN_00715a60(); ...refcount++ } }`. asm: 0x711d04 `8b55e8 837a2c00`, 0x711d18 `8b4de8 8b492c`, 0x711d1e `CALL 0x00739a10`, 0x711d27 `6a01 ff15d4609800` (Sleep import), 0x711d2f `ebe7` (loop), 0x711d34 `CALL 0x00715a60`.
- Only a CRes with flag 0x10 takes it; flag 0x10 is set only by Update (0x714300) after `Service*(res,1)` returned nonzero and flag 4 still clear (`& 0xffffffef | 0x10`), i.e. only for the queue head produced by Request (18 helper call sites, `param_3 != 0` async loads of MDL/TGA/TPC/IFO/WAV/2DA/LYT/NCS/...). Update is called once per invocation of 0x781be0 (main-loop object, caller 0x73f9c0) and handles ONE head item per call; in flight at most one resource (resman+0x28).
- The completion predicate is `FUN_00739a10 -> FUN_0073de00: return DAT_00a7ea98;` (no arguments used; ECX ignored). globals.tsv/imports.tsv and a full grep of every .asm for `a7ea98` shows exactly ONE reference (the read at 0x73de09). So either (a) the flag is written through a base pointer not visible by absolute address (e.g. the async I/O object writes via a struct pointer), or (b) async is compiled as "always done later" and this loop can spin forever if ever entered. Since the retail game does not hang, (a) or "never entered" is what holds; cannot be decided statically. Label: speculative.
- Static reasoning about frequency: Demand hits the loop only when Demand(x) is called for the currently in-flight Request'd resource. Because Update handles one queued resource per main-loop pass and a following Demand of another resource takes the sync cold path (0x713fb0 with param_3=0, does not wait for the async one), the loop is entered mostly at level load where a helper does Request(x) then soon Demand(x). Each iteration costs Sleep(1) (1 ms on Wine/Linux timer, up to ~15.6 ms on Windows without timeBeginPeriod). Expected cost = async read latency rounded up to whole ms per hit. Runtime counters in (c).
- Event-based replacement needs: (1) a manual-reset event (or the OVERLAPPED hEvent) signalled by the reader when the read/decode-to-buffer for the in-flight CRes completes; (2) Demand: `WaitForSingleObject(evt, INFINITE)` in place of the loop at 0x711d18..0x711d2f (12 bytes `8b4de8 8b492c e8ed7c0200 85c0 750a 6a01 ff15 d4609800 ebe7`); (3) the same event tested in Update in place of 0x739a10 (both callers 0x711d1e and 0x714300 go through the one function 0x739a10/0x73de00, so patching 0x73de00 to `return WaitForSingleObject(evt,0)==WAIT_OBJECT_0` covers both without touching Demand's loop; replace Sleep(1) by SwitchToThread/Sleep(0) or Wait); (4) knowing which vtbl+0x20/+0x38 read (type 0/2) or `FUN_00739990` (type 3) starts the I/O, to arm the event; not in R1 scope.

### F5 Key-table removal / lifetimes (Q6 part 1)
- RemoveKeyTable (0x7131d0) erases the table node and runs `FUN_00722ff0` + `operator delete(table)` after `FUN_00726350` with no check that CRes objects hanging off its key entries (entry+0x10, set by SetResObject 0x712b60) are unreferenced and none is still in the evict list (resman+0x20 holds raw CRes* nodes). If a CRes with refcount 0 (flag 0x100, data cached) belongs to a removed table (AddEncapsulatedResourceFile/RemoveEncapsulatedResourceFile 0x7116b0 = module/save switch), the evict list still points at it. Whether 0x726350/0x722ff0 purge those objects is not shown in R1 (speculative UAF window during module change; a FreeChunk pass after a table removal would deref freed memory via `local_8[3] & 0x10U`).
- Normal owner protocol is ok: helper dtor 0x93d200: `if (param_1[1]) FUN_007111c0(); iVar1 = FUN_00713010(param_1[2]); if (iVar1==0) delete`, i.e. CancelRequest -> ReleaseResObject -> delete; ReleaseResObject unlinks the key entry first and 0x711e60/0x711fe0 erase the evict-list node (search by pointer) before the delete. Edge: if flag 0x10 is set 0x711fe0 returns 0 without freeing, yet the caller deletes the CRes; CancelRequest normally cleared 0x10 before (`0x711a30: if (count==0 && (flag & 0x10))`), but only when the helper's own "requested" bit (`param_1[1]`) was set.
- Stale [this+0x28]: Update sets `resman+0x28 = head CRes` at its first statement but sets flag 0x10 only if Service returned nonzero. CancelRequest clears +0x28/+0x2c only inside `if (count==0 && flag & 0x10)`. If the head Service* fails (returns 0, e.g. resource missing) the head stays stuck (Update retries every pass), and if it is then cancelled + deleted, +0x28 dangles and Update derefs `*(*(this+0x28)+8)` (0x714300). Speculative UAF/queue-stall; low frequency.

### F6 Leaks on error paths (Q6 part 2)
- 0x713fb0 sync branch (asm around 0x7141b2): `iVar1 = vtbl+0x34(...); if (iVar1 == local_c) {...} else { (**+0x14)(); return 0; }` after Malloc succeeded: the buffer stays in `CRes+0x10`, `CRes+0x18` stays, budget already reduced, flag 4 clear, refcount 0, the CRes is not in the evict list. FreeChunk cannot see it; the dtor path `0x711e60` needs `(flag & 4) || (flag & 0x10)` (`if ((((*(uint *)(param_1 + 0xc) & 4) != 0) || ((*(uint *)(param_1 + 0xc) & 0x10) != 0)) && *(int *)(param_1 + 0x10) != 0)`) so it also skips it. A later Demand of the same CRes calls Malloc again which overwrites `CRes+0x10` => the first buffer leaks permanently and the budget is double-charged. Same shape in 0x713bf0 (sync, RA 0x713da4 area) and the OnResourceServiced failure: `iVar1 = (**(code **)(*param_2 + 0x10))(); param_2[3] = param_2[3] & 0xfffffffb | -(uint)(iVar1 != 0) & 4; return iVar1;` (0x713fb0, 0x713bf0, 0x7133a0): a rejected resource (parse failure) leaves data allocated with flag 4 cleared. Impact: only bad/corrupt/mod-conflicting resources; measurable as Malloc count minus FreeResourceData count with `CRes+0x10 != 0 && !(flag&4)`.
- Demand cold path with Service* returning 0 returns 0 with no refcount++, so a caller cannot Release: consistent with the leak above (no owner).
- Release paths: no missing Release on error was found in the Demand helpers 0x93f8b0/0x93ffb0 (both Release on parse failure: `FUN_007112b0(); uVar3 = 0;`). 0x93ffb0's trailer write `iVar4 = local_2c + local_18; ... puVar1 = (undefined2 *)(iVar4 + 4 + iVar2)` relies on size+10 having been allocated: that only holds if Malloc branch +0x24 was chosen (true for CResTPC ctor), OK.
- ServiceFromDirectory (0x7133a0) handles its own FILE-buffer frees on every failure branch (`FUN_00739880(); FUN_009196fd(iVar3)`), no leak seen.
