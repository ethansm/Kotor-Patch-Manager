# W4: KT (key-table dangling CRes+0x14) + AB (action-bar churn / SetSize shrink overflow): patch-ready designs (Steam swkotor2.exe 6a522e71)

Summary (5 lines):
1. KT fix is a 12-byte IN-PLACE patch at 0x726505 (no cave): `80 CE 02 C7 41 14 00 00 00 00 90 90` (OR DH,2 == the AND/OR pair; plus `MOV [ECX+0x14],0` with ECX = CRes). Same bytes fit the sibling bug in 0x726A50 at 0x726C83. Plain NULL is NOT fully safe: two unguarded readers of CRes+0x14 remain (0x711270 GetResRef; 0x713fb0 BIF post-service log 0x71427D/0x714288/0x7142B9); recommended variant stores the address of a zeroed 0x24-byte DLL-static "dummy key entry" instead of 0 (same 7-byte instruction, imm32), which makes 0x713010's write harmless AND leaves no NULL deref.
2. KT guards verified: 0x713010 skips the write when +0x14==0 (0x713060); 0x714630 and 0x7133a0 have `CMP [..+0x14],0` guards (return 0, no crash); Demand/Release/FreeChunk/evict code never read +0x14. Orphaned CRes cannot be re-found through another table (name lookup builds a NEW CRes); module-unique resources are type 2 (ERF/RIM/MOD) -> 0x713bf0, which has no +0x14 deref.
3. AB shrink: CONFIRMED statically reachable through ONE site only, 0x8427A0 (`SetSize(idx+1)` with idx reset to 0 at 0x8428D3 while the array may already hold 2 entries) via MainLoop 0x78382E -> 0x7CEB50 -> 0x74CFE0 -> 0x743540 -> 0x77E370 -> 0x842D40 -> 0x8427A0; the other 39 sites pass live count+1 or 0. Runtime trigger is state-dependent: SPECULATIVE.
4. Fix A (min(old,new) copy bound): cave at 0x58C61A, 8 bytes stolen (`8B 55 EC 3B 51 04 7D 1C`), 23-byte cave, bytes below; alternative clamp of this[1] at 0x58C576. Fix B (capacity reuse) re-derived at 0x58C406 (12 B), behaviour-preserving, removes ~21-42 allocs + frees per 0x74CFE0 call (~0.98 calls/frame, runA 62953/64081).
5. Every cave below was assembled with GNU as and disassembled back with objdump (placeholder cave base 0x10001000) to verify encodings; rel32 formulas show the next-instruction base. No relative branch/call target exists inside any stolen range (greps quoted).

Conventions: all addresses VA, image base 0x400000. `C` = address of the cave (runtime DLL memory); rel32 = C - (site+5).
Branch-target scan command used everywhere: `grep -rE "(J[A-Z]+|CALL|JMP) +0x0*<addr>\b" decomp/*/*.asm` (regex validated: it finds the known `JLE 0x0072653e` at 0x726496).

Can the orphan be re-found through another table? No. After branch 3 nothing references the CRes except its holders (the entry's pointer lives in the array that 0x722FF0 frees: `FUN_00723190(3)`). A later lookup by name goes through `0x712360`/`0x712970` and, if another table has the name, creates/uses a different CRes (branch 1 would already have rebound the CRes in the first place: "CRes+0x14 = local_120"). So the only way to touch the orphan is through its holders (texture wrappers) calling Demand (loaded -> refcount++ only), Release, or ReleaseResObject.

Can an orphan ever reach the unguarded readers? 0x713FB0 requires `CRes+8 >> 0x1e == 0` (Demand switch `case 0: FUN_00713fb0`) AND data not loaded. Branch-3 CRes are module-unique, i.e. come from RIM/MOD/ERF tables (type 2 -> 0x713BF0, which does not deref +0x14), so 0x713FB0 is unreachable for them in practice (SPECULATIVE: a custom BIF key table removed while still demanded would reach it). 0x711270 callers (0x6CF910/0x6CFA70, both from 0x6C53F0) are non-texture helpers and are fed a CRes `this`; reaching them with an orphan is SPECULATIVE. Difference 3: a shrink (n < count) no longer destroys tail entries (they are re-defaulted when re-extended).
3. n==count. Original reallocs+copies identical contents; reuse does nothing: observably the same.
4. Memory. First call per array allocates cap = max(n, 2*alloc, 4) entries (0x3C*4+4 = 0xF4 B); ~10 arrays: < 3 KB total; the n==0 callers (0x7B40F0) free as before.

CPU estimate (SPECULATIVE): 3-10 us/frame, i.e. memory-churn win, not an FPS win (frame time is VSync capped, runA hist bucket 5 = 16-31 ms holds 46,082 of 64,081 frames).
