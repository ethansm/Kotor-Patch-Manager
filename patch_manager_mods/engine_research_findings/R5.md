# R5: error handling near the 4 GB ceiling (KOTOR II Steam swkotor2.exe)

## Summary (5 lines)
1. Allocation failure never yields NULL for game code: operator new 0x919723 loops `_malloc` -> `__callnewh` and finally throws std::bad_alloc; the new-handler (DAT_00a80514) is only ever set to encoded-NULL by CRT init and there is no swallowing `catch` in game code, so every one of the 404+49 "unchecked" new / new[] sites (and all "checked" ones: dead code) means an uncaught C++ exception = immediate process death, not a NULL write. The only game-side raw `_malloc`/`_calloc` users are 0x73A380 (checked, 0x724F00 KEY reader) and 0x73A8A0/0x73A9E0 (unchecked `_calloc` in a `CExoArrayList<int-sized>` grow/ctor: real NULL deref, rare).
2. New-found crash bug (hot, unbounded): text 2DA tokenizer FUN_0071C180 copies a token into a caller's 256-byte stack buffer (`local_130[256]` in 2DA loader 0x71C3D0) with NO length limit; any 2DA cell/header token > 255 chars overwrites the frame (stack smash).
3. GUI loader FUN_0040F620 (CSWGuiPanel::InitControl) pads the panel control vector with NULLs up to the control's ID (`while (*(panel+0x28) < id) push(0)`) with no upper bound: an ID like 0x7FFFFFFF from a GFF layout = multi-GB allocation loop; C2DA getters (0x71AFA0, 0x71B3F0, 0x71B8B0, 0x71BCF0 ...) ARE bounds-checked and return defaults (benign).
4. IsBadWritePtr user 0x555D00 (only IsBad*Ptr user in the exe; no IsBadReadPtr) is a pathfinder "GridDFS transposition table" (512 x 16 B = 0x2000) re-init; IsBadWritePtr cannot detect freed-but-committed heap so a dangling table pointer would be silently reused; in the code I traced the pointer is zeroed on every free (no confirmed UAF), but the cached table in `param_2+0x1B4` has no visible destructor free (8 KB leak per abandoned path state, speculative).
5. File-header-trusting readers: KEY reader 0x724F00 ignores the fread byte count and indexes entries with header counts (no bound), MDL/MDX loader 0x5122E0 trusts two u32 sizes from the file and `memcpy`s that many bytes (OOB read in the memory-mapped mode; uninitialised data on short read in file mode), and it duplicates the whole 6.6-12.9 MB model blob (resman copy + private `_Dst` copy); resman BIF/ERF path 0x713FB0 does compare the read size and is safe.

## (b) Findings

### F1. What allocation failure does (Q1)
- operator new 0x919723 (quoted above): `_malloc` -> `__callnewh` -> if handler NULL/returns 0 -> `__CxxThrowException_8(local_10,&DAT_009c1690)` (std::bad_alloc). It never returns NULL and never loops forever unless a handler returns non-zero.
- `__callnewh` 0x923A62: handler slot `DAT_00a80514`. Its only writer is 0x923A53, whose only caller is `__init_pointers` 0x91CEB4 passing `__encoded_null()`. imports.tsv has no `_set_new_handler`/`set_new_mode` use by game code. => handler always NULL.
- `_malloc` 0x9215E6: returns NULL (errno 12) when `DAT_00a80c00 == 0` (new-mode off): callers of raw malloc/calloc see NULL, but only 0x73A380, 0x73A8A0, 0x73A9E0 are game-side (callgraph: callers of 0x9215E6 are CRT + 0x73A380; callers of `_calloc` 0x920D6C are CRT + 0x73A8A0 + 0x73A9E0).
- Catch handlers: every game `Catch_All@` funclet in decomp only cleans up and rethrows (`FUN_009196fd(*(undefined4 *)(unaff_EBP + -0x14)); __CxxThrowException_8(0,0);` e.g. 0x4D4BC9); the 3 non-rethrowing ones (0x405749, 0x406F0F, 0x406A17) are iostream ios_base catch(...) blocks. SetUnhandledExceptionFilter is only in CRT (`__invoke_watson`, `___report_gsfailure`). => bad_alloc is fatal (terminate/Wine crash), and the "NULL-tested" sites (2000 `checked=yes`) contain dead code. Consequence table for **unchecked** operator_new sites: severity = crash (uncaught exception), NOT NULL-write; the heap-exhaustion case near 4 GB (large-address-aware 32-bit) therefore dies at whichever allocation happens to fail first (largest/most frequent = texture `size+10` mallocs, CExoResMan::Malloc 0x712F30).
- Side effect (benign-to-corruption, speculative on exact path): 0x712F30 reserves budget before allocating: `*(int *)(param_1 + 8) = *(int *)(param_1 + 8) - *(int *)(param_2 + 0x18);` then `FUN_00919723(...)`. On bad_alloc the decrement is not undone (the undo at `if (!bVar3)` is dead), but the process is dying anyway.
- Dead NULL tests worth knowing (they mislead reading of the code): 0x712F30 `bVar3 = *(int *)(param_2 + 0x10) != 0`; 0x483700 `if (local_34 != (void *)0x0)`; 0x71C3D0 `if (local_180 == 0)` etc.; 0x555D00 has none.

### F2. Raw malloc/calloc users that DO return NULL (real NULL deref) (Q1/Q2)
- 0x73A9E0 `pvVar1 = _calloc(param_4,4); *param_1 = pvVar1;` (asm caller 0x73AC70/0x726790). Later element stores `*(param_1[0]+i*4)` fault at low addresses. severity crash, reachability rare (only when the CRT heap is exhausted; but note `_calloc(0,4)` with n=0 returns a 1-byte block, fine).
- 0x73A8A0 grow: `pvVar1 = _calloc(local_c,4); for (local_10 = 0; ...) *(pvVar1+local_10*4) = ...` then `_free(*param_1)`. NULL => crash in copy loop. Also perf: growth is `local_c = local_c + 5` (linear), i.e. O(n^2) element copying for big arrays (`if ((int)local_c <= param_1[1]) local_c = local_c + 5;`). severity: crash/perf, reachability: 0x73AAD0/0x73A5F0 array inserts (used by string/list containers).
- 0x73A380 is fine: 0x724F00 tests it: `local_54 = FUN_0073a380(local_60); if (local_54 == 0) { *local_19c = 0; ...` (KEY file table).

### F4. IsBad*Ptr (Q5): 0x555D00
Full code:
```
if (*(int *)(param_1 + 0x274) != 0) {
  BVar1 = IsBadWritePtr(*(LPVOID *)(param_1 + 0x274),0x2000);
  if (BVar1 == 0) goto LAB_00555d4a;      // keep & re-init in place
}
uVar2 = FUN_00919723(0x2000);  *(param_1 + 0x274) = uVar2;
```
- imports.tsv: only IsBadWritePtr at 0x555D24 (`CALL dword ptr [0x00986144]`); no IsBadReadPtr/IsBadCodePtr.
- Latent reuse: on a free()d 8 KB block the process heap page is still committed, so IsBadWritePtr returns 0 ("still writable") and the loop `for (local_8 = 0; local_8 < 0x200; ...)` writes 8 KB through a dangling pointer. In 0x5532F0 every free zeroes `param_1+0x274` and (at the two failure sites) `param_2+0x1B4` too: `FUN_009196fd(local_15c); *(undefined4 *)(param_1 + 0x274) = 0; ... *(undefined4 *)(param_2 + 0x1b4) = 0;` (0x55338x/0x5533Cx) and the success path moves the pointer `*(param_2 + 0x1b4) = *(param_1 + 0x274); *(param_1 + 0x274) = 0;`. I could not find another free of `param_2+0x1B4` (grep of decomp for `+ 0x1b4)` gives only unrelated structs), so **no confirmed UAF**; the latent risk exists only if the owner of `param_2` is freed or reset elsewhere while `param_1+0x274` still aliases it (aliasing window = between `*(param_1+0x274) = *(param_2+0x1b4)` at LAB_00553a8b and the tail). severity: corruption (latent), reachability: per path query (0x5532F0 caller 0x55AC80).
- Same-shape sibling with NO IsBad check: 0x552A90 (`if (*(param_1 + 0x1b8) == 0) alloc 0x2000`). No destructor free of `+0x1B4`/`+0x1B8` located (speculative 8 KB leak per abandoned search state).
- Also: 0x5532F0 line ~206 allocates `param_1[0x25C]*4` bytes into `param_2+0x1D8` only `if (local_94 == 0)`; if `param_1+0x25C` (grid size) grows between calls while the cached buffer is reused, the buffer is undersized (speculative OOB write).

### F5. 2DA and GUI bounds (Q4)
- C2DA getters are safe: quoted checks above (0x71AFA0, 0x71B3F0, 0x71B8B0, 0x71BCF0). On failure they write a default to the out-param (`*param_4 = local_10; bVar4 = false;`) so callers that ignore the bool get 0/default, not garbage. severity benign.
- **F5a (crash, hot): tokenizer overflow.** 0x71C180 copy loop (asm):
  `0071c246 8b45fc MOV EAX,[EBP-4]`, `0071c249 8a08 MOV CL,[EAX]`, `0071c24b 880a MOV [EDX],CL`, `0071c250 83c201 ADD EDX,1` (EDX = `[EBP+0x10]` = dst). The only bound is `local_c < *param_2` (remaining input bytes), never the destination size. Callers (0x71C3D0) pass `&local_130` in a frame `SUB ESP,0x184` with `char local_130; char local_12f[255];` (256 B). Any header token, cell or quoted string of >= 256 chars smashes locals (`local_30` cookie slot, saved EBP, return address). The loop calls it for every header/cell token: `while (iVar3 = FUN_0071c180(&local_20,&local_18,&local_130,local_2c), iVar3 != 0)` and `iVar3 = FUN_0071c180(&local_14,&local_134,&local_130,local_2c);`. Trigger: modded 2DAs with very long quoted cells (long descriptions, path lists). Reachability: all text 2DAs (binary V2.b variant path is at `param_1+0x3C != 0`). severity: crash (or worse). Unknown whether /GS check is present (I did not see `__security_check_cookie` in this frame's tail, speculative).
- **F5b (crash/DoS): GUI control ID padding.** 0x40F620 asm:
  `0040f9a6 8b8574ffffff MOV EAX,[EBP-0x8c]` (panel), `0040f9ac 8b4828 MOV ECX,[EAX+0x28]` (count), `0040f9b5 8b55b0 MOV EDX,[EBP-0x50]` (id = `param_2[0x15]`), `0040f9b8 3b9578ffffff CMP EDX,[EBP-0x88]`, `0040f9be 7e12 JLE`, `0040f9c0 6a00 PUSH 0`, `0040f9cb e890f04200 CALL 0x0083ea60`, `0040f9d0 ebd4 JMP 0x0040f9a6`. Only `-1 < id` is tested (`(param_4 != 0) && (iVar6 = param_2[0x15], -1 < iVar6)`), so a layout ID of e.g. 0x00FFFFFF pushes 16M NULLs (64 MB vector, doubling copy = 128 MB transient), 0x7FFFFFFF exhausts address space (bad_alloc).   Consumers are NULL-tolerant for the padding entries (0x40EC90 `if ((*(int *)(... + local_18 * 4) != 0) &&`), but indexed users (`GetControl(id)`, not traced) may not be (speculative).
- Direct index: `if (iVar6 < *(int *)(param_1 + 0x28)) *(int **)(*(int *)(param_1 + 0x24) + iVar6 * 4) = param_2;` overwrites without freeing the earlier control at that slot (duplicate IDs in a layout leak the old control; benign leak).

### F6. Unchecked / untrusted file reads (Q3)
There is no direct ReadFile/CreateFile use by game code (imports.tsv: `ReadFile` only in `__read_nolock`/`__ftelli64_nolock`); all game reads go through CRT `_fread` (0x91F3EF) via these game functions (callgraph callers of 0x91F3EF: 4761B0, 4762F0, 482CE0, 482E40, 482F50, 483100, 4833F0, 483440, 483700, 64E910, 6F4850, 70CAA0, 73D1A0, 73DC30, 73DD20).
- **F6a (corruption, medium reach): KEY reader 0x724F00.** `local_1c = FUN_00739990(&local_84);` (0x18-byte header read; return count ignored, `local_1c` is never read again: grep shows only the two assignments at lines 215 and 328), then `local_60 = local_70 + -(int)local_74;` (KEY key-table offset minus file-table offset, both from the file, no `>=` check), `local_54 = FUN_0073a380(local_60);` (checked), `local_1c = FUN_00739990(local_54);` (read result ignored), then `for (local_14 = 0; local_14 < local_7c; ...)` reading `*(local_54 + local_14*0xc + ...)` and `*(int *)(local_54 + 4 + local_14 * 0xc) - (int)local_74` used as a pointer offset `local_54 + offset` with no `offset < local_60` test. A truncated/corrupt chitin.key gives uninitialised or OOB heap reads. Reachability: once at startup (chitin.key), only corrupt install triggers. severity: crash/corruption.
- **F6b: MDL/MDX loader 0x5122E0 (per model load, hot).** sizes straight from the stream: `*param_1 = *psVar1;` ... `param_1[1] = *psVar1;` then `_Src = FUN_004762f0(*param_1,param_2); _Dst = FUN_00919723(*param_1); _memcpy(_Dst,_Src,*param_1);`. In memory-mapped mode 0x4762F0 just advances a pointer (asm `00476310 8b510c MOV EDX,[ECX+0xc]`, `00476313 035508 ADD EDX,[EBP+8]`, `00476322 2b5508 SUB EDX,[EBP+8]` (remaining count goes negative, never tested)) so a bad size makes memcpy read past the resource (AV) or, with size >= 2 GB, throw bad_alloc. In file mode `_fread(_DstBuf,1,param_1,...)` result ignored (asm 0x476357 `CALL 0x0091f3ef`, next insn `ADD ESP,0x10`): short read leaves uninitialised bytes (operator new does not zero). severity crash/corruption, only on corrupt models.
- **F6c (memory cost, near-4GB relevant): double copy.** In memory-mapped mode 0x4762F0 returns a pointer into the CRes blob, then 0x5122E0 does `FUN_00919723(*param_1)` + `_memcpy` again, so every loaded model blob exists twice (CRes data + private copy), matching census blobs 6.6-12.9 MB. If the private copy is what the model owns, the resman copy could be released earlier / the copy skipped (speculative, needs ownership proof; see R1/doc 10 model cache).
- **F6d: loose-file texture readers (legacy).** 0x483100: `_fread(param_2,4,1,param_1);` x5 reads w,h,format,size from the file, `uVar2 = FUN_00483360(*param_2,*param_3,*param_4);` computes the full mip-chain size, allocs it, then `_fread(_DstBuf,1,*param_5,param_1);` reads `*param_5` (file supplied) bytes into that buffer: a header whose size field exceeds the computed chain size overflows the heap buffer; the mip loop then advances `local_10 = local_10 + local_c` without bounds. 0x482CE0 `_DstBuf = FUN_00919723(*param_2 * *param_3 * 2); _fread(_DstBuf,1,*param_2 * *param_3 * 2,...)`: 32-bit multiply overflow (e.g. 65536 x 32768) allocates small, reads big. 0x483700 same with `local_3c * local_38 * 2`. Reachability: callers 0x4219A0 / 0x421BC0 (from 0x4252C0 / 0x425800); probably rarely used for Steam K2 (resman path uses TPC/TGA via CRes classes) so label speculative on hotness. severity heap overflow (only on hostile/corrupt file).
- **F6e: async reader 0x73D1A0.** `sVar1 = _fread(...); *(undefined4 *)(param_1 + 0x20) = sVar1 * *(int *)(param_1 + 0x18);` records actual bytes so a short read is visible; 0x73D1A0 also sets `+0xC = 1` even when `+0x14 == 0`. Consumer 0x715A60 (called at 0x711C20 after the wait loop, `iVar2 = FUN_00715a60(); if (iVar2 == 0) uVar1 = 0;`) evidently checks it (not decompiled here). severity benign.
- **F6f: resman BIF/ERF read (0x713FB0/0x713BF0):** expected size is `local_c = (vtbl+0x24)(param_2[2] & 0x3fff)`, read is `(vtbl+0x34)(...)` and `if (iVar1 == local_c) {...} ... return 0;` so short reads fail cleanly; but the *size* `local_c` comes from the BIF variable-resource table and is fed to `FUN_00712F30` (`FUN_00919723(*(param_2+0x18)+10)`) with no cap: a corrupt BIF entry with size ~0xFFFFFFFF+ throws bad_alloc. benign for vanilla.
- **F6g: CExoFile::Read 0x73DC30 / 0x73DD20** check `_ferror`/`_feof` and close the file on error; returned counts propagate (0x73DD20 returns `sVar1 * param_3`), callers such as 0x724F00 ignore them (F6a).
- GetLastError users in game code: 0x409550, 0x40DD10, 0x40CC70, 0x531BE0, 0x737540, 0x737D60 (window/OS helpers, not in the load path).

## (d) Open questions
1. Does the K2 2DA reader ever see tokens >= 256 chars in a real (modded) install? Needs an offline scan of Override + game 2DAs (cheap, read-only); is the `/GS` cookie present in 0x71C3D0's frame (tail at 0x71CF61-0x71CF71)? If yes the failure is a fast-fail crash, if no it is exploitable stack corruption.
2. Exact owner and free path of `param_2+0x1B4` / `+0x1B8` tables (who owns `param_2` of 0x5532F0, 0x55AC80 callers)? Needed to confirm or refute the IsBadWritePtr reuse-after-free and the suspected 8 KB leak.
3. Who owns the MDL private copy `_Dst` (0x5124D0 / 0x512750)? If the model retains it, the resman blob copy (CRes data of 6.6-12.9 MB) is pure duplication and a release/skip point is worth ~ the census "model blob" bytes.
4. Whether any caller of the 0x40F620 control list indexes by ID with `GetControl(id)` without a NULL test (padding entries are NULL).
5. Census overlay: rank the 404 unchecked new sites by live-heap a2 weight (not done here); most are irrelevant given F1 (they cannot produce NULL).
6. `DAT_00a80dd8` heap mode (V6 small-block heap vs plain HeapAlloc) was not examined; it changes whether `_malloc` fails earlier than address-space exhaustion (fragmentation near 4 GB), speculative.
