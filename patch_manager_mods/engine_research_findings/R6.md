# R6: grass and render buckets (K1 GrassMemorySafety / TextureBucketSafety equivalents in K2 Steam)

## 5-line summary
1. CAurTriangleBin is fully mapped (mapper vote, delta -0x38ee50, 11/11): ctor 0x50c660, dtor 0x50c7a0, DestroyGrassPolys 0x50da00, BuildGrassPolys 0x50d960, CreateArrays 0x50ebc0, Render 0x50dac0, wind 0x510f70. The seed 0x4664E0 is really Scene::DoBinBucket (the per-frame loop that calls Render 0x50dac0), not the class method.
2. K1 double free is ABSENT at rest: dtor (0x50c7a0) and DestroyGrassPolys (0x50da00) do delete([+0x3c]) then delete([+0x38]); the fields DO alias transiently ([+0x3c]=[+0x38] at 0x50ec34 and at 0x50db.. render), but both write sites reset [+0x3c]=0 (0x510f4b, and param_1[0x1e]=0/[0x1f]=0 in 0x50dac0) before any destroy can run; delete(NULL) is a no-op and bit0 of [+2] is cleared after the first delete. No port needed (residual risk: destroy during an exception/re-entry inside the alias window, speculative, no evidence).
3. K2 mesh buckets are not arrays: they are a std::map-like red-black tree keyed by uint (texture object +0x58 key) at 0xA73374 (mesh), 0xA73318 (fade), 0xA733A0 (cap), each value a doubling pointer vector (16, x2). Insert = FUN_004946b0 (AddPartToMeshBuckets equivalent) at 0x49472b..0x494737; unbounded, no capacity/index, so the K1 5000-entry overflow is ABSENT by construction.
4. Reset equivalent of K1 ClearBuckets is FUN_00495760 (3 map clears via 0x4727a0, counters zeroed); it calls AurTextureGetMaxTexID 0x427A60 and discards the result. 0xA1BB84 (max texid) is only computed by scans 0x427810/0x427970 and pushed into a doubling list; nothing indexes an array by it.
5. Only fixed-size things in the render path are bounded by construction: grass info records are a growing array of 0x60-byte records (DAT_00a7d698, count DAT_00a7d69c, grown on demand by 0x50c430 -> 0x511600 -> 0x511a60), 4-entry weight arrays (loop < 4). One minor hazard: `operator new` at 0x50ebed in CreateArrays is unchecked (crash only on OOM). Name_map entries 0x652810/0x6527c0 ("AurGrassAddInfo"/"AurGrassMaterialInUse") look WRONG (0x652810 is a recursive octree traversal); real equivalents are 0x50c430 (AddInfo) and 0x50c3e0 (MaterialInUse).

## (b) Findings

### 1. Grass object layout and free sites (Q1)
Layout (Steam): +0x00 short stride, +0x02 flags (bit0 buffer allocated, bit2 built/destroyed marker, bit3/4 variants), +0x10 grass id (-1), +0x18 tri count, +0x38 buffer, +0x3c work cursor, +0x44 size, +0x54 texture. Destructor 0x50c7a0:
```
if ((*(byte *)(param_1 + 2) & 1) != 0) {
  FUN_009196fd(*(undefined4 *)(param_1 + 0x3c));  *(undefined4 *)(param_1 + 0x3c) = 0;
  FUN_009196fd(*(undefined4 *)(param_1 + 0x38));  *(undefined4 *)(param_1 + 0x38) = 0;
  *(byte *)(param_1 + 2) = *(byte *)(param_1 + 2) ^ 1;
```
DestroyGrassPolys 0x50da00 has the identical delete pair guarded by bit0 and clears bit0. Both are "delete +0x3c, then delete +0x38" exactly as the K1 bug shape.

### 2. Double-free verdict: ABSENT at rest, aliasing transient only
Assignments of the fields:
- Alloc in CreateArrays: 0x50ebed `CALL 0x00919723`; 0x50ec07 `MOV dword ptr [ECX + 0x38],EDX`; 0x50ec34 `MOV dword ptr [ECX + 0x3c],EAX` (EAX = [EDX+0x38]): decompile `*(undefined4 *)(param_1 + 0x1c) = local_120; ... *(undefined4 *)(param_1 + 0x1e) = *(undefined4 *)(param_1 + 0x1c);` (short* units: 0x1c*2=0x38, 0x1e*2=0x3c). So [+0x3c]==[+0x38] during generation.
- Reset at the end of CreateArrays: `0x00510f4b (in the 0x50ebc0 asm listing): C7403C00000000 MOV dword ptr [EAX + 0x3c],0x0` followed by `OR EDX,4` on [+2] (decompile: `param_1[0x1e] = 0; param_1[0x1f] = 0; *(byte *)(param_1 + 1) = (byte)param_1[1] | 4;`). The listing's tail lines belong to 0x50ebc0 (function size 9133 bytes).
- Per frame in RenderGrassPolys 0x50dac0: `*(undefined4 *)(param_1 + 0x1e) = *(undefined4 *)(param_1 + 0x1c); FUN_00510f70(param_4); param_1[0x1e] = 0; param_1[0x1f] = 0;` (alias set, wind update, alias cleared).
Result: at destructor time [+0x3c]==0, so the first delete is delete(NULL); no double free. Bit0 is cleared after freeing so a second Destroy/dtor also skips. The only exposure is a destroy occurring inside the alias window (0x50ec34..function end, or around 0x510f70). Those windows call only math helpers (0x507680, 0x507250, 0x5142f0, 0x50e910); no evidence of re-entry, single threaded. Verdict: K1 double free not present; no patch needed. `speculative`: an SEH exception in the window would leave the alias set.
Minor: unchecked `new` at 0x50ebed (alloc_sites `checked no`), result stored at +0x38 and used immediately; OOM-only crash.

### 3. Mesh bucket insert (Q3): tree map keyed by texture, no bound
AddPartToMeshBuckets equivalent FUN_004946b0, asm:
```
0049470f  8b5508   MOV EDX,dword ptr [EBP + 0x8]
00494712  8b4a44   MOV ECX,dword ptr [EDX + 0x44]
00494715  e876680400 CALL 0x004daf90        ; -> FUN_00426be0 -> texture obj +0x58 (key)
0049472b  b97433a700 MOV ECX,0xa73374       ; mesh-bucket map
00494730  e8fbdefdff CALL 0x00472630        ; map[key] (find-or-insert)
00494735  8bc8       MOV ECX,EAX
00494737  e804f8fdff CALL 0x00473f40        ; vector.push_back(mesh)
00494745  ...        MOV ECX,0xa732a0 ; CALL 0x00473f40   (also global list)
```
Alternative branch when `*(char*)(ctx+0x186) != 0`: push to unkeyed list `0xa73394` (0x494703). 0x473830 shows the RB tree descent `if ((uint)local_c[3] < *param_2)`; capacity is dynamic (nodes are new'd in 0x472840, vector doubles 16 -> 32 ...). No index into a fixed array; K1 overflow ABSENT. DoMeshBuckets reads via the same operator[] (`iVar3 = FUN_00472630(&local_4c); if (*(int *)(iVar3 + 4) != 0)`), iterating ids gathered by 0x427970. Cost note (speculative, not a bug): every 0x472630 call in DoMeshBuckets is O(log n) plus repeated lookups (loop calls it 2-3 times per id).

## (c) Runtime measurements
- Grass alias check (only if paranoid): counter at dtor 0x50c7a0 entry: log when `[this+0x3c] != 0 && == [this+0x38]`. Expected: never fires. Hook site 0x50c7e8 (`CALL 0x009196fd`) is a relative call; better hook at function start (see .asm) with >=5 byte prologue.
- Bucket sizes: read map header count at `[0xA73374+0x1c]` (0x472630 uses `+0x18` head node, `+0x1c` count per 0x4727a0) each frame, and `[0xA732A0+4]` list count; expect tens to few hundred entries, monotone growth would indicate leak (0x495760 clears them).
- Texture id spread: log `DAT_00a1bb84` after 0x427970 (inside DoMeshBuckets) to confirm ids are far below any fixed array size (no such array exists, informational).
- Hook for map insert visibility: 0x494730 `E8 FB DE FD FF` (CALL rel32 0x472630, relative call; stealing 5 bytes needs relocation) or entry of 0x4946b0 `55 8B EC 83 EC 68` (6 bytes, no relative branch).
