Batch V6 (leads L9, L10; candidate TD). Static only. ROOT = `~/Games/KOTOR2_Mod_Workspace/ghidra_dumps/steam_6a522e71/`; constants/files read read-only from `backups/vanilla_clean/`.

## Summary (5 lines)
1. There is ONE parser, `0x71C3D0` (named C2DA::LoadText, really "Load"): it is selected per resource by `CRes2DA+0x38`, set by the magic check in `CRes2DA::OnResourceServiced` `0x729FD0` (`"2DA "` + `"V2.0"` text / `"V2.b"` binary), so Override loose files, `2DA.bif` entries and ERF/RIM all take the same parser chosen by the first 8 bytes only; `0x71D360` is NOT a parser (it is `C2DA::Init`: find/create the CRes2DA, type 0x7E1). The binary path reuses the tokenizer `0x71C180` only for the HEADER (column names, same 256-byte `local_130` buffer, same overflow at token length >= 256); binary row labels and cells are offset/NUL-based and never copied to the stack.
2. Premise correction: all 424 `2DA.bif` entries of the vanilla K2 install are binary `2DA V2.b`, and all 37 live `override/*.2da` are binary too; the text path is only reached by hand-made/mod text 2DAs. Vanilla binary headers are tiny (longest column name 23 chars, <= 94 columns, <= 999 rows, header <= 921 B, label region end <= 3901 B, data <= 19225 B), so L9 cannot fire on this install today; scanner danger thresholds are stated in F4.
3. The community table (`2da_row_limits.md`) describes KOTOR 1 (v1.03), not K2: it cites `CSWGuiScriptSelect` and `CExoSoundInternal::LoadSoundProvider` (present in `kotor1_0_3.db`, absent from the K2 GOG DB and from K2 Steam strings) and uses K1 class names `CSWClass::LoadSpellGainTable/LoadAttackBonusTable/LoadSavingThrowTable/LoadFeatGain` (K2 GOG symbols are `Global::`). K2 vanilla itself contradicts rows `placeables 256` (361 rows vanilla, 402 live) and `upgrade 32` (369 vanilla, 464 live).
4. Row verdicts vs K2 Steam: `appearance` 65536 CONFIRMED (u16 at creature+0x194 and client+0x18); `portraits` CONFIRMED but usable ids stop at 0xFFFD (sentinels `>= 0xFFFE`); `soundset` CONFIRMED with a worse failure (row count truncated to u16: 65536 rows -> count 0); `classes` 256 CONFIRMED with the same truncation (byte count; 256 rows -> 0 classes); `heads` 256 CONFIRMED only for the per-creature byte path (0xFF is the sentinel so ids 1..254; head 0 is remapped to 1), the appearance.2da NORMALHEAD/BACKUPHEAD int path is unbounded; `baseitems` unbounded (i32 count, bounds-checked accessor) CONFIRMED; `placeables` 256 REFUTED for K2; `upgrade` 32 REFUTED as a row limit (the 32-bit `Upgrades` mask is real, row-vs-bit use SPECULATIVE).
5. Practical headroom on this install: `heads.2da` has 249 live rows against 254 usable byte-path ids (only ~5 spare for creature templates using `Appearance_Head`); every other table checked is far below its width (appearance 802/65536, portraits 90, soundset 70, classes 17/255, baseitems 109, placeables 402, upgrade 464).

## (b) Findings

### F1. Which parser each load path takes (question i)

The magic is read in the resource's own vtable method, never in the loader of the 2DA object:

```
0x00729fd0 CRes2DA::OnResourceServiced
  param_1[0xb] = param_1[6] + -8;  param_1[0xd] = param_1[4];       // +0x2C = size-8, +0x34 = data
  if (*(int *)param_1[0xd] == 0x20414432) {                         // "2DA "   asm 0x72A01B CMP dword ptr [EAX],0x20414432
    if (*(int *)(param_1[0xd] + 4) == 0x622e3256) { param_1[0xe] = 1; }       // "V2.b"  -> CRes+0x38 = 1 (binary)
    else if (*(int *)(param_1[0xd] + 4) != 0x302e3256) { (**(code **)(*param_1 + 0xc))(); return 0; }  // "V2.0" text; else fail
    param_1[0xc] = param_1[4] + 8;  param_1[10] = 1;                // +0x30 = data+8, serviced
```
`param_1[0xe]` is CRes+0x38; the ctor zeroes it (`*(undefined4 *)(this + 0x38) = 0;`, 0x729ED0). Anything else than `"2DA V2.0"` / `"2DA V2.b"` (8 bytes) is rejected (vslot +0xC, returns 0).

Every resman source ends in that vtable call, so the parser depends only on the first 8 bytes of the data, not on where it came from:
- `CExoResMan::Demand` 0x711C20 `switch(*(uint *)(param_2 + 8) >> 0x1e)`: case 0 `FUN_00713fb0` (KEY/BIF: reads via `(vtbl+0x34)`, then `iVar1 = (**(code **)(*param_2 + 0x10))();`), case 1 `FUN_00713e80`, case 2 `FUN_00713bf0` (`iVar1 = (**(code **)(*param_2 + 0x10))();` line 47), case 3 `FUN_007133a0` (loose file through CExoFile `0x7397F0/0x739970/0x739990`; line 227 `iVar3 = (**(code **)(*param_2 + 0x10))(uVar1,iVar3);`). Which case is "Override" vs "ERF/RIM" is inferred from callees (case 3 uses `CExoFile` open/size/read and the `"REBOOTDATA:"` alias string): speculative; it does not matter for the parser choice.
- The consumer `C2DA::Load` 0x71C3D0 copies the flag: asm 0x71C450 `8b5138 MOV EDX,dword ptr [ECX + 0x38]` / 0x71C465 `89483c MOV dword ptr [EAX + 0x3c],ECX` (C2DA+0x3C = binary flag), data ptr `FUN_006f3d90` = `*(this+0x30)`, size `FUN_00703bd0` = `*(this+0x2c)` (both quoted: `return *(undefined4 *)(param_1 + 0x30);`, `... + 0x2c`).
- 0x71C3D0 has 135 distinct caller functions (callgraph rows with callee 0x71C3D0, each a loader of one table), 0x71D360 has one (the ctor). No path constructs a C2DA without going through these two.

Measured data (offline read of the vanilla install, no code run): `data/2DA.bif` has 424 resources of type 2017 and the first 8 bytes of ALL of them are `2DA V2.b`; the live `override/` has 37 `*.2da`, all `2DA V2.b` (Patch Manager writes binary). So on this install the text path (`+0x3C == 0`) is exercised only by hand-written / third-party text 2DAs, not by vanilla. (The brief's "usually text V2.0" is wrong for K2 Steam.)

### F2. What the shared code does per format (the dangerous sites)

Frame of 0x71C3D0 (asm, authoritative; Ghidra's `local_130` naming is off by 4): prologue `0071c3e1 81ec84010000 SUB ESP,0x184`; cookie `0071c3ee 8945d4 MOV dword ptr [EBP + -0x2c],EAX`; token buffer = `[EBP-0x12c .. EBP-0x2c)` (`LEA EAX,[EBP + 0xfffffed4]` is the dest pushed at 0x71C4A4, e.g. before `CALL 0x0071c180` at 0x71C4B9). The buffer is exactly 256 bytes and ends exactly at the cookie slot.

All 8 tokenizer call sites pass that same buffer (checked: dest pushed before each `CALL 0x0071c180`; 0x71C4B9, 0x71C4FE, 0x71C564, 0x71C5A2, 0x71C64B, 0x71CA05, 0x71CDBD, 0x71CE27):

| call site | what is tokenized | runs for binary? | length bound passed (remaining) |
|---|---|---|---|
| 0x71C4B9 | first token after magic/newline (tested against `"DEFAULT:"`/`"DEFAULT"`) | YES (first column name in binary) | line length (`FUN_0071c130`) |
| 0x71C4FE, 0x71C564, 0x71C5A2 | tokens after a `DEFAULT` marker | only if header starts with DEFAULT | line length |
| 0x71C64B | column COUNT pass: every token on the header line | YES | line length `[EBP-0x18]` |
| 0x71CA05 | text only: column-name pass (`__strlwr` then store) | no (binary branch starts 0x71C6D7, ends 0x71C8EE, contains no tokenizer call) | WHOLE remaining `[EBP-0x14]` (a quote can span lines) |
| 0x71CDBD | text only: row label (first token of every row) | no | WHOLE remaining `[EBP-0x130]` |
| 0x71CE27 | text only: each of the `cols` cells of every row | no | WHOLE remaining |

Binary branch (asm 0x71C6D7-0x71C8EE) uses NO tokenizer: column names are located by scanning to `\t`/`\0` and storing 16-bit offsets, row labels likewise, cells by 16-bit offsets into a data blob:
- `0071c757 66891448 MOV word ptr [EAX + ECX*0x2],DX` (column-name offset, `(undefined2)local_13c`), scan loop `0071c764 0fbe08 MOVSX ECX,byte ptr [EAX]` / `83f909 CMP ECX,0x9` / `85c0 TEST` (stops at tab or NUL, NO end-of-buffer test);
- row count read unaligned from the file: `0071c7c8 8b0a MOV ECX,dword ptr [EDX]` / `0071c7ca 894824 MOV dword ptr [EAX + 0x24],ECX` (this+0x24 = rows, u32 from file, no validation);
- row-label offsets: `0071c846 66891448 MOV word ptr [EAX + ECX*0x2],DX` (u16); label scan `0071c853`-`0071c869` (tab/NUL, no end test);
- cell offset table size: `0071c8ba d1e2 SHL EDX,0x1` / `0071c8c2 0faf5028 IMUL EDX,dword ptr [EAX + 0x28]` (rows*2*cols, 32-bit, unchecked), data size word `0071c8cf 668b11 MOV DX,word ptr [ECX]` read and DISCARDED (stored to `[EBP-0x13c]` only), data start `0071c8eb 895140 MOV dword ptr [ECX + 0x40],EDX`.
- Cell read (getter 0x71AFA0, 0x71B8B0): `(uint)*(ushort *)(*(int *)(param_1 + 0x44) + (param_2 * *(int *)(param_1 + 0x28) + param_3) * 2)` added to `this+0x40` and handed to `CExoString` assign: so a binary cell is a NUL-terminated string at a u16 offset; any length, copied by heap allocation, never to the stack.
- Column lookup by name in binary (0x71AEF0): `__stricmp((char *)((uint)*(ushort *)(*(int *)(param_1 + 0x50) + local_8 * 2) + *(int *)(param_1 + 0x48)),_Str2)`.

Consequence for question (i): a >255-char CELL or ROW LABEL cannot overflow on the binary path (they are never tokenized); a >255-char COLUMN NAME can overflow on BOTH paths (tokenized at 0x71C4B9 and counted at 0x71C64B on both). On the text path every token class can overflow.

### F3. L9 overflow geometry (exact dangerous lengths)

Buffer `[EBP-0x12c, EBP-0x2c)` = 256 bytes; the tokenizer writes `L` characters then a NUL (asm 0x71C308 `c60200 MOV byte ptr [EDX],0x0`); loop bound is only `local_c < *param_2` (remaining input), never the destination size (0x71C289-0x71C2EE loop; quoted loop 0x71C224-0x71C268). Byte `k` of the token goes to `EBP-0x12c+k`:

| token length L (chars, excluding NUL) | what is written | outcome |
|---|---|---|
| 0..255 | fits, NUL at k=L <= 255 | safe |
| 256 | NUL at k=256 = `[EBP-0x2c]` (cookie, low byte) | cookie mismatch unless its low byte was already 0 (1/256): `0071cf71 8b4dd4 MOV ECX,dword ptr [EBP + -0x2c]` / `0071cf74 33cd XOR ECX,EBP` / `0071cf76 e873c71f00 CALL 0x009196ee` -> `CMP ECX,dword ptr [0x00a11f20]` / `JNZ 0x9196f8` -> `JMP 0x0092394d` (cookie-failure handler; that it terminates the process is not read here, speculative) |
| 257..259 | more cookie bytes | same |
| 260.. 283 | `[EBP-0x28]` (tokenizer out param `local_2c`), `[EBP-0x24]/[EBP-0x1c]` (data cursors), `[EBP-0x20]` (row counter), `[EBP-0x18]/[EBP-0x14]` (remaining counts), `[EBP-0x10]` | loop state corrupted before the function can return: wrong parse / AV (speculative on which one) |
| >= 288 | `[EBP-0xc]` (saved SEH prev), `[EBP-8]`, `[EBP-4]` (SEH state) | exception unwinding derails |
| >= 300 / 304 | saved EBP / return address | masked by the cookie check only if the function reaches its epilogue |

(Offsets computed as `k = (EBP-0x12c) + k`: `[EBP-0x2c]`=k 256, `[EBP-0x28]`=260, `[EBP-0x24]`=264, `[EBP-0x20]`=268, `[EBP-0x1c]`=272, `[EBP-0x18]`=276, `[EBP-0x14]`=280, `[EBP-0x10]`=284, `[EBP-0xc]`=288, `[EBP-8]`=292, `[EBP-4]`=296, saved EBP=300, return=304.) The /GS cookie IS present (R5 open question 1 answered): `local_30 = DAT_00a11f20 ^ (uint)&stack0xfffffffc` at entry, `__security_check_cookie(local_30 ^ (uint)&stack0xfffffffc)` at 0x71CF61-0x71CF76 (decomp tail). So the minimum failure is a deterministic fast-fail on return for L = 256 (the cookie compare happens only on normal return; the rows loop continues to run with the corrupted frame until then).

Quote rules (decide token length): unquoted token = run up to space, tab, LF, CR or NUL (0x71C2B3-0x71C2C4 compares `0x20 0x09 0x0a 0x0d` and `TEST EAX,EAX`); quoted token = chars after the opening `"` until the closing `"` or NUL or the remaining-count bound; quotes are not copied, spaces/tabs/LF inside quotes ARE copied. At the row/cell sites the remaining count is the whole file remainder, so a LONE `"` in a text 2DA makes the token run to the next `"` anywhere later in the file (length = distance, across line ends): any odd quote count therefore also needs to be flagged.

Observed data: the vanilla binary 2DAs' longest column name is 23 chars; live override 2DAs are binary; no text 2DA exists to measure, so "does any real 2DA reach 256" is NO for vanilla+live (offline read) and only reachable by third-party text 2DAs.

### F4. Scanner specification (question iii; scanner NOT written)

Common: first 8 bytes must be exactly `2DA V2.0` or `2DA V2.b`, else the engine fails the load (0x72A04F-0x72A06E: `(**(code **)(*param_1 + 0xc))(); return 0;`).

Text path (`V2.0`), emulate the tokenizer exactly (do not use a regex): flag
1. any token of L >= 256 (see rules above) among: the first token after the magic (and tokens following a `DEFAULT`/`DEFAULT:` line), every header-line token, every row label (first token of each non-blank row), and the first `cols` tokens after the label of each row (extra cells beyond the column count are never tokenized: loop `local_138 < *(int *)(param_1 + 0x28)`);
2. an odd number of `"` anywhere (the quoted token then swallows lines): report the token length from the stray quote to the next `"`;
3. no rows / no columns (`*(param_1 + 0x28) < 1` -> load fails, 0x71C69C-0x71C6C2);
4. limits stored: rows `this+0x24` and cols `this+0x28` are `int`, arrays sized `(cols*8+4)`, `rows*4`, `rows * (cols*8+4)` with `-1` on 64-bit overflow (new throws bad_alloc): no 16-bit limit in the text path; cell strings are heap `CExoString`.

Binary path (`V2.b`), layout the engine assumes: `"2DA V2.b"`, newline, column names each ended by TAB, one NUL, u32 row count, row labels each ended by TAB, `rows*cols` u16 offsets, u16 data size, data. Flag:
1. any column name of L >= 256 (same overflow, 0x71C4B9/0x71C64B);
2. any column name containing a SPACE or `"` or an empty name (two adjacent TABs): the tokenizer count (`this+0x28`, used for the offset-table size and the cell index stride) then disagrees with the TAB scan (`for (local_24 < cols)` 0x71C72D-0x71C7A8): the row count is then read from the wrong place (0x71C7C8) (desync; magnitude speculative);
3. header size: `hdr = bytes from after the magic newline to the NUL`; column-name offsets are u16 (0x71C757): need `hdr <= 0xFFFF`; row-label offsets are u16 relative to the header start (0x71C846): need `hdr + 1 + 4 + sum(len(label)+1) of all but the last label <= 0xFFFF`, i.e. roughly rows*(avg_label+1) < 64 KB (else labels wrap silently);
4. every row label must be TAB-terminated and the header NUL must exist inside the blob (the scan loops 0x71C75B-0x71C78B and 0x71C84A-0x71C87A have no end-of-buffer test: over-read until a stray NUL/TAB, speculative on consequence);
5. `8 + 1 + hdr + 1 + 4 + labels + 2*rows*cols + 2 + data == file size` (engine checks none of it; `rows*cols*2` is unchecked 32-bit IMUL at 0x71C8C2); cell offsets are u16 so the data blob a writer can address is <= 65535 bytes + the last string (a writer-side limit, not engine-checked);
6. NOT dangerous on the binary path: cell and row-label length (no stack copy).

Vanilla baselines measured offline from `2DA.bif` (all 424 resources binary): max column name 23, max columns 94, max rows 999, max header 921 B, max label-region end 3901 B, max data-size word 19225, no column name contains a space.

### F7. Cross-cutting notes
- The doc's "Row Limit" is "largest id representable by the consumer's integer width", not an engine array size (L10 premise in `15a` section 7.2 holds); K2 code mixes widths per table: u8 (classes count, head byte), u16 (appearance, portraits, soundset), i32 (baseitems, placeable appearance). All C2DA getters return a default and a false bool on out-of-range (R5/0x71B1D0), so exceeding a width does not itself crash; the silent truncations (rows 5 `soundset` and 8 `classes`) are the dangerous ones because the table loads "successfully" with the wrong count.
- Name quality: `0x71C3D0` is named `C2DA::LoadText` in `name_map.tsv` but is the single parser for both formats; `0x729ED0` carries the Ghidra RTTI label `CStatusBar::CStatusBar` (it is `CRes2DA::CRes2DA`: first store `*(undefined ***)this = CRes2DA::vftable;`). Both are worth renaming in the knowledge DB.
