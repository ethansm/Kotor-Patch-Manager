# V4 - Minimap zoom (K1 "K8") and message popup width cap on K2 Steam swkotor2.exe (sha256 6a522e71...)

Summary (5 lines)
1. (i) Minimap = NO BUG for a K8-style zoom mismatch. K2 has no hard-coded 120 px radar basis: the radar (LBL_MAPVIEW) and the map texture (LBL_MAP) sizes are both copied from the loaded GUI rects (ctor `0x747210` -> `[this+0x5d44..0x5d50]`, `[this+0x5d54/0x5d58]`), the map is drawn at `zoom * scaledW x zoom * scaledH` and the player offset uses the same scaledW/H (`DrawMap 0x750790`), so zoom = scaledW / radarW is a pure GUI-file ratio. The user's live `mipc28x6_p.gui` has the vanilla LBL_MAPVIEW (17,5,120,120) and LBL_MAP (17,5,512,256) (read from the file; the ultrawide generator does not touch them).
2. The only vanilla ultrawide defect in this path is that the engine's HUD 4:3 anchoring (`0x40F620`/`0x40FA80`) widens LBL_MAP's scaled width (3071 px instead of 1364 at 3840x1600, 9.6:1 against the radar instead of 4.27:1); the live `K2AspyrMapAspectFix` hook at `0x007508AA` rewrites `[this+0x5d54]` to `height*588/294` before use, giving 4.276:1 at 3840x1600 (vanilla 4.267). Fog (`0x751230`) divides by the same `[+0x5d54]`, so fog and map stay in step. No pan clamp exists (`0x750938-0x7509C9` has no compare/branch): near an area edge the viewport shows whatever lies outside the map rect (vanilla behaviour, SPECULATIVE what colour).
3. (ii) Popup = NO BUG for the width cap. `FixMessageLabel 0x75C080` has the same loop as K1, but its caps are `440.0 * fs` (width) and `280.0 * fs` (height) with `fs = 1 + 0.5*((W-1022)>>10)` from `0x479AB0` (K1 has bare immediates); the start width of `confirm_p` is `290 * W/800`, so the widening branch can only run for W < 1214 (below that: 800x600, 1024x768). At 3840x1600 start width 1392 px vs cap 880 px: the loop only grows height (start 266 px, cap 560 px). 0x69BEA0 is the script-command handler (no layout code) and 0x68ECE0 is PopUpGUIPanel/PopUpDeathGUIPanel (no popup layout); both addresses exist in the Steam decomp.
4. UNCLEAR sub-item: the "icon/datapad" popup variant (`0x75B370` with param_3 != 0, GUI `datapad_p`) is laid out by `FixMessageLabel` from hard-coded constants `fs * {400,300}` (panel) and `fs * {33,27,334,208}` (list) that overwrite the GUI rect; at 3840x1600 that is 800x600 px. The user's `--popup-scale 2.2` edit of `datapad_p.gui` (live: root 880x660) therefore may have little or no effect on the panel size (SPECULATIVE until measured).
5. No hook feasibility needed (no BUG verdict). Log-only measurements are in (c): DrawMap rect dump at `0x7509CC` (10 bytes, no branch) and popup final-rect dump at `0x75C80F`. Adjacent finding: full-map `CSWGuiInGameMap::Draw 0x894CD0` hard-codes a 640x480 centring offset (`SUB EAX,0x280` / `SUB EAX,0x1e0`), gated on `[this+0x48]&1`; not in V4 scope, listed as open question.

ROOT = `~/Games/KOTOR2_Mod_Workspace/ghidra_dumps/steam_6a522e71/`. Constants not in the dump were read from the vanilla exe (`backups/vanilla_clean/swkotor2.exe`, PE section map parsed with python, RVA = VA - 0x400000). #### B1. Where radar and map sizes come from (GUI file, not constants) - CONFIRMED

- The constructor loads the three controls with the scale-enabled loader (`0x40F620`; pushed args `1,0,name,ctrl` for LBL_MAP/LBL_MAPVIEW, i.e. scale flag = 1, register flag = 0) while the HUD anchor mode global is 1:

  ```
  00747eba 6800db9900            PUSH 0x99db00                       ; "LBL_MAP"

  00747eeb e83077ccff            CALL 0x0040f620
  00747eff 68f4da9900            PUSH 0x99daf4                       ; "LBL_MAPVIEW"
  00747f1e 8d959cfeffff          LEA EDX,[EBP-0x164]                 ; ctrl = local_168
  ```

  (decomp `FUN_00733570("LBL_MAP"); ... FUN_0040f620(param_1 + 0x16ad,local_290,0,1);` and `FUN_0040f620(&local_168,local_298,0,1);`.)
- The ctor then copies LBL_MAP's scaled width/height into `[this+0x5d54]` / `[this+0x5d58]` and LBL_MAPVIEW's rect (local at `EBP-0x160`) into `[this+0x5d44..0x5d50]`:

The map rect is then `{left, top, w, h}` = `[this+0x5ab8..]` with only left/top replaced, passed to LBL_MAP's slot 1 (`007509e8 8b5004 MOV EDX,[EAX+0x4]`, `007509eb ffd2 CALL EDX`), then the map is drawn (`00750b2c ffd2 CALL EDX`, slot 0x38), then the fog `00750b38 e8f3060000 CALL 0x00751230` with `&local_28` (left,top), then the arrow (`[this+0x5bfc]` slot 0x38).
- `InitializeMap 0x750C10` (only when the stored area resref is empty: `FUN_00710c20(this+0x5b6c,"")` returns 1 on equal strings, decomp `0x710c20`) sets the map rect to `{0,0, ftol(zoomf*[+0x5d54]), ftol(zoomf*[+0x5d58])}` (asm `00750d11 d945d4 FLD [EBP-0x2c]` = zoomf, `00750d17 FIMUL [ECX+0x5d58]`, `00750d2b FIMUL [EDX+0x5d54]`, `00750d47-00750d50` stores). So map extent and player offset use the same `scaledW/H` and `zoomf`: the map pixel under the player is always at the radar centre, and the visible fraction is `radarW / (zoomf*scaledW)`, a ratio of two GUI-file rects.
- `zoomf = 1.0/(float)MapZoom` (asm `005f6bfe..005f6c08`). Data check (read-only scan with pykotor of every `.rim`/`.mod` ARE in this install's `modules/`, 298 ARE resources with a `Map` struct, `.mod` and `.rim` duplicates both counted): `MapZoom` = 1 in all but one (`tatruins2.mod`: MapZoom 2, MapResX 2); `MapResX` = 0 in 26 of them (map object not initialised: `0x5F6B90` is skipped when param_2==0 and `DrawMap` takes the `*(local_8 + 4) == 0` early exit, decomp `if ((local_8 == 0) || (*(int *)(local_8 + 4) == 0))`). So zoom != 1 essentially never happens.
- Contrast with K1 K8 (lead): K1 draws "in radar pixels" with the fog on a separate 440x256 basis, and KMRP's fix replays a 120 px radar. K2's fog is on the SAME scaledW/H basis as the map (decomp 0x751230: `local_24 = (float)*(int *)(param_1 + 0x5d54) / (float)local_c;` and quads divided by `*(int *)(param_1 + 0x5d4c)`), so the two cannot desynchronise through a radar-only enlargement.
- Residual: fog tile step uses `scaledW/gridW` but does not multiply by `zoomf`, whereas the map and player offset do; harmless while MapZoom = 1 (all but `tatruins2`). SPECULATIVE whether `tatruins2` shows it (MapResX 2 means a 2-column grid).

#### B3. Ultrawide: engine widens LBL_MAP; the live hook corrects it - CONFIRMED (arithmetic mine, +-1 px)

HUD controls are scaled by `(W/800, H/600)` (asm `0040f6e9..0040f707`, `0040f733..0040f751`), then, for mode 1 (`DAT_00a1b9f0 == 1`, set at `00747e24`), each x edge is remapped with `k = (4/3)/(W/H)` (asm `0040f83a d875cc FDIV float [EBP-0x34]`, `0040f83d dc3d88749800 FDIVR double [0x00987488]`) by `0x40FA80/0x40FA30`: left of `W/2` -> `x*k`, right of `W/2` -> `W-(W-x)*k` (centre band `0.4375..0.5625*W` only for `y >= H/2` or mode 4; constants `0x9874A0`=0.4375, `0x987498`=0.5625). #### B4. Pan clamp: none - CONFIRMED (absence in asm), consequence SPECULATIVE

Between `00750938` and `007509c9` (the whole left/top computation) there is no `CMP`/`Jcc`; `left`/`top` are stored as computed (`0075099c 8945dc MOV [EBP-0x24],EAX`, `007509c9 8945e0 MOV [EBP-0x20],EAX`). Near an area edge the map rect stops covering the radar once `left > 0` or `left + zoomf*scaledW < radarW`, i.e. when the player is closer to the border than `(radarW/2)/(zoomf*scaledW/588)` domain units: 60 / (512/588) = 68.9 of 588 = 11.7% of the map width at 800x600 (resolution independent because radar and map scale together). The uncovered part of the radar shows whatever was drawn beneath it (LBL_MAPBORDER interior; SPECULATIVE), as in vanilla. #### B6. FixMessageLabel auto-fit loop and caps - CONFIRMED structure; K1 cap mechanism present but fs-scaled

Loop (decomp 0x75C080):
```
while ((iVar2 = FUN_0041e790(), iVar2 != 0 &&
       (((float)local_10 < local_30 * (float)_DAT_0099e758 ||
        ((float)local_c < local_30 * (float)_DAT_0099e750))))) {
```

Here `local_30` = `fs` from `0x479AB0` (asm `0075c090 e81bdad1ff CALL 0x00479ab0`, `0075c095 d95dd4 FSTP [EBP-0x2c]`), `local_10` = panel WIDTH (`[EBP-0xc]` = saved `[+0x998+8]`), `local_c` = panel HEIGHT (`[EBP-0x8]`), `iVar1` = font line height (0x4178B0). The asm for the four compares (read from exe: `0x99E758` = 440.0, `0x99E750` = 280.0):
```
0075c6fd db45f4  FILD [EBP-0xc]            ; width
0075c700 d945d4  FLD  float [EBP-0x2c]     ; fs
0075c703 dc0d58e79900 FMUL double ptr [0x0099e758]   ; 440.0 * fs
0075c712 db45f8  FILD [EBP-0x8]            ; height
0075c718 dc0d50e79900 FMUL double ptr [0x0099e750]   ; 280.0 * fs
0075c72b 817df8a0000000 CMP dword ptr [EBP-0x8],0xa0 ; height > 160 before widening
0075c749 8b55cc / 83c228  ADD EDX,0x28    ; +40 width per step   (matches KMRP "40 units at a time")
```
The 4 refs to `0x99E758/0x99E750` are the only readers in the whole binary (grep of `decomp/*/*.asm`: 4 hits, all in `0x75C080`), so a data write to those two doubles would affect only this loop.

Differences from K1: K1's caps are immediates (`cmp eax,0x118` / `cmp ecx,0x1B8` per `message-popup.md`) with no resolution factor; K2 multiplies by `fs`. The start width of `confirm_p` is `290 * W/800` (root loaded with plain scale: asm `0040f2e1..0040f31c`; `fs` steps by 0.5 per 1024 px above 1022):

| res | fs | start w (290*W/800) | cap_w (440*fs) | widening branch | start h (100*H/600) | cap_h (280*fs) | cap_h / H |
|---|---|---|---|---|---|---|---|
| 800x600 | 1.0 | 290 | 440 | runs (290->450 in 4 steps once h>160) | 100 | 280 | 47% |
| 1280x720 | 1.0 | 464 | 440 | dead | 120 | 280 | 39% |
| 1920x1080 | 1.0 | 696 | 440 | dead | 180 | 280 | 26% |
| 2560x1440 | 1.5 | 928 | 660 | dead | 240 | 420 | 29% |
| 3440x1440 | 2.0 | 1247 | 880 | dead | 240 | 560 | 39% |
| 3840x1600 (user) | 2.0 | 1392 | 880 | dead | 266 | 560 | 35% |
| 5120x1440 | 3.0 | 1856 | 1320 | dead | 240 | 840 | 58% |

The widening branch can run only when `290*W/800 < 440*fs`, i.e. W < 1213 (fs = 1.0 tier); since `fs` jumps at 2046, 3070, ... the start width always exceeds the cap above that. This is the same "loop never widens at HD" situation KMRP describes for K1, but in K2 it is harmless: the box starts 0.36*W wide (list 278*W/800 wide) so text is not narrowed by a 640x480-era cap, and the loop still grows the HEIGHT up to `280*fs` px. Terminates: each iteration increases width (while `w<capW`, h>160) or height (while `h<capH`); since `capH >= 280 > 0xa0`, a state with `w<capW` and `h<=160` always grows height. Infinite loop only if `iVar1 == 0` (no font, `0x4178B0` returns 0) with `w>=capW`, `h<capH`, text still overflowing: SPECULATIVE and not reachable with the stock `fnt_d16x16` (TutorialBox ctor sets it, `FUN_00710840("fnt_d16x16")` at 0x898CA0).

Text-length trigger: the loop starts when `FUN_0041e790` reports overflow, i.e. the wrapped text is taller than LB_MESSAGE's inner height (list initial height `20*H/600`: 53 px at 3840x1600, one or two lines). It then adds `iVar1` (font height, >= 16) per iteration until the panel reaches `280*fs`: at 3840x1600 the list can reach about `53 + (560-266) = 347` px, roughly 20 lines of 16-17 px (SPECULATIVE font height) of wrap width ~1334 px minus padding; at 1920x1080 the list reaches about `36 + (280-180) = 136` px, about 8 lines of ~667 px. Longer text shows the list scrollbar (`SCROLLBAR` control exists in `confirm_p`); no clipping mechanism from the cap itself. The K1 doc's clipped last character belongs to V3 (glyph advance), not to this cap.

Single-button case (what `DisplayMessageBox` uses via `SetAllowCancel(0)`): ctor sets `[+0x68]` bits 1 and 2 and clears bit 3 (`param_1[0x1a] |= 2; |= 4; &= 0xfffffff7`), `SetAllowCancel(0)` clears bit 1, so the code takes the `else if (bit1==0)` branch (asm `0075c1da..0075c227`): `height -= (cancelH + 2.0*fs)` with `cancelH = [this+0x4e8]` (already scaled). ## (e) Verdict

- **(i) Minimap zoom (K8 analogue): NO BUG.** K2 sizes the radar and the map from GUI rects and draws the map at `zoomf*scaledW x zoomf*scaledH` while offsetting by the same scaled player position (asm `00750941`/`00750947`/`00750992`), so zoom = GUI ratio `512/120 = 4.267`; the user's live HUD file has vanilla 120x120 / 512x256 and the generator leaves them alone; the vanilla ultrawide width distortion of LBL_MAP (9.6:1 at 3840x1600) is removed by the live aspect hook (4.28:1). Pan-clamp absence is vanilla behaviour (design). No hook needed.
- **(ii) Popup width cap: NO BUG.** Caps are `440*fs` x `280*fs` (`0x99E758`/`0x99E750` doubles, only 4 readers, all in `0x75C080`), start width is `290*W/800` so the widening branch is dead for W >= 1214 but nothing is clipped by it (list is already 0.34*W wide; height grows to `280*fs` then a scrollbar). 0x68ECE0 contains no popup layout; 0x69BEA0 only dispatches to `CSWGuiMessageBox` vtbl+0x70 -> 0x75C080.
- **(ii-b) Icon/datapad popup: UNCLEAR.** Hard-coded `fs * {400,300}` panel and `fs * {33,27,334,208}` list; the user's datapad_p file scaling may be overwritten by it (SPECULATIVE; one measurement at hook 2 decides).
- **Adjacent (not asked): full-map 640x480 centring offset at `0x894D1A`/`0x894D34`: UNCLEAR reachability.**
