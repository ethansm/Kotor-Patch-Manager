# U5: TX / KT / TextureController / resman follow-ups + TX standalone patch design (Steam swkotor2.exe 6a522e71)

Static analysis only (decomp/asm/callgraph + runA metrics; vtable dwords read from the vanilla exe .rdata; one external read-only header scan of the installed Modules/ and TexturePacks/ capsules, labelled EXT). Nothing modified. No mapper run (no GOG name was needed; every target below was identified from the Steam decompile).

## 5-line summary
1. TX standalone patch: SAFE WITH GUARD stays (re-verified; runA GETIMG other=0 ctrl=0, BUILD tpc_with_ctrl=0). The ~160 "requeued built TPC textures" are real re-uploads of identical pixels (0x4260E0 re-enters with E4==1: `0042613d CMP dword ptr [EDX + 0x44],0x0 / 00426141 JZ 0x0042619d`), caused by SetFlagDE 0x422E20 (`CALL 0x00474000` with ECX=0xA1BC2C; the env-map texture slot of every mesh node via 0x4DA820 and 0x426D00); after TX that re-entry skips glImage, never re-Demands and never uploads NULL (cave at 0x4261CF given below, keeps TGA and controller textures bit-identical to vanilla; +0xEA need NOT be preserved). The startup 31 are NOT requeues: 0x427DE0 (init 0x93B6EB) pre-constructs every texture via 0x427A70 so E4==1 at flush.
2. NEW (CONFIRMED path + runA numbers): every TPC texture is read from disk TWICE at creation. ParseTXI 0x424B10 -> `FUN_00475ab0` -> provider 0x93BC00 "TXI" branch falls back to the TPC wrapper (`0093be6b CALL 0x0093dab0`, `0093beac CALL 0x0093f870` size, `0093becb CALL 0x0093f830` ptr) = Demand of the whole CResTPC, text copied, released and freed through ReleaseResObject; later LoadImage Demands it again. runA load 1: RT 3007 allocN=547 allocB=429,401,712 but freeN=327 freeB=226,467,200 relZero=327 (resident 202,934,512): ~226 MB of TPC buffers were read and freed within the load; FREECALLER 0x712064 = 815 (EvictOne via ReleaseResObject, not FreeChunk).
3. KT (DestroyTable still-in-demand leaves CRes+0x14 dangling) is REACHABLE on module change: CONFIRMED sequence (server module dtor -> RemoveKeyTable runs before the client scene dies; texture death -> 0x93EA10 -> wrapper dtor 0x9404A0 -> ReleaseResObject 0x713010 -> `MOV dword ptr [ECX + 0x10],0x0` at 0x71306C into the freed 0x24-stride key array) and EXT data shows module-unique TPC exist (lev4.mod 22, gra801/gra802 13/12, tathideout 13, belsavis1 4 ...; vanilla-looking .rim have none). Save-list browsing: REFUTED/unlikely (TGA Demand is released at flush before the next table swap). TX closes the window for TPC (Demand dropped at flush => branch 2, no dangling). Minimal fix: cave at 0x726527 adds `MOV [EAX+0x14],0`.
4. C2 is zero by construction: texture/model loaders never issue async Requests (`0093e8bf PUSH 0x0` flag before the 0x93FE10 ctor; every CResHelper Init site passes literal 0). The only constant-1 requesters found: 0x78D800 (2DA "texpacks" helper, `PUSH 0x1 / PUSH 0x99F770`), 0x835A20 (GUI panel resource via 0x70AF20); variable-flag: module ctor 0x556BE9, 0x55A4D6 (via 0x521360). Flag 0x10 has exactly one writer: Update 0x714300 at 0x71447A (`OR ECX,0x10`). So FS/CR hazards need a failing async/sync Service on those rare resources, not on textures.
5. Fix designs (all behaviour-preserving, bytes below): TX cave 0x4261CF; KT cave 0x726527 (10 B stolen); FS free-before-Malloc cave 0x712F55 (6 B stolen, guarded by flags&0x14==0 and +0x10!=0, reuses 0x7120C0); CR clear `[resman+0x28]/[+0x2c]` when the cancelled request is the current head, cave 0x711BD4 (7 B stolen). Hooks: Update 0x71447A, Request 0x713310, DestroyTable branch 3 0x72650B, ReleaseResObject detector 0x71306C (`[CRes+0xC]&0x200`), TXI-via-TPC 0x93BEA6.

Correction to T1: ReloadTXIByName 0x461230 is in the Gob vtable 0x98B5CC at slot 0x44, not "scene vtable 0x98B5AC slot 0x64". Evidence: `00458bd6 c702ccb59800 MOV dword ptr [EDX],0x98b5cc` (Gob ctor 0x458B70), `0045a1bb c700ccb59800 MOV dword ptr [EAX],0x98b5cc` (Gob dtor 0x45A190); dword at 0x98B610 = 0x461230 and 0x98B610-0x98B5CC = 0x44 (the earlier 0x98B5AC base is 0x20 bytes before the real start; 0x98B5C8 holds the RTTI pointer 0x9BAB48). The derived vtable 0x98C27C (stored at `+4` by 0x47ED27/0x47F0D2) has it at 0x98C2C0 = 0x98C27C+0x44 too.

## (b) Findings (ranked by expected impact within each axis)

### Q1. TX standalone patch: re-verification of SAFE WITH GUARD, and what the "BUILD requeue" does

**V1. Post-upload readers of the TPC pixels (CONFIRMED: none besides [tex+0x34] controllers).**
* runA (all 3 loads, ~10k builds): `GETIMG calls=551 tpc=385 tpc_retained=385 upload=551 ctrl=0 other=0` and `BUILD ... tpc_with_ctrl=0` (final snapshots). Static classification in T1 + this batch agree: every GetImage call is inside the four upload routines.
* TPC-embedded TXI is NOT read from `tex+0x44`. CResTPC keeps the TXI text inside its own buffer (`0x945F20: *(int *)(param_1 + 0x38) = (*(int *)(param_1 + 0x18) + -0x80) - *(int *)(param_1 + 0x30);`), the texture class only receives its SIZE (`0x945DB0: *param_7 = *(undefined4 *)(param_1 + 0x38);` -> `tex+0x64` via 0x4252C0 arg `param_1 + 0x19`), and uses it only to locate the tag behind the pixels (`FreeImage -> 0x421C40(... +0x60, +0x64 ...)`). The TXI TEXT is obtained separately, through the resource provider (F2 below), i.e. through a fresh Demand of the CRes, not through `tex+0x44`. So TX cannot break TXI parsing.
* 0x482980 (T1 open Q4) = in-place gamma LUT (`pow(x/255, 1/gamma)`), called at ConstructImage entry (0x426270) with `+0x44`: at that moment `+0x44 == 0` for a fresh or Reset texture (FreeImage cleared it), so it is a no-op on a first build and cannot touch a retained TPC buffer. Robustness note (SPECULATIVE, vanilla, independent of TX): after Reset, `+0x68/+0x6C/+0x74` are not cleared (FreeImage keeps them, T1 F5) while `+0x44` is 0; if a TXI sets `gamma != 1` (`+0x24`), 0x482980 loops `w*h*bpp` times writing to `NULL + i` (`*(undefined1 *)(param_4 + local_8) = local_24;`). Needs a gamma-TXI texture to be present when options are applied; not seen in runA.
* Controller guard: unchanged from T1; textures with a controller and uncompressed data are the only ones where Life Init (0x492310) / GetImage-based copies would see NULL. runA says 0 such TPC textures; the guard costs nothing.

**V2. Why ~160 built TPC textures are re-queued, and exactly what the rebuild does (CONFIRMED mechanism; per-cause shares SPECULATIVE until the 0x474000 hook below).**
Pending list = 0xA1BC2C/0xA1BC30; flush 0x427810 pops entries and calls 0x4260E0 per entry. A texture enters it from: (i) creation (0x427520 `FUN_004491c0(local_54)`, E4==0 => first build), (ii) 0x474000 UniquePush with `MOV ECX,0xa1bc2c` from SetFlagDE 0x422E20 (`00422e72`), ReloadTXI 0x427740 (`00427785`), ReloadProceduralParams 0x4277A0 (`004277ef`), downsample 0x426960 (`004269de`), dynamic 0x426C60 (`00426cf2`), (iii) 0x427DE0/0x427D90 which copy EVERY live texture into the pending list (`00427e17 CALL 0x00428fc0`, 0x428FC0 = copy of 0xA1BC60) and Reset them.
* Per-load source (+53 in load 1, +57 in load 2 = the runA delta, 368 builds each): SetFlagDE. Its callers: 0x4DA820 (mesh-node texture-slot setup: `uVar1 = FUN_004274e0(*(undefined4 *)(param_1 + 0x24),0); ... *(undefined4 *)(iVar2 + 0x14) = 1; ... FUN_00422e20(1);`), 0x426D00 (`FUN_00422e20(local_5);`, called from the node texture-replace helpers 0x4DB0A0/0x4DAFC0), and the four Gob slots 0x460C20/0x460910/0x460E50/0x461300 (`if (*(int *)(param_1 + 0x1d4) != 0) { FUN_00422e20(1); }`). SetFlagDE writes `+0xDE` (= TXI key "isenvironmentmapped": strings.tsv `00988190 isenvironmentmapped`, asm `004247b5 ADD EAX,0xde`) and requeues if the flag is non-zero WITHOUT checking E4: `00422e5e MOVZX ECX,byte ptr [EAX + 0xde] / 00422e65 TEST ECX,ECX / 00422e67 JZ 0x00422e77 / ... CALL 0x00474000`. A built texture is not in the list (flush popped it), so UniquePush appends it again (`if (iVar1 == 0) FUN_004491c0(param_1)`). Which of these is the dominant caller is unproven (SPECULATIVE: the 0x4DA820 env-map slot looks the most likely because it sets the flag on every mesh node whose 3rd texture is not "NULL"); hook H-T3 measures it.
* Startup +31 (before any game load; also first METRICS of both launches): NOT requeues. `0x93B650 ... 0093b6eb CALL 0x00427de0` runs at init (and 0x78DB17 on options apply): 427DE0 copies all live textures into pending, Resets them (E4=0) and runs 0x427B60 -> 0x427A70 which calls ConstructImage for all (`if (*(char *)(iVar1 + 0xe4) == '\0') { FUN_00426270(); }`, which sets `+0xE4=1`), THEN flushes: 0x4260E0 sees E4==1 and `+0x44 != 0` for a first build, which perf-lab counts as "requeue" (`E4==1 && [tex+0x44]!=0`, PerfLab.cpp PerfLabBuildTex). So the counter over-counts by every build that follows 0x427DE0 (init, options apply, shutdown). SPECULATIVE only in the exact attribution of the 31.
* What the re-entry does today (TPC, retained): 0x4260E0 path with E4==1: `00426132 MOV ECX,[EBP-4] / 00426135 CALL 0x004258b0` (empty), `0042613d CMP dword ptr [EDX + 0x44],0x0 / JZ` not taken -> `00426148 CALL 0x004265e0` = glImage(0): `glFinish` then, since `[+0x58]!=0 && [+0x40]!=0`, NO glGenTextures (names reused, `if ((param_1[0x16] == 0) || (param_1[0x10] == 0))` false) and re-uploads every mip with glTexImage2D from the same pixels (0x434350). Pure redundant work: ~0.22 ms glFinish (runA `glfinish_ms=103.7` over 468 glImage) plus the upload itself (unmeasured); ~53 of 468 glImage calls (11%) in load 1.
* What it does after TX (`+0x44 == 0`, E4 stays 1): `0042613d CMP dword ptr [EDX + 0x44],0x0 / 00426141 JZ 0x0042619d` jumps over BOTH glImage and the avg-colour block (`0042618b MOV ECX,[EAX+0x44]`). No Demand (ConstructImage is skipped because E4==1 and 0x4258B0 is empty), no GL call, never a NULL handed to GL (glImage's own guard `if (param_1[0x11] == 0) { param_1[0x16] = 0;` is not reached). Then `0042619d CMP dword ptr [EAX + 0x5c],0x0` -> controller Init only for uncompressed+controller (guarded, 0 in runA) -> `004261cd CALL EAX (vt+0x30)` -> `FreeImage` (no-op: `CMP dword ptr [EAX + 0x44],0x0 / JZ` at 0x42516C). The previous GL object is untouched. Observable difference: none for pixels; any TXI state that glImage would have re-applied through `FUN_00421cf0(name,[0xDF],flag)` is not re-applied, but SetFlagDE only changes `+0xDE`, which glImage/Upload* never read (`grep 0xde`: only 0x422210, 0x426270 (ConstructImage colour fix-up, E4==0 only), 0x423ab0).
* Verdict: TX behaviour delta = "redundant re-uploads skipped". CONFIRMED.

**V3. +0xEA (C4) CONFIRMED not needed.** After TX, FreeImage writes `+0xEA=0` for TPC too (asm 0x42525A `MOV byte ptr [EAX + 0xea],0`). `+0xEA` is read only by ParseTXI 0x424B10 and 0x45BF50 (`GetFlagEA`). ParseTXI runs (a) once per new texture at 0x427520 (before any build; `+0xEA` still 0), (b) from ReloadTXI 0x427740 (only reachable through the unresolved Gob slot 0x44), (c) 0x45BF50 (Gob slot 0x150, no resolved caller). In the "file branch" (`+0xEA==0`) the text is re-read via the provider (F2) and copied into `+0x48` (SetTXIText) exactly as at creation; the memory branch only reads that copy (`(**(code **)(*param_1 + 0x98))()` / `0x94`). All three SetTXIText callers (0x424B10, 0x45BF50, 0x4DA3F0) fill it from `FUN_00475ab0` text, so memory text == file text. Same result, at the price of a TPC re-Demand per re-parse (F2). Callers of slots 0x44 (68 `CALL [reg+0x44]` sites enumerated: GUI/scene SetFog 0x7A8300/0x7A86D0 with float args, none passes (name, text)) and 0x150 were not found: the two Gob methods appear unreferenced in this exe (SPECULATIVE: tool-only / dead). C4 hook below.

### Axis 3: crash / robustness paths

* **R1 (highest) KT UAF write (L1).** Data-triggered by module change from a module whose capsule contains textures used by the old area (list above).

## Fix designs (behaviour-preserving, hook sites with exact bytes)

**TX (standalone, no perf-lab dependency).** Site 0x4261CF..0x4261D5, 7 bytes `0F B6 C8 85 C9 75 10` = `MOVZX ECX,AL / TEST ECX,ECX / JNZ 0x004261e6` (three whole instructions; the only branch inside is the JNZ; nothing jumps into 0x4261D0..0x4261D5: targets in the function are 0x42611A, 0x426132, 0x42613A, 0x42619D, 0x4261C2, 0x4261E6). On entry AL = vtable+0x30 result (TPC flag). New bytes: `E9 <rel32 to cave> 90 90`. Cave:
```
movzx ecx, al
test  ecx, ecx
jz    0x004261D6          ; non-TPC: free (identical to vanilla)
mov   eax, [ebp-4]        ; this
cmp   dword ptr [eax+0x34], 0
jne   0x004261E6          ; TPC with procedural controller: keep buffer (identical to vanilla)
jmp   0x004261D6          ; TPC without controller: FreeImage
```
Why equivalent: TGA path and controller textures unchanged; TPC without controller only loses the retained pointer (no reader, V1; re-entry skipped, V2; Reset/dtor FreeImage idempotent by the `+0x44` guard, T1 F5). `+0xEA` need not be restored (V3). Do NOT also patch 0x4261D4 alone with `90 90` unless the controller guard is dropped deliberately (runA: 0 controller TPC).

**KT (DestroyTable branch 3).** Site 0x726527, 10 bytes `89 50 0C C7 45 FC FF FF FF FF` = `MOV [EAX+0xC],EDX / MOV dword ptr [EBP-4],-1` (the second is the SEH state store; no branch target at 0x72652A; the join target is 0x726531). EAX = CRes there (loaded `00726523 MOV EAX,[ECX+EAX*1+0x10]`). New bytes `E9 <rel32> 90 90 90 90 90`. Cave: `mov [eax+0xC],edx ; mov dword ptr [eax+0x14],0 ; mov dword ptr [ebp-4],-1 ; jmp 0x00726531`. Behaviour: identical except `CRes+0x14 = 0` (same value branch 2 already writes at 0x726571); `CRes+8` deliberately kept (data still owned; FreeResourceData uses it). Reader side already tolerant: 0x713010 guards `[+0x14] != 0`, 0x714630 guards `+0x14 == 0`; 0x711270 is unguarded (R4) but only used by non-texture helpers.

**FS (free the old buffer before re-Malloc).** Site 0x712F55, 6 bytes `8B 45 F0 8B 4D 08` = `MOV EAX,[EBP-0x10] / MOV ECX,[EBP+8]`; 0x712F55 is the join point of the budget loop (JLE at 0x712F45, JZ at 0x712F51), nothing jumps to 0x712F58. New bytes `E9 <rel32> 90`. Cave:
```
mov  ecx, [ebp+8]               ; CRes
cmp  dword ptr [ecx+0x10], 0
je   L_ok
test byte ptr [ecx+0xC], 0x14   ; flags 4|0x10: data valid or in flight -> never touch
jnz  L_ok
push ecx
mov  ecx, [ebp-0x10]            ; resman
call 0x007120C0                 ; frees [CRes+0x10] (size-6 variant handled), budget += [CRes+0x18], zeroes +0x10/+0x18
L_ok:
mov  eax, [ebp-0x10]
mov  ecx, [ebp+8]
jmp  0x00712F5B
```
Caveat: `CRes+0x18` must still hold the OLD size at the call; it is overwritten by the caller before Malloc (`param_2[6] = local_8` in 0x713BF0), but for a re-Demand of the same resource the size is identical (SPECULATIVE if a resource's size can change between attempts); if counter H-F1 shows 0 hits, skip this patch.

**CR (clear resman+0x28 on cancel).** Site 0x711BD4, 7 bytes `8B 45 F4 50 8B 4D E8` = `MOV EAX,[EBP-0xC] / PUSH EAX / MOV ECX,[EBP-0x18]` (start of the queue-node removal `if (*(short *)(param_2 + 6) == 0) FUN_0064dde0(local_10);`; no branch targets inside; the next instruction 0x711BDB `ADD ECX,0x24`). New bytes `E9 <rel32> 90 90`. Cave: the three original instructions, then `mov eax,[ebp+8] ; cmp [ecx+0x28],eax ; jne L ; mov dword ptr [ecx+0x28],0 ; mov dword ptr [ecx+0x2c],0 ; L: jmp 0x00711BDB`. Behaviour: only when the cancelled CRes is the Update head and flag 0x10 is clear (the in-flight case already clears at 0x711B8E/0x711B98); Update refetches a head next pass (`if (*(int *)(param_1 + 0x28) == 0) { uVar2 = FUN_00521060(); ...`).
