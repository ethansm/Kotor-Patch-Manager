## Findings that contradict or correct earlier reports (read first)

2. W6 TD counter: W6 table row says count `len >= 255`; a 255-char token fits exactly (idx 0..254 + NUL at 255). Overflow starts at len >= 256 (NUL at idx 256 = first cookie byte). Counter condition is `len > 255`.
3. W6 S2 says the skipped SS-b block is "matrix prep + re-render"; `FUN_00408740(3)` is `glClear(0x4000 | 0x500)` (colour + depth + stencil; `0x408740.c`: `glClear(-(uint)((param_1 & 2) != 0) & 0x500 | -(uint)((param_1 & 1) != 0) & 0x4000 | ...)`), then `glLoadIdentity`, then the camera `Render`. ## 1. FS - failed-Service buffer leak (CExoResMan::Malloc 0x712F30)

### Evidence
Malloc body, whole join region (exe bytes agree):
```
00712f39  8b4508   MOV EAX,[EBP+8]            ; CRes
00712f3f  8b5018   MOV EDX,[EAX+0x18]         ; size (read BEFORE the site)
00712f42  3b5108   CMP EDX,[ECX+8]            ; budget
00712f45  7e0e     JLE 0x00712f55             ; -> site
00712f51  7402     JZ  0x00712f55             ; -> site
00712f55  8b45f0   MOV EAX,[EBP-0x10]         ; <- site start: 8B 45 F0
00712f58  8b4d08   MOV ECX,[EBP+8]            ;                8B 4D 08
00712f5b  8b5008   MOV EDX,[EAX+8]            ; resume (instruction boundary)
00712f5e  2b5118   SUB EDX,[ECX+0x18]         ; budget -= size   (reads +0x18)
00712f73  8b4218   MOV EAX,[EDX+0x18]  ... 00712f76 ADD EAX,6 / 00712fab ADD EDX,0xa / 00712fcb MOV EAX,[EDX+0x18] ; malloc(size[+6/+10])
00712f8b/00712fc3/00712fe0  MOV [ECX/EAX+0x10], <new>   ; unconditional store of the new buffer
```
FreeResourceData 0x7120C0 (ret 4, ECX = resman, `[EBP+8]` = CRes), full body quoted: `007120c9 CMP [EBP+8],0 / 007120d4 CMP [EAX+0x10],0 / 007120e2 AND EDX,0xc0000000 / 007120eb CMP EDX,1 / 007120ee JZ 0x0071213a` (source type 1 = no free, no refund) `/ 007120f3 CMP [EAX+0x20],0 -> free(ptr-6) else free(ptr) (0x9196FD) / 00712131 ADD EDX,[EAX+0x18] / 00712137 MOV [ECX+8],EDX` (budget refund by +0x18) `/ 0071213d MOV dword ptr [EDX+0x18],0x0 / 00712147 MOV dword ptr [EAX+0x10],0x0`. Callers (dump header): 0x711FE0 (FreeChunk worker), 0x722A30 (CResWave service), 0x712160.

Canonical engine free sequence (0x711FE0): `00712030 MOV EAX,[EDX]` / `00712035 MOV EDX,[EAX+0xC]` / `00712038 CALL EDX` (vtbl+0xC = OnResourceFreed) then `0071205f CALL 0x007120c0`, then flags 4, 0x10, 0x100 cleared. Slot-3 targets of every CRes vtable I could resolve from the ctors (read from the exe .rdata): default 0x946250/0x942160, CResGFF 0x7175B0 (clears 9 cached pointers), CResWave 0x7229C0 (AIL-frees `+0x10` only if `+0x28 != 0`), CRes2DA 0x729F80, CResTPC 0x945EC0 (zeroes +0x28..+0x44), TGA 0x945410 (frees `+0x44` only if `+0x28 != 0`), 0x941BA0, 0x943FC0, 0x8F84B0: all `__fastcall`, `ret 0`, return 1, no stack args (dump headers). Slot 4 (+0x10, OnResourceServiced): 0x717300 (GFF), 0x729FD0 (2DA), 0x722A30 (Wave), 0x945F20 (TPC), 0x9454B0 (TGA), 0x8F84D0, 0x941A20/0x941C20, 0x9421A0, 0x9443C0, default 0x946280 (returns 0 only when `+0x10 == 0`).

Leak mechanism: Demand 0x711C20 re-enters Service when `((flags & 4) == 0) || (+0x10 == 0)` and `(flags & 0x10) == 0` (`.c` quoted in W7, same). A Service that fails after Malloc leaves `+0x10 != 0`, flag 4 clear, flag 0x10 clear. Release/FreeIfUnreferenced 0x711E60 needs flag 4|0x10 and 0x711FE0 frees only through the evict list, so nothing reclaims it, and the next Service's Malloc overwrites `+0x10`. Async completion cannot create this state: `0x715A60` always sets flag 4 and clears 0x10 before calling vtbl+0x10 (`.c`: `& 0xffffffef` then `& 0xfffffffb | 4`), and Update 0x714300 marks 0x10 only after a successful async Service. So the stale state is sync-Demand only.

### Trigger / rarity
Two causes (both VERIFIED paths, neither observed):
1. short read: `00713df3 CMP EAX,[EBP-4] / 00713df6 JZ 0x00713e13` (ERF/RIM/MOD/SAV, type 2) and `00714216 CMP EAX,[EBP-8] / 00714219 JZ 0x00714243` (BIF, type 0) not taken -> close, `XOR EAX,EAX`, return 0 (`00713e0f / 00714231..0071423e`): truncated or mis-sized archive.
2. OnResourceServiced == 0 with the buffer kept and flag 4 cleared (`00713e46 NEG EAX / 00713e48 SBB EAX,EAX / 00713e4a AND EAX,4 / 00713e52 MOV [ECX+0xC],EDX`): GFF with a tag/version mismatch (0x717300 composes the expected 4-char tag from `[this+0x8D..0x90]`, compares it with the first dword of the buffer and the version with `[0xA100C8]`; mismatch returns at `00717466 XOR EAX,EAX` / `007174b8 XOR EAX,EAX`), a 2DA whose magic is not `2DA V2.0`/`V2.b` (`00729fd0`: `(**(code **)(*param_1 + 0xc))(); return 0;`), a Wave whose ASI/ADPCM decode returns 0 (`00722abf XOR EAX,EAX`). That is a mod-supplied wrong-type/wrong-version resource, not only a corrupt archive.
Retry is needed for the cave to matter: a re-Demand of the same CRes (each load of that area/object). Never observed in the logged sessions (no counter existed; runA `redemand_60s` 511 are WAV/other re-demands of loaded data). Expected size per event = the resource size (a 2DA tens of KB, a GFF KB, a TPC MBs). With no retry the leak is a one-off (the cave does not reclaim it); with N retries unpatched = N x size, patched = 1 x size at most. Rarity: zero for vanilla + the live mod set as far as any evidence shows; only a broken mod file triggers it.

### Corrected design (save/restore +0x18, faithful free order)
Site 0x712F55, stolen `8B 45 F0 8B 4D 08` (2 whole insns; 0x712F5B is a boundary). Interior scan 0x712F56-0x712F5A: empty. Start-hits: 0x712F45 JLE, 0x712F51 JZ only. No jump table. Live-in at the site: none (EAX/ECX/EDX all reloaded first; flags rewritten by the SUB at 0x712F5E). Live-out at 0x712F5B: EAX = resman, ECX = CRes (the replay), as in the original.
Hook write: `E9 <C-0x712F5A> 90`.
Cave (C = cave address; assembled and re-disassembled):
```
C+00 8B 4D 08              mov ecx,[ebp+8]              ; CRes
C+03 83 79 10 00           cmp dword [ecx+0x10],0
C+07 74 30                 je  C+39                      ; nothing attached
C+09 F6 41 0C 14           test byte [ecx+0xC],0x14      ; 4 = loaded, 0x10 = async in flight
C+0D 75 2A                 jnz C+39
C+0F 8B 51 18              mov edx,[ecx+0x18]            ; NEW size (what Malloc is about to use)
C+12 F0 FF 05 <fs_stale>   lock inc dword [fs_stale]
C+19 F0 01 15 <fs_bytes>   lock add dword [fs_bytes],edx
C+20 52                    push edx                      ; save size across the free
C+21 8B 01                 mov eax,[ecx]
C+23 FF 50 0C              call dword [eax+0xC]          ; vtbl+0xC OnResourceFreed, same as FreeChunk 0x712038
C+26 8B 4D 08              mov ecx,[ebp+8]
C+29 51                    push ecx                      ; arg
C+2A 8B 4D F0              mov ecx,[ebp-0x10]            ; this = resman
C+2D E8 <0x7120C0-(C+0x32)> call 0x007120C0              ; ret 4 pops the arg
C+32 8B 4D 08              mov ecx,[ebp+8]
C+35 58                    pop eax                       ; saved size
C+36 89 41 18              mov [ecx+0x18],eax            ; RESTORE +0x18 (the W7 bug)
C+39 8B 45 F0              mov eax,[ebp-0x10]            ; replay 1
C+3C 8B 4D 08              mov ecx,[ebp+8]               ; replay 2
C+3F E9 <0x712F5B-(C+0x44)> jmp 0x00712F5B
```
Stack: one `push edx`, one `push ecx`, callee `ret 4` removes the arg, `pop eax` removes the saved size: balanced. Callee-saved EBX/ESI/EDI untouched by every callee used. Budget: 0x7120C0 refunds `+0x18` (new size) then Malloc charges it again at 0x712F5E: net one charge per Service (fixes W7's F2 double charge, difference only if the size changed between attempts; budget is advisory). A vtbl+0xC that frees `+0x10` itself (Wave/TGA with `+0x28 != 0`) leaves `+0x10 == 0`, and 0x7120C0 then exits at `007120d4 CMP [EAX+0x10],0 / 007120d8 JNZ 0x007120dc` (not taken) -> `007120da JMP 0x0071214e` without a second free. Source-type-1 CRes: 0x7120C0 zeroes without freeing (cannot double-free a mapped pointer). Perf-lab interaction: it hooks 0x7120C0's entry (`55 8B EC 83 EC 0C`), the cave's call goes through that detour and is classified as "not FreeChunk" by return address; metric noise only.
Residual risks (INFERRED): (a) a class whose failed Service leaves a non-malloc `+0x10` with flag 4 clear (none found: Wave replaces `+0x10` only on success; GFF/2DA/TPC keep the raw malloc block); (b) mapped (type 1) CRes whose type bits changed to a heap type between attempts (needs flag 4 clear, but the mapped Service always sets flag 4): not reachable by any path found.
Counter `fs_stale` fires exactly once per Malloc entry on a CRes with `+0x10 != 0 && !(flags & 0x14)`; `fs_stale_bytes` accumulates the resource size. Harness: fake resman (`+8` budget) and CRes (`+8` type bits, `+0xC` flags, `+0x10` malloc block, `+0x18` size, `+0x20` 0) with a counting allocator, vtable slot 3 stub: expect old block freed once, `+0x18` equal to the pre-cave size afterwards, `+0x10` replaced, budget = start - size; variants flags 4 and 0x10 (must not free), `+0x20 != 0` (free(ptr-6)).
Verdict: FIX, optional. Value is small (never observed), risk is small, the counter will settle whether it ever fires. Alternatives rejected: freeing at the 5+ failure tails (0x713DF8, 0x713E37, 0x714243 region, 0x7133A0 tail, 0x714B30) needs 5+ caves.

### Would Sleep(1) slow playback?
No. Playback is on the movie thread; the main loop only polls the status. A Sleep delays the main thread's reaction to "status != 1" by at most one sleep. Exit and ESC are not main-loop dependent (ESC: MovieWndProc 0x40C4A0 -> `FUN_0040cc30(0,0)` on the movie thread, T4).
BUT a Sleep(1) on every iteration, as asked at 0x798A87, has a real cost: the pump runs once per 501 iterations, so the pump cadence would become 501 x (Sleep granularity). Wine/Proton ~1 ms -> ~0.5 s between pumps; a native 15.6 ms timer (the exe imports no `timeBeginPeriod`, grep of imports.tsv VERIFIED) -> ~7.8 s. That would delay every window message for the duration of a movie (activation, close, alt-tab) and could approach the Windows "not responding" threshold. So 0x798A87 per-iteration is rejected, independently of the fact that perf-lab owns that address.

### Proposed site: the pump branch, 0x798A47
Sleep once per pump (once per 501 spins): CPU duty falls to roughly 5-10% (spin of ~0.1 ms, then Sleep), pump cadence stays about one per Sleep (~1 ms on Wine), exit latency <= one Sleep.
Stolen 0x798A47..0x798A4F = `8B 45 84 | 8B 88 54 02 00 00` (2 whole insns, 9 B; no relative branch; resume 0x798A50 is a boundary; interior scan 0x798A48-0x798A4F empty; no start-hits). Live-in: nothing (the preceding CALL clobbered EAX/ECX/EDX; the replay reloads EAX and ECX). Flags dead (`0x798A53 CMP` follows its own MOV). Sleep is stdcall, clobbers EAX/ECX/EDX only. IAT slot `Sleep` = 0x009860D4 (`imports.tsv`: `CALL dword ptr [0x009860d4]` in 0x711C20 / 0x798CD0 / 0x40D6F0; same encoding the 0x711D27 hook uses).
Hook `E9 <C-0x798A4C> 90 90 90 90`. Cave (assembled and re-disassembled):
```

C+07 6A 01                 push 1
C+09 FF 15 D4 60 98 00     call dword [0x009860D4]           ; Sleep(1)
C+0F 8B 45 84              mov eax,[ebp-0x7C]                ; replay
```

### Interaction risk with the load hang (H1; doc 09/10, T4 finding 5)  [INFERRED, flag for the gate]
- The hang chain is timing-sensitive around PlayMovies' exit: the movie thread clears `[movie+0x30]` at 0x40D623 BEFORE it reaches `0x40D637` (`a1b76c := 1` when `[movie+0x1c] == 1`, else 0 at 0x40D6BA) and posts the synthetic `WM_ACTIVATEAPP(0,0)` (`0040d69e CALL [PostMessageA]`); main, on leaving the spin, runs `0x781DF5 CALL 0x40BF40` (reads `a1b76c`) and tests `[0xA1B4E0]` at 0x781E0B (T4). T4's race: main may read a STALE `a1b76c`. A Sleep in the spin makes main leave the loop up to one tick later (>= ~1 ms vs a few hundred ns for the thread to run three more instructions), which turns that race into "thread first" deterministically. In the case where the movie window saw a deactivate (`[movie+0x1c] == 1`: focus loss / Wine startup glitch), thread-first = `a1b76c == 1` correct = main does NOT force `[0xA1B4E0] = 1`, and the posted WM_ACTIVATEAPP(0) leaves it 0 = the H1 end state ("load screen never dismissed"). The stale-read race could today be hiding or causing that. So F1 can change H1's odds in either direction; it must not ship in the same soak as the H1 probe/fix, and a 10+ launch soak with `hangprobe` logging (PlayMovies exit point 0x798B39, `a1b76c`, `[0xA1B4E0]`) is the acceptance test.
- Multi-clip queues: `IsMoviePlaying` has no queue-empty check and the movie thread sets `+0x30 = 0` between clips for a window of >= `Sleep(5)` + CreateWindow time (T4); the spin currently catches that gap at ~200 ns resolution and may leave early. With Sleep(1) per pump the gap is still sampled (5 ms window vs ~1 ms cadence on Wine), but on a 15.6 ms timer it can be missed (behaviour change: PlayMovies would then NOT leave between clips). Wine/Proton is the target here, so low risk, but it is a behaviour difference.
- PlayMovies exit block 0x798B39 compares `[0xA1B4E0]` with the entry snapshot `[EBP-0x18]` and restores the input flag only if equal; a longer loop (Sleep) widens the window in which a deactivate/activate can change `[0xA1B4E0]` while main is in the loop (the pump dispatches WM_ACTIVATEAPP): same direction of effect as above, still INFERRED.
Verdict: FIX conditional. Key `movspin`, default OFF, enable only after the H1 acceptance soak; value = idle CPU/heat during movies only (no load-time or frame-time effect, doc 10 already rates it "CPU only").
