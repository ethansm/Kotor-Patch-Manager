## V1. Dialogue letterbox sizing (lead L1; K1 bug "K7")
K1 mechanism: each bar = `(H - W / (7/3)) / 2` with 7/3 a float constant read by 6 sites (SetTop/SetBottom of the letterbox panel, the NPC-line label height in the top panel ctor + SetReply, the reply panel top in the cinematic panel ctor + Reset). Past 21:9 (W/H > 2.333) the bar goes NEGATIVE. The reply panel is a hard-coded 100 px tall. KMRP fix: bar = H/6.
Start at `FUN_004113a0` (`decomp/41/004113a0.{c,asm}`: letterbox draw, glScissor + glClear per `shield_bar_src/blackout_investigation.md`) and its callers via `callgraph.tsv`, but the sizing is probably in the `CSWGuiDialog*` panels (grep `name_map.tsv`/`steam_functions.tsv` for `Dialog`, `Letterbox`, `Cinematic`; grep `strings.tsv` for `LB_REPLIES`, `LBL_MESSAGE`, `letterbox`). Find (1) where bar height/width derive from screen w/h and whether a 7/3 / 2.333 / 0.428 / 0.75 constant exists, (2) the reply-panel height and `LB_REPLIES`, (3) the NPC-line label height. Evaluate numerically for 800x600, 1920x1080, 3440x1440, 3840x1600 (2.4:1, the user's), 5120x1440: flag any negative/zero/oversized result and any 640x480 assumption. Also read what `Patches/SemiTransparentLetterbox` in `~/Games/KOTOR2_Mod_Workspace/tools/kotor-patch-manager/Patches/` hooks so we know it is orthogonal. NOTE: the user's install also has custom ultrawide GUI overrides (menus laid out by `scripts/generate_ultrawide_gui_overrides.py`); check whether the dialogue GUI panels (`dialog*.gui`) are laid out by the engine code or by the GUI files, since that decides whether the code path is even reached.

## V2. CSWGuiListBox row-height inflation on repopulate (lead L2; K1 bug "K2")
K1 mechanism: `OrganizeControls` spreads leftover list height over the visible rows by making each row taller, writes the enlarged height into the reused row controls and into a local; the next pass takes the max row height as the list's item height field (`+0x368` in K1) and inflates again. Fix there = NOP two stores of the inflated height.
Read Steam K2 `CSWGuiListBox::ClearItems 0x41D290`, `AddControls 0x41FC30` / `0x41FD90`, `OrganizeControls 0x41EA50`, `OrganizeUnequal 0x41F170`, `OrganizeOversized 0x41F7F0`, `SetExtent 0x41D710`, `Load 0x41FFD0`, `LoadProtoItem 0x420180`. Question: does any row / proto-item height field get written with an enlarged value that is later READ BACK as the base for the next layout pass (so repeated repopulation compounds)? Identify the K2 field offsets, the stores, the reads, and say if the cycle closes. Then trace Mod 6's path (`11_inventory_sort_filter.md`: `PopulateItemListBox 0x8A7BA0`, hooks `0x8A7E22` / `0x8A7E76`, source `inventory_sort_filter_src/`) and say whether sort/filter re-population goes through the same fields (ClearItems -> AddControls ... ), i.e. whether Mod 6 users would already see the growth. ## V3. Text layout: line-breaker hang, glyph advance, scrollbar widths (leads L3, L4; K1 bugs "K1", "K5", "K6")
