# T1: can anything read a TPC texture's pixel buffer (tex+0x44) after BuildAndStoreTexture 0x4260E0 returned?

Static analysis only (dump text + read of the vanilla exe .rdata for vtable slot values; nothing modified).
Conventions: `tex` = CAurTextureBasic (vtable 0x988094), `proxy` = CAurTexture (vtable 0x987fcc). Class ids were read from the exe: both vtables are identical except slot 0x0 (dtor 0x421ED0 vs 0x4233C0), slot 0x4 (proxy 0x4558A0 vs basic 0x458940), slot 0xB4 (proxy 0x422DD0 vs basic 0x425160) and slot 0xBC (proxy 0x4274A0 vs basic 0x4233A0).

## 5-line summary
1. GetImage (vtable slot 0x3C = 0x422640) has NO reader outside (i) the four upload routines 0x433CD0/0x432FA0/0x433320/0x434350 (callers = 0x4265E0 only, run before the free) and (ii) the procedural "TextureController" family at 0x48FF30/0x490710/0x491C40/0x492310/0x492460/0x4907F0, whose object is `[tex+0x34]` and whose `[ctrl+4]` is the owning CAurTextureBasic. All ~50 other `+0x3C` indirect calls in the exe were classified as non-texture classes (evidence in b/F1).
2. Every direct `[reg+0x44]` access to the texture field is inside 0x42xxxx (LoadImage 0x4252C0, ConstructImage 0x426270, 0x4260E0, glImage 0x4265E0, FreeImage 0x425160, 0x422640, 0x422D50, 0x425800, 0x4261F0, ctor 0x423000) and all are guarded by `+0x44 == 0` (FreeImage `CMP [EAX+0x44],0 / JZ`, glImage `CMP [ECX+0x44],0`, 0x4260E0 `CMP [EDX+0x44],0`) or run before the free.
3. Quality change / Reset / video option apply never re-upload from the retained buffer: 0x427D90/0x427DE0 -> Reset 0x423990 (FreeImage + `+0xE4=0`) -> 0x427A70/0x4260E0 -> ConstructImage 0x426270 -> LoadImage 0x4252C0 (own FreeImage, then a fresh loader call/Demand). FreeImage is idempotent (guard on +0x44), so Reset/dtor after an early free are no-ops.
4. Only real behavioural deltas of `75 10 -> 90 90`: (a) procedural-controller textures that are uncompressed TPC (`+0xE9==1 && +0x5C==0 && [tex+0x34]!=0`): Life controller init 0x492310 writes THROUGH GetImage without a NULL guard and Life update 0x492460 re-uploads via 0x422D50(1,0), so a second 0x4260E0 run (or the update) would run with `+0x44==0` (already the case today for every TGA texture); (b) re-queued already-built TPC textures (0x422E20, 0x427740, 0x4277A0, 0x426960) stop re-uploading the same pixels (glImage is skipped, GL object unchanged); (c) FreeImage side effect `+0xEA=0` (TXI-in-memory flag) now also hits TPC textures (same as TGA today).
5. Recommended guard: skip the free when `[tex+0x34] != 0` (controller present); code-cave sketch in (c). Runtime proof: hook 0x422640 (M3) and count calls whose return address is outside the four upload functions.

## (b) Findings

### F1. Q1: every indirect call through slot 0x3C, classified
Method: grep of all `.c` for `+ 0x3c))(` (159 lines / 106 functions) cross-checked against a python pass over all `.asm` for `MOV reg,[reg+0x3c]` immediately followed by `CALL reg` (107 functions; the 4 extra ones 0x41D940, 0x41E870, 0x499610, 0x730E90 are also classified below).

Texture receivers (CONFIRMED, receiver = CAurTextureBasic/CAurTexture):
* 0x434350 / 0x433CD0 / 0x432FA0 / 0x433320: `callers=004265e0` only (header line of each file); the calls are at the top of each routine (`local_38 = (**(code **)(*param_1 + 0x3c))();`); run inside glImage, BEFORE 0x4260E0's free decision. They pass the result to glTexImage2D/glTexSubImage2D (`glTexImage2D(iVar7,0,iVar4,iVar2,iVar3,0,iVar5,0x1401,local_18);` at 0x433320).
* 0x48FF30 (slot 0x18 of every controller class; vtables at 0x9882CC, 0x9882FC, 0x98833C, 0x988368, 0x9883A8, 0x98D6F8, 0x98D818, 0x98D8B4, 0x98D8D0, 0x98D910; slot 0x18 = 0x48FF30 at 0x9882E4/0x988314/0x988354/0x988380/0x9883C0/0x98D710/0x98D834/0x98D8CC/0x98D8EC/0x98D92C). Receiver proof: `[ctrl+4]` is the texture: `FUN_0048f710` `param_1[1] = param_2;` with `FUN_0048f710(param_1)` called from the texture's own 0x423AB0 (`FUN_0048f710(param_1);` after `local_c4 = FUN_00919723(0x48)`), and the same field is used as `(**(code **)(**(int **)(param_1 + 4) + 0x48))()` = texture GetWidth (slot 0x48 = 0x422740, slot 0x4C, 0x54) and `(vt+0xB0)` = UploadImage 0x422D50. * 0x491C40 (Wave Init, guarded by `if (iVar4 == 0)`), 0x492310 (Life Init, unguarded write), 0x492460 (Life Update, dead value), 0x4907F0 (Perlin Update, dead value). Quotes in table (a).

GetImage proxy chain and NULL behaviour (Q1 second part):
* Chain: this -> `vt[8]` (0x421F00: `this+0x10 ? [this+0x10] : this`) -> `vt[4]` on that object (basic: identity 0x458940; proxy with no basic: 0x4558A0 returns 0) -> `[obj+0x44]`. ### F3. Q3: quality change / Reset / device path never reads the retained buffer
Quote chain (all read):
* Callers of Reset 0x423990: only 0x427D90 and 0x427DE0 (callgraph `00427d90 00427dcb 00423990 CALL`, `00427de0 00427e45 00423990 CALL`); callers of those: 0x78D6A0 (video options, `0078d6a0 0078d9fd 00427d90`, `0078db17 00427de0`), 0x93B650 (init), 0x426C30 (shutdown). No window-resize/fullscreen/device-reset path calls either (callgraph grep for callee 00427d90/00427de0/00423990 is complete for direct calls; Reset itself has no vtable slot reference other than FreeImage).
* Reset body: `(**(code **)(*param_1 + 0xb4))(); param_1[0x17] = 0; ... *(undefined1 *)(param_1 + 0x39) = 0;` (= `+0xE4 = 0`) `*(undefined1 *)((int)param_1 + 0xe9) = 0; ... glDeleteTextures(...)`. So after Reset the texture is "unbuilt"; next build goes through ConstructImage -> `FUN_004252c0()`, whose first statement is `(**(code **)(*param_1 + 0xb4))();` then the loader `FUN_004219a0` (fresh Demand via 0x93B9C0). The old buffer is not consulted (it was freed by Reset's FreeImage).
* 0x427DE0 `FUN_00423990()` loop then `FUN_00427b60(...)`, which calls 0x427A70 (`if (*(char *)(iVar1 + 0xe4) == '\0') { FUN_00426270(); }`) and 0x426960 (`*(undefined1 *)(param_1 + 0xe8) = 1; FUN_00474000(param_1);`), then `FUN_00427810();` -> `FUN_004260e0()` per pending texture. Re-upload of an already built texture without a Reset would only happen via a requeue (F6).
* 0x422D50 (slot 0xB0) is the only other glImage caller. With `param_3 == 0` it uses the existing `+0x44` (only the Life update calls it that way: `(**(code **)(**(int **)(param_1 + 4) + 0xb0))(1,0);`); every other caller passes an explicit buffer (list of `+ 0xb0))(` texture callers: 0x4935D0, 0x490FD0, 0x492460, 0x4907F0, 0x493720, 0x491E10, 0x492BF0, 0x493DD0; the other `0xb0` hits are non-texture classes).

### F4. Q4: "uploaded" state fields (exact)
glImage 0x4265E0 (asm 0x4265FE `CMP dword ptr [ECX + 0x44],0x0`; decompile):
```
if (param_1[0x11] == 0) { param_1[0x16] = 0; ... }
else { if ((param_1[0x16] == 0) || (param_1[0x10] == 0)) { ... param_1[0x10] = new[tiles*4]; glGenTextures(tiles, param_1[0x10]); param_1[0x16] = *(int *)param_1[0x10]; }
```
* `tex+0x40` (`param_1[0x10]`): GL name array (new[], `tiles = *(short*)(+0xC6) * (short)+0xC8`), freed in Reset/dtor (`FUN_009196fd(param_1[0x10]); param_1[0x10] = 0;`).
* `tex+0x58` (`param_1[0x16]`): first GL name; 0 = not uploaded (set to 0 when glImage runs with `+0x44==0`, and in Reset/dtor). This is the best single test "is uploaded": `[tex+0x58] != 0 && [tex+0x40] != 0`. Note: `+0x58` is set BEFORE the per-tile upload calls (and hence before the GetImage calls inside 0x434350 etc.), so it does not separate "during upload" from "after upload"; use the return address for that (F7/c).
* `tex+0xE4`: "ConstructImage done" (`*(undefined1 *)(param_1 + 0xe4) = 1;` 0x426270; cleared by Reset). Set BEFORE the upload; stays 1 through FreeImage.
* `tex+0xE5`: "no pixel data / placeholder" (`*(undefined1 *)(param_1 + 0xe5) = 1;` when `+0x44==0 && +0x34==0`); skipped by 0x427810/0x427970 max-id scan.
* `tex+0xE6`: NormCubeMap special (0x427110). `tex+0xE8`: downsample requeue flag (0x426960; ctor/Reset set it).
* `tex+0xE9`: TPC path (loader sets `*param_10 = 1;`); cleared only by Reset; **not** by FreeImage.
* `tex+0xEA`: NOT "uploaded": TXI-text-in-memory flag (SetFlagEA slot 0xA8 is called at the end of ParseTXI 0x424B10 and 0x45BF50; GetFlagEA slot 0x34 drives the file/memory branch in 0x424B10 and 0x45BF50). FreeImage clears it (`*(undefined1 *)(param_1 + 0xea) = 0;`, asm 0x42525A `MOV byte ptr [EAX + 0xea],0`).
* `tex+0xEB`: "bound this frame" (`*(undefined1 *)((int)local_8 + 0xeb) = 1;` in Bind 0x422ED0).
Hook test for M3 "post-upload retained TPC buffer": `[tex+0xE9]==1 && [tex+0xE4]==1 && [tex+0x58]!=0 && [tex+0x44]!=0`.

### F5. Q5: FreeImage 0x425160 side effects, idempotence, Reset/dtor after it
Full behaviour (asm 0x42516C `CMP dword ptr [EAX + 0x44],0x0 / JZ 0x004252b7` is the first thing it does):
* if `+0x44 != 0`: recompute the mip-chain byte length from `+0x74` (3 -> 8, 4 -> 0x10 bytes per 4x4 block), `+0x68/+0x6C`, `+0x5C`, `word +0xD2`; write `+0xEA = 0` (asm 0x42525A); call 0x421C40 with (`+0x44`, `+0x68`, `+0x6C`, `+0x74`, size, `+0x60`, `+0x64`, `&+0xE7`, `+0xE9`, 0); write `+0x44 = 0` (asm 0x4252B0).
* NOT touched: `+0x5C`, `+0x60`, `+0x64`, `+0x68`, `+0x6C`, `+0x74`, `+0xE4`, `+0xE9`, `+0x40`, `+0x58`, `+0x48` (TXI text), `+0x34` (controller). So dimensions/format survive, which is what the re-tag computation and Width/Height/Bpp slots (0x48/0x4C/0x54) rely on.
* 0x421C40: `if (*param_9 == '\0') { FUN_0091c6aa(param_2); } else { if (param_11 == '\0') { (*DAT_00a1bbc0)(param_2,...); } else { (*DAT_00a1bbc4)(...); } *param_9 = '\0'; }`: `param_9 = &tex+0xE7`. For a resman-owned buffer `+0xE7` is 1 (0x4252C0 `if ((DAT_00a1bbc0 == 0) || (param_1[0x11] == 0)) ... = 0 else ... = 1`; `DAT_00a1bbc0 = FUN_0093bad0;` at 0x93B650) so the release goes through 0x93BAD0, cleared to 0 afterwards. A second FreeImage returns at the `+0x44` guard, so no double Release / no `free()` of resman memory.
* Reset after FreeImage: 0x423990 starts with `(**(code **)(*param_1 + 0xb4))();` -> guard -> no-op; then only frees GL names and clears flags.
* Destructor after FreeImage: 0x423480 ends `FUN_00425160();` (direct call) -> guard -> no-op.
* FreeImage before LoadImage: 0x4252C0 / 0x425800 first statement `(**(code **)(*param_1 + 0xb4))();` -> no-op when already freed.
* Refcount: Release path = 0x93BAD0 -> ... -> 0x93EA10 -> 0x941520 -> 0x7112B0/0x7130B0 (R3); exercised today for every TGA texture. `+0x44 = 0` guarantees a single Release per Demand.
* One vanilla leak that the patch would REMOVE (SPECULATIVE on reachability): UploadImage 0x422D50 with a non-zero buffer does `*(int *)(iVar2 + 0x44) = param_3; ... *(undefined4 *)(iVar2 + 0x44) = 0;`, which overwrites a retained TPC pointer with 0 and leaks its Demand reference. Reachable when a controller Update (all except Life) fires on an uncompressed TPC texture that still retains `+0x44`.

### F7. Requeue / reload paths (behaviour that changes with the patch, not crashes)

### Guard implementation sketch (design, not applied; SPECULATIVE until built and tested)
Patch site 0x4261CF..0x4261D5 = 7 bytes `0F B6 C8 85 C9 75 10` (three whole instructions `MOVZX ECX,AL / TEST ECX,ECX / JNZ 0x4261E6`, no other instruction jumps into the middle; branch targets 0x4261D6 and 0x4261E6). Replace with `E9 rel32 90 90` to a cave: `mov eax,[ebp-4] ; cmp dword ptr [eax+0x34],0 ; jnz 0x4261E6 ; jmp 0x4261D6`. Effect: FreeImage now runs for TPC (as for TGA) unless the texture owns a procedural controller. `[EBP-4]` is `this` in this frame (asm 0x4261C2 `MOV ECX,dword ptr [EBP + -0x4]`). Optionally also preserve `+0xEA`: after the `CALL EDX` at 0x4261E4 restore `byte [this+0xEA]` saved before the call (adds a second cave; only needed if C4 > 0). The plain `75 10 -> 90 90` patch is equivalent for every texture without a controller.
