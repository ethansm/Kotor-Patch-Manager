# U4: VFX / particles / lights / GUI per-frame work, RB and AB fix designs, BR (in-game TGA reload)

## 5-line summary
1. AB: the action-bar rebuild 0x74CFE0 runs on ~98% of in-game frames (runA FRAME `frames=64081 actionbar_calls=62953`), NOT 8.6% as R7 inferred from the census; it is the ONLY per-frame CExoString producer visible in the census (~40 allocs/call, 13 of them from the +1 growth `0x58C3B0 -> 0x58C540`, which also has a heap overflow when shrinking, asm 0x58C61D). A capacity-reuse patch at 0x58C406 (12 bytes) is designed in section 4b.
2. RB: the 3 bucket maps are GLOBALS (0xA73374 / 0xA73318 / 0xA733A0) wiped per frame at 0x4957AA..0x4957C7; 2 of the 3 maps never receive a vector (only read-inserts), so nodes are pure churn (7.63 node + 1.76 vector allocs/frame, ~3% of runA's 256-511 allocs/frame). Node-reuse design = replace the 30-byte clear sequence by "zero every node's vector count, keep nodes" (behaviour preserving: draw order comes from the texture-id list 0x427970, never from map order). Expected gain is tiny (estimate < 0.05 ms/frame, SPECULATIVE); do RB only as low-priority cleanup.
3. Particles are POOLED per emitter (active vector [+0x1C8], free pool [+0x1D4]); new(0x78/0x74) only when the pool is empty; 3 render fns hold a one-time static 0x5DC0 buffer; live-emitter counter already exists at DAT_00A7BD28. VFX-on-object records (new 0xFC, 0x7F0790) are removed per tick when IsDone (0x7F0B50) and on object teardown (0x7F0A50): no leak found. Lights: candidate vector persistent, `_qsort` over in-range lights (0x508CA0), no allocation.
4. BR: every by-name GUI image setter reachable from MainLoop by direct edges (minimap 0x7CEEC0->0x750C10 `lbl_map%s`, action bar 0x7418A0, map panel 0x894320->0x416090, Fury fx 0x442090) is GATED by a 16-byte lowercase resref compare (0x414840 asm 0x41485D..0x41486A); the minimap hypothesis is REFUTED statically. The mechanism that makes any gate miss expensive is CONFIRMED (release-before-acquire + last-reference delete), and three name-logging hooks with exact bytes are given.
5. Top items by expected impact: (a) BR root cause unknown, needs the 0x414870 / 0x427609 name log (only item that is ~1 texture/frame = 360 KB read + mipmap build + upload); (b) AB reserve patch; (c) RB keep-nodes patch; all (b)(c) are allocator-churn cleanups, not ms-level wins (frame time is VSync capped per runA).

Conventions: addresses Steam swkotor2.exe. `ret N` from decomp header. Everything labelled SPECULATIVE is not directly shown. Mapper TSVs: `findings/U4_map_{PartEmitter,CSWCVisualEffectOnObject,LightManager,CSWGuiMainInterface,CAuroraInterface}.tsv`. Confirmed mapper rows are noted in (a); the mapper mislabels 0x4FAC30 ("Destructor_2") which actually contains `new(0x78)` spawn code, and 0x7409A0 ("GetModelXInternal") which is a cursor-style wrapper calling 0x79E550.

## (b) Findings

### 1. Particles (Q1, Q6 partly)

Live-heap facts (census): a1 0x4E8EE8 (return of `new(100)` in 0x4E8A30) live 88 + 85 blocks at snapshot, 100 B each (`004f9f23 ... 8800 88` and `004fac13 ... 8500 85`); 0x5089DE (light vector buffers) live 1280 B / 20 blocks. Particles themselves are not in the top lists (pooled, steady).

**Axis 1 leaks / growth.** Particle lifetime: spawn pops the pool (`local_20 = *(int **)(*(int *)(param_1 + 0x1d4) + -4 + local_64 * 4); FUN_0049b840();` 0x4F9F40) or allocates `new(0x78/0x74)` only when the pool is empty (`if (local_64 < 1)`); death moves the pointer active -> pool (asm 0x4f3235 remove from `this+0x1c8`, 0x4f3247 push onto `this+0x1d4`). So the per-emitter peak particle count stays allocated until the emitter dies (bounded by emitter max particles, CONFIRMED structurally; peak size SPECULATIVE). Emitter death: dtor 0x4E8F60 drains BOTH vectors (`param_1[0x73]`/`[0x72]` active, `[0x76]`/`[0x75]` pool) with virtual deleting dtors, frees the image holder (`FUN_004da1b0(); FUN_009196fd(iVar3)`), decrements `DAT_00a7bd28`. Lightning emitter subclass 0x4FBA10 (`*param_1 = LightningEmitter::vftable`) frees its extra array then chains to 0x4E8F60. Emitters are created only by factory 0x4E54D0 (caller 0x453EF0 = model-instance build, SPECULATIVE by name) so area-unload freeing follows model-instance destruction (not traced here; runA module change drops live heap to 7 MB, consistent with no gross leak).
Remaining unbounded-ish growth: emitter vectors use the doubling `push_back` 0x473F40 (capacity never shrinks); bounded by peak.

**Axis 2 per-frame churn.** Steady state allocates nothing per particle. One-time statics: the three render variants each init a function-local 24,000 B scratch buffer behind a guard bit (asm 0x4f3b6e `MOV EAX,[0x00a7bd68] / AND EAX,1 / JNZ 0x004f3bb4` ... `PUSH 0x5dc0 / CALL 0x00919723`). Call chain (vtable-only entries, R7): Scene::Render 0x46C2B0 -> 0x46C190 -> 0x4EC080 (Animate) ; 0x469950 -> 0x4E92A0 -> 0x4F3B40/0x4F5F50/0x4F8000 (render); per-tick spawn/recycle 0x4F9F40 -> 0x4F31A0 (per-frame, per emitter). Per-frame cost is CPU (bezier math in 0x4EC080, `_rand()` calls in the spawn loop `iVar8 = _rand(); ... iVar8 % local_60`), not allocation. The first push into each of an emitter's two vectors allocates a 64 B buffer (capacity 16): plausibly part of the census `0x473F80` 64 B family (118,969 allocs, 1.76/frame) whose share between bucket vectors and emitter vectors cannot be separated statically (SPECULATIVE; counter in (c)).

**Axis 3 robustness.** Spawn: `new(0x78)` result is tested before the ctor call (`if (iVar8 == 0) { local_208 = (int *)0x0; }`) but then `(**(code **)(*local_20 + 8))(param_2)` is called on local_20 unconditionally (0x4F9F40 lines ~175/180): NULL vcall on OOM (SPECULATIVE trigger; only OOM). The 0x4F31A0 loop indexes `*(param_1+0x1c8) + local_10*4` backwards with a bound check (`while (local_10 = local_10 + -1, -1 < local_10)`): safe.

### 2. Lights (Q2)

Not rebuilt with allocation: 0x508CA0 resets the candidate count (`*(undefined4 *)(param_1 + 0x48) = 0;`), walks lights `[+0x2C]` (count `[+0x30]`), pushes qualifying lights with 0x473F40 into the persistent vector `[+0x44]` (capacity kept), then `_qsort` over `[+0x48]` entries. Only the first 3 of the sorted list are examined by the following loop (`if (2 < local_14) break;`) and GL lights are limited to min(param_2,[+0x48]) with slots up to 3 disabled (0x508F70 `for (local_c = local_10; local_c < 3; ...) glDisable(local_c + 0x4001)`). Number sorted = lights passing the filter (`*(float *)(... + 0x80) <= _DAT_00986b50` or forced by param_2, and `+0x58 != 0`). Max-lights patch exists: note only. Entry points have NO direct callers in callgraph.tsv (vtable/indirect; `grep 0x00508ca0 */*.asm` = no hit), so per-frame frequency is not proven statically (SPECULATIVE). Light record array growth: 0x508000 reallocs to EXACTLY n records (`local_34 = FUN_00919723(... uVar5 + 4 ...)` with `uVar5 = n*0x18`), i.e. the SetSize(+1)-style pattern like R8 found for 0x58C3B0; only reached through 0x507DE0/0x507D60 (census: 0x5089DE 20 blocks live), so scene-load-time only.

### 4. RB and AB concrete fixes

#### 4a. RB: bucket maps (Q4)

Facts (CONFIRMED from asm):
* The maps are globals: `MOV ECX,0xa73374 / CALL 0x00472630` (0x46607E, also 0x46609C, 0x4660F0, 0x466110, 0x4661A8, 0x4661C9 in 0x465F90), `0xa733a0` in 0x4662E0 (0x46635C ...), `0xa73318` in 0x466700 (0x46689B ...). Only 0xA73374 has a writer of vectors: 0x4946B0 `00494730 CALL 0x00472630 ; MOV ECX,EAX ; CALL 0x00473f40` (`MOV ECX,0xa73374` at 0x49472B). `grep` of `0xa73318|0xa733a0|0xa73374` across all .asm finds only 0x465F90, 0x4662E0, 0x466700, 0x464D70 (teardown, `0x4650FB MOV ECX,0xa73374 / CALL 0x004727a0`), 0x4946B0, 0x495760, plus static ctor/dtor stubs (0x9838xx/0x984Fxx). => maps 0xA73318 and 0xA733A0 never hold a non-empty vector; every node in them is created by a read (`FUN_00472630` is find-or-insert: `piVar3 = (int *)FUN_00472840(...)` when `*param_2 < *(uint *)(local_14 + 0xc)`).
* Per-frame clear (exact code), 0x495760: asm
```

004957af  e8eccffdff            CALL 0x004727a0
004957b4  b91833a700            MOV ECX,0xa73318
```

* Reinsert: drain 0x465F90 iterates the texture-id LIST (0x427970), not the map: `local_4c = *(undefined4 *)(local_1c + local_20 * 4); iVar3 = FUN_00472630(&local_4c); if (*(int *)(iVar3 + 4) != 0)` and `while( true ) { local_5c = 0; iVar3 = FUN_00472630(&local_5c); if (*(int *)(iVar3 + 4) <= local_34) break;` . `iVar3+4` is the vector count (vector = {ptr, count, cap}; `FUN_00473f40`: `*(undefined4 *)(*param_1 + param_1[1] * 4) = param_2; param_1[1] = param_1[1] + 1;`). Node layout (0x473B30): `*puVar1 = left; [1] = parent; [2] = right; puVar1[3] = key; ... *(undefined1 *)(puVar1 + 7) = color; *(undefined1 *)((int)puVar1 + 0x1d) = 0 (isnil)`; value = vector at node+0x10; 32 B node via `FUN_00474110: FUN_00919723(param_1 << 5)`.
* runA: 0x472630 ~225 calls/frame (max 972); node allocs 7.63/frame (R7), i.e. list size per pass is small (~2-3 distinct ids per map, SPECULATIVE) and ~220 of the calls are pure finds.

Design (minimal node reuse): replace the 30 bytes 0x4957AA..0x4957C7 by `E8 rel32 <cave>` + 25 x `90`. The cave (new code in the patch DLL, C-like):
```
void ResetBucketMaps(void) {            // called instead of the 3 x std::map::clear
  for each map in {0xA73374, 0xA73318, 0xA733A0}:
     if (*(int*)(map+0x1C) > 256) { call 0x4727A0 with ECX=map; continue; }   // safety cap: wipe stale nodes
     head = *(int*)(map+0x18);  walk tree from root=*(int*)(head+4) in any order;
       for node with *(char*)(node+0x1D)==0: *(int*)(node+0x14) = 0;   // vector count at node+0x10+4
}
```
Stolen range: 30 bytes, three whole `MOV ECX,imm32 / CALL rel32` pairs, no Jcc in 0x495760 at all (straight-line function), no instruction jumps into the middle. The relative CALLs are discarded (the cave performs the calls itself if the cap is hit: `mov ecx,map; call 0x004727A0`).
Why behaviour preserving: (1) draw order comes from the id list `FUN_00427970` (`local_4c = *(undefined4 *)(local_1c + local_20 * 4)`), and within a bucket from vector index order; nothing iterates the tree (only 4 callers of 0x472630, all quoted; tree iterator `FUN_004738a0` is only used to fetch the looked-up node); (2) a kept node with count 0 is read exactly like an absent key after the old insert (`*(int *)(iVar3 + 4) != 0` false; `<= local_34` true); (3) stale texture ids: nodes for deleted GL ids keep count 0 and are never dereferenced; vector buffers keep capacity (no double free: 0x472F90 frees them only at real erase, and 0x464D70 still calls the real clear at teardown); (4) the 0xA733xx global `_DAT_...` counters zeroed around the call are untouched. Memory bound: nodes are keyed by GL texture name, bounded by distinct names seen between real clears (cap 256/map). Gain: removes ~7.6 node alloc/free + ~1.8 vector alloc/free per frame = ~3% of runA's allocator calls (alloc hist bucket 9 = 256-511 per frame in 61,554 of 64,081 frames); time saving estimated < 0.05 ms (SPECULATIVE; frame time is VSync-capped, runA hist_ms bucket 5 = 16-31 ms holds 46,082 frames). Verdict: LOW priority.
Alternative even smaller (not recommended): turn the 18 read-only `FUN_00472630` sites into `find`: needs new code in 3 fns, no benefit over the above.

original_bytes (12) at 0x58C406: `8B 45 08 50 8B 4D F4 E8 2E 01 00 00`. Replace by `E9 rel32 <cave>` + 7 x `90`; cave returns with `JMP 0x0058C412`. Cave semantics (C-like; `this` = [ebp-0xC], `n` = [ebp+8]):
```
int cnt = this[1], alloc = this[2]; char* data = (char*)this[0];
if (data != 0 && n >= 1 && n <= alloc) {                    // reuse capacity
    for (int i = cnt; i < n; i++) fastcall 0x007ECFA0(data + i*0x3C);   // default-state new slots
} else {                                                     // grow geometrically
    int cap = max(n, max(alloc*2, 4)); if (cap < cnt) cap = cnt;
    thiscall 0x0058C540(this, cap);                          // sets this[2]=cap and array header
}
/* then fall to 0x58C412 which does: this[1] = n */
```
Behaviour preservation: (1) a fresh slot after original SetSize is default-constructed (ctor 0x58C690 ends in 0x7ECFA0); the cave applies the same 0x7ECFA0 to slots [cnt,n) in the reuse path, so callers that only set some fields see identical values (0x77A9E0 sets +0x8, +0xC..+0x18, +0x1C, +0x38, name, +0x20 resref only; +0x10..+0x14/+0x30/+0x34 rely on defaults); (2) `[-4]` array header and `this[2]` stay consistent since growth still goes through 0x58C540 (vector deleting dtor 0x58C430 uses `*(param_1 - 4)`); (3) shrink case n<cnt with n<=alloc now keeps the tail entries alive (no overflow); they are re-defaulted on the next extension. Risks (SPECULATIVE, need a check of the 40 callers): code that assumes `this[2] == this[1]` or that entries past count are freed. Mitigation: counters in (c) (reuse vs grow counts) and a run with the existing 2DA/inventory UI.
Expected effect: per call ~13 of ~40 allocs disappear after the first frame (array allocs), plus the k(k-1)/2 string copies; the remaining allocs are 2DA column-name CExoStrings and "%s (%d)" formats (0x77BCF0, 0x77A9E0). Time: ~26 alloc/free pairs + copies per frame, estimate 3-10 us (SPECULATIVE): LOW ms impact; worth doing for heap churn only.
Dirty gate alternative (NOT recommended): gating 0x74CFE0 needs all inputs (party, selected char `iVar3+4 != this+0x6c`, powers, equipment, cooldowns `FUN_0077d800`); no cheap version counter is visible. A safe intermediate is a measurement only: hash category counts+ids after rebuild and count "identical to previous frame" (hook in (c)); if >95% identical a version-counter design is worthwhile.

### 6. BR: in-game TGA reload churn (extra Q8)

Question: which code creates/looks up a texture by name every frame, then releases it.

**Lifetime mechanism (CONFIRMED)**: texture records are refcounted by back-reference and deleted with the last release. `0x4276A0`: `if ((param_1 != (int *)0x0) && (param_1[2] == 0)) { ...
