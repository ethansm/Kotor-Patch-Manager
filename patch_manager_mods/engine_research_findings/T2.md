# T2: module-change teardown (static half of the S2 leak test), Steam swkotor2.exe 6a522e71

## 5-line summary
1. SEQUENCE (CONFIRMED): server `CServerExoAppInternal::UnloadModule` 0x5315e0 sends a DumpPlayer message per player (`0x53186f CALL 0x006375f0`, major 3 / minor 8) and THEN deletes the server CSWSModule (`0x5319f0 CALL EAX` = vtable[0](1) -> 0x556cf0 -> 0x556d20). The message is only queued (0x647050 -> 0x704060 ring buffer), the client handles it later in 0x811450 (`case 7` -> 0x73f250 -> 0x785410 -> client CSWCModule delete). So the server module dtor (which removes the module's key tables via 0x560070 at 0x556ebc) runs BEFORE the client area/scene/textures/models are destroyed.
2. TEXTURES/MODELS (CONFIRMED): no LRU, no "keep forever" cache. Textures and models are reference counted and destroyed the instant the last owner lets go: texture = back-reference list count (`0x4276a0`, `param_1[2]==0` -> delete -> `~CAurTextureBasic` 0x423480 = glDeleteTextures + FreeImage 0x425160 -> Demand Release), model = `+0x54` refcount (`0x452cf0` -> destroy 0x452120, removal from the sorted model array `[0xA1FFA8]` in 0x452be0). Both only run when the client scene (`CSWCArea+0x188`, deleted in UnloadArea 0x7a5fa0) and its objects die, i.e. on the client UnloadModule message, not at the server unload.
3. RESMAN HAZARD (CONFIRMED code path, reachability SPECULATIVE): `CExoKeyTable::DestroyTable` 0x726350 handles a CRes that is still Demand-held (`[CRes+4] != 0`, exactly the case for area textures/models still alive on the client) by only OR-ing flag 0x200 (`0x72650b OR EDX,0x200`); it neither rebinds nor clears `CRes+0x14` (the key-entry pointer), and the message it builds ("CExoKeyTable::DestroyTable: Resource %s still in demand during table deletion") goes only to a local `_sprintf` buffer, never logged. The 0x24-byte entry array is then freed (0x722ff0 -> 0x723190(3)), so `CRes+0x14` dangles and `ReleaseResObject` 0x713010 later executes `*(*(CRes+0x14)+0x10) = 0` (write into freed heap).
4. GL (CONFIRMED): area geometry GL names die only in `~CAurTextureBasic` 0x423480 (glDeleteTextures at 0x4235eb) and `Reset` 0x423990 (0x423a77); `glDeleteLists` (0x474486) is font-only; VBOs go through a pool manager (`RequestPoolManagerVBO`, glDeleteBuffersARB at 0x429a73/0x42a418) whose lifetime was not traced. No global "unload walks the texture table" exists (R3 F6).
5. GROWTH candidates (all SPECULATIVE, small): CRes objects of a destroyed key table with `+0x1c` object refcount only held by the table (0x726350 refcount-0 branch drops the pointer without delete), one `c_FocusGobDummyModel%d` model per scene never released by the scene dtor 0x464d70 (`DAT_00A20030` counter), plus the dangling-CRes hazard of item 3. Free live counters exist for the S2 test: `DAT_00A1BBE0` (textures), `DAT_00A1BBA0` (GL bytes est.), `[0xA1FFAC]` (models), `DAT_00A1DEE0` (mesh node bytes est.), `DAT_00A1FF68` (Gob instances), `DAT_00A1FF60` (node objects), `DAT_00A200F4` (scenes).

Scope note: no GOG mapper output was trusted without reading the Steam decompile. Mapper runs wrote only `findings/T2_map_module.tsv`, `T2_map_server.tsv`, `T2_map_srvapp.tsv`, `T2_map_swsmsg.tsv`, `T2_map_cswcmsg.tsv`, `T2_map_room.tsv`. WARNING: `inputs/name_map.tsv` has `0x004737e0 CSWCArea::LoadArea` which is wrong: 0x4737e0 is a 79-byte `std::length_error` destructor (`*(undefined ***)param_1 = std::length_error::vftable;`). The real client area loader is 0x7a2fb0 (GOG 0x44f9b0 + the class delta 0x353600 that maps dtor GOG 0x44f680 -> 0x7a2c80; body contains `FID_conflict_Create("mainscene")` at 0x7a40a9). `CSWCRoom`/`CAurRoom` classes do not map (mapper: unmapped).

## (b) Findings

### F1. Module-change sequence (Q1)  -- CONFIRMED
Trigger chain on the server: `0x52fda0 StartNewModule` -> `0x530170 ExecuteLoadModule` (`FUN_00531c50(param_1,0);`) -> `0x531c50 LoadModule`:
```
00531d4b  CALL 0x005315e0      ; if (local_24 != 0) { FUN_005315e0(); local_24 = 0; }   (UnloadModule of the OLD module)
```
Server `0x5315e0 UnloadModule`, in order (asm addresses):
1. `0x531623 CALL 0x0052f4c0` old module ptr; `0x53169b/0x5316aa CALL 0x00538ed0` (2,0)/(1,0);
2. `0x5316cd..0x5316e0` delete+recreate holder `[+0x10070]`, `0x531781` same for `[+0x10074]`;
3. loop over players (`0x5317fd CALL 0x007a1720`, `0x53181f CALL 0x00561430`): `0x53186f CALL 0x006375f0` (DumpPlayer message, major 3 minor 8), `0x53187x CALL 0x00632a20` player creature cleanup;
4. `0x5319cd CALL 0x0071eb80`, then `005319f0  ffd0  CALL EAX` with `PUSH 0x1` / `MOV EAX,[EDX]` = vtable[0] scalar-deleting dtor on the old module (`local_14`), which is 0x556cf0 -> 0x556d20;
5. `0x531a11 MOV dword ptr [ECX + 0x10060],0x7f000000` (module id cleared), recreate `[+0x10054]` (0x664280), recreate `[+0x1005c]` via `0x53d690(1)` (0x531b37), `0x531b79 CALL 0x0051dfe0`.
Server module dtor 0x556d20 (asm order): `0x556d74 CALL 0x007112b0` (Release of the module IFO CRes when `[0x7e]==0`), area lookup `0x556dd5 CALL 0x0051c120` + `0x556de6 CALL 0x0052dc50` (CSWSArea::ClearObjects) + `0x556e09 CALL EAX` (delete area, vtable[0](1)), list cleanups, then `0x556ebc CALL 0x00560070` (RemoveModuleResources), `0x556fa3 CALL 0x00557f80` (area cache clear), CExoString dtors, `FUN_0051c080/0053dea0/0051cee0` game-object array removal.

### F2. Textures across module change (Q2)  -- CONFIRMED policy, no cross-module name cache
* Cache key: name lookup 0x4269f0 scans `DAT_00A1BC60/64` (only live textures): `iVar3 = __stricmp(param_1,(char *)(*(int *)(DAT_00a1bc60 + local_14 * 4) + 0x7c));`. The entry is removed in the destructor (0x423930 `FUN_00449170(param_1);`), so there is no persistent by-name cache: a texture lives exactly as long as it has owners.
* Refcount = back-reference list: `0x421e30` shows list base at `this+4` and safe pointer at `this+0x10` (`ADD EAX,0x4 ... CALL 0x00449230`; `ADD ECX,0x10 ... CALL 0x004741e0`); `0x449230` zeroes `[0]=ptr,[1]=count,[2]=cap`, so `texture[2]` in `0x4276a0` is the list COUNT at `this+8` ... (list base `this+4`: ptr `+4`, count `+8`, cap `+0xC`). `0x4741e0` registers the owner's pointer in the target's list (`FUN_00474370`: `if (*(int *)(param_1 + 8) == 0) FUN_00449320(2); FUN_004491c0(param_2);`).
* Owner destruction path (every one quoted): proxy dtor 0x4233f0 `uVar1 = param_1[4]; FUN_004741e0(0); FUN_004276a0(uVar1,uVar2);`; Gob dtor 0x45a190 `uVar1 = param_1[0x75]; FUN_004741e0(0); FUN_004276a0(uVar1);`; scene dtor 0x464d70 releases 8 texture slots (`param_1[0x3c..0x42]`, `[0x2c]`) with the same pair; triangle-bin dtor 0x50c7a0 and ~60 other owners (R3 F6).
* `0x4276a0`: `if ((param_1 != 0) && (param_1[2] == 0)) { iVar1 = (**(code **)(*param_1 + 4))(); if (iVar1 == 0) { (**(code **)*param_1)(1); } else { puVar2 = ... (**(code **)(*param_1 + 4))(); (**(code **)*puVar2)(1); }` (which object is deleted for a proxy: SPECULATIVE, vtable[1] not resolved; the basic is the intended victim since `~CAurTexture` 0x4233f0 calls it on the basic pointer).
* Deletion executes `~CAurTextureBasic` 0x423480: `glDeleteTextures(...,param_1[0x10]); FUN_0091c6aa(param_1[0x10]);` ... `FUN_00425160(); DAT_00a1bbe0 = DAT_00a1bbe0 + -1;` so the TPC Demand reference (kept until FreeImage per R3 F1) is Released at texture death: `FreeImage 0x425160 -> 0x421C40 -> 0x93BAD0 -> 0x93EA10 -> 0x941520 -> Release 0x7130B0` (R3).
* Policy: refcount (owner list) with immediate destruction. Not LRU, not never-free. The only other eviction is the resolution budget system 0x427DE0 (Reset all, R3 F3) which does not run on module change.
* Consequence for the S2 hypothesis: textures of the old area are freed only when the client scene tree (F1 client half) dies. If ANY owner survives (e.g. a leaked scene object) the texture, its GL name, and its 195 MB-class CResTPC buffer survive.

### F3. Models across module change (Q3)  -- CONFIRMED (evict on last release), blob free CONFIRMED for binary models
* Cache = sorted pointer array `[0xA1FFA8]` count `[0xA1FFAC]` (name order, `_stricmp`): `0x48dfc0`, insert `0x48e090` (via `FUN_0050c380`), dedupe `0x48e2a0`. Lookup does NOT AddRef; instances do: `0x462320`: `local_7c[0x21] = local_24; FUN_00452d40(local_7c);` (`+0x54++`).
* Eviction path (only one): `0x452cf0`:
```
  if (DAT_00a1ff54 == 0) { *(int *)(param_1 + 0x54) = *(int *)(param_1 + 0x54) + -1; ... if (== 0) FUN_00452120(param_1);
```
`DAT_00A1FF54`: exactly one reference in the whole corpus (asm `00452cf9 CMP dword ptr [0x00a1ff54],0x0`), no writer found by grep of all .asm (`grep -h a1ff54 decomp/*/*.asm` -> only that line). Since a store via `[reg+off]` to a global is impossible (absolute address), a missing writer here IS conclusive: release is always enabled (initial value 0 in .bss; not read from the exe file).

### F4. Resman: capsule removal, refcount>0 CRes (Q4)  -- code path CONFIRMED, consequence partly SPECULATIVE
* Removal: `0x560070` (RemoveModuleResources) makes wrapper calls `007116b0 -> 0x7131d0(name,3)`, `007116d0 -> 0x7131d0(name,4)`, `00711710 -> 0x7131d0(name,2)` (e.g. `007116b7 6a03 PUSH 0x3 ... 007116c0 CALL 0x007131d0`). NOTE: the brief calls 0x7116B0/0x7116D0 RemoveEncapsulatedResourceFile/RemoveResourceImageFile; from the code they are type-3/type-4 `RemoveKeyTable(name,type)`, `0x711710` = type 2 (the `MODULES:`/`RIMS:` capsules per the strings around 0x560070: `"MODULES:"`, `"RIMS:"`, `"CURRENTGAME:"`). Callers of 0x560070: 0x5582f0 (LoadModuleStart), 0x556d20 (module dtor, `00556ebc CALL 0x00560070`), 0x55a460.
* `0x7131d0`: finds the table by name in `resman+0x10/0x14/0x18/0x1C`, then `FUN_00726350(); FUN_0064dde0(local_10); ... FUN_00722ff0(); FUN_009196fd(iVar1);`.
* `0x726350 DestroyTable`, per entry (0x24-byte entries at `table+0x10`, CRes at `entry+0x10`, id at `entry+0x14`):
  1. Resource also present in another table (`FUN_00712360` finds `local_120`): CRes is REBOUND to the surviving entry (`*(local_120+0x10) = CRes; CRes+8 = *(local_120+0x14); CRes+0x14 = local_120`), then `if ([CRes+4]==0) FUN_00711230(0); else flag = (flag & 0xfffffeff) | 0x100`. No dangling.
  2. Resource only in this table, refcount 0: `FUN_00711230(0); *(CRes+0x14) = 0; *(CRes+8) = 0xffffffff;` data freed (0x711e60 -> 0x711fe0 when flags 4|0x10 and data set); the CRes object pointer is dropped.
  3. Resource only in this table, refcount > 0 ("in demand"): asm
```

00726502  8b510c         MOV EDX,dword ptr [ECX + 0xc]
00726505  81e2fffdffff   AND EDX,0xfffffdff
```

  The callee list of 0x726350 contains no logger (`00734010 00710930 00712360 00733780 00733540 00919671 009196ee 00711230`): the message is built and discarded. `CRes+0x14` and `CRes+8` are NOT cleared. The entry array is then freed: `0x722ff0: if ((param_1[4] != 0) ...) FUN_00723190(3);` -> `_eh_vector_destructor_iterator_(param_1,0x24,...)` + `FUN_009196fd((int)param_1 + -4)`.
* What happens to such a CRes (Demand refs still held by textures/models of the still-alive client area): NOT freed at removal, NOT orphaned safely: `CRes+0x14` points into the freed entry array (dangling). Later, when its owners release: `Release 0x7130B0` (refcount to 0, evict list AddHead, flag 0x100) is safe; FreeChunk/0x7120c0 use `CRes+8` (id bits), not `+0x14`; but `ReleaseResObject 0x713010` does `if (*(int *)(param_1 + 0x14) != 0) { *(undefined4 *)(*(int *)(param_1 + 0x14) + 0x10) = 0; }` = 4-byte zero write into freed heap memory (use-after-free write). Reached only if the object refcount `+0x1c < 2` and data refcount 0 at that time (0x713010 conditions), from ~40 callers (e.g. helper deleters 0x93d200, 0x93d2b0, 0x93f480). Whether textures/models go through 0x713010 after the table died: SPECULATIVE (needs the H3 counter).
* Do Demand references get Released BEFORE the capsule is removed? For the server: irrelevant (server holds GFF CRes only). For the client textures/models: NO. Client texture/model Demand refs are dropped in `~CAurTextureBasic`/model destroy, which run when the client scene dies, i.e. after the DumpPlayer message is processed; the key-table removal happens in the server module dtor (F1). CONFIRMED order at the call sites; queue-drain timing SPECULATIVE. Practical effect on correct-case: only resources UNIQUE to the module capsule (module `.rim/_s.rim/.mod` contents) hit branch 3; base-game BIF/override resources hit branch 1 (rebind).
* Also mind the LoadModuleStart side: `0x5582f0` calls `0x560070` first, i.e. it also removes tables of the module being loaded (stale name) before adding: same branch-3 exposure if the same module is re-entered while the previous client area still lives (S2 round trip A -> B -> A).

### F5. Things that only grow across module changes (Q5)  -- all SPECULATIVE unless stated
