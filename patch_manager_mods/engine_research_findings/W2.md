# W2: M1 hardware mipmaps (replace CPU gluBuild2DMipmaps for TGA textures and cube faces)

## Summary (5 lines)
1. The engine ALREADY has a HW mip path: `0x433CD0` at 0x434032-0x434065 does `glTexParameteri(0xde1,0x8191,1)` then `glTexImage2D`. It is the only 0x8191 constant in the dump (`grep 0x8191 decomp/*/*.c` -> only 00433cd0.c:116). It is dead on any modern driver because the gate `0x484A60` returns 0 whenever ext bit 0x100000 is set, and 0x100000 is set by GL_ARB_fragment_program / GL_ATI_text_fragment_shader (0x431BC9-0x431C10).
2. A 1-instruction gate flip is NOT enough/safe: it covers only the TGA call site (0x4340B7). Cube faces (0x432FA0 -> 0x4331A6) and the two generated textures (0x432CE0 LUT 256x256, 0x436250 normalisation cube 6x256x256) never consult the gate. The gate flip also redirects the 16-bit and "update" (param_2 != 0) routes, which today use the engine's own CPU box loop 0x4337B0, into a full `glTexImage2D` re-specify (speculative perf regression for dynamic textures).
3. Recommended: replace gluBuild2DMipmaps itself. All 4 call sites go through ONE thunk `0x93B430` = `FF 25 24 60 98 00` (JMP [IAT 0x986024]); the IAT slot's only reader is that thunk (byte scan of vanilla exe: the dword 24 60 98 00 occurs once). The call sites are `__stdcall` (no stack cleanup after CALL), return value unused. One detour/IAT write covers TGA + cube + LUT + normalisation cube with identical entry conditions as today.
4. Context is a legacy `wglCreateContext` (no wglCreateContextAttribsARB string in strings.tsv), so GL_GENERATE_MIPMAP (0x8191, deprecated, removed from core 3.1+) is available on compat contexts; glGenerateMipmap is NOT resolved by the engine (no "glGenerateMipmap" string) and must be fetched by our code with wglGetProcAddress.
5. Expected gain: ~500 ms of the 574 ms / 52 calls per load (R4 runtime), ~480 ms at the main menu. Risks: filter differences vs GLU (both are 2x2 box for POT; engine's own 0x4337B0 is box too), NPOT (GLU rescales to POT; fall back), cube-map per-face generation order.

FINAL: FIX replace-at-thunk 0x93B430 (6 bytes, `E9 rel32 90`) with fallback to the original GLU; gate stub 0x484A60 only as a quick experiment.

- `00431b37 PUSH 0x989b7c` ("GL_ARB_framebuffer_object") -> `00431b51 OR EDX,[0x009f60b4]` = **0x40000**.

- `00431bb5 PUSH 0x989b30` ("GL_ARB_vertex_program") -> `[0x9f60c0]` = 0x200000.
- `00431bdf PUSH 0x989b18` ("GL_ARB_fragment_program") -> `00431bf9 OR EDX,[0x009f60e4]` (0x40000000) then `00431c0a OR EAX,[0x009f60bc]` = **0x100000 as well**.

- Bit 0x80000 has exactly ONE reader in the dump (`grep 0x009f60b8 decomp/*/*.asm`: 00431b7b writer, 00484a6f reader).

Why 0x100000 forces CPU: the code says so structurally (0x484A6D/0x484A89/0x484AB8 above) but no string/comment gives the reason. speculative: a 2003-era workaround for drivers with ARB/ATI fragment shader support but broken SGIS auto-mip (the engine's "shader-capable" mode = bit 0x100000 also swaps in vertex/fragment program render paths: `00432ad0 MOV [0x00a1bcb4],0x4b7f40`). Runtime confirms the CPU branch is live: runA 52 gluBuild2DMipmaps calls/load, i.e. the gate returns 0 on the test GPU. (GL_ARB_fragment_program is advertised by compat contexts of NVIDIA and Mesa; speculative that every target driver does.)

### 2. gluBuild2DMipmaps call sites (all stdcall via thunk 0x93B430)
Thunk (not in decomp; bytes from vanilla exe VA 0x93B430): `ff 25 24 60 98 00 | ff 25 28 60 98 00 (gluPerspective 0x93B436) | ff 25 7c 64 ...`. 16 bytes before it: `00 00 00 00 0f 00 00 00 0c ff ff 80 00 00 00 00` (data/padding, not code). IAT: `0x986024 -> hint "gluBuild2DMipmaps"`, `0x986028 -> "gluPerspective"`, `0x986020` and `0x98602c` = 0 (import descriptor terminators). Byte scan of the vanilla exe for `24 60 98 00` finds exactly one hit (the thunk operand at 0x93B432), so the thunk is the sole reader of the slot. Callers of the thunk (callgraph.tsv + grep `CALL 0x0093b430`): 0x4340B7, 0x4331A6, 0x432E39, 0x43640B only. No stack cleanup after any of the CALLs (e.g. `004340b7 CALL 0x0093b430` / `004340bc JMP 0x004341a9`) -> callee pops 28 bytes = `gluBuild2DMipmaps@28`; EAX (GLint) is ignored at all four.

Argument order (push order is reversed: first push = data, last push = target):
- **TGA 0x4340B7** (`decomp/43/00433cd0.asm` 0x43409A-0x4340B7):
  `PUSH [EBP-8]`(data) `PUSH [EBP-0x64]`(type) `PUSH [EBP-0x60]`(format) `PUSH [EBP-0x3c]`(height) `PUSH [EBP-0x20]`(width) `PUSH [EBP-0x5c]`(internalformat) `PUSH 0xde1`(target). Decompile: `gluBuild2DMipmaps(0xde1,local_60,local_24,local_40,local_78,local_68,local_c)`. w = `local_24 = texW / cols` (vtable+0x48 / vtable+0x5c), h = `local_40 = texH / rows`, ifmt = channel count 1..4 (`local_60 = local_14` = vtable+0x54 for non-16-bit), format 0x1907 (3ch)/0x1908 (4ch)/0x1909 (1ch), type 0x1401 (or 0x8033 for 16-bit, not reached here). Bound: texture bound by 0x4265E0 `FUN_00421cf0(*(param_1[0x10]+local_c*4), ...)` -> `FUN_00421de0` -> `glBindTexture((&DAT_009f4928)[param_1],param_2)` (00421de0.c line 6) before each tile.
- **Cube 0x4331A6** (`00432fa0.asm` 0x433187-0x4331A6): `PUSH [EBP-0x14]`(data) `PUSH 0x1401` `PUSH [EBP-0x20]`(format) `PUSH [EBP-0x3c]`(h) `PUSH [EBP-0x28]`(w) `PUSH [EBP-0x10]`(ifmt = channels) `PUSH [EBP-0x2c]`(target = `[0x9f50c0+i*4]+0x8515`). `[0x9f50c0..]` = {1,0,2,3,4,5} -> targets 0x8516,0x8515,0x8517,0x8518,0x8519,0x851A (last = 0x851A). Taken when `0x70()` (mip flag) != 0, REGARDLESS of param_2 (decompile: `else { gluBuild2DMipmaps(iVar5,...); }`). Bound: 0x4265E0 binds with isCube flag `[this+0xDF]` (`FUN_00421cf0(...,*(param_1+0xdf),..)` -> `FUN_00421de0(0xc,id)`).
- **LUT 0x432E39** (`00432ce0.asm`): `PUSH [EBP-4]`(data) `PUSH 0x1401` `PUSH 0x190a` `PUSH [EBP-8]`(w=0x100) `PUSH [EBP-8]`(h) `PUSH 0x190a`(ifmt) `PUSH 0xde1`. Bound by `00432e02 CALL [0x009862b8]` (glBindTexture) right before. One-time per process (glIsTexture guard) but called from 0x42ABC0, 0x4B50C0, 0x4B7F40 (callgraph `00432ce0` callers).
- **Normalisation cube 0x43640B** (`00436250.asm`): `PUSH [EBP-0x1c]`(data) `PUSH 0x1401` `PUSH 0x1907` `PUSH [EBP+8]`(h) `PUSH [EBP+8]`(w; = 0x100 from `00427211 PUSH 0x100` / `CALL 0x00436250`) `PUSH 3` `PUSH [0x9884fc + [0x9f50d8+i*4]*4]`(target 0x8515..0x851A for i=0..5, table `[0x9f50d8]={2,3,4,5,6,7}`, `[0x9884fc]={0xde1,0x8513,0x8515,...,0x851a}`). Bound at 0x427209 `CALL 0x00421de0` (arg 0xc, cube). Created from 0x427110 (callers 0x4260E0 chain, 0x427330 x25 callers).

NPOT: sizes are texture dims / tile counts; no POT enforcement anywhere before the call (0x4337B0 handles non-square by `FUN_00481f60(... local_54,local_54)` rescale to square of max dim, so the engine anticipates NPOT/non-square inputs). GLU rescales NPOT to POT (speculative on which GLU: Windows glu32 or Wine's Mesa GLU; both historically rescale if no NPOT ext). A HW path must therefore fall back to the real gluBuild2DMipmaps for NPOT or w/h > GL_MAX_TEXTURE_SIZE, or replicate rescale. Cube faces and the two generated textures are 256x256 (POT).

### 3. wglGetProcAddress / context / SubImage
- `wglGetProcAddress` is imported and used heavily by 0x4317D0 (names at 0x988744.. e.g. "glDebugMessageCallback", "glFramebufferTexture2D", "glBindFramebuffer", "glGenFramebuffers"; imports.tsv rows 004317d0 `CALL dword ptr [0x0098632c]`). strings.tsv has NO "glGenerateMipmap"/"glGenerateMipmapEXT": our code must resolve it itself. FBO entry points exist, so the driver's ARB_framebuffer_object function set is already resolved by name in the same function (bit 0x40000 from `GL_ARB_framebuffer_object`), but not glGenerateMipmap.
- Context creation: `wglCreateContext` only (imports.tsv: 0x43BB50, 0x43C290 x7, 0x441DD0, 0x477990, 0x476BE0); no "wglCreateContextAttribsARB" string in strings.tsv -> legacy/compat context, whatever the driver gives for a plain request (compat profile on NVIDIA/Mesa: GL_GENERATE_MIPMAP and glGenerateMipmap both available when GL >= 3.0 / ARB_framebuffer_object).
- Extension string source: `glGetString(0x1f03)` (GL_EXTENSIONS) at 0x4317D0 -> would be NULL in a core profile; works only because compat. The WGL ext string via `wglGetExtensionsStringARB` is separate (`local_8`).
- Later `glTexSubImage2D` users (imports.tsv): 0x433CD0 @0x434132 (non-mip branch, `local_18==0`), 0x4337B0 @0x433906/0x433CAA (engine box chain, level-by-level, param_5), 0x432FA0 @0x4331D4 (cube, only when mips NOT wanted), 0x434350/0x433320/0x436780 (TPC / compressed, own pre-baked chain). I.e. no re-generation is needed after initial upload for textures that went through gluBuild2DMipmaps; but the 4337B0 SubImage path on a GENERATE_MIPMAP-sticky texture would regenerate (see finding 1) -> reset the flag to 0 after the upload in our replacement.

### 4. Replacement design

Contract: `GLint __stdcall hwBuild2DMipmaps(GLenum target, GLint ifmt, GLsizei w, GLsizei h, GLenum fmt, GLenum type, const void* data)`; returns 0 on success, otherwise the result of the original GLU call (we tail-call original `gluBuild2DMipmaps` read from the saved IAT value, so GLU error codes pass through). Callers ignore the value.

Fallback to original GLU when ANY of:
1. `w`/`h` not powers of two, or `w`/`h` > GL_MAX_TEXTURE_SIZE (GLU would rescale), or `data == NULL`.
2. `type != GL_UNSIGNED_BYTE (0x1401)` (GLU also handles packed 0x8033; not reached today).
3. target not in {0xDE1, 0x8515..0x851A} (not seen today).
4. `ifmt` not in {1,2,3,4,0x190A (432CE0)}, or compressed internal formats (never passed: all compressed uploads use glCompressedTexImage via 0x434350/DAT_00a32d04).
5. Capability: option (a) needs GL >= 1.4 or GL_SGIS_generate_mipmap; option (b) needs `wglGetProcAddress("glGenerateMipmap") != NULL` and GL >= 3.0 / ARB_framebuffer_object. Probe once at first call.
6. `glGetError()` != 0 after the HW sequence (drain stale errors first with a bounded loop; on error call original GLU, which re-specifies every level).

Option (a), GL_GENERATE_MIPMAP (this is what the engine already does at 0x43403E-0x434065):
```
glTexParameteri(target2D_or_0x8513, 0x8191 /*GL_GENERATE_MIPMAP*/, 1);
glTexImage2D(target, 0, ifmt, w, h, 0, fmt, type, data);   // driver builds levels 1..n
glTexParameteri(texTarget, 0x8191, 0);                      // clear stickiness (avoid regen on later SubImage)
```
For cube targets the texture-level state lives on 0x8513 (the engine sets wrap/filter on 0x8513 at 0x432FA0 end: `glTexParameteri(0x8513,0x2802,0x812f)`), so the parameter must be set on 0x8513, not on the face enum. Per-face generation semantics (does face N's upload regenerate only face N's chain or all?) are driver-defined: speculative. Final state is correct after the last face either way because each face's level 0 is uploaded and the chain regenerated after it; leave the flag TRUE until the 0x851A call, then clear it.

Option (b), glGenerateMipmap:
```
glTexImage2D(target, 0, ifmt, w, h, 0, fmt, type, data);
if 2D (0xDE1): glGenerateMipmap(0xDE1);
if cube: only after the call with target == 0x851A (last face in BOTH orders: 432FA0 = {0x8516,0x8515,0x8517,0x8518,0x8519,0x851A}; 436250 = 0x8515..0x851A): glGenerateMipmap(0x8513);
```
(b) needs all 6 level-0 faces present and equal size at that moment; true here (both callers upload 6 same-size faces in one loop). If a face upload is skipped (fallback path error), the cube would be incomplete: so on the 0x851A call verify the previous 5 uploads in this sequence succeeded (thread-local counter) else fall back to (a)/GLU. (b) is the cleanest on modern GL; (a) is the zero-new-entrypoint option and matches the engine's own existing code. Recommended order: (b) when available and non-cube; for cube use (b) with the counter guard; (a) otherwise.

Install (choose ONE):
- I1 thunk detour (file or runtime): at VA 0x93B430 replace `ff 25 24 60 98 00` with `E9 <rel32> 90`, rel32 = `&hwBuild2DMipmaps - 0x93B435` (E9 opcode; displacement base = address of next instruction = 0x93B430+5). Stolen range 0x93B430..0x93B435 is a complete thunk (6 bytes); no branch lands inside (`grep -rE "(J[A-Z]+|CALL|JMP) +0x0*93b431..93b435 decomp/*/*.asm` -> empty for all five; only `CALL 0x0093b430` x4 target the entry). Next thunk (gluPerspective at 0x93B436) untouched. Registers: stdcall thunk, nothing live except the 7 stack args and the return address, EAX/ECX/EDX are caller-saved (callers at 0x4340B7 etc. do not use them after: 0x4340BC `JMP`, 0x4331AB `JMP`, 0x432E3E `PUSH 0x812f`, 0x436410 `JMP`). Keep a copy of the original target by reading `*(DWORD*)0x986024` (loader-resolved) before patching.
- I2 IAT slot (runtime only): `VirtualProtect(0x986024,4,PAGE_READWRITE)`, `*(DWORD*)0x986024 = &hwBuild2DMipmaps`, restore. Reader of the slot: only the thunk (above). Side effect: none on gluPerspective (0x986028). The slot is in the loader-filled IAT, so a static file patch is not possible (file holds the hint/name RVA 0x5f2a34); needs the patch-manager DLL.
I2 is the least invasive (no code bytes changed, trivially reversible). I1 works even if the IAT is re-resolved.

### 5. Risks
- Filter: GLU = 2x2 box per level from the previous level (and the engine's own 0x4337B0 chain is also a 2x2 box average, see 004337b0.c lines 70-105: `(a+b+c+d) >> 2` per channel); GL_GENERATE_MIPMAP / glGenerateMipmap is implementation-defined but a box on NVIDIA/AMD/Mesa in practice (speculative). Expect LSB-level differences, not visible except on high-frequency normal-ish content; compare with PSNR in the harness.
- sRGB: ifmt values are legacy component counts 1..4 / 0x190A (non-sRGB); neither path gamma-converts. No sRGB internal format reaches any call site (all 4 sites listed above).
- Alpha: both average straight (non-premultiplied) alpha; same.
- Compressed formats: never reach gluBuild2DMipmaps (TPC/DXT go through 0x434350 / DAT_00a32d04 with pre-baked mip chain, R3).
- Cube maps: need target 0x8513 for the flag / glGenerateMipmap, completeness only after face 6, see (b). Wrap/filter params are applied on 0x8513 after the loop (0x432FA0 end) so they do not interfere. Cube face 0x8516 is uploaded first by 0x432FA0, 0x8515 first by 0x436250: do not key on "first face".
- Unpack state: both GLU and glTexImage2D use the current GL_UNPACK_*; `glPixelStorei` is called only from 0x4743C0 (`PUSH 0xcf5 / CALL [0x00986258]` = GL_UNPACK_ALIGNMENT, value 1 pushed at 004743c4) so alignment is whatever the engine left; identical for both paths (speculative: that 0x4743C0 runs before textures).
- GL errors: the engine never calls glGetError (no import), so the replacement should use it only for its own validation and not leave an error set that other code could treat as meaningful (none does).
- NPOT sizes would change the texture dimensions with GLU (rescale) but not with the HW path -> only if we allow them; fallback rule 1 avoids it.
- Thread/context: all calls happen on the render thread with the context current (the existing GL calls in the same functions rely on that).
