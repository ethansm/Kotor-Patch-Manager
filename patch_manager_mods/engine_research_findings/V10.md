# V10: GUI focus geometry and texture residency (Steam swkotor2.exe 6a522e71)

## 5-line summary
1. Button focus: K2 `CSWGuiButton::Draw` 0x41A0A0 draws the HILIGHT border (+0xE8) INSTEAD of the normal one (+0x70) when `[this+0x48]&1`, exactly as in K1. The fill is inset by DIMENSION (raw GFF int, never scaled by fs) ONLY when the border has a CORNER image (`CMP [ECX+0x6C],0` at 0x4153A0). Of 1110 K2 buttons (Override first, then chitin) only 17 galaxy-map planet buttons (normal inset 6, focus 0 -> fill GROWS ~16% at 3840x1600) and 6 inventory filter buttons (focus-only 2 px inset) change inset with focus: NO BUG, authored vanilla design.
2. Texture budget = `texpacks.2da` row `[Texture Quality]` (user: 2 = `swpc_tex_tpa`, mem 134217728, dynmemratio 0.75). NEW detail vs K1 doc: K2 splits it into a dynamic list A (hard limit 100,663,296, target x0.8 = 80,530,640) and a static list B (33,554,432), selected by a global flag `[0x9F4768]` (default 1 = list A).
3. K2 DOES run the downsample bookkeeping (0x427B60 bumps `+0xC0` until the accounted size fits) but the step that would change pixels, `ApplyDownSampleLevel` 0x4258B0, is jumped over (`004258b9 e9e4040000 JMP 0x00425da2`; the original body is still in the exe, dead). So HD textures are NOT silently downsampled; the enforcement only runs inside 0x427DE0 (SetTexturePack, init, GL-context re-creation), never per frame or per load.
4. NEW runtime proof that the accounting is a one-shot snapshot: perf-lab `LIVE gl_bytes_est` (= `[0xA1BBA0]`) is NEGATIVE and falls monotonically (-49 MB, -92 MB, -142 MB ... -680 MB) because the texture dtor 0x423480 subtracts sizes that were never added at creation (only writer of the totals is 0x427DE0). Resident TPC is 205.1 MB (latest run, RT 3007) vs Mem 134.2 MB: by the accounting formula the set IS over budget, but nothing acts on it.
5. No BUG verdicts, no hook needed, no overlap with live hooks (nearest are perf-lab 0x4260E0/0x427609/0x423480, none within +-8 of anything proposed). WARNING recorded: re-enabling 0x4258B9 would downsample the user's largest HD textures (205 MB accounted vs an 80.5 MB list-A target / 33.5 MB list-B limit); do not "fix" the JMP.

## (b) Findings

### Part 1: button focus border

**F1. Focus replaces normal (CONFIRMED, same as K1).** Decompile 0x41A0A0 quoted in the table. Asm: `0041a0b0 7420 JZ 0x0041a0d2` skips to the normal-border call `0041a0d6..0041a0e8` (`ADD ECX,0x70 ... CALL EAX`), the focus path is `0041a0b2..0041a0ce` (`ADD ECX,0xe8 ... CALL EDX`); both fall to the text draw `0041a0ea..0041a106` (`ADD ECX,0x160`). So a focused button never draws its normal border block. K1's two border blocks at 0x80/0xF4 (stride 0x74) correspond to K2 0x70/0xE8 (stride 0x78): same structure, different offsets (shown by the quotes above, not by a name match). The focus bit is set by `SetActive` 0x41A290 (`*(uint *)(param_1 + 0x48) & 0xfffffffe | param_2 & 1`); who calls it (manager focus change, vtable only: callers empty) was not traced (SPECULATIVE that it is the mouse-hover/pad-focus path).

**F2. Does DIMENSION shrink the fill? Yes, only with a CORNER image (CONFIRMED).** `CSWGuiBorder::Draw` 0x415300 initialises the four inset locals to 0 (decompile: `local_28 = 0; local_8 = 0; local_1c = 0; local_10 = 0;`) and fills them only inside `if (*(int *)(param_1 + 0x6c) != 0)`. Asm: `004153a0 83796c00 CMP dword ptr [ECX + 0x6c],0x0` / `004153a4 0f848c050000 JZ 0x00415936`. Inside, `FUN_00414980()` (DIMENSION) is called on `border+0x14` (`004153aa..004153b0`); if non-zero it is used for BOTH the corner width and height and for the edge step (`0041542a..00415447`: `EAX = DIMENSION -> [EBP-0x38] -> [EBP-0x3c] -> [EBP-0x50]`), otherwise the corner image's own size is used (`004153b9..00415428`). The fill rect is then (asm `00415955..00415985`):
`h = [this+0x10] - [EBP-4] - [EBP-0x24]`, `w = [this+0xC] - [EBP-0xC] - [EBP-0x18]`, `x = [this+4] + [EBP-0xC]`, `y = [this+8] + [EBP-4]`; i.e. inset = DIMENSION on each side. With no CORNER image the guard `JZ 0x00415936` skips the block and the fill uses the full extent (`[EBP-0xC] = [EBP-4] = 0`). FILLSTYLE (`+0x34 & 3`) then dispatches `0x415A60` (tile) / `0x415D20` (centre) / direct image draw (`00415991..004159ae`). INNEROFFSET is NOT used by the fill; it only widens the text rect in 0x414D80 (`local_54 = *(param_1+0x18)` ... `param_2[2] = local_2c + local_54 * 2`), which `0x419ED0` computes once in SetExtent, not per focus change. This resolves the open K1 question (DIMENSION vs edge texture) for K2: the inset is `DIMENSION` when non-zero (corner image size is irrelevant), and a block without CORNER has no inset at all.

**F3. DIMENSION is a raw pixel value; never scaled (CONFIRMED for this path).** `0x415080`: `uVar1 = FUN_00718c80(local_8,"DIMENSION",local_c,0); *(undefined4 *)(param_1 + 0x14) = uVar1;` (asm-level scaling is absent in 0x415080 and 0x415300: no FMUL/FILD of the manager size, no `fs` read). The user's generator never touches it: `grep -n -i "dimension\|inneroffset\|hilight" scripts/generate_ultrawide_gui_overrides.py` returns no DIMENSION/INNEROFFSET/HILIGHT hit (only `CORNER`/`BORDER` words in unrelated comments/FILL helpers at lines 22, 227, 430, 810-1026). The generator scales only EXTENT (L/W by 1/M, docstring lines 4-14). The engine stretch of the authored 800x600 extents to screen pixels is taken from the generator docstring ("engine stretches across the full display") and V4 (`widths ftol(w * W/800)`); where that scaling happens in code was not re-read here (SPECULATIVE detail, does not change the verdict). fs (`1 + 0.5*floor(max(W-1022,0)/1024)` = 2.0 at 3840x1600) is not used by any of 0x41A0A0/0x415300/0x415080/0x414D80.

**F4. Census of what is user-visible (computed from the user's install, pykotor read-only).** 159 distinct `.gui` (Override wins over chitin; 437 of the 1110 CONTROLTYPE==6 buttons come from Override, 673 from chitin). For each button: BORDER vs HILIGHT CORNER present?, DIMENSION, FILL.
- 369 + 204 buttons: identical state (no inset either way). 133: `uibit_fill_16gd` (dim 1) vs `uibit_fill_16t` (dim 2), FILL empty in both -> only the outline art changes, no fill to shrink.
- Fill drawn AND inset differs between states: **23 buttons**. (i) 17 in Override `galaxymap_p.gui` (`LBL_Planet_*`, `LBL_EbonHawk`, `GUI_slehe_1`, `gui_yavin_1`, `lbl_imana`, `lbl_itato`): BORDER = `uibit_brdr_clear`, DIMENSION 6, FILL = planet art; HILIGHT = no CORNER, DIMENSION 0, same FILL. Normal fill is inset 6 px per side, focused fill is the full extent. Vanilla chitin extent 32x32 (`LBL_Planet_Dantooine [469,105,32,32]`): 20 -> 32 px (+60%). User's override extent `[439,106,18,32]` (virtual units; x scaled by 1/1.8 by the generator) = 86.4 x 85.3 px at 3840x1600 (x 3840/800 = 4.8, y 1600/600 = 2.667): fill 74.4 x 73.3 px normal -> 86.4 x 85.3 px focused = +16% (the planet "pops" by 6 px each side). (ii) 6 chitin `inventory_x.gui` `BTN_FILTER_*`: normal has no CORNER/FILL, HILIGHT has `uibit_brdr_2wc` dim 2 + `uibit_gradient` fill: a 2 px inset gradient appears on focus, nothing shrinks.
- So at 3840x1600 the only focus-induced size change of a fill is the planet icon grow of +16%, smaller than at 800x600 (+60%) because DIMENSION does not scale. No K1-style "badge shrinks on focus" exists in K2 (no controller badges; the K1 badge was a FILL on the normal block with CORNER `boxline3` inset 6 vs a block with none).

### Part 2: texture residency / budget

**F5. Where the budget comes from (CONFIRMED).** `0x788D90` (called at startup; `callers=0073fad0`) reads `Texture Quality` from `.\swkotor2.ini` [Graphics Options] and calls SetTexturePack: asm `00789c01 CMP [EBP+0xfffffe34],0 / 00789c0a 83bd3cfeffff04 CMP dword ptr [EBP + 0xfffffe3c],0x4 / 00789c11 7d17 JGE 0x00789c2a` then `00789c13 6a00 PUSH 0x0 / 00789c15 0fb6853cfeffff MOVZX EAX,byte ptr [EBP + 0xfffffe3c] / 00789c23 e8783a0000 CALL 0x0078d6a0`; when the key is absent or >= 4: `00789c2a 6a01 PUSH 0x1 / 00789c2c 6a02 PUSH 0x2 / 00789c34 CALL 0x0078d6a0` (default quality 2). The user's `swkotor2.ini` has `Texture Quality=2` (line 35 of the file), so row 2. `0x78D6A0` rejects an index >= the 2DA row count (`0078d87e MOV EDX,[ECX+0x24] / 0078d8a0 3b9544ffffff CMP EDX,[EBP+0xffffff44] / 0078d8a6 0f8c89000000 JL 0x0078d935`, otherwise `return 0`), reads the four columns (`0078d935 6868f79900 PUSH 0x99f768` = "Texture", `0078d967 6864f79900 PUSH 0x99f764` = "Gui", `0078d999 6858f79900 PUSH 0x99f758` = "DynMemRatio", `0078d9cb 6854f79900 PUSH 0x99f754` = "Mem", strings read from the vanilla exe), mounts the Texture/Gui packs (`0x93C7A0(1, name)` / `(2, name)` after pushing the string `TEXTUREPACKS:` 0x99F744; semantics of 0x93C7A0 not read beyond its guard `if (param_1 < 4)`: SPECULATIVE that it registers the resource alias), then `0078db04..0078db17`: `FLD [EBP-0x20] / FSTP [ESP] / CALL 0x004218c0` (ratio) and `PUSH [EBP-0x34] / CALL 0x00427de0` (Mem). Return value of 0x427DE0 is discarded.

**F6. K2 splits the budget into two lists (NEW vs K1 doc).** 0x427DE0 (asm 0x427DE9..0x427EF6): `DAT_009f475c = Mem; dyn = round(Mem * [0x9F4758])`; then
`FUN_00427b60(&DAT_00a1bc38, dyn, &DAT_00a1bb64, _DAT_009f4760)` (list A, factor `[0x9F4760]`) and `FUN_00427b60(&DAT_00a1bc6c, Mem - dyn, &DAT_00a1bb88, 1.0f)` (list B). **F7. When enforcement runs, and the gate (CONFIRMED).** 0x427B60's only caller is 0x427DE0 (callgraph rows `00427de0 00427e64 00427b60`, `00427de0 00427e92 00427b60`); 0x427DE0's callers are 0x78D6A0 (`0078db17`), 0x93B650 (`0093b6eb`, init) and 0x426C30 (`00426c4c`, itself only called from GL context creation 0x476BE0 per W1). Nothing per frame: 0x427F30 (called every frame) computes `FILD [0x9F475C] / FMUL [0x9F4758] / FRNDINT / FISTP [EBP-8]` at 0x427F45..0x427F62 and never reads the result (dead store; no compare, no call to 0x427B60). Gate inside 0x427B60 (asm `00427b8e..00427be1`): `if (total <= param_2*param_4) timer = 0 else { timer += [0x9F62B0] (the last frame delta in seconds); over = 50.0 < timer }; if (over || param_2 < total) { loop }`. The timer `[0xA1BC14]` is touched only here and is zeroed by every call that fits; reaching 50.0 would need ~50 s of accumulated frame deltas over repeated over-budget calls, and calls happen only at startup / context re-creation / quality change, so the loop runs in practice only when `total > param_2` (the hard limit: A 100,663,296 / B 33,554,432 at Quality 2), then continues until `total <= param_2*param_4` (A 80,530,640 / B 33,554,432) or no candidate remains (`004268f0` false for every texture). Each iteration picks the candidate with the largest accounted size, `SetNewDownSampleLevel(1)` (`+0xC0++`, dirty flag) and re-adds the new size: pure bookkeeping. It terminates (candidates require `+0xC0 < +0xBC`, default max 15 from the ctor `004230ea b90f000000 MOV ECX,0xf / 004230f2 ... [EDX+0xbc]`, and `(w>>shift) > 2`).
When it runs on a populated list: SetTexturePack at runtime (options, 0x7856C0 -> 0x78D6A0, which also calls `0x427D90` Reset-all before) and GL-context re-creation (0x426C30). In both, 0x427DE0 first calls `FUN_00423990` (Reset) on EVERY texture then 0x427A70 force-constructs every texture (`CALL 0x00426270` at 0x427AE7) synchronously: a full-texture reload hitch, not a downsample (NEW detail; W1 covered the re-Demand safety of the context path, not the budget loops).

**F8.
