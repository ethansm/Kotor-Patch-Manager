## 2. Critical Bugs & Latent Vulnerabilities in Updated Code

### 🚨 Bug 1: Companion Profiles Orphaned on Load (Transient Object IDs)
* **Location**: [`ForcePowerHotbar.cpp#L238-L251`](file:///home/ethansm/orca/workspaces/local-setup/KOTOR-II/patch_manager_mods/force_power_hotbar_src/ForcePowerHotbar.cpp#L238-L251)
* **The Problem**:
  `computeCharacterKey()` falls back to formatting the creature's object ID:
  ```cpp
  unsigned oid = (unsigned)rdInt(c, 4);
  char b[24]; snprintf(b, sizeof b, "obj%08x", oid);
  return b;
  ```
  In KotOR II, object IDs are dynamically assigned heap indices. While the player character's ID is always `0xFFFFFFFD` (Exile), companions (Atton, Kreia, etc.) receive dynamic IDs (e.g. `obj80000249`, `obj80000240`) that change on every savegame load or module transition.
  **Result**: Custom companion hotbar bindings saved to `force_power_hotbar.ini` are permanently lost whenever a savegame is reloaded, because the companion spawns with a new object ID!
* **Architectural Fix**:
  Do not rely on creature tags or object IDs for companions. In KotOR II's `CSWPartyTable` (`party = *(*(app+4)+4)+0x270`), party members have **fixed, stable roster indices (0 to 11)**:
  * `0`: Atton
  * `1`: Bao-Dur
  * `2`: Mandalore
  * `3`: Mira
  * `4`: Hanharr
  * `5`: HK-47
  * `6`: Kreia
  * `7`: T3-M4
  * `8`: Visas
  * `9`: Handmaiden
  * `10`: Disciple
  * `11`: G0-T0
  Sample the controlled creature against the party roster table to resolve the permanent companion name (e.g. `[Profile.Atton]`, `[Profile.Kreia]`). This makes companion hotbar profiles 100% stable across saves and module transitions!

* **Resolution (2026-10-05)**: OPEN (partly mitigated) -- tracked in `patch_manager_mods/07_force_power_hotbar.md` (build 14 research notes, "Portrait-id key FAILED"), not in doc 24 HP4-HP7. Roster-index key rejected: `PartyTable::GetMember` indexes party positions, not the NPC roster (4f3726f). Portrait-id key (`+0xB8`) tried in 4f3726f, reads 0xFFFF on client creatures, removed as dead code in 9134fb5. Current key is still `obj%08x` (`HotbarLogic.h:61-69` `characterKeyFor`, `ActionHotbar.cpp:308`). Mitigation: companion ids were identical across sessions of one save, and per-save hotbar snapshots are restored on load (261a294, 706a6d3). Cross-save/party stability is unverified.

### ⚠️ Issue 2: Stuck Modifier Keys in DirectInput Hook
* **Location**: [`ForcePowerHotbar.cpp#L1024-L1031`](file:///home/ethansm/orca/workspaces/local-setup/KOTOR-II/patch_manager_mods/force_power_hotbar_src/ForcePowerHotbar.cpp#L1024-L1031)
* **The Problem**:
  `CaptureHotbarKey` tracks modifier states (`g_ctrl`, `g_alt`, `g_shift`) purely via DirectInput device events. If the player Alt-tabs, uses an OS shortcut, or releases Alt/Ctrl while a modal dialog or overlay is open, the key-up event is lost. `g_alt` or `g_ctrl` remains stuck `true`, causing all subsequent number key presses to trigger row 1 or row 2 actions instead of row 0.
* **Remediation**:
  Periodically resynchronize or verify modifier states using `GetAsyncKeyState`:
  ```cpp
  g_ctrl = (GetAsyncKeyState(VK_CONTROL) & 0x8000) != 0;
  g_alt = (GetAsyncKeyState(VK_MENU) & 0x8000) != 0;
  g_shift = (GetAsyncKeyState(VK_SHIFT) & 0x8000) != 0;
  ```

* **Resolution (2026-10-05)**: RESOLVED -- `GetAsyncKeyState` resync on digit key-down at `ActionHotbar.cpp:1693-1696` (only clears stuck flags); introduced in 404c5b8.

### ⚠️ Issue 3: Party Switch Fallthrough on Ring Buffer Overflow
* **Location**: [`ForcePowerHotbar.cpp#L1049-L1052`](file:///home/ethansm/orca/workspaces/local-setup/KOTOR-II/patch_manager_mods/force_power_hotbar_src/ForcePowerHotbar.cpp#L1049-L1052)
* **The Problem**:
  When a hotbar digit is pressed, the hook attempts to enqueue the action into `g_ring` (capacity 16). If the ring buffer is full:
  ```cpp
  int next = (g_ringHead + 1) % 16;
  if (next == g_ringTail) decision = "pass(ring full)";
  ```
  Passing the key through to the engine causes the engine to process the digit as a party selection command (keys 1–3), unexpectedly switching the active party member in combat!
* **Remediation**:
  Always swallow the key (`rec->dwOfs = 0; rec->dwData = 0;`) if it was bound to an active hotbar slot, even if the queue dropped the event:
  ```cpp
  if (next == g_ringTail) {
      logf("cap: ring full, dropping request but swallowing key");
      g_downSwallowed[dik] = true;
      rec->dwOfs = 0;
      rec->dwData = 0;
  }
  ```

* **Resolution (2026-10-05)**: RESOLVED -- bound keys are always swallowed when the ring is full: `ActionHotbar.cpp:1701` (`ke.ringFull`), `HotbarLogic.h:240` (`SWALLOW(ring full, request dropped)`), test `hotbar_logic_test.cpp:419`; introduced in 404c5b8.

### ⚠️ Issue 4: Window Subclassing Conflict with Mod 1
* **Location**: [`ForcePowerHotbar.cpp#L765-L778`](file:///home/ethansm/orca/workspaces/local-setup/KOTOR-II/patch_manager_mods/force_power_hotbar_src/ForcePowerHotbar.cpp#L765-L778)
* **The Problem**:
  Both `ForcePowerHotbar` and `Inventory3DViewport` call `SetWindowLongPtrA(..., GWLP_WNDPROC, ...)` on the main window.
  Neither DLL restores `g_oldProc` on `DLL_PROCESS_DETACH`. Unloading one DLL while the other is hooked leaves an invalid function pointer in the window chain.
* **Remediation**:
  Add `SetWindowLongPtrA(g_gameWnd, GWLP_WNDPROC, (LONG_PTR)g_oldProc)` on `DLL_PROCESS_DETACH` in `DllMain`.
* **Resolution (2026-10-05)**: RESOLVED -- guarded restore on detach (404c5b8), now via `kp::WindowHook` (`ActionHotbar.cpp:1018`, `WheelHook::uninstall` at :1865): restores only when still on top, otherwise stays chained but inert and the DLL image is pinned so the proc never dangles (c2be15c; `_shared_src/WindowHook.h`).
