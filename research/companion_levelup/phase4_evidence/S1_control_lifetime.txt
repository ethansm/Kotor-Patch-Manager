## Character panel (CSWGuiInGameCharacter, vtable 0x9A3E7C) destruction chain (C)
- 0x84DEF0 (scalar deleting dtor, slot 0): `call 0x84DF70` then `if (flags&1) operator delete(this)` (0x84DEFA..0x84DF0B), `RET 4`. Mod 14 hooks this entry (CharEffectsDestroy).
- 0x84DF70 (the real dtor body, 1872 bytes): sets the vtable, deletes the preview `(*vt[0])(1)` on this+0x4B6C*... (`param_1[0x12db]`, lesson 130), then runs the IN-PLACE member destructors in reverse order (CSWGuiLabel / CMFCToolBarButtonsListButton-named button members at fixed
  offsets, the 3D scene view at +0x3C24, `_eh_vector_destructor_iterator_` for the 6 x 0x148 array at +0x3E98), and last calls the base 0x40E860. It never walks panel+0x24 and never frees an element of it.
- 0x40E860 (CSWGuiPanel base dtor, 276 bytes): sets vtable CSWGuiPanel, deletes the objects at this+0x60 and this+0x30 (vtable delete, flag 1), calls 0x40F5A0 (StopLoadFromLayout: frees layout sub-object +0x30 if flag bit1), then `0x410670` only if the panel is registered
  in the parent GUI manager (+0x1C), then Free + vtable = CSWGuiObject. NO iteration over the control array at +0x24, NO free of the array buffer (the CExoArrayList {ptr,count,cap} has no dtor call here).
  => entries in panel+0x24 are borrowed pointers: native controls are EMBEDDED members (destroyed by 0x84DF70's member dtors), heap controls like ours are never freed by the engine; the array buffer itself leaks (lesson 75).
- Panel lifetime: the character panel is created lazily ONCE per GUI init: 0x7CB7C0 `if ([guiInGame+0x14] == 0) { new(0x4B7C); 0x84C3A0(this, [gui+0x38]) ; [gui+0x14] = panel }` (0x7CB88C..0x7CB8D9). It is reused on every open and
  re-created only when the in-game GUI is rebuilt (load / new game / resolution rebuild) - then the old one goes through 0x84DEF0 (I: from lesson 130 + doc 14 hooks 0x84D871 ctor / 0x84DEF0 dtor firing together on load).
## Ownership rule (recommended)
 1. **Never free our labels, never free from the engine's dtor path.** Same policy as Mod 1 / Mod 3 (shipped, Phase F reviewed): create with `new(0x148)` via the engine allocator 0x919723 (FnNew), append once, leak at panel death (a few hundred bytes per rebuild).
    Freeing is unsafe even from a 0x84DEF0 hook: the label's border holds a POOLED image pointer (+0x74, shared per resref via 0x47EB60), and the label dtor chain (0x417290/0x414C60/0x418640) would release it -> double free / dangling for every other holder (Mod 3 Phase F item (4) "shared-image ownership invariant").
 2. Appending IS safe (nothing iterates ownership): Draw 0x40EC90 and hit-test 0x40EAE0 walk the list only; the panel dtor ignores it. Do it ONCE per panel instance: key our state on the panel pointer, rebuild on the ctor hook (0x84D871, panel = [ebp-0x254]) and drop it at the dtor hook 0x84DEF0 (ECX = panel) WITHOUT freeing; every tick (Update 0x84FBB0 hook) refuse to touch labels whose panel != the panel seen at the last ctor.
 3. Never append before the panel's own ctor binds finished (append after the last native bind, at the same ctor hook point as Mod 14's bind: `Panel_CtlCount` read at runtime, id = index) and never after StopLoadFromLayout has freed the layout struct (templates are read through InitControl, which needs the layout still loaded: do all InitControl calls at the ctor hook BEFORE 0x40F5A0 runs at 0x84D877, as Mod 3 does at 0x748502).
 4. Do not reuse a label across two panel instances (the old panel's list array is freed/leaked independently; a stale pointer in a new panel would be drawn after the old owner is gone).
