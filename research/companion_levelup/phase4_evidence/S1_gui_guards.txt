## How the panel finds its creature (C)
- SetStats 0x84E6F0: `party = 0x73FB90(ECX=[A1B4A4]+4)` (= *(*(clientApp+4)+0x270), 0x73FB90 disasm), `entry = 0x7E5DA0(party, idx=0)` (push 0; 0x7E5D80 is the same with idx 0), `creature = 0x77D800(entry)`,
  `stats = *(creature+0x1198)`. Index 0 = party LEADER (the screen shows whoever leads; doc 14 confirms). StartAutoLevelup (0x84FE62) and DoAutoLevelup (0x850054..0x850062) use the identical chain; the
  panel stores nothing for it. ShowLevelUpGUI itself builds CSWGuiLevelUpCharGen for the leader via 0x8F4AF0(panel+0x1C, 0x73F450()+4, panel+0x4B6C) (I: creature = the preview at panel+0x4B6C).
- A handler therefore gets the creature either by calling the same three engine functions (typed pointers: 0x73FB90 thiscall(ecx), 0x7E5DA0 thiscall(ecx,int) RET 4, 0x77D800 thiscall(ecx)), or - at
  0x850062 - as the return value of 0x77D800 itself.

 Handler for the first two: `uint guard(ecx /*clientApp*/, ebp)`: r = real 0x740FC0(ecx); if (!r && held(leaderCreature)) return 1; return r;  leaderCreature via the 3-call chain above.
 Why not hook the entry calls themselves (0x84F9BD / 0x84FA17 / 0x7CB8E6): ShowLevelUpGUI has a pushed arg + `RET 4`, so skipping the call at 0x84F9BD or 0x7CB8E6 would leave the argument on the stack (imbalance); 0x84FA17 has no args but is the only Auto entry and 0x84F9FE
 covers it earlier. The 0x740FC0 guard calls are exactly the engine's own "refuse" gates, so the veto looks like a vanilla refusal.
 Side effects (C): with a 0x84F9A2/0x84F9FE veto the click sound call 0x4122A0 is skipped too; with only the 0x84FD2F guard the sound plays and nothing opens (harmless).
 With 0x84FD2F, 0x7CB7C0 (script path) still runs `0x73FEE0(2,1)` after ShowLevelUpGUI returns 0 (opens the character screen) - acceptable.
