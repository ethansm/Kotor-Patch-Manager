## 1. Hover -> tooltip path

CONFIRMED (D:004113a0, D:00412c00, D:00413c50, D:00419420, D:00413e90, D:0075ff50):

1. `CSWGuiManager::HandleMouseMove` Steam 0x412C00 [0x911080]: stores mouse x,y at `mgr+0x00/+0x04` (the global `0xA1B49C` = GUI_MANAGER_PTR holds the manager; confirmed by the live DB row GUI_MANAGER_PTR=10597532=0xA1B49C), then `FUN_00411030` hit-tests: top of modal stack (`mgr+0x94` list, `+0x98` count) else `mgr+0x88` panel list (`+0x8C` count) from last to first, calling **panel vtable +0x40 (HitCheckMouse)**. Result control -> `mgr+0x08` (mouse-over control). If it changed: remove current tooltip (`0x413F00` [0x912380]) and restart timer via `0x413FE0(0)` (sets `mgr+0x44 = 0.0` when the Enable Tooltips option is on, `mgr+0x4C = 0`).
2. Per frame, `CSWGuiManager::Update` Steam 0x4113A0 (D:004113a0, tail): if `FUN_00741290()==0` (game-state gate, meaning not decoded: HYPOTHESIS "suppressed in some modes") and `mgr+0x44 >= 0.0` then `mgr+0x44 += dt`; when `mgr+0x44 > mgr+0x48` (**appear time at mgr+0x48**) and `mgr+0x08 != 0`: calls **mouse-over control's vtable slot 36 (+0x90) = DisplayToolTip**; on non-zero return `mgr+0x40 = mgr+0x08` (tooltip owner); timer set to -1.0 (`0x987474`) so it shows once per hover.
3. Base `CSWGuiControl::DisplayToolTip` 0x419420: text source = **`ctl+0x28` int TLK strref** (if non-zero, `GetSimpleString`) **else `ctl+0x2C` inline CExoString** (`{char*,uint}`). If strref==0 AND the CExoString is empty (`0x733A60` = CExoString==char* ; true for null/empty) it **delegates to the parent control** (`ctl+0x18`) vtable +0x90 and returns that result (0 if no parent) -> nothing shows. Optional: `ctl+0x34` = action id -> 2DA row `KeyNameStrRef` -> appends the bound key name (second line). Then `mgr->ShowToolTip(&text)` Steam 0x413E90 [0x912310], then `ctl+0x48 |= 0x40` (tooltip-shown flag; HandleMouseOver 0x419060 clears it on leave), returns 1.
4. `0x413E90`: only if `mgr+0x4C == 0` and client-options flag `[[0xA1B4A4]+4 -> GetClientOptions 0x72FB00] +0x1C bit10` (Enable Tooltips option, string "Enable Tooltips" at 0x9A00B8) is set: `mgr+0x1C |= 8`, `tooltipPanel(mgr+0x3C)->SetText (0x75FF30 -> CSWGuiText::Set 0x416E30)`, `0x75FF50` positions/sizes it.

Control types taking part: any control whose vtable slot 36 is the base. **CSWGuiLabel vtable Steam 0x9878BC slot 36 = 0x419420 (base)** (steam_r2.txt 3566+; GOG 0x98998C slot 36 = 0x9176C0). Overrides exist for the portrait char button (0x744B40 family, `+0x1D4`) and `CSWGuiListBox::DisplayToolTip` (Steam 0x420F10, forwards to a child; GOG 0x91EE10). Buttons: not checked individually (HYPOTHESIS: inherit base like the label).

"Has a tooltip" = (`ctl+0x28 != 0`) OR (`ctl+0x2C` non-empty) OR (`ctl+0x34` action key) OR (parent has one). No per-control enable flag in the base path. Default-constructed controls (ctor 0x418990) have strref 0, empty string, action 0, so no vanilla label shows anything. Who fills `+0x28/+0x2C` in vanilla layouts: NOT determined (HYPOTHESIS: GFF Load of specific controls or code setters; not needed for our use).

## 2. Can a GuiKit label show one by setting the string?

- Hit-tested by the manager: **CONFIRMED yes, if visible and click-through cleared.** GuiKit `appendToPanel` writes the panel control list (`panel+0x24` ptr, `+0x28` count). Panel HitCheckMouse Steam 0x40EAE0 [0x90CF60] (D:0040eae0) iterates exactly that list in reverse (last = topmost) calling control vtable +0x44. Label HitCheckMouse 0x418D20 [0x916FC0] (D:00418d20) returns the control iff `flags(+0x48)` bit1 set AND bit5 clear AND cursor inside `ctl+4/+8/+0xC/+0x10` (panel-local coords). GuiKit `setVisible(true)` already sets bit1 and clears bit5 (`GuiKit.h:229`); hidden/click-through controls (bit5 set, bit1 clear) are skipped. Our appended controls are last in the list, so they win over native controls they overlap (side effect: a clickable label hides the native hover/highlight of controls under it).
- Hover-enable flag needed: **none beyond bit1 set / bit5 clear.** (The bit1 test inside the portrait override 0x516140 is that class only.)
- What to write: **`ctl+0x28 = 0` (explicit; ctor zeroes it, `InitControl` template load not verified to leave it 0) and a CExoString at `ctl+0x2C`**. The field is a constructed empty CExoString, so `g_gk.exoCtor(ctl+0x2C, "text")` (GuiKit already holds the engine CExoString ctor 0x733570 for template tags) is leak-free for the first set; to change text later use the engine assign/ctor-after-dtor pair (`exoDtor` 0x733780 then `exoCtor`). `\n` for multi-line (portrait tooltip format string uses `\n`, D:0075ff50 sizes from the text object's ideal size). Leave `ctl+0x34 = 0`. Parent `ctl+0x18` should stay 0 (InitControl addToList=0 sets parent only via GFF `Obj_ParentID`, template has none) so no delegation.
- Remaining uncertainties (HYPOTHESIS, hence the probe): (a) the character-screen panel may override vtable +0x40 or not be the hit-tested panel (modal stack top / panels order); (b) `0x741290` gate; (c) user's Enable Tooltips option off -> by design no tooltip; (d) coordinate space: the manager hit test subtracts the panel offset and the 640x480 centring (`0x40EAE0` uses `(W-0x280)/2`, `(H-0x1E0)/2` for non-fullscreen panels) so native hit-testing compares in panel-local coordinates, same space as the control ext values, so it should be MORE reliable than GuiKit's own OS-cursor `hit()`.

## 3. Where the tooltip draws

CONFIRMED (D:0075ff50, gog_r1.txt PositionToolTip 0x531550): panel at **cursor + (15,15)** (cursor = `mgr+0/+4`, engine pixels), size = text ideal width/height + 8 (auto-sizes; no wrap limit seen, long lines widen the box), **clamped to the screen**: `x = W - w - 2` / `y = H - h - 2` where W,H = `0x9F42A4/0x9F42A8` (Steam; same framebuffer globals GuiKit uses). Panel = `mgr+0x3C`, a `CSWGuiToolTipPanel` (ctor Steam 0x75FDA0 [0x5313A0], layout "tooltip"; label at panel+0x1A8, frame at +0x68). Z-order: drawn in the manager Update after all panels and the overlay object (D:004113a0: `if (mgr+0x1C bit3) (*(mgr+0x3C)->vtbl+0x34)(dt)` after the panel loops), so it is on top of every panel including the character screen's 3D column and BTN_AUTO. CONFIRMED order in code; "above the 3D view" is HYPOTHESIS only because the 3D scene view draws inside its panel pass (not live-observed). The shield-bar mod already relies on this same panel live (docs 08 "Session 4": `Shield: cur/max` appended to the portrait tooltip, 275 TIP log lines, works).

## 4. Existing GameAPI wrapper usability

- `CSWGuiControl.h:43` `DisplayToolTip` is only a vtable-slot enum name (no wrapper function, no tooltip-string accessor). `CSWGuiManager.h:26-28` `Get/SetTooltipAppearTime` and `CClientOptions` `GetTooltipDelay` need address-DB offset rows. **CONFIRMED missing**: both `AddressDatabases/kotor2_steam_aspyr.db` and the live `addresses.db` have 21 offsets, none for CSWGui*/tooltip; `CSWGuiManager::InitializeOffsets` (`CSWGuiManager.cpp:44-60`) requests `tooltip_appear_time` and catches the throw, so `offsetsInitialized` stays false and the accessor returns a default. Live DB: 48 functions, 14 globals (GUI_MANAGER_PTR is present).
- Build: GameAPI is compiled into `Common.lib` by `create-patch.py` for every Windows patch, but **none of our mods use it** (rg across `patch_manager_mods`: zero GameAPI includes). Upstream users: ModOptions, Snake, K1GUITests, ExpandedVanillaOptions, ScriptExtender, etc. Our mods use the repo-local `_shared_src` (GuiKit.h, GameAddr.h, K2Addr.h, SafeRead.h) with raw verified Steam addresses and `saferead`.
- Recommendation: do not pull in GameAPI. Write `ctl+0x28/+0x2C` directly via a small `GuiKit::setTooltip(ctl, text)` helper using the existing `exoCtor/exoDtor` Engine fields; read `mgr = *(uintptr*)0xA1B49C` (`gameaddr`/K2Addr global) for probe logging. Appear time is `mgr+0x48` (read-only here; do not change the user's setting).

## VERDICT: NATIVE+PROBE
Static path is complete and consistent (label slot 36 = base DisplayToolTip, panel-list hit test, text at ctl+0x2C, auto-sized cursor-relative top-most panel), but nothing has been observed live for a GuiKit control, and the panel-level hit-test/gate (Q2 a,b) are unverified.

### The probe (log-only, add to the character-screen mod's per-frame hook, once per state change, behind the existing probe flag)
1. After creating and appending the label and showing it (bit1 set, bit5 clear): `*(int*)(ctl+0x28)=0`; `exoCtor(ctl+0x2C, "Native tip test\nline 2")`.
2. Each frame read (via `saferead`, no calls into the engine): `mgr=*(u32*)0xA1B49C`; `over=*(u32*)(mgr+0x08)`, `owner=*(u32*)(mgr+0x40)`, `timer=*(float*)(mgr+0x44)`, `appear=*(float*)(mgr+0x48)`, `mflags=*(u32*)(mgr+0x1C)`, `disabled=*(u32*)(mgr+0x4C)`, `ctlFlags=*(u32*)(ctl+0x48)`, mouse `*(int*)(mgr+0)/(mgr+4)`.
3. Log a line only when any of {`over==ctl`, `owner==ctl`, `(mflags&8)`, `(ctlFlags&0x40)`} changes: `TIPPROBE over_is_ours=%d owner_is_ours=%d shown=%d ctl40=%d timer=%.2f appear=%.2f dis=%u mouse=%d,%d`.
4. Pass criteria: hover the label for > `appear` seconds -> `over_is_ours=1` then `shown=1 owner_is_ours=1 ctl40=1` and the user sees the engine box next to the cursor, clamped at screen edges, above the 3D column. Diagnosis table: `over_is_ours=0` -> hit-test never reaches the label (panel vtable +0x40 override/modal order; fall back to CUSTOM or hook that panel); `over_is_ours=1` but `shown=0` and `timer<0` -> `dis=1` or Enable Tooltips off or gate 0x741290; `over_is_ours=1`, timer stuck >=0 below `appear` -> gate 0x741290 true (log it with a read-only call later).
5. Then remove the test string, set the real strings, keep the probe lines for one release.
