## FeedbackMessage(0xb) as used by SetExperience
- SetExperience 0x6B6BD0 thiscall(stats, newXP, flag). Sequence (U2_raw_disasm_setexp.txt, U2_raw_disasm_setexp2.txt): 0x6B6EAA `cmp [ebp-0x18],0` ([ebp-0x18] = 0x51C600(creatureId) = "creature is a player-controlled creature", decompile U2.. dec_b2 local_1c) ; 0x6B6EB6 CanLevelUp(ecx=stats) ; XP-before < table[level] (just crossed the next threshold) ; then **0x6B6F0B push 0 ; push 0xB ; ECX = *(stats+0x24) (server creature) ; 0x6B6F13 call 0x584DA0**.
- **0x584DA0 = SendFeedbackMessage (SERVER)**: `thiscall(ECX = server creature, u16 feedbackId, payload* or 0)`, RET 8 (U2_raw_decomp_1.txt:35-82). 0x51C600(creature+4) -> 0x52F330 = player-list lookup (only the CONTROLLED creature has a player; DB lesson 198) else NOTHING is sent. payload==0 -> it allocs new(0x34)+0x5E2540 itself; stores feedbackId at int[9] (0x5E1BD0(9,id)); sends via 0x648CC0(playerId = *(player+4), minor 0xB, payload, 0) (= ClientSideMessage major 0x12 minor 0xB serializer, case 0xB U2_raw_decomp_2.txt:306, string[0] serialised for id 0xCC at ~line 405); then ALWAYS frees the payload (0x5E25D0 + 0x9196FD). It is queued in the net ring and handled next frame by the client.
- CLIENT side: dispatcher 0x810CF0 -> 0x816400 (minor 11 case 0x81E622) -> switch(feedbackId-1) (byte table 0x828730, dword table 0x8286B4). id 0xB is NOT a case (index 30 -> default 0x821423) and default = `0x73F100(id, 0, "")`; id 0xCC -> case 0x81FB5E: reads the string, builds a fresh payload (string[0]) and calls 0x73F100(0xCC, payload, "") (U2_raw_disasm_client_cc.txt:1-120 / 121-160).
- 0x73F100 (U2_raw_decomp_3.txt:45, U2_raw_disasm_73f100.txt) = client AddFeedbackMessage: `thiscall(ECX = CClientExoApp, u16 id, payload*, CExoString* extra)` RET 0xC. -> 0x78F160 (30 KB switch on id, ECX = *(clientApp+4) = CClientExoAppInternal). case 0xB: text = TLK strref 0x59E (= 1438, "Your character has gained enough experience to advance a level.", verified in dialog.tlk, U4_raw_classes_tlk.txt). case 0xCC: text = payload.string[0] (0x5E2690(payload,0)). Tail: if text non-empty -> 0x7BE090(ECX = GuiInGame = *(internal+0x40), CExoString* text, 0x80, 0) (or 0x7BE1B0 for the second list) = append to the on-screen feedback list (16-byte entries, cap 0x3F, oldest dropped) (U2_raw_disasm_78f160_tail.txt:48-75, U2_raw_decomp_5.txt). The tail also FREES the payload (0x79671E 0x5E25D0 dtor + 0x9196FD free) -> payload ownership passes to 0x73F100.
- Consequence: for a held creature the vanilla message 0xB can still fire (SetExperience's CanLevelUp calls 0x6B6E33/0x6B6EB6 are not vetoed) but only for the controlled creature and only when XP crosses a threshold; companions never get it.

## The custom-string API (what vanilla SendMessageToPC does)
- Script command SendMessageToPC 0x690A90 (U2_raw_decomp_1.txt:84-150, disasm 0x690B1C..0x690BC3 in U2_raw_disasm_setexp2.txt:50-80): pops object id + string, creature = 0x51C100 (server GetCreature by id, ECX=[[0xA1B4A4]+8]); `p = new(0x34); 0x5E2540(ECX=p); 0x5E1CB0(ECX=p, 0, CExoString* s); 0x584DA0(ECX=creature, 0xCC, p)`. 0x5E1CB0 = thiscall(payload, int idx, CExoString*) RET 8 (copies the string into the string array at +0x1C, growing via 0x40DFE0).
- Two usable routes:
  (A) **CLIENT direct (recommended)**: build the payload as above (p = cdecl 0x919723(0x34); 0x5E2540 fastcall ECX=p; 0x5E1CB0 ECX=p idx 0 &text), `extra` = an empty CExoString (0x733570(ECX=buf,"")), then
      `thiscall 0x73F100 (ECX = clientApp, push extra, push p, push 0xCC)` RET 0xC. clientApp = *(*(0xA1B4A4) + 4) (0x8289A0 = `return *(ecx+4)`; exactly how the engine does it at 0x81FCAE/0x81FCB4). NO player/controlled-creature requirement, works for companions, no network hop, immediate. Free the CExoStrings you built with 0x733780; DO NOT free p (callee frees it). Guard: clientApp != 0, internal = *(clientApp+4) != 0 and *(internal+0x40) (GuiInGame) != 0 before calling (0x78F160 derefs it unchecked) - e.g. not on the main menu / during load.
      Even simpler fallback: 0x7BE090 thiscall(ECX = *(internal+0x40), CExoString* text, int 0x80, byte 0) RET 0xC (adds the line directly; no payload).
  (B) server replica of SendMessageToPC: 0x584DA0(ECX=creature, 0xCC, payload) - only reaches the player for the CONTROLLED creature (use the leader's server creature = 0x77D800(0x7E5DA0(0x73FB90([A1B4A4]+4),0)), the same chain as the GUI guards) and queues through the net ring. Works but needs the leader object and is deferred a frame.
- Rate limits: none in the engine except the list cap 0x3F (older lines shift out, 7BE090). Every call adds a line -> the mod must gate (once per XP-award event / once per change of the banked count; never per tick). Display duration/fade is handled by the GUI list (not examined).

## Call context recommendation
RECOMMEND route (A) 0x73F100(0xCC) called from the SERVER XP-award hold gates (0x5FD7CE XP tail, 0x5FE2A3 DistributeExperience, 0x66C95C AddMultiClass): they fire once per XP grant, exactly when levels get banked, and the creature there = *(stats+0x24) gives the tag for the text ("<Name> is holding N levels for <Jedi class>"). The same process runs server+client on one thread (0x690A90 does the equivalent server-side), so a direct client call is safe; keep the null guards. Do NOT call from the per-tick sites (0x74F3C7 portrait tick, 0x84F221 SetStats) unless the DLL de-duplicates by (tag, banked count).
Uncertain: (1) behaviour of 0x73F100 when called during the server tick before the client finished a frame (I: fine, same thread); (2) on-screen duration and colour of the list line (flag 0x80 fixed in the engine path); (3) whether the 0x7BE090 list is the one drawn in the CURRENT GUI skin (the engine uses it for all non-combat feedback, so yes I).
