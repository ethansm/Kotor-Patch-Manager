## 2. Decisions (OPEN items from T1a/T1b/T1c)

- D1 (which signal): window = server state `+0x520==1 && byte(+0x11E8)==2 && client +0x138==0 && (( +0x528==0 && 0<+0x524<=8000 ) || +0x528!=0)`. Reuse the +0x524 countdown; no hook (T1c C accepted). The `+0x528!=0` arm is new: it is the script "fake combat" hold ((1,2,1)), which the DELAY gate never cuts and the engine never expires, so the script owns its end; without this arm a scripted fake-combat pose would show the weapon on the hip.
- D2 (where to evaluate): inside HolsterPlace at the draw gate, lazily, only when `readable && combat==0 && !holdActive` (the common out-of-combat case short-circuits first). No per-slot arrays written by runDelay, no 100 ms latency, independent of combat_exit_ms/flourish_exit_ms. Reasons: the flourish animation is 1500 ms (0x27AE, 0x5DC), a 100-350 ms stale window pops the weapon from the hip visibly; reading is 5 dword reads on a cached server pointer (cheap, no engine call).
- D3 (T1a O1 / T1c NPCs, enemies): window applies to the 3 party slots only (owner pointer == g_party.cli[i], srv from the cache, id re-checked like runDelay). Non-party NPCs/enemies keep today's mod behaviour (hip when client flag 0): (a) only the PC can trigger 0x79F430; (b) the DELAY cut and hostile scan exist only for party slots, so an NPC window would run the full 8 s with no exit; (c) enemies reach (1,2,0) through 0x57AC30 alerts and would draw before attacking, which changes combat readability; (d) calling 0x77D800 per frame per NPC adds engine calls with a miss side-effect. Scripted NPC flourishes (cmd 847, cutscenes) stay on the hip: documented gap, follow-up WI "NPC window with 100 ms TTL cache" only if play shows it.
- D4 (width, T1a O2): mask the byte in pure code: `stanceByte(raw) = raw & 0xFF`, used by delayGate and the new predicate. This also fixes HD2 for creatures with dirty padding. Read site stays a dword read (in-bounds, safe).
- D5 (+0xD0 unit, T1b gap 1): ms, see claim 11; confirm with HD1.
- D6 (T1b gap 6, stance follows +0x520 vs wield byte +0xC5): not decidable statically. Window follows +0x520/+0x524; HD2 notes the observed stance end. If the stance outlasts the cut, widen by holding the window until the stance anim ends (not planned).
- D7 (T1b gap 7 detour choice E1 A/B vs E3 opt 2; stolen bytes at 0x57A560): DROPPED. No detour at 0x57A560 or 0x79F621. A call-site detour would miss the script path and the AIUpdate exit; a function-entry detour needs a full reinstall and a server->client reverse map for no gain.
- D8 (T1b gap 4/5/9, caller of 0x8993F0, kind=flourish mislabel, 0x7680A0): not blocking. The `kind=` label is only `combat != 0 ? combat : flourish`; documented in R3 below.
- D9 (re-holster): no code needed. After the window closes (cut writes 0, or expiry) HolsterPlace writes the hip pose again on the next frame; the pose snaps back as it does after combat today. Expected timing: flourish anim 1500 ms, DELAY cut at elapsed >= 1500 plus up to 100 ms tick = weapon returns about 1.5-1.6 s after the press.
- D10 (config): new ini key `flourish_draw` (default 1; 0 = old always-hip behaviour) as the escape hatch for R2/R3.

## 6. Risks

- R1: lazy read per weapon Gob per frame (5 dword reads, party only after a 3-compare scan, only when combat==0). Expected well below frame noise; if frame time moves, add a 16 ms per-slot cache. Failure mode: any unreadable value = window closed = hip (the safe/current direction).
- R2: false-positive windows (claim 8): equip-from-inventory, ally alert broadcast (0x57AC30), upgrade UI. All draw the weapon for up to 1.5 s (party, DELAY cut) or up to 8 s if a hostile is within 30 m. Cosmetic; `flourish_draw=0` is the escape hatch. Area load equip is the one to watch (FL4b); unknown what InGameGui+0xCC means (EquipItem gate).
- R3: `DELAY kind=flourish` label is a client-flag test (Holster.cpp:643) and will also tag the alert/equip cases; do not read it as proof of a keypress flourish. Use `FLOURISH` + play context.
- R4: owner pointer identity: `[par+0x1D8]` must equal `party::member(t,i)`. Evidence is indirect (the drawgate flips on the client +0x138 live). FL1 verifies; if no match the window stays closed (fail-closed) and `FLOURISH` never logs.
- R5: DELAY cut and HD1-HD3 have never run live (T1b gap 2); the cut closing the window at about 1.5 s depends on HD1/HD2 behaving as designed. If the stance anim outlasts the cut the weapon re-holsters mid-pose (D6).
- R6: the party cache is refreshed every 250 ms; a swapped party member inside that gap gets no window for up to 250 ms. Cosmetic.
- R7: held stance arm (`+0x528 != 0`) is script-driven and is never cut by DELAY; a script that never ends the fake combat keeps the weapon drawn (same as vanilla). Only SetFakeCombatState produces it among the six callers.
- R8: `holsterTick` runs from HolsterGobUpdate (0x5047B0 event handler); if that hook does not fire reliably the party cache goes stale and the window stays closed (fail-closed).
