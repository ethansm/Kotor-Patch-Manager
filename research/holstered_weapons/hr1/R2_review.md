# R2 review: HW9 draw/stow slide (topic 2). Reviewer: Sonnet, read-only, 2026-10-20

Base H = patch_manager_mods/holster_src/. Inputs: T2a, T2b, T2c, T4 (context only). Everything below was re-read in the repo; "UNVERIFIED" = no anchor or measurement exists.

## 0. Verdict in one paragraph

The recon is sound on facts but the wiring sketch (T2a W2-W4: add `hs::Fsm` to `Ent`, call `onCombat(hip?0:1)` with a `stowDelay` parameter) has three defects that must not ship: (B1) the 1.5 s `kStowDelayMs` stacks on `combat_exit_ms`; (B2) `Fsm::onCombat` restarts at fraction 0 on re-entry (hand -> hip snap); (B3) a new `Ent` created while already in combat (area load, cache eviction, recycled gob address) would play a bogus hip -> hand slide. Recommended design: do NOT drive the render path from `Fsm`; add a ~16-byte `hs::Slide` follower in `HolsterSlide.h` that low-pass-filters the existing gate boolean (`hip`). It is continuous by construction, has no stow-pending state (so the T4 `onSwap` bug cannot occur), and uses a signed-delta clock. `Fsm` stays untouched here (topic 4 owns its fix or retirement).

## 2. Decisions (every OPEN in T2a / T2b / T2c)

D1. Stow delay (T2a F1, T2b stow timing): `stowDelay = 0` for the drawgate. The slide follows the gate boolean directly; `combat_exit_ms` (default 1500, clamp 200..7800, 0 = vanilla 8 s) stays the single user-facing "how long after calm" knob. Do not add a second delay. F8 stow (holdUntil = now) and the corpse path (0x807962 immediate clear) then slide at once, which is what the user expects from an explicit key. Result: weapon in hand again ~1.5 s after calm, holstered ~1.85 s.

D2. Durations: new ini keys `draw_slide_ms` default 350, clamp 0..570 (0 = off = today's instant behavior, doubles as kill switch); `stow_slide_ms` default 350, clamp 0..1000 (0 = instant). Draw ceiling 570 = vanilla draw_weapon window end. Full-travel time; a retarget from fraction f takes `ms * |target - f|` (constant speed, no slow tail).

D3. First evaluation and owner change (new, not in recon): when `ent->gate.hip < 0` (first eval) or `ent->gate.owner != owner` (recycled address, new owner), set the slide silently to the current gate state (hand = 1 or hip = 0), no slide. Also silently set to hand when the owner is unreadable (fail-safe, matches `!readable -> hip=false`). Only real transitions seen on a live Ent animate.

D4. Clock and pause (T2b OPEN, T2c #11): wall clock via QPC converted to uint32 ms (`slideNowMs()`), not GetTickCount, not the engine round clock. A slide is purely cosmetic; it should run during pause (an F8 key press polled in H7 while paused should give visible feedback). Whether H7 runs while paused is UNVERIFIED but harmless either way: if it does, the slide finishes on wall time; if not, nothing is written, the last written pose stays on the Gob, and the first call after resume sees `now - t0 >= len` and lands on the endpoint (one-frame jump of at most the hip-hand distance, cosmetic). Add the gap guard (step 3): if the Ent was not seen for > 100 ms mid-slide, shift `t0` forward by the gap so the slide resumes from where it froze instead of jumping. No server pause flag read (would add a new CServerExoApp+0x10078 dependency).

D5. Keying (T2c open question): per-`Ent` (existing key node + gob + handle), one `Slide` per entry. Reasons: the hand is already part of the key (rhand and lhand are separate Ents), lifetime equals the Gob (weapon swap = new Gob = new Ent = silent init), no new table or eviction logic, no object-id lookup. Both hands run on the same gate predicate and the same clock so they stay in step within one frame (<= ~16 ms). Per owner+hand would need a second cache with its own eviction and no despawn signal. Size: `Slide` 16 B (float from, uint32 t0, uint32 len, uint8 dir+init) + 4 B lastSeen = 20 B; `Ent` grows 128 x 20 B = 2.5 KB static. Hot-path lookup cost unchanged (existing 128-entry linear scan). Cache eviction (round-robin, 128) mid-slide re-inits silently: worst case one 350 ms slide snaps once in a crowd of > 128 weapon Gobs; accepted, noted in Risks.

D6. Re-entry mid-stow (T2a F2, T2c #7): fraction continuity. In `Slide::target(dir, now, ms)`: `from = frac(now); dir = d; t0 = now; len = ms * |d - from|` (rounded, min 1; 0 if ms == 0). Draw at 0.5 stays at 0.5 and continues; there is no jump at the edge. For the legacy `Fsm` (only if topic 4 keeps it): `onCombat` edge computes `f = handFraction(now)` then `phase = PhDrawing; phaseLen = kDrawMs; phaseStart = now - (uint32_t)(f * kDrawMs)`; from PhDrawn f = 1 so it stays in the hand; update holster_logic_test.cpp:157 to assert `handFraction == 1` instead of `phase == PhDrawing`.

D7. Hand end of the blend: the raw `in` (engine hand pose, no placement). Hip end: `applyPlacement(mountPose, pl)` exactly as shipped. Ease: `easeSmooth(frac)` before `blendPose`. At frac 1 return without writing (identical to today's drawn path); at frac 0 write the pure hip pose (identical to today's hip path), so both ends are bit-identical to the current behavior.

D8. In-combat weapon-set swap (Fsm `kSwapMs` 1000): not modeled. Out of scope; new Gob = new Ent = D3.

D9. Dead/ghost corpses: no special handling. The flag clear at 0x807962 flips the gate; the slide just softens what is today an instant jump.

## 6. Risks

1. H7 call rate: if the attach refresh is sparse (C4 item 5 unknown), a slide has few steps and could stop mid-way until the next call (the last written mid pose persists on the Gob). Mitigation: the F8 poll evidence says calls are frequent; `frames=` in `SLIDE end` measures it; kill switch `draw_slide_ms=0 stow_slide_ms=0`.
2. Straight-line blend hip -> hand can pass through the leg or torso and nlerp of far-apart orientations rotates quickly mid-way (cosmetic). Tune with `easeSmooth` only; do not add arc paths in HW9.
3. Cosmetic mismatch during the first 350 ms of combat: the attack animation's hand swings while the weapon is still travelling. By design (draw never delays an attack); the user can set `draw_slide_ms` lower.
4. Cache eviction at 128 Ents and recycled (node,gob,handle) triples: Slide re-inits silently (D3), one snap at worst. Pre-existing weakness: a stale hit also reuses the old `mname`/category (the owner-change reset does not refresh them); out of scope.
5. Pause: wall clock may animate during pause or jump on resume (D4); cosmetic. Gap guard handles the resume jump.
6. Fsm becomes unused by production after this change: it keeps its failing edge cases (T2c probes A-F, T4). Topic 4 should either fix it per D6 or delete it and its tests so nobody wires it later; leaving both a tested-but-dead Fsm and a live Slide is a drift risk.
7. Unverified: blur/trail effects reading the weapon Gob transform; Translate/Rotate behavior subtypes writing after H7 (pre-existing for the hip path, T2a U3).
8. Dual-wield sync: the two Ents read the clock separately; up to one frame apart. Imperceptible; do not add shared state.
