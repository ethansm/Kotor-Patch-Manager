### Holster.cpp entry lifecycle (T5a section C, lines 1074-1200)
- VERIFIED T5a C13-C16: cache key is (node N=[beh+0x18], gob g, handle h=[N+4]) (Holster.cpp:1102-1103). Entry creation (the `else` at :1112) reads `mname` from `[g+0x84]+0x08` once (:1121-1122), classifies `cat` (:1123), sets `gate=gateInit()`, `seq=-1`, and fills mname/body (:1137-1141). On a hit (:1105-1111) only `left`/`seq` are touched in repoint mode; in drawgate mode NOTHING is re-read.
- CONFIRMED BUG RISK, sharper than T5a C20: N is the BODY's rhand/lhand node (c4 item 8-9: beh+0x18 = attach node of the parent), so N and h=[N+4] (node name handle) are IDENTICAL for every weapon ever held in that hand of that body. The `handle` field was meant to catch a reused (node, gob) pair (comment at Holster.cpp:1096-1098) but it only varies if the NODE is freed, not if the weapon Gob is freed. The key therefore degenerates to the Gob address.
- Consequence if the engine frees the old weapon Gob and the next weapon Gob lands on the same address (same-size heap block, LIFO reuse is typical): `ent` hits, and the entry keeps the OLD `mname` (so `isWeaponModel` at :1167 stays true even if the new Gob were a non-weapon), the OLD `cat`/`r`/`body`, and the old `gate`. `ent->r` was resolved by `resolveFull(s_tune, ent->mname, cat, ...)` (:1203-1204) for the old weapon; the new weapon gets the old weapon's type placement (e.g. a blaster pistol set to a long-sword hip pose, or the reverse). No PLACENODE line appears for the new weapon and no reset happens until owner/hip flips or the ring overwrites the slot. `gateUpdate` does not help: owner and hip are unchanged across a swap.
- Whether the Gob address is actually reused is UNVERIFIED (no live evidence; the executor moves item ids, the Gob is created inside singleton vtbl+0x7C from the item handle, and the previous slot object is closed first). It is not swap-specific: any equip-screen weapon change, area load or party switch that frees a weapon Gob has the same exposure. The weapon models themselves are resource-cached, so a model pointer comparison distinguishes weapons.
- VERIFIED T5a E21 / defaults: live game-dir holster.ini has probe=1, ch_comb/attach/swap/anim/gob=1, bone_test=1, ch_place=1, place=1, max_lines=30000 (checked `rg` on the live file, T5b F3 confirmed).
- LOG CAPS the draft rows must respect (new finding, missing from T5a/T5b): PLACENODE is capped at the first 40 lines per process (`s_nodeLines`, Holster.cpp ~1145); HANDATTACH at 64 (`kHandLines`, :774); DRAWGATE is rate-limited per creature (`keyedWant(...,8,10)`, :1066) and shares `max_lines=30000`. A swap tested late in a long session may produce no PLACENODE/HANDATTACH line even when entries are created.

## 2. Decisions (answers to T5a / T5b OPEN)

D1. Does the in-game X key reach the 0x5DF920 hook out of combat? YES by static chain (0x754950 case 6 -> 0x77DA50 -> server 0x547BB0 param=0 -> action 0x47 -> 0x5DF920) except two UNVERIFIED hops (key binding to event 6; 0x879C50 -> 0x65BE70). The out-of-combat swap is immediate; the in-combat swap waits for the 1000 ms round slot. Either way `SWAP exec=` must appear once per swap; 0 after a visible swap would falsify the chain.
D2. Gob reused or new on swap? Not settleable statically. The attach is by item handle and closes the previous slot object, so "new Gob per attach" is the likelier reading, and an address coincidence between the freed and the new Gob is plausible. Treat reuse as a live risk and neutralize it in code (D3) instead of waiting for evidence.
D3. Is a code change needed? YES, a small guard fix, independent of the play result: include the model pointer `[g+0x84]` in the entry identity so a changed weapon model at the same Gob address creates a fresh entry (re-classify, new gate, new resolve). Plus one rate-limited log line `GOBREUSE` when (node, gob, handle) matches but the model differs, which turns the open question into evidence in the next play session. The fix is risk-minimal: one extra safe read per call, no new hook, no behavior change when the model is unchanged.
D4. What does the player see? Out of combat: the weapons start on the hip. Swap: the unequip packet empties each main slot (the hip Gob is detached or closed), the equip packet attaches the new item to the hand node. New Gob pose starts as N's world pose (hand, c4 item 6); the hip pose is written at its first per-frame refresh that reaches the 0x504EF5 hook. So the new weapon shows in the hand for 0 or 1 rendered frames (UNVERIFIED which; the per-frame caller of behavior vtbl+0x08 is unknown) and then sits on the hip. There is no draw animation (0x5DF920 calls no anim function). With the stale-entry bug and a reused address the new weapon would instead sit on the hip with the OLD weapon's type pose. In combat: `[owner+0x138]` stays non-zero through the swap, so `shouldWriteHip` is false for the new Gob and it stays in the hand; the old pair vanishes at the same instant. Combat gate is unaffected by the swap. Side effect not owned by holster: 0x5DF920 calls ClearAllActions twice (cancels walking/attacking) and re-queues the attack.
D5. T5b M2 ("holster does not react to swaps"): correct and intended for the drawgate design. No HolsterLogic wiring is required: the drawgate follows the Gob, not the FSM. Do not add a caller for `onSwap` (it models the abandoned FSM draw window).

## 6. Risks
1. Guard fix reads `[g+0x84]` every call: one extra saferead per weapon Gob per frame; negligible next to the existing `readAt(g, 0xA4)` and mountPose reads. Mitigation: read once, reuse for the creation path.
2. Model pointer equality could in theory be defeated if both the Gob AND its model object were freed and reallocated at the same addresses; model objects are resource-cached, so this needs unloading the model resource at the same moment. Accepted; GOBREUSE would miss it, the visual symptom (wrong pose) would not.
3. Log caps (PLACENODE 40, HANDATTACH 64) can hide entry creation in a long session. The rows say to test right after launch; GOBREUSE has its own counter (20) so it is not starved by PLACENODE.
4. One-frame hand flash on the swap frame out of combat (D4) is UNVERIFIED and possibly present; it is cosmetic. If SW1 shows a visible flash, the remedy is a separate item (write hip from the attach hook P2 at 0x4616F3), not part of this fix.
5. The X key binding to input event 6 and the 0x879C50 -> 0x65BE70 hop are UNVERIFIED; SW1 settles them (`SWAP total` must rise). If it does not rise, record the key and stop; the hook is proven installed.
6. Equip-packet sender in RunEquip is untraced; if the client never runs 0x76E130 for the equip step the swapped-in weapon would not show at all (vanilla bug class, not holster); SW1 screenshots would show an empty hand, which would be a new finding.
7. Shared worktree: another session's uncommitted holster edits may break scoped tests; verify on a scratch copy and commit only own hunks (feedback-verify-in-scratch-shared-tree).
