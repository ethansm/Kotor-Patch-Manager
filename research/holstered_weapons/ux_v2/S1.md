## Q1 Does yaw rotate the camera? VERDICT: NO. Camera is fixed, the creature turns. H8 right, H2 right, H1 not in conflict.
- applyView (preview_3d_src/Preview3dProvider.cpp:379-394): yaw -> p3d::yawVec(yaw) = (cos, sin, 0) (_shared_src/ViewDrag.h:16-19) -> creature vtable CrSetFacing. Zoom -> sceneview::cameraFov only. No rig/camera/root rotation anywhere in SetView.
- The rig ("charrec_light", :70, :497) and the creature are separate scene objects. Camera is attached once at CreateView (:505, cameraAttach(block, rig, "camerahook", 1)). Nothing rotates the rig afterwards, so camerahook's world pose is constant per view (panZ moves the creature only, :388-392).
- So on screen the character really rotates; the camera basis never changes. The editor's fixed drags (HolsterEditor.cpp:911 dp=(0,dx,-dy); :946 axis=(0,-dy,dx)) are therefore yaw-independent AND camera-correct iff camera right=+Y, up=+Z in world. H8's "conditional" reduces to one fact: the camerahook world quaternion of charrec_light. Not logged yet (HolsterEditor.cpp:1054-1059 logs pos only; q is initialised {0,0,0,1}, w-last, wrong order for Q{w,x,y,z}).
- Precedent: inv3d_light camerahook (a renamed copy of the same family) = fwd -X, up +Z, right +Y (inventory_3d_viewport_src/RigCamera.inc:3-6; 01_inventory_3d_viewport.md:36). The editor's hard-wired mapping matches that exactly, which is probably why it was written that way. charrec_light unverified.
- H2 item 5 ("attach almost certainly drives pose every frame", 01_inventory_3d_viewport.md:93) is consistent: pose = node pose, no extra yaw term. Flag 1 vs 3 differs only in engine behaviour we have not seen; sceneview_test.cpp:483 uses 3 for the item path.

## Q2 WorldToScreen without a GL hook? VERDICT: YES in principle (PARTIAL: one probe line to confirm).
Inputs (all available): C,q = GetNodeWorld(rig,"camerahook") (_shared_src/HolsterApi.h:60; q w-first, HolsterQuat.h:10); fovy = fovForZoom(22.726, zoom) (Preview3dProvider.cpp:381); aspect = extent w/h (:488-489 logs it; same ratio the engine uses, DUMP :129 aspect = cam+0x220/+0x224).
- fov is VERTICAL: DUMP :188 gluPerspective(fovy=*(cam+0x204), aspect=local_8, near, far) and local_8 = w/h (:129). Live-proven by inv3d: fov_axis=v "was correct" (01_inventory_3d_viewport.md:18; Inv3dLogic.h:166 tanV = tan(fov/2)).
- Camera axes: Aurora camera looks down node-local -Z, up +Y, right +X (RigCamera.inc:2; make_inv3d_light.py:80: fwd,up,right = qrot(q,(0,0,-1)/(0,1,0)/(1,0,0))). Same recipe validated live by inv3d's fit.
- Formula: d = P - C; xc = dot(d, R(q)*(1,0,0)); yc = dot(d, R(q)*(0,1,0)); depth = dot(d, fwd), fwd = R(q)*(0,0,-1). t = tan(fovy*pi/360). ndcX = xc/(depth*t*aspect); ndcY = yc/(depth*t). Reject depth <= 0.05. Screen (top-left UI units): sx = ext.x + (ndcX+1)/2*ext.w; sy = ext.y + (1-ndcY)/2*ext.h. Near/far irrelevant (H2 item 4 correct).
- Y sign: inv3d default hit_flip_y=0 means the view extent Y is already top-left in the same space as the cursor (Inv3dLogic.h:202; doc 01 line 18), so the (1-ndcY) form needs no extra flip. H2's "unproven" is narrowed to the cursor space; ext and cursor share it in inv3d, but holster-editor reads cursor via its own path (HolsterEditor.cpp:842-845): confirm.
- Residual unknowns: (a) charrec_light camerahook q; (b) extent units vs cursor units (UI units, not px; same space as SetRect); (c) engine may add a camera-local offset beyond the node pose (cam+0x22c matrix, DUMP :140-155 sets constants only, looks neutral).
- H1 vs H2 on matrices: H2 "cannot build P*M" is true only for GL-side access; the camera is fully determined by (node pose, fovy, aspect), all readable, so H2's conclusion is too pessimistic. H1's post-draw hook is not needed for projection.
- ONE live log line confirms it: in the LIVE branch (HolsterEditor.cpp:1054) log CAMHOOK pos + q(w,x,y,z, fixed order) + fovy + extent, plus PROJ of two known points: the mount bone world pos (GetMountWorld) -> (sx,sy), and mount + 0.3 m along world +Z. Pass = point 1 lands on the visibly drawn weapon/bone within ~10% of view size and +Z point lands ABOVE it (sy smaller). Needs only a hot-swap of holster-editor, no reinstall.

## Q3 Render options, ranked for a first version
1. (c) 2D markers via mod-config SetRect: lowest risk. Pure math (testable in HseView.h, H2 item 17), no engine hook, no reinstall, existing re-layout pattern (ModConfigApi.h:97, parking at -9999 HolsterEditor.cpp:481). Limits: points not lines; buttons are drawn over the view (RuntimeGuiControls.md:106) but cannot be created per frame (ModConfigApi.h:86-91), so a fixed pool: origin + 3 axis tips + 3 mid-dots; gaveUp latch after 8 re-layouts (ModConfig.cpp:67,271); view drags must ignore marker hits (insideView is a raw cursor test, :845).
2. (a) GL overlay: real lines/depth-off, but reinstall, new address row at mid-function 0x480385 (H1 risks 1-4), unrestored GL state, no existing GL-draw precedent in any mod (H1 C2/C3). Only if (c) proves insufficient. H1's feasibility claim stands, "no risk" does not.
3. (b) native .mdl gizmo: worst. Native depth test stays on so it hides inside armour, no hide primitive, sibling misses holster offset, authored-model/MDLOps path unproven for hand-written static meshes (H3 items 3-5, 7, 8). H3's own verdict PARTIAL is generous.
Minimum probe: the Q2 log line (CAMHOOK with q + fovy + extent + two projected points). Cost: one holster-editor hot-swap and one play row in PLAY_TEST_QUEUE.md; no new engine address.
