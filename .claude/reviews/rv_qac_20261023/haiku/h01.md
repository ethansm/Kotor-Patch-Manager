# H1 findings

## H1-F1 [high] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:2371-2384 (arg reads and posPtr dereference), 2403-2406 (trace), 2421-2422 and 2430-2431 (stores); patch_manager_mods/07_force_power_hotbar_evidence/target_modes/disasm_775700.txt 0x775725-0x775747 (read past window); patch_manager_mods/07_force_power_hotbar_evidence/target_modes/decomp_7791a0.txt:85,110 (read past window); patch_manager_mods/07_force_power_hotbar_evidence/target_modes/FINDINGS.md:9 (read past window)
- Claim: H10 reads the 3rd stack arg (ebp+0x10, the float* position) as `targetId`, and the 7th stack arg (ebp+0x20, an int flag) as `posPtr`, then dereferences that flag as a float pointer. Every observed caller (ForceMenuAction x2, vanilla 0x899270) passes a pointer to a zeroed float[3] as arg 3 and 0 as arg 7, so the captured point is always zero, `hasPos` is always false, and the real ground point is never stored.
- Scenario: Leader is paused, queue busy, player clicks a Force power on a ground point. H10 buffers it with `targetId` = a stack address, pos = {0,0,0}, hasPos = false. On unpause the replay has no point (see H1-F2). Any ground-targeted cast loses its point at capture.
- Fix: Dereference ebp+0x10 for x,y,z. Read ebp+0x20 into a separate int flag. Keep ebp+0xC (arg2) as the target object id. Set hasPos from the non-null pointer, and treat a cast as ground-targeted only when the vector is non-zero, because vanilla object casts also pass &zero.
- Confidence: high (disasm pushes arg 3 as a dword into the message builder; both decompiled callers and FINDINGS Q3 agree on arg 3 = pointer, arg 7 = 0). Gameplay impact medium: not checked whether any KOTOR II power is ground-targeted.

## H1-F2 [high] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1111-1129 (replay call: a.targetId in the engine's pos slot, pp in the flag slot); patch_manager_mods/queue_hud_src/QueueHudLogic.h:633 (a.targetId = stored stack address), 650-652 (replayPos)
- Claim: The stored `targetId` is the caller's stack address, which is dead once the click returns. Replay passes it as the engine's float* position (3rd arg). The 7th arg (engine int flag) gets `pp`: NULL by default, and a non-null pointer (nonzero flag) when spell_replay_pos=0.
- Scenario: Ground-target power clicked while paused and buffered; unpause several seconds later. The engine reads 3 floats from the stale ForceMenuAction frame, so the point is garbage. For object-target casts, vanilla passes &zero there and replay passes a garbage pointer; the visible effect depends on whether the engine reads pos for object targets (not verified).
- Fix: Replay with `a.hasPos ? a.pos : nullptr` (or &zero to match vanilla object casts). Never pass a stored raw pointer. Pass the flag as an int. Correct the typedef order at the same time (see H1-F3).
- Confidence: high on the mismatch (direct code path). Medium on in-game effect: engine handling of pos for object casts is unknown.

## H1-F3 [med] doc-mismatch
- Where: patch_manager_mods/_shared_src/GameAddr.h:71; patch_manager_mods/queue_hud_src/QueueHud.cpp:82 (PerformCastSpellFn typedef, which drives the replay call); patch_manager_mods/30_queue_hud.md:78 (read past window)
- Claim: The address-table comment, the replay typedef and doc 30 all put `float* pos` as the 8th parameter (7th stack arg). Disassembly and decompiled callers show arg 3 is the pointer and arg 7 is an int. The typedef is what the replay call (H1-F2) uses, so the same error reaches the dispatch path.
- Scenario: A fix written against the typedef or GameAddr.h reproduces H1-F2 (the pos slot gets the target id). Anyone reading the trace takes `posptr=` as a pointer when it is the flag.
- Fix: Change all three to (creature; spellId, targetClientId, float* pos, byte multiclass, byte meta, byte domain, int flag). Rename the typedef parameters to match.
- Confidence: high (same disasm and decompile evidence as H1-F1).

## H1-F4 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:654-662 (serverRouteEligible, target = arg2); patch_manager_mods/queue_hud_src/QueueHud.cpp:1029 and 1101 (routing)
- Claim: serverRouteEligible approves any spell whose arg2 is a valid object id and never looks at the point. With H1-F1 the point is never captured, so a ground-targeted cast whose arg2 is a valid id (FINDINGS Q2 says ForceMenuAction pushes the bar owner id there) is server-cast as an object cast on the companion, dropping the ground target.
- Scenario: Companion's ground-target power is buffered with companion_server_cast=1 (default) while the companion is not leading. serverCast targets the companion's own object id (arg2), not the ground point.
- Fix: Server-route only object-targeted casts (captured vector zero and flag 0). Hold ground casts until the owner leads.
- Confidence: low-medium (depends on whether ground-target casts carry a valid id in arg2; FINDINGS Q2 suggests they do; not checked in game).

## H1-F5 [med] ux
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:2439-2443 (spell drop_full), 2340-2344 (item drop_full); patch_manager_mods/queue_hud_src/QueueHudLogic.h:817-822 (decideAction full check)
- Claim: With 3 buffered plus an active action, the next click returns 1 (consumed) and only a QLOGV warning is written. Nothing in this path gives the player a cue.
- Scenario: Leader paused with 1 active and 3 buffered powers. A fifth click does nothing visible, and the player thinks the input was ignored.
- Fix: Play a denied cue or flash the strip before consuming. Do not return 0 here: that would send the click into the engine queue while paused, out of order.
- Confidence: medium (did not check whether the strip already shows a full state).

## H1-F6 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:817-822 (decideAction has no pause input), 1491-1499 (curReal: paused only changes the cur-node test); patch_manager_mods/queue_hud_src/QueueHud.cpp:2413-2418 (spell decision inputs)
- Claim: decideAction gets no pause state. When paused, the engine queue is empty (gate 0), no cur node (haveCur false), the buffer is empty, and nothing is active, the click returns DISPATCH_NOW. The original wrapper runs, and the action sits in the paused engine queue outside the buffer.
- Scenario: Pause with an idle leader. Click 1 (Force Heal) goes straight to the engine. Click 2 buffers behind it. Order holds, but click 1 is not captured and depends on the pause_reinject/eaten path.
- Fix: Decide explicitly. Either pass s.paused into decideAction and buffer while paused, or document that the first paused command is engine-queued and covered by the eaten/reinject path.
- Confidence: medium (the code read is exact; design intent is not in my window).

## H1-F7 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:915-928 (queueCountOf: unreadable gives gateNe -1, haveCur false); QueueHud.cpp:2314-2317 and 2413-2416 (gateQ -1 clamped to 0)
- Claim: When engine state is unreadable (gatherFor false: server creature 0 or actq::read fails), the gate sees 0 and no cur node. With an empty idle buffer the click dispatches straight through, unbuffered, whatever the pause state. The trace shows engq=-1 but does not label the decision as fail-open.

- Confidence: low-medium (the fail path is in the code; not confirmed that server creatures go unresolved during play).

## H1-F8 [low] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:2293-2305 (H9 memberK), 2386-2398 (H10 memberK); patch_manager_mods/07_force_power_hotbar_evidence/target_modes/disasm_775700.txt 0x775709-0x775717 (read past window: the wrapper reloads ECX from the app object before its call, so its own `this` is ignored); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:617 (caller passes the leader as ECX)

ActionHotbar passes the leader for a targeted item use, which files it to member 0. Nothing checks the value against the action's real owner.

- Fix: Add a trace field for ECX-to-slot per call. Confirm the ECX value at the three real call sites before relying on per-member queues.
- Confidence: low (wrapper behaviour is shown in the disasm; caller-side ECX at ForceMenuAction and 0x899270 is not verified).
