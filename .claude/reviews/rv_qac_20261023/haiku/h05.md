## H5-F1 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:941-967 (doCancel, ServerClearAll at :965); patch_manager_mods/queue_hud_src/QueueHudLogic.h:48 (isQualifying), :90-101 (buildSlots keeps only 0x0C/0x0F/0x2E/0x3F); patch_manager_mods/queue_hud_src/QueueHud.cpp:836 (Cancel placed only when icons are drawn); patch_manager_mods/30_queue_hud_evidence/R7_cancel/FINDINGS.md:40 (route empties cr+0x100 and the round list)
- Claim: doCancel calls CServerExoApp::ClearAllActions, which empties the member's whole engine queue and round list. The panel draws only four entry types, so any other queued entry (a companion's resting FollowLeader 0x3D, a leader's move or other order) is removed with no icon and no per-entry log. The Cancel control exists only while at least one icon is drawn, so the player cannot see what the click also removes.
- Scenario: Companion 1 has its resting 0x3D at head and one buffered Force power (QL20 server cast). Player clicks that strip's Cancel X. The power icon goes (intended), and so does 0x3D. If the engine does not re-add 0x3D on an empty queue, the companion stops following. Not established in the repo.
- Fix: For a buffer-only cancel, remove only the buffered commands instead of clearing the whole queue. If the full clear stays, re-add 0x3D for companions after it, and log the invisible entry count (engineNe minus drawn) on the CANCEL line.
- Confidence: high (clear scope and type filter read in code); med on player impact (follower re-add not verified). Vanilla Cancel Combat uses the same route per R7 FINDINGS, so the leader case matches vanilla.

## H5-F2 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:2066-2087 (onFrameBegin hides only for cfg-off, menu, hard combat; no capture-age check); :480-493 (cwApply runs only from HUD_DRAW); :950 (doCancel's 250 ms capture gate); patch_manager_mods/_shared_src/GuiKit.h:251-259 (setClickable: a shown control swallows clicks)
- Claim: Cancel visibility changes only in HUD_DRAW (cwApply) and in the FRAME_BEGIN hide branch. If HUD_DRAW stops running without a menu flag or combat, the last shown Cancel stays visible and clickable, and clicks on it never reach the world. doCancel refuses on the 250 ms gate, so the queue survives, but the click is lost.
- Scenario: Leader has queued items; a cutscene or dialogue starts and HUD_DRAW stops. The Cancel bar stays at its last rect. A click there does nothing (WARN "act=refused stale HUD capture" per click) and the world does not get it. Whether the engine hides child controls in that state is not verified in the repo.
- Fix: In onFrameBegin, when GetTickCount() - g_capTick >= 250u, call cwHideAll("stale capture") and skip the hit test. This uses the same gate as doCancel.
- Confidence: med (code path certain; engine HUD-draw behaviour during dialogue or cutscene not verified).
