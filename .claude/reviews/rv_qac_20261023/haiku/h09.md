## H9-F1 [med] bug
- Where: patch_manager_mods/action_hotbar_src/HotbarLogic.h:285-289 (makeScale, read past window); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1547-1551 (aspectFix), 1579-1580 (createLabel uses unitRect with g_scale); patch_manager_mods/action_hotbar_src/hotbar_logic_test.cpp:419 (pins the identity at 1600x1200, read past window)
- Claim: makeScale returns the default Scale (sx=sy=1) whenever c==1.0, which is every exact 4:3 client (800x600, 1024x768, 1280x960, 1600x1200). Only the non-4:3 branch sets sx=w/rw and sy=h/rh. The header comment at ActionHotbar.cpp:1539-1540 says the HUD draws at a uniform H/600 px per unit, which the identity does not do.

The bar's top edge lands at y=478 px instead of about 612 px (478 x 1.28), so the bar is misplaced for every 4:3 player. The unit test locks the wrong value, so it does not catch this.
- Fix: For c==1 still set sx=w/rw and sy=h/rh (keep k.c=1.0). Change hotbar_logic_test.cpp:419 to expect sx=2.0 at 1600x1200 and keep the identity only for 800x600.
- Confidence: med (derived from the code and the file's own derivation; not run in-game; the user's 21:9 setup never reaches this branch).

## H9-F2 [med] bug
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1296-1297 (moveDuplicates and g_cfg.SetSlot mutate the in-memory profile), 1300 (Save), 1307-1308 (return false with no rollback and no refreshEffective)
- Claim: assignSlot mutates g_cfg before the save and never rolls back when Save fails. The bar keeps showing the old assignment, while g_cfg holds the new one and any duplicate it moved.
- Scenario: The INI is locked or read-only. The user binds a power to slot 3 -> "Saving the config failed (see log)" -> bar unchanged. The user later binds slot 7 successfully -> Save serializes the whole in-memory config, so slot 3's refused power, and the slot it was moved from, are written to disk silently.
- Fix: Mutate a copy of the profile and commit it to g_cfg only after Save succeeds. On failure, leave g_cfg untouched.
- Confidence: high (no rollback exists on this path); med on how often Save fails in practice.

## H9-F3 [med] doc-mismatch
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1802-1803 (comment), 1864-1868 (restoreFromSave); patch_manager_mods/action_hotbar_src/HotbarLogic.h:602-607 (pickSnapshot SS_Absent, snapStatus; read past window); patch_manager_mods/action_hotbar_src/hotbar_logic_test.cpp:752,754 (pins "absent (live hotbar kept)"; read past window)
- Claim: The comment says a load "empties them when the save has none (older saves, new games)". The code and its tests keep the live hotbar when the save has no snapshot: SS_Absent returns early with the log "absent (live hotbar kept)".
- Scenario: Save A is written with bar X, so it gets a snapshot. Save B has no action_hotbar.ini (made before the mod, or its snapshot copy failed with "no ini yet?"). Load A -> bar X. Load B -> bar X is still shown and the live INI is untouched, so save A's bar leaks into save B.
- Fix: Pick one policy. For "empty", call replaceLiveProfiles(nullptr, ...) on SS_Absent. For "keep", correct the comment at 1802-1803 and the documented per-save promise.
- Confidence: high (code, tests and comment disagree); the policy choice belongs to the owner.

## H9-F4 [low] perf
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1420-1438 (edPicker build; the gate at 1435 only throttles the copy into ed.list), 1426-1427 (GroupSnapshot over six groups); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:219-240 (readGroup, probeRead per entry; read past window)
- Claim: While Pick mode is open, edPicker reads all six HUD group lists, rebuilds the entry vector with string copies, and runs an O(n^2) dedupe on every frame. The signature and 60-frame check only decide whether to copy the result into ed.list.
- Scenario: Editor open in Pick mode with the cursor still, game at 60 fps -> each frame reads up to 6 x 256 entries and reallocates the list. Cost is not measured; likely small but unconditional.
- Fix: Read groups and rebuild the list only on the ButtonRefreshFrames cadence or when a group count or pointer changes. Keep ed.list between refreshes.
- Confidence: med (code path certain; magnitude unmeasured).

## H9-F5 [low] ux
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1476-1478 (cell tip re-shown only when the hovered index changes), 1313-1319 (scrollPicker does not touch the tip), 1481-1484 (toggle tip), 1412-1416 (mode-button tip)
- Claim: These tooltips are re-shown only when the hovered control index changes. Three texts can change while the cursor stays put: the picker cell under the cursor after a wheel or arrow scroll, the toggle text ("Edit hotbar" vs "Finish editing") after a click, and the mode-button text after a mode click.
- Scenario: Cell 2 shows its tip "Power A" after 450 ms. Wheel-scroll one notch without moving the mouse: cell 2 now shows "Power B" but the tip still reads "Power A". Or: click the toggle while its tip is up; the tip keeps "Edit hotbar" while editing is on.
- Fix: Key the tip on the entry or mode and re-show it when that changes, or hideTip() from scrollPicker and from the mode change.
- Confidence: high (no other code path re-shows these tips).

## H9-F6 [low] logging
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1205-1219 (ensureWheelHook, connected branch); patch_manager_mods/gui_input_src/GuiInputProvider.cpp:180-186 (provider WARN on every -1; read past window); patch_manager_mods/_shared_src/GuiInput.h:125-127 (wheel_subscribe returns 0 without a provider function; read past window)
- Claim: When connected but wheel_subscribe returns <=0, the hotbar retries every frame with no log of its own. The connected branch returns before the subclass fallback, so picker wheel scrolling has no fallback. The provider logs a WARN on every -1.
- Scenario: The game window is not found for some time (or the provider lacks WheelSubscribe) -> one provider WARN per frame in the provider log, and picker wheel scrolling is silently dead in action-hotbar.
- Fix: Log the first failure in ensureWheelHook and retry every ~60 frames. If subscribe keeps failing and nothing is subscribed, fall back to the local subclass.
- Confidence: high on the code path; low on how often the trigger happens (the window is normally found at once).

## H9-F7 [low] logging

- Claim: The stance/form read-failure WARN fires once per process. A later failure after a recovery is never logged, and the recovery itself is not logged either.

## H9-F8 [low] ux
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1837-1851 (replaceLiveProfiles copies the live INI to LoadBakPath on every load, line 1840); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1300 (each assignSlot writes the live INI immediately)
- Claim: Every bar edit is written to the live INI at once, and every save load overwrites both the live INI and .ini.load.bak. Bar edits made after the last game save are dropped on the next load, and the only copy is the .bak, which the next load overwrites.
- Scenario: Edit the bar without saving the game -> load save A (bak = edited bar) -> load save B (bak = save A's bar). The edit is now in no file.
- Fix: Keep a rotated or timestamped backup per load, or log a summary of the discarded profile. If per-save is intended, document that edits not written into a save are lost on load.
- Confidence: med (per-save discard is by design per the comment; the loss of the second-level copy may not be wanted).
