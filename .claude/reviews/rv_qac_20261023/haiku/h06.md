# H6 findings

## H6-F1 [med] logging
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:1356-1368 (modeChanged, modeWhy); patch_manager_mods/queue_hud_src/QueueHud.cpp:871 (producer, read past window: combat = -1 when g_combatUnreadable)
- Claim: modeChanged and modeWhy treat the unreadable combat value -1 as a real transition. A read gap writes a MODE line with why=ended (1 to -1), and the next readable frame writes why=edge (-1 to 1). Each flip also spends one line of mode_cap.
- Scenario: Combat is on and the flag read fails for one frame, giving `MODE ... combat=? ... why=ended`. The next frame reads combat=1 and gives `... combat=1 ... why=edge`. No combat started, but a reader using why=edge to time a combat start is misled. A flickering read can use up the 2000-line cap, and later MODE lines are then lost.
- Fix: In modeChanged and modeWhy, do not treat -1 as a transition. Hold the last readable combat value, as combatEdgeStep does, or return a distinct why (for example "unread") when either side is -1.
- Confidence: high (the branch at line 1362 maps any change to edge or ended, and -1 reaches it from QueueHud.cpp:871). Medium on frequency: unreadable flags in live play were not measured.

## H6-F2 [low] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:306-310 (left-side x0 clamp at 308-309); 292-294 (doc)
- Claim: With strip_side=left, stripRects clamps the row's left edge to x=0 when vit.x - reserve - rowW is negative. The row then covers the selfheal footprint that `reserve` exists to keep clear, and the caller still gets a normal icon count.
- Scenario: Hypothetical values, not from a measured layout: vit.x=180, reserve=80, auto icons 58 px, 4 icons, 2 px gap. rowW = 58 + 3*60 = 238, x0 = 180-80-238 = -138, clamped to 0. The row covers x 0-238, over the selfheal button at about x 100-180. The row should be shortened or hidden instead.
- Fix: On the left side, when the unclamped x0 is negative, drop trailing icons until the row fits, or return 0 so the strip hides. Do not clamp into the reserve.
- Confidence: medium on the arithmetic (checked by hand against the code). Low on reachability: vit.x was not measured for any supported resolution (the live layout is 3840x1600).

## H6-F3 [low] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:575 (parseIni discards parseIniLine's return), 510-523 (parseIniLine: no BOM skip, no inline-comment strip), 503 (doc lists whole-line comments only)
- Claim: Rejected lines vanish with no trace. Three realistic inputs are rejected: a UTF-8 BOM on line 1 (the key becomes the bytes EF BB BF plus the name), an inline comment after a value (`log=0 ; quiet` yields the value "0 ; quiet"), and any typo.
- Scenario: An editor saves queue_hud.ini with a BOM and line 1 is `enabled=0`. The mod stays enabled, and no log line says the key was ignored. The same holds for `log=0 # quiet`, which leaves logging on.
- Fix: In parseIni, skip a leading EF BB BF. In parseIniLine, cut the value at a ';' or '#' that follows a space. Have parseIni return the count of rejected lines so loadIni can log it once.
- Confidence: high for the parse path (hand-traced; queue_hud_logic_test.cpp has no BOM case, and rg found none). Low impact: the shipped queue_hud.ini starts with a ';' comment, so the BOM case costs nothing there.

## H6-F4 [low] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:1331-1333 (party match on the low 24 bits), 1386-1393 (softCombat), 1395-1404 (bannerAct)
- Claim: A hostile target is classed as a party member when its low 24 bits equal a party id's low 24 bits. The combat then looks soft, so bannerAct hides the top banner and red bar during a real fight.
- Scenario: Member 0 targets hostile id 0x7F0001AF while party member 1 is 0x800001AF. softCandidate sets anyParty=1 and anyHostile=0, softCombat returns true, and the banner is hidden. This needs an id collision in the object-id space, which was not checked.
- Fix: Match the full id first. Accept the 24-bit fallback only when the target's high byte is 0x80 (the party form), and log which path matched in SOFT_CAND so a collision shows in the trace.
- Confidence: low. It needs a collision I did not verify against the id allocator. The comment at line 1321 shows the 24-bit match was chosen to tolerate a representation difference.

## H6-F5 [low] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:72-78 (nodeKey), 103 and 113 (call sites); patch_manager_mods/30_queue_hud_evidence/RE.md section 2, arg table row 2 (read past window)
- Claim: nodeKey hashes only the sub-type and the id. The icon resolver 0x74E0B0 also reads the action's type dword (RE.md section 2, arg 2), so the key ignores whether the node came from a 0x0C or a 0x3F entry.
- Scenario: Queue [0x0C, 0x3F]. The current node A has sub-type 1 and is shown by the 0x0C entry. A pending sub-type-1 node B is expanded by the 0x3F entry. Both get the same key, so one cached icon serves both. If the resolver's output differs by action type for sub-type 1, one slot shows the wrong icon. Not verified.
- Fix: Pass the action type into nodeKey and mix it into the tag. This removes the question at no cost.
- Confidence: low. RE.md gives the inputs but not the per-type icon output, so the wrong-icon result is unconfirmed.

## H6-F6 [low] logging
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:958-963 (sigEqual); patch_manager_mods/queue_hud_src/QueueHud.cpp:2012-2015 (journal fill and compare, read past window)
- Claim: sigEqual compares only the first 8 queue types. buildSlots reads up to kMaxEntries=16 entries, and the journal signature keeps only 8.
- Scenario: A 10-entry queue where entry 9 changes from 0x3F to 0x2E, with ne, round, cur and both flags unchanged. sigEqual returns true, so no QJ line is written and jm.sig is not updated. The panel is correct; only the trace misses the change.
- Fix: Store and compare all ne types (up to 16, the cap buildSlots uses), or compare a hash of them.
- Confidence: high on the code path. Low impact: it affects only the QJ trace.

## H6-F7 [low] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:1518 (ev.executing), 1480 (activeVerdict rule 2); patch_manager_mods/queue_hud_src/QueueHud.cpp:1855 (notePresent caller, read past window)
- Claim: ev.executing is true for any unpaused aa8 or ab8 flag. Those flags belong to the creature, not to our action. The caller latches sawExecuting from it, so rule 2 later reports AV_EXECUTED for an action that was wiped without running.
- Scenario: A buffered item is dispatched. Another command for the same creature sets aa8 inside that window. Combat then clears the queue. activeVerdict returns AV_EXECUTED, so the action is resolved and never re-sent. The HANDOFF_OUT doc (line 1256) says aa8/ab8 count as exec by design; the risk is that a foreign busy window also counts. No such sequence was seen in a log.
- Fix: Count a flag as our execution only when the current node matches the active action (sub-type 9 with the spell id, or sub-type 10 with the item id). Otherwise record the source of exec in the trace.
- Confidence: low. It is by design per line 1256, and it needs a foreign command inside the dispatch-to-wipe window, which was not seen.

## H6-F8 [low] doc-mismatch
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:227-228 vs 235 (slotStyle); 271-272 vs 278-279 (stripHeadSize); 503-509 (parseIniLine key list)
- Claim: Three doc comments disagree with the code. (a) slotStyle says the head icon always dims with waiting_alpha; the code does it only when waitingIconDim is on. (b) stripHeadSize says the head is never taller than the vit bar; when vit.h is below the strip size, the code returns the strip size. (c) The parseIniLine key list omits 19 keys the switch accepts, for example waiting_icon_dim, strip_head_pct, pause_reinject, handoff_keep_new, companion_server_cast and hide_banner_soft.
- Scenario: No runtime failure. A maintainer who trusts the key list concludes that handoff_keep_new or strip_head_pct is unsupported and edits the ini or head-size code on that basis.
- Fix: Update the three comments: state the icon-dim rule with waitingIconDim, say the head is capped at vit.h only when vit.h is at least the strip size, and regenerate the key list from the switch.
- Confidence: high (each comment was compared line by line with the code).
