## H7-F2 [med] bug
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:452-459 (checkConfig); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1281-1300 (assignSlot); patch_manager_mods/_shared_src/FileWatch.h:77-87 (changed() records the stamp before Load runs)
- Claim: checkConfig() records the new file stamp inside filewatch::changed() before Load() is attempted. When Load() fails, the previous config is kept and the stamp is never retried. assignSlot() then calls checkConfig(true) and writes the stale in-memory config with g_cfg.Save(), ignoring the failed read.
- Scenario A: The user deletes action_hotbar.ini to reset their bars while the game runs. The next slot assignment recreates the file from the old in-memory profiles, so the reset does not stick. Scenario B: A transient open failure during a poll (file locked or being replaced) leaves the config stale until the next external change. Any hand edits made in that window are overwritten by the next assignSlot.
- Fix: Call filewatch::accept only after a successful Load(). In assignSlot, refuse to Save when checkConfig could not read the file, and log the refusal.
- Confidence: high (the code path is traced end to end; the user-intent reading of Scenario A is inferred).

## H7-F5 [med] edge-case
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1975-1986 (modifier tracking and digit-down resync); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1968-1972 (events from other devices ignored)

- Scenario: Ctrl is held while focus returns to the game, so the Ctrl-down event is never seen. g_ctrl stays false and Ctrl+1 is decoded as plain 1. It is swallowed and invokes slot 1, when the game should receive Ctrl+1 (the code comments say Ctrl/Alt+digit stay the game's).

- Confidence: med (the path is certain; a missed modifier-down is inferred, not observed in logs).

## H7-F6 [med] edge-case
- Where: patch_manager_mods/action_hotbar_src/HotbarLogic.h:310-317 (decideKey down branch with no clearDown on pass); patch_manager_mods/action_hotbar_src/HotbarLogic.h:311 (up branch swallows when downSwallowed is set)
- Claim: A swallowed key-down sets downSwallowed. A later key-down that is not swallowed (unbound slot, gate closed, Ctrl) does not clear it. If the key-up for the swallowed press was lost, the next release is swallowed even though its press reached the game.
- Scenario: Press 1 while bound (swallowed), and the key-up is lost on alt-tab. After returning, slot 1 is unbound or a menu is open. Press 1 and it passes. Release, and the release is swallowed. The game never sees key-up for digit 1.
- Fix: Clear downSwallowed on every key-down that is not swallowed (set clearDown on the pass branches).
- Confidence: med (requires a lost key-up, not seen in the logs; the code path is certain).

## H7-F7 [med] bug
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1837-1851 (replaceLiveProfiles; backup at 1840, read past window per the brief's scope); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1299 (first-edit backup, once per process)
- Claim: The single file action_hotbar.ini.load.bak is overwritten on every save load and every new game (ActionHotbar.cpp:1840). Two loads in a row lose the INI as it stood before the first load. The first-edit backup action_hotbar.ini.bak is written only once per process (ActionHotbar.cpp:1299), so it can be days old.
- Scenario: The user builds a bar in the live INI without saving to any save file. Load save A, so .load.bak holds the edited file. Load save B, so .load.bak is overwritten with save A's state. The edited bar exists on no disk.
- Fix: Keep a rotating set of backups (for example .load.1 to .load.3), or write a backup only when the live file holds bindings the snapshot lacks.
- Confidence: high (the code is explicit; severity depends on how often users edit without saving).

## H7-F8 [med] bad-assumption
- Where: patch_manager_mods/action_hotbar_src/HotbarLogic.h:93-115 (characterKeyFor: key = creature tag, or "slot<N>" for untagged companions); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:398-405; patch_manager_mods/k1_port/k1_port_vfs_pack.py:484-485 (default tag k1p_<char id>, read past window); patch_manager_mods/k1_port/k1_port_spawn_build.py:11-13 (default tag k1p_probe_npc, read past window)
- Claim: The profile key is the creature tag. Two live creatures with the same tag share one [Profile.<tag>] section. The K1-import and probe tooling gives deterministic tags, so duplicates are plausible. Untagged companions get "slot<N>", which follows party order, so a leader switch can move their profile to another creature.
- Scenario: Two copies of one imported NPC are in the party (or a spawned probe sits next to the real one). An edit to one overwrites the other's bar, and switching leader shows the shared bar.
- Fix: Key on tag plus a per-creature discriminator (template resref, or object id for non-player companions), and log a WARN when two party members produce the same key.
- Confidence: med (duplicate tags are a property of the tooling; no in-party live test in the repo).

## H7-F9 [low] edge-case
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1837-1849 (replaceLiveProfiles, recomputeBound at 1847); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:2143-2150 (character key resolved on the next tick)
- Claim: replaceLiveProfiles runs on K2SE_LOAD_REQUEST, before the loaded character exists. It calls recomputeBound() with the outgoing g_charKey, so g_slotBound and refreshEffective (on the next tick) reflect the old character's key against the new snapshot. The live INI is overwritten before the load has succeeded.
- Scenario: A digit pressed in the window between the load request and the next tick is swallowed or invoked using the outgoing character's key on the new snapshot.
- Fix: Skip recomputeBound in replaceLiveProfiles while a reload is pending, and let the tick rebuild the bindings once the key resolves.
- Confidence: med (the window is about one tick; the exact load timing is not in the repo).
