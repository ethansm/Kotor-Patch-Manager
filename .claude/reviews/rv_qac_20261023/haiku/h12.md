## H12-F1 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1786-1788 (round node counts as present); patch_manager_mods/queue_hud_src/QueueHud.cpp:1847 (verdict skipped when round==0); patch_manager_mods/queue_hud_src/QueueHudLogic.h:1477 (rule 1, no age limit) ; patch_manager_mods/queue_hud_src/QueueHudLogic.h:885-893 (dispatchWhy blocks on nrn) [read past window: QueueHudLogic.h]; patch_manager_mods/29_paused_command_evidence/PQ2.md:84 and :86 [read past window]
- Claim: A round node (subtype 9/10) always counts as "action present", and AV_PRESENT has no age limit. A ClearAllActions (SaveMember on save/autosave, script clears, BumpFriends, effects) empties the engine queue (0x3F/0xF) but leaves the round node (PQ2 4.4). The active action then reads PRESENT forever, and dispatchWhy blocks every buffered command while nrn != 0. The eaten/re-inject logic never runs for this case.
- Scenario: Leader's buffered item is dispatched while paused (0x3F queued, round node present). Player saves (or autosave runs SaveMember) so the 0x3F is wiped and the round node stays. After unpause the HUD keeps the item as active, commands 2-3 never dispatch, and only Cancel (ServerClearAllActions empties the round list) clears it. If the round timer end drops orphan nodes, this shrinks to a stall of about 3 s.
- Fix: Before rule 1, treat a round node with no engine 0x3F/0xF/0x2E and no real cur as an orphan after about 1500 unpaused ms (same clock as kStaleCurMs). Then re-inject it or clear the member's round list once, and log an ORPHAN line. Also give AV_PRESENT an unpaused ceiling.

## H12-F3 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:1505-1518 (makeEngineView: engine 0x2E/0x0F counted as executing) [read past window]; patch_manager_mods/queue_hud_src/QueueHud.cpp:1855 (notePresent latches sawExecuting); patch_manager_mods/queue_hud_src/QueueHudLogic.h:1480 (rule 2 returns AV_EXECUTED); patch_manager_mods/queue_hud_src/QueueHud.cpp:1857-1860 (resolve, no re-inject)
- Claim: Once the 0x3F expands the round node into a 0xF/0x2E engine node, the verdict sets sawExecuting even though the spell (conj 170 ms) or item has not fired yet. If that engine node is wiped before it fires, the absent action is judged AV_EXECUTED and resolved: no re-inject, no DROP line, and the command vanishes silently.
- Scenario: Unpaused leader casts a Force power. Expansion puts the 0xF in the queue and sawExecuting latches. A ClearAllActions (save or autosave) runs before the 170 ms conj elapses, or the player pauses in conj and then saves. After the 150 ms debounce the action reads gone, the verdict is EXECUTED, and the command is resolved without ever firing.
- Fix: Set executing only on evidence that the action fired (cur 9/10 with aa8 or ab8 set, or the conj time elapsed). Track the expanded-but-unfired state separately so a vanish before fire goes to the eaten path.
- Confidence: med (the code path is CONFIRMED; the window is about 170 ms for spells and about 1 ms for items; if the round cur still points at the node during conj, the wipe is masked until cur goes stale at 1500 ms, which is OPEN).

## H12-F4 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1523 (g_detached is per slot, no owner); QueueHud.cpp:1547-1584 (detachTick re-pushes into whoever holds slot k: 1555-1558, 1574-1579); QueueHud.cpp:1685-1687 (detachTick runs only in combat); QueueHud.cpp:1700-1724 (identity pre-pass swaps buffers and timers but not g_detached); QueueHud.cpp:1309-1310 (no identity pre-pass in combat)
- Claim: Held round nodes are stored per slot index with no owner. The identity pre-pass that re-files buffers when party members rotate does not run in combat, and it does not swap g_detached. detachTick therefore pushes a companion's held nodes into the round list of whoever takes that slot.
- Scenario: In combat a companion's power is detached (handoff_detach_held). The companion leaves the party, or the slots reorder, while its node is out. Once the new slot-k creature has no nodes of its own and the last send is at least 300 ms old, the old companion's node is pushed into the new creature's round list, and that creature executes another character's power.
- Fix: Store the owner creature in Detached. Reattach only to the owner's current slot, and discard with DR_IDENTITY_LOST when the owner is gone. Swap g_detached in the identity pre-pass as well.
- Confidence: med on the code (no owner check in detachTick); low on reach (needs a party reshuffle while a node is held in combat; whether a leader switch is allowed in combat is OPEN).

## H12-F5 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1012-1022 (owner is a raw creature pointer, matched by pointer only); QueueHud.cpp:1700-1738 (identity pre-pass, 20 s clock 1727-1734); patch_manager_mods/_shared_src/ActQueue.h:69-75 (unreadable pause chain returns not paused) [read past window]; no load, area, module, transition or dialogue hook anywhere in patch_manager_mods/queue_hud_src (grep)
- Claim: Buffers are never reset on load or area change. They match party slots by raw pointer with no object-id check. If party creatures are respawned on load or area change (PQ2 4.1 lists SavePuppet and SpawnPUP as ClearAllActions callers), every buffered command goes identity-lost. It is held for 20 unpaused seconds, then dropped as DR_IDENTITY_LOST. If heap reuse gives a new party creature an old address, the old commands match it and are dispatched.
- Scenario: Queue 2 commands while paused, load a save from the menu, unpause. The HUD shows the queue for about 20 s, then the commands disappear with a DROP identity_lost line. Heap-reuse variant: old commands run on the new occupant of the address.
- Fix: Clear every buffer on load and area change (hook, or detect a change in the party table generation). Store the object id beside the pointer and match on id.
- Confidence: med that the hold and drop follow if pointers change (code CONFIRMED); low on whether party pointers change on load or area change (unverified, needs a PQ2-P1 or play log); the heap-reuse variant is low.

## H12-F7 [low] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:760-767 (eaten clock: 1000 ms step cap); patch_manager_mods/queue_hud_src/QueueHud.cpp:1847-1849 (eaten clock accrues only in the verdict branch); QueueHud.cpp:1727-1734 (identity clock); patch_manager_mods/queue_hud_src/QueueHudLogic.h:842-859 and QueueHud.cpp:1916-1917 (flag hold: 2 s cap from wall-clock holdSince; paused ticks step with busy=false); QueueHud.cpp:630, 1554 (detach 600 s wall clock) and 1582 (reattach guard 5 s wall clock)
- Claim: The 20 s eaten and identity clocks do count only unpaused time (CONFIRMED). The eaten clock under-counts, though: 1 s per-step cap, and no accrual on RI_OK, round==0 or menu ticks. The identity clock treats an unreadable pause chain as unpaused. The flag cap and the detach timers are wall-clock, so pause time counts toward them.
- Scenario: Pause for 3 s during a flag hold. step() sees busy=false, and after 150 ms of clear it returns true while still paused. Once unpaused, the cap has already run out, so the next busy tick dispatches at once (hold=flag_cap) into a round that is still running.
- Fix: Measure the flag hold and the detach timers on unpaused time, the same way accrueEaten does. Treat paused ticks as "hold continues" rather than as a clear run. Treat an unreadable pause chain as unknown, not unpaused.
- Confidence: high on the code; low on player impact (a 2 s hold cap and a pause during a hold are both rare).
