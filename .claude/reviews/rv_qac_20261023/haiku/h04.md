# H4 findings

## H4-F1 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1725-1737 (identity-lost 20 s wait, runs only while another creature holds the slot); patch_manager_mods/queue_hud_src/QueueHud.cpp:1748-1755 (empty-slot clear, runs before the skip check); patch_manager_mods/queue_hud_src/QueueHud.cpp:998-999 (traceDropAll, gated by trace_queue); patch_manager_mods/_shared_src/Party.h:80-84 (member() returns 0 at i >= partyCount; read past window)
- Claim: A buffer whose owner has left the party is cleared at once when its slot is now empty (DR_NULL_CREATURE). The 20 s identity-lost wait only applies when another creature moved into that slot. The drop is logged only through traceDropAll, which needs trace_queue on, so default logs show nothing.
- Scenario: The player led B and buffered a Force power on B's behalf, then switched leader, so B's buffer sits in slot 2. Story removes B: party becomes [A, C]. Next tick the buffer is cleared, no log line. If B rejoins later the power is gone. If D joins into slot 2 instead, the buffer waits up to 20 unpaused seconds and is then cleared.
- Fix: Keep the buffer through the same 20 s identity-lost timer whether or not the slot is empty, and QLOG one line per dropped command at default verbosity.
- Confidence: high (read the pre-pass and per-member loop end to end); med that the immediate clear is unintended (the 20 s comment suggests waiting was the design).

## H4-F2 [low] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1710-1722 (swap and skip assignment; the swap also resets g_identLostMs for both slots); patch_manager_mods/queue_hud_src/QueueHud.cpp:1755 (skip use)
- Claim: skip[k] is set only on the iteration that performs the swap. A later iteration can swap a correct buffer into index k, and skip[k] is never recomputed. Hand trace of party [A,B,C] to [C,A,B]: the final buffers are right, but skip[0] stays true, so member 0 loses one tick of dispatch and re-inject. No wrong dispatch found for 2- or 3-slot permutations.
- Scenario: Leader switch that rotates three party members. Member 0 (new leader) does nothing for one frame, then runs normally on the next tick.
- Fix: After the loop, recompute skip[] for every index a swap touched, or repeat the pre-pass until no swap happens (at most 3 passes).
- Confidence: high (hand trace of the code); low impact (one tick).

## H4-F3 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1067-1091 (serverCast; refusals at 1072-1082, WARN at 1089); patch_manager_mods/queue_hud_src/QueueHud.cpp:1095-1110 (dispatchAction is void and drops the serverCast result at 1102); patch_manager_mods/queue_hud_src/QueueHud.cpp:1824-1840 (RI_OK re-inject calls dispatchAction again); patch_manager_mods/queue_hud_src/QueueHudLogic.h:1476-1488 (activeVerdict resolves the absent action as UNSEEN)
- Claim: serverCast reports refusal (no server creature, not commandable, id mask unreadable, or engine returns 0), but dispatchAction discards it and buf.active stays true. While the companion still has its 0x3D, RI_OK re-sends the same refused call on consecutive ticks, up to kMaxReInjectCount = 2 times, with no spacing. Then the verdict resolves it as UNSEEN with no DROP line.
- Scenario: Companion B is not commandable (for example during a scripted sequence) while the player's Force power for B is buffered. Dispatch is refused, re-injected and refused twice more, then resolved after about 500 ms. The strip icon disappears with no effect; the only record is one WARN line per attempt.
- Fix: Make serverCast return bool. On refusal, drop the active action at once with a DROP line and skip the re-inject for not_commandable.
- Confidence: high (control flow read end to end); med on how often CrCommandable reads 0 while an action is buffered.

## H4-F4 [low] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:733-743 (memberDown); 759, 1595, 2001 (its only callers: strips, round watch, poll); 1067-1076 (serverCast gates, no Down check); 1758 and 1914 (ownerCtrl and DS_NOT_CTRL, no Down check); 1824 (re-inject, no Down check); 1355-1400 (hand-off, no Down check)
- Claim: Dispatch, re-inject, hand-off and serverCast never consult memberDown(k). A Down companion is guarded only by CrCommandable (0xEC), and the code and notes do not record its value while Down, as opposed to dead (the comment in QueueHud.cpp:1094 covers the commandable gate only).
- Scenario: Companion B is Down but not dead, with a buffered Force power. If CrCommandable reads 1, serverCast appends the 0x3F to a creature that is not acting. The buffer stays active until B is revived, and the power fires late after the player has moved on.
- Fix: Hold the route for member k while memberDown(k) is true, the same rule the strips use, and log the hold once per episode.
- Confidence: low (the Down-state value of CrCommandable and the engine's handling of a queued action on a Down creature are unverified).

## H4-F5 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1153-1181 (kickStarved: no time limit, rotates at most once per 250 ms, called at 1809 only while buf.active); patch_manager_mods/queue_hud_src/QueueHudLogic.h:1148-1155 (castStarvedAt returns 0 when the first 0x3F is at index 4 or deeper); patch_manager_mods/queue_hud_src/QueueHudLogic.h:1476-1488 (AV_PRESENT while a round node exists, no timeout); patch_manager_mods/companion_selfheal_src/CompanionSelfHeal.cpp:844 (selfheal gives up after 5 s; read past window)
- Claim: queue-hud's kick has no give-up. If the kicked 0x3F never completes, the companion's 0x3D stays behind it, so the companion stops following, and the buffer stays active because the round node keeps the verdict at AV_PRESENT. Selfheal's kick gives up after 5 s; queue-hud's never does. A 4th 0x3D ahead of the 0x3F also disables the kick entirely.
- Scenario: Companion B's server-routed power targets an object that becomes invalid while the 0x3F is at head. B stands still, its buffer never clears, and later buffered commands for B wait indefinitely. The only trace afterwards is the 1 s WAIT heartbeat.
- Fix: Add a per-action give-up (for example 5 s starved or unchanged, as selfheal does), log it as DROP, and let the kick run at any index up to the queue cap.
- Confidence: low (a stalled kicked 0x3F and a 4th 0x3D were not observed in logs; the missing timeout and the index cap are read from code).

## H4-F6 [low] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1079-1080 (AddUseTalentOnObject call: a.domain is not forwarded, no target check); patch_manager_mods/queue_hud_src/QueueHudLogic.h:659-662 (serverRouteEligible checks only the client id against 0 and 0x7F000000); research/holstered_weapons/keybind/H3.txt:29 (ClientToServerObjectId semantics; read past window)
- Claim: The companion route forwards no domain (UseTalentOnObjectFn has no slot for it) and checks nothing about the target at dispatch time: not that it exists, is in range, or is still hostile or friendly. A target that died or left during the wait is still sent to the server route.
- Scenario: Companion B's buffered heal targets the leader A or an enemy. The target dies while B's action waits. The server route queues the cast on the stale id; the result depends on engine behaviour, which the notes do not record. The leader path replays a stale target the same way (see H1 findings).
- Fix: Look up the target before the call and drop with a DROP reason if it is gone. Check whether domain must be forwarded, since the leader path passes it.
- Confidence: low (engine target validation and the meaning of the domain argument are not verified in the notes).

## H4-F7 [low] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1710-1719 (the swap moves g_itemQueue, g_lastOurs, g_identLostMs/LastTick, g_prevRiWhy, g_prevDsWhy only); 1187 (g_flagGate[3]); 1146 (g_kickLast[3]); 1230 (g_outWatch and g_spellWatch, trace only); 1197 and 1201 and 628-629 (g_handoff, g_roundOrder, g_detached, combat only)
- Claim: The identity swap moves the buffer but not the per-slot state that describes it. The flag-hold gate and the kick rate limit stay with the slot, so the buffer that lands in a slot inherits that slot's hold. The watches only feed traces. The combat-only arrays are not reached by the swap in practice.
- Scenario: Buffer X was holding for the aa8/ab8 flag window in slot 1 (g_flagGate[1] holding since an earlier tick). A leader switch moves X to slot 2 and buffer Y into slot 1. Y inherits X's hold start, so it can dispatch as soon as the 2 s cap is passed or immediately if the cap already passed, inside the 0.7 s flag window where a dispatch is wiped (QL6b comment at patch_manager_mods/queue_hud_src/QueueHudLogic.h:841-847). The eaten path re-injects, so the effect is one wasted re-inject, not a lost command.
- Fix: Reset g_flagGate and g_kickLast for both slots in the swap block (simplest), or move them with g_itemQueue.
- Confidence: med (read from the code; the consequence is inferred from the QL6b comment, not measured in a log).
