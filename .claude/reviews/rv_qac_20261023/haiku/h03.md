# H3 findings

## H3-F1 [high] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1332 (headValid), 1378-1403 (send path, exec evidence not checked); patch_manager_mods/queue_hud_src/QueueHudLogic.h:669 (150 ms vanish debounce, read beyond window)
- Claim: At the combat edge a non-held head is re-sent whenever `buf.active && !inEngine`. Exec evidence (`h.sawExec`, `buf.sawExecuting`) is read only inside the headHeld branch, so a command that already ran is dispatched again.
- Scenario: a medpac or Force power leaves the engine (executed) within about 150 ms before combat starts. Buffer resolve is debounced and runs only out of combat, so `active` is still true at the edge; inEngine is false, headValid is true, and the head is dispatched a second time (second medpac consumed, FP spent twice). Same path if gatherFor fails at the edge (gEdgeOk false forces inEngine false). Paused edges lose aa8/ab8 evidence (execEvidence:1223, beyond window), so only buf.sawExecuting would catch them.
- Fix: At the edge, when `!inEngine` and (`sawExec` or `buf.sawExecuting`), end the head as already executed (log it) instead of re-sending. Re-send only when the head was wiped with no exec evidence.
- Confidence: med (code path is unambiguous; the 150 ms window and trigger timing were not reproduced).

## H3-F2 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1373-1376 (detach), 1686-1687 (detachTick only in combat branch), 1742 (non-combat hand-off end, no reattach); 1547-1585 (detachTick, beyond window)
- Claim: Round nodes the player created during a held-head hand-off are detached and reattached only by detachTick, which runs only on combat frames. Combat ending with nodes still detached leaves them stranded until the next combat edge discards them (1686).
- Scenario: player clicks a Force power while the head is engine-held; the node is detached; the buffered commands finish; the last enemy dies before the 300 ms quiet window and !busy hold, so combat ends. Nothing reattaches the node, the power never fires, and the discard at the next combat is logged only with trace_queue on (traceDetach gate).
- Fix: Run the reattach (or an explicit discard with a log line outside the trace gate) from the non-combat branch while `g_detached[k].n > 0` and the engine is quiet.
- Confidence: med (code path explicit; needs combat to end inside the detach window, not reproduced).

## H3-F3 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1380-1393 (held-head cancel, drops member buffer at 1390), 1566-1573 (detachTick cancel, runs before reattach), 2055 (g_lastClickTick set by any LMB edge), 834 (queue Cancel hidden in real combat); patch_manager_mods/queue_hud_src/QueueHudLogic.h:159-165 (beyond window)
- Claim: "Cancel click" means any left-button press within 600 ms, not a press on a cancel control. The queue Cancel is hidden in real combat (834), so the heuristic can only misfire there.
- Scenario: a held head (engine-held grenade) is wiped at combat start. The player clicks an enemy 100 ms after the edge to attack. On the next frame heldHeadAction returns DROP with cancelClick true and sawExec false, so the member's whole buffer is cleared as DR_CANCEL. Variant: detached node, engine quiet, any click within 600 ms of now discards the node and clears the buffer before the reattach check.
- Fix: Count only presses on the vanilla BTN_CLEARALL / BTN_CLEARONE rects (or the queue's own Cancel rect). Otherwise treat a vanished head as RESEND.
- Confidence: med-high (code is explicit; not reproduced in play).

## H3-F4 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1523-1531 (detachRound stores pointers only, no owner), 1547-1585 (detachTick reattaches into party::member(tbl,k), beyond window), 635 (drawDetachedSlots reads g_detached[0] only; beyond window)
- Claim: Detached state is indexed by slot, not creature. Heads and buffers are protected by owner-slot holds (1310, 1361), but detachTick reattaches the old creature's nodes into whichever creature now occupies slot k. Detached nodes are off-list, so the engine never frees them: this is wrong-owner reattach, not use-after-free (no UAF found).
- Scenario (conditional on leader switch being allowed in combat, not verified here): leader A's power is detached into g_detached[0] during a held head; the player switches leader to B mid-hold; detachTick(0) reattaches A's node into B's round list, so A's power runs as B. Separately, companion detached nodes are never drawn because drawDetachedSlots reads slot 0 only.
- Fix: Store the owner creature in Detached. Reattach only when that creature still sits in the slot, otherwise discard with a logged reason. Draw detached slots for every member.
- Confidence: low-med (code path certain; depends on whether mid-combat leader switch is possible).

## H3-F5 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1333 and 1342 (head moved out of buf into g_handoff), 1361 (owner hold), 1377 and 1400 (stalls), 1742 (combat-end drop), 1275-1278 (endHandoff DROP line, trace-gated)
- Claim: An unsent head exists only in g_handoff. Combat end discards it with `h = Handoff{}`, and the only log line is trace-gated, so the loss is silent by default.
- Scenario: the head is a companion's Force power and the owner is no longer slot k (leader switch, 1361), or the member's own engine cast keeps midFlight true (1400). Combat ends before the stall clears: the head leaves the buffer and is never dispatched, with no log unless trace_queue is on.
- Fix: On combat end, put an unsent head back at the front of its buffer when its owner is not yet controlled. Log DROP outside the trace gate.
- Confidence: med (code path clear; needs combat to end during a stall).

## H3-F6 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:2269-2270 (item hook passes through in combat), 2356-2357 (spell hook), 1417-1419 (foreign set taken at first send only); patch_manager_mods/30_queue_hud.md:152 (doc promises click order)
- Claim: In combat both hooks return to vanilla at once, even while a hand-off is still sending buffered commands. A click made after the first send bypasses the buffer and is not in the foreign set, so it can run before buffered commands that were clicked earlier.
- Scenario: buffer [medpac, Force Push] at combat start. Medpac is sent on frame 0. The player clicks Force Lightning on frame 3 and it goes straight to the engine. Push is sent on frame 5, so the round list runs [medpac, Lightning, Push]: Lightning runs before Push although Push was clicked first.
- Fix: While `g_handoff[k].pending` or the buffer is busy in combat, append the click to the buffer (or the hand-off tail) instead of passing through.
- Confidence: med-high (code is explicit; assumes the engine runs round nodes in list order, which doc 30 implies).

## H3-F7 [med] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1373-1376 and 1374 (comment: pending nodes are the player's click), 1527-1531 (detachRound pops all nrn); patch_manager_mods/queue_hud_src/QueueHudLogic.h:1211-1219 (engineHoldsAction, any subtype 9/10; beyond window)
- Claim: Detach and the held test treat every pending subtype 9/10 round node of member k as the player's click. Companion AI-chosen powers and any orphan of the wiped head fall in the same set.
- Scenario: a companion AI casts a power as combat starts. Its node is detached and delayed until the hand-off ends. If doc 29 D6 holds (the combat-start wipe leaves the head's own round node), the orphan is detached, held turns false, the head is re-sent (RESEND), and the orphan is reattached and runs later, so the command executes twice.
- Fix: Track the head's round node pointer at dispatch and test or detach only the player's nodes. Skip detach when the only pending node is not the player's click.
- Confidence: low (the delay is code-certain; the double run depends on doc 29 D6, which is unverified).

## H3-F8 [low] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1412-1414 (stale comment and keep path), 1428-1437 (clear on first send); patch_manager_mods/30_queue_hud.md:12 (open risk: companion follow after clear), 152 (D2 says the clear empties the round list); patch_manager_mods/29_paused_command_queue.md:34 (D6 says ClearAllActions does not)
- Claim: The clear-first path wipes member k's whole server queue, which for a companion removes its 0x3D FollowLeader head and AI entries. Default config never reaches it, because keepNow is true (QueueHudLogic.h:1223, keep_unpaused defaults on at QueueHudLogic.h:214).
- Scenario: handoff_keep_unpaused=0 and combat starts unpaused with a buffered companion Force power. ServerClearAllActions runs on the companion, its follow entry is gone, and nothing re-adds it until the AI acts.
- Fix: Do not clear companion queues on the first send (keep path only), or probe the follow state after a clear before relying on it. Fix the stale comment at 1412-1413.
- Confidence: med that the path is reachable with those settings; low on the engine effect (docs disagree and the follow question is open).

## H3-F9 [low] edge-case
- Where: patch_manager_mods/_shared_src/ActQueue.h:120 (round loop stops at kMaxRound=4, no overflow flag; beyond window), patch_manager_mods/queue_hud_src/QueueHudLogic.h:40; patch_manager_mods/30_queue_hud.md:92 (doc: engine round cap is 4)
- Claim: gatherFor reads at most 4 round nodes and never reports overflow. detachRound and roundOrderTick pop only s.nrn nodes, so a fifth node would remain at the list head and run first after reattach or reorder.
- Scenario: only if the engine ever holds more than 4 round nodes, which doc 30 says it cannot: a detach pops 4, and after reattach the fifth node runs before the detached player click.
- Fix: After the snapshot loop, check whether the next node is non-null. If so, skip reorder and detach for that frame.
- Confidence: low (relies on doc 30's cap of 4, not verified in this recon).
