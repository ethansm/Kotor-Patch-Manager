# H8 findings

## H8-F1 [med] bug
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:605-620 (useOnMember), :624-669 (targetedUse, selfUse), :689-692 (drainRing route choice); patch_manager_mods/07_force_power_hotbar_evidence/target_modes/decomp_751750.txt:84-124 (vanilla HudInvokeGroup flag gate, read past window); patch_manager_mods/action_hotbar_src/HotbarConfig.h:85 (EntryUsable)
- Claim: The direct routes (@self, @lowhp) never read the HUD entry flags. Vanilla HudInvokeGroup runs the item callback only when flags bit0 (usable) is set; with bit0 clear it reports the why-not bits 1-4 instead. The direct path skips both and checks only CanUseItem(strict).
- Scenario: An item whose HUD entry is dimmed (bit0 = 0, why-not bits set) but which CanUseItem accepts on the target is used when its slot is pressed in @self or @lowhp mode. Vanilla would refuse with its message. When CanUseItem refuses, useOnMember returns true (ActionHotbar.cpp:606-607), so the press is consumed with no effect and no message.
- Fix: In drainRing take the direct route only when `e.flags & hb::EntryUsable`; otherwise fall through to invokeEntry so the vanilla why-not path runs. Keep CanUseItem as a second gate.
- Confidence: med (both sides read directly; not verified what sets bit0 on live entries, or what CanUseItem(strict) covers).

## H8-F2 [med] edge-case
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:643-655 (target chosen at drain time), :616-617 (member id sent as targetId); patch_manager_mods/queue_hud_src/QueueHud.cpp:2319-2330 (buffer stores targetId), :1128-1134 (dispatch re-sends stored targetId)
- Claim: While the queue is paused or busy, the @lowhp target is decided at press time and buffered as a raw member id. Dispatch sends that id without re-checking HP, Down, or party membership.
- Scenario: Game paused, companion Mira at 20% HP, press a @lowhp healing slot. Mira regenerates, or goes Down, or leaves the party. Unpause: dispatch uses the item on a full-HP Mira (wasted) or on a Down or absent id.
- Fix: Buffer the target mode (lowhp / self) instead of the member id and resolve it at dispatch. Or re-check ok/down/eligible at dispatch and drop or re-target.
- Confidence: med (both sides read in code; live behaviour after a party change while paused is not verified).

## H8-F3 [med] doc-mismatch
- Where: patch_manager_mods/action_hotbar_src/HotbarLogic.h:311-320 (decideKey: bound-digit swallow sits behind hudActive; comment at :318 says "ALWAYS swallowed"); patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:1988 (hudActive = gate && tick age < 250 ms), :2002-2008 (stale-tick WARN says "not invoked")
- Claim: With the gate open but the HUD tick older than HudFreshMs, a bound digit falls to "pass(hud inactive)" and reaches the game. Keys 1-3 then switch the party leader. The comment says a bound key is always swallowed, and the WARN does not say the key was passed on.
- Scenario: The HUD tick stalls over 250 ms while the gate is still open (frame hitch, or the tick not running during pause). Player presses bound key 2: nothing fires and the party leader switches to companion 2.
- Fix: Swallow bound digits whenever g_hudGateOk is set, even when the tick is stale. Change the WARN to say the key was swallowed, not invoked.
- Confidence: med (the decision path is unambiguous; whether the tick stalls in normal play or during pause is not verified).

## H8-F4 [low] ux
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:605-607 (CanUseItem refused -> return true), :659-668 (selfUse)
- Claim: A direct use that CanUseItem refuses is reported only as a KP_LOG line, and the press is consumed. The vanilla invoke would run its own why-not path with feedback.
- Scenario: Press a @self item slot after the target state changed so CanUseItem now refuses. Nothing happens on screen and no message appears.
- Fix: On refusal return false so drainRing falls through to invokeEntry (vanilla message), or show the same feedback.
- Confidence: low (refusal needs a state change between the candidate check and the use; vanilla message content not checked).

## H8-F5 [low] bad-assumption
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:510 and :517 (active group saved, then restored unconditionally); patch_manager_mods/07_force_power_hotbar_evidence/target_modes/decomp_751750.txt:57 (vanilla writes hud+0x1C98 on entry)
- Claim: The restore assumes nothing after HudInvokeGroup needs hud+0x1C98 to keep the value that the vanilla call set. Any pending state keyed off ActiveGroup is reset right after the call. Not checked in this window.
- Scenario: Default mode, targeted power bound, two or more members. Vanilla arms a portrait pick, then line 517 resets ActiveGroup. If the portrait completion reads ActiveGroup, the click casts nothing.
- Fix: Read the portrait-pick completion before relying on the restore. If it reads 0x1C98, skip the restore when the call armed a pick.
- Confidence: low (07 doc says Default mode works live, which argues against this; only the pick-completion decompile would settle it).

## H8-F6 [low] logging
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:515-516 (restore skipped when sel differs; logged at WARN)
- Claim: If the group selection changes during the call, the player's quick-bar selection for that group is not restored and a WARN is logged. The decompile shows HudInvokeGroup itself only reads sel, so the change would come from a callback that rebuilds the list (for example an item stack emptied). That is a normal event logged as a warning.
- Scenario: An item callback uses the last item in group 1 and the list rebuild resets sel. The player's group 1 selection changes and a WARN is logged each time.
- Fix: Restore whenever oldSel is still present in the group list. Log the change at DEBUG.
- Confidence: low (callback-driven rebuild not verified).

## H8-F7 [low] edge-case
- Where: patch_manager_mods/action_hotbar_src/ActionHotbar.cpp:611 (memberId check rejects only 0), :617 (sent as targetId); patch_manager_mods/action_hotbar_src/HotbarLogic.h:73-81 (pickPartySlot treats 0 / 0xFFFFFFFF as transient)
- Claim: useOnMember accepts member object ids 0xFFFFFFFF and the 0xFFFFFFF0-0xFFFFFFFE sentinel range, which pickPartySlot treats as transient, and sends them as the target id.
- Scenario: Member ids read during a load or fast-travel sentinel state with Vitals.ok set. @lowhp sends target 0xFFFFFFFF; the heal lands on nothing, or on whoever the engine maps that id to.
- Fix: Treat 0, 0xFFFFFFFF and 0xFFFFFFF0-0xFFFFFFFE as TARGET_FAIL in useOnMember.
- Confidence: low (not checked whether Vitals.ok can be true with such ids).
