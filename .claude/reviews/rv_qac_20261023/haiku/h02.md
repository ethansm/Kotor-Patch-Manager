## H2-F1 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:874-883 (reInjectWhy; 875 ignores paused and now); patch_manager_mods/queue_hud_src/QueueHud.cpp:1812-1846 (RI_OK branch 1823-1846, reInjectCount++ at 1836); patch_manager_mods/queue_hud_src/QueueHudLogic.h:206,209 (defaults pause_reinject=1, pause_eaten_wait=1)
- Claim: The RI_OK re-inject branch runs before the verdict path, so it skips the 500 ms settle (kMinActiveMs) and the 150 ms debounce. It also ignores pause. Each tick that is RI_OK re-dispatches and bumps reInjectCount, so the cap of 2 allows the initial dispatch plus two re-sends within about two frames.
- Scenario: Companion (slot >0) with a resting 0x3D at queue head. A cast is dispatched (serverCast refused, or a leader switch while its queue still holds 0x3D). On the next frame the action is not yet visible, so RI_OK re-sends it on frame+1 and frame+2. If the game is paused, the same re-sends happen although pause_eaten_wait=1 documents "no re-inject while paused".
- Fix: Put RI_OK behind the same settle, debounce and pause/eaten-wait gates as the verdict path, or require one kMinActiveMs after markDispatched before the first RI_OK re-inject.
- Confidence: med (control flow is certain; whether a 0x3D sits at queue head on the first absent frame is not confirmed in play).

## H2-F2 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:1477 (activeVerdict rule 1 returns AV_PRESENT before any timer); patch_manager_mods/queue_hud_src/QueueHud.cpp:1786-1787 (round-list loop has no staleness check, unlike cur at 1775); patch_manager_mods/queue_hud_src/QueueHud.cpp:1164,1167 (kickSkip gates for a starved 0x3F)
- Claim: actionInQueue counts round-list nodes of subtype 9/10 with no staleness check; curReal() staleness applies only to cur. A 9/10 node that never leaves keeps buf.active set, and DS_ACTIVE / DS_NRN_BUSY block all dispatch. No timer runs in that state. The only escape is the Cancel button.
- Scenario: A starved 0x3F (cast behind a resting 0x3D) sits in rn while kickStarved's gates never pass (round 0, RoundHasPending 0, or aa8/ab8 stuck nonzero). The buffer waits indefinitely, with a WAIT heartbeat each second, until the user presses Cancel.
- Fix: Add an unpaused lifetime cap on an active action (for example 30 s) that logs a DROP and ends it with a ServerClear. Apply curReal-style staleness to rn 9/10 nodes.
- Confidence: low-med (the code path is certain; no evidence in the code that such nodes persist in play).

## H2-F3 [med] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:842,859 (FlagGate cap 2000 ms); patch_manager_mods/queue_hud_src/QueueHud.cpp:1915-1917 (flagsBusy), 1952 (flag_cap dispatch); patch_manager_mods/queue_hud_src/QueueHud.cpp:1777 (code comment: a dispatch while a spell or item holds the creature ClearAllActions it)
- Claim: After 2 s of aa8/ab8 being set, the buffered command is dispatched anyway. aa8/ab8 belong to the creature, not to the buffered action. If they come from an unrelated long action, that action is cleared by our dispatch.
- Scenario: An unrelated flagged action on the same creature stays set for more than 2 s while a buffered item waits. The cap sends the item and the engine clears the unrelated action.

- Confidence: low-med (depends on aa8/ab8 staying nonzero for more than 2 s outside our own actions; not measured).

## H2-F4 [med] bug
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:818 (decideAction returns DISPATCH_NOW whenever inCombat, regardless of buf.active); patch_manager_mods/queue_hud_src/QueueHud.cpp:2317-2321 and 2416-2420 (hooks set active=true and overwrite activeAction); patch_manager_mods/queue_hud_src/QueueHud.cpp:1685-1689 (tickItemQueues returns early in combat)
- Claim: In combat each click passes through, and the hook overwrites activeAction without resolving the command still in flight. The displaced command gets no RESOLVE, VANISH, DROP or re-inject line, and nothing closes it while combat lasts, because tickItemQueues returns early in combat.
- Scenario: Two clicks in combat, the first still pending in the engine. Only the second is tracked. If the first is eaten, nothing re-injects it and the trace shows nothing.
- Fix: When buf.active is already set in combat, emit a DROP or RESOLVE line for the displaced cmdId before overwriting, or keep a small list of in-flight pass-through commands.
- Confidence: med (the overwrite is certain; whether the first click is still in flight at the second click is plausible but not confirmed).

## H2-F5 [med] logging
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:80,82 (PerformUseItem and PerformCastSpell return void); patch_manager_mods/queue_hud_src/QueueHud.cpp:1116-1135 (dispatchAction ignores any result); patch_manager_mods/queue_hud_src/QueueHudLogic.h:1479,1481 (refusal resolves as AV_UNSEEN); patch_manager_mods/queue_hud_src/QueueHud.cpp:1079-1094 (server route logs its refusal, client route does not)
- Claim: The client wrappers return nothing, so a refused cast (no FP, target gone) cannot be told apart from an action that vanished. It resolves after about 0.65 s (500 ms settle plus 150 ms debounce) as RESOLVE seen=0 with no refusal marker. This is not a stall: unpaused with round != 0 it resolves in that window; paused it waits, then re-injects at most 6 times at 250 ms spacing and gives up.
- Scenario: The leader casts a buffered power with no FP left. The engine refuses silently. The trace shows UNSEEN and the icon disappears with no reason logged.
- Fix: Compare the caster's FP or item count (or the next-tick queue) before and after dispatch, and log REFUSED when neither changes.
- Confidence: high on the code (void return), med on impact.

## H2-F6 [low] bad-assumption
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:1518 (ev.executing from aa8/ab8 and any 0x0F/0x2E entry); QueueHudLogic.h:776-778 (notePresent sets sawExecuting); QueueHudLogic.h:1480 (rule 2 EXECUTED); QueueHudLogic.h:806-814 (gateEngineCount counts player entries as busy); patch_manager_mods/queue_hud_src/QueueHud.cpp:1855 (notePresent call site)
- Claim: "Executing" is read from creature-level signals, not from our own command. There is no owner check on the 0x0F/0x2E entries or on aa8/ab8. A foreign action on the same creature while our action is eaten sets sawExecuting, so the eaten action later resolves EXECUTED and is never re-injected. Player entries that are not 0x3D/0x3F also block dispatch through gateEngineCount, without ever resolving it.
- Scenario: Our item is wiped by FollowLeader. In the same window an unrelated flagged action runs on the creature. sawExecuting latches. When that action ends, our action resolves EXECUTED with no re-inject. BG23 (QueueHudLogic.h:1778 comment) already names the presence half of this confusion.
- Fix: Set sawExecuting only when the executing node matches our spell or item id (cur or entry param0), and ignore aa8/ab8 for that decision unless our node is present.
- Confidence: low-med (needs a same-creature foreign action inside the eaten window; no log evidence checked).

## H2-F7 [low] bug
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:666,831,879 (kMaxReInjectCount is checked only in shouldReInject and reInjectWhy); patch_manager_mods/queue_hud_src/QueueHud.cpp:1886-1894 (verdict re-inject increments eatenReInjects, not reInjectCount; markDispatched clears eaten at 1894); patch_manager_mods/queue_hud_src/QueueHudLogic.h:776-779 (notePresent resets eatenReInjects and eatenUnpausedMs); patch_manager_mods/queue_hud_src/QueueHudLogic.h:1481 (rule 3 UNSEEN)
- Claim: kMaxReInjectCount is not a total cap. Verdict re-injects never increment reInjectCount. A present frame at least 2 s after the last re-inject resets both the per-episode budget (6) and the 20 s unpaused clock, so a repeating present-then-eaten cycle has no bound. Separately, after an EATEN_REINJECT, eaten is cleared, so if the re-injected action is not visible within 500 ms unpaused, rule 3 resolves it UNSEEN even if the engine applies it later.
- Scenario: A non-executing rn-only node stays present about 2.5 s, vanishes, is re-injected, and repeats. Each cycle resets the budget and clock. Verdict re-injects need eaten latched by a pause (rule 4b) or a non-idle engine (rule 5), so this is uncommon.
- Fix: Count total re-injects per action in the verdict path too. Reset eatenUnpausedMs only on resolve or dispatch, not on presence.
- Confidence: low (needs a repeated present-then-eaten cycle; not seen in any log I checked).

## H2-F9 [low] bug
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1709-1720 (identity swap moves g_itemQueue, g_lastOurs and per-slot tails, not g_flagGate); patch_manager_mods/queue_hud_src/QueueHud.cpp:1187 (g_flagGate[3] is per slot); patch_manager_mods/queue_hud_src/QueueHud.cpp:1917 (gate use)
- Claim: FlagGate state is per slot, but buffers move with the creature on a party rotation. The hold timer (holdSince, sawBusy, clearing) stays with the slot, so the buffer that moves in inherits another buffer's hold.

- Fix: Swap g_flagGate[k] with g_flagGate[slot] together with the buffers, or reset both on swap.
- Confidence: med (state ownership is certain; impact is small).

## H2-F10 [low] edge-case

## H2-F11 [low] edge-case
- Where: patch_manager_mods/queue_hud_src/QueueHudLogic.h:761-762 (pausedEaten latch; unpause edge resets the budget); QueueHudLogic.h:764-766 (unpaused accrual, capped at 1000 ms per verdict tick); QueueHudLogic.h:1478-1479 (debounce and 500 ms settle are wall-clock); QueueHud.cpp:1935-1956 (dispatch path has no pause input)
- Claim: On pause timing: the 20 s give-up counts only unpaused time, but only on verdict ticks and at most 1000 ms per step. kMinActiveMs and the debounce are wall-clock, not pause-aware, so a dispatch made during a long pause is already past its settle at unpause. Dispatch is not gated on pause. GetTickCount wrap is safe: every delta is uint32 arithmetic.
- Scenario: A dispatch made while paused has not yet been applied by the engine at unpause. Pause_eaten_wait latches eaten (rule 4b). At the unpause edge the budget is reset and rule 5 sees an idle engine, so the action is re-injected on the first unpaused tick, possibly as a second copy if the first is applied late.
- Fix: Measure the settle and debounce in unpaused time (or restart them at the unpause edge), the same way eatenUnpausedMs is measured.
- Confidence: low (depends on whether the server applies a paused dispatch before unpause; see RECON OPEN).
