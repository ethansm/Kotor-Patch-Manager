## V4-2 [med] CONFIRMED bug (layout)
- Sources: h09-F1
- Where: HotbarLogic.h:285-289 (makeScale returns the identity when c == 1.0); ActionHotbar.cpp:1547-1551 (aspectFix); ActionHotbar.cpp:1579-1580 (createLabel -> unitRect -> guikit::setRect); hotbar_logic_test.cpp:417-419 (pins the identity at 1600x1200); _shared_src/GuiKit.h:241-249 (setRect writes raw px)
- Defect: setRect takes engine px (the 3840x1600 rows in the test table are px: y 478 -> 1274). For every exact 4:3 client (c computes to exactly 1.0: 1024x768, 1280x960, 1600x1200, 1920x1440) makeScale leaves sx=sy=1, so labels are placed at layout units (bar at y=478 px) instead of units * H/600. Only 800x600 is right. The ultrawide branch is correct.
- Scenario: Windowed 1024x768: bar, editor, tooltip, picker are created at their 800x600 coordinates, so the bar sits at y=478 of 768 (should be 611) and every frame is 0.78x its intended size, and the HUD panel clamp/hit boxes follow the same wrong rects.
- Fix: In makeScale set `k.sx = (double)w/rw; k.sy = (double)h/rh;` whenever w,h,rw,rh are all > 0 and keep `k.c = c` (1.0 for 4:3); return the pure default only when a size is unknown (aspectCorrection already returns 1.0 then). 800x600 stays the identity (sx = sy = 1).
- Test: change hotbar_logic_test.cpp:419 to `i2.sx == 2.0 && i2.sy == 2.0 && i2.c == 1.0`; add makeScale(1024,768,800,600): sx == sy == 1.28, unitRect(4,478,20,35,...) == {5,611,25,44}; unitRect at 1600x1200 == {8,956,40,70}. Keep the 800x600 identity case. PLAY row: set a 1024x768 window, load a save, expect `H3: window ... client=1024x768 ... x correction 1.0000` and the bar bottom-left, frames square.
- Engine question: None for the arithmetic; assumes GuiRefW/H read 800x600 (log line `ref=` shows it).

## V4-3 [med] PLAUSIBLE edge-case (dialogue digits)
- Sources: h07-F1
- Where: ActionHotbar.cpp:312-336 (gateEval); ActionHotbar.cpp:1988 (hudActive = g_hudGateOk && tick < 250 ms); HotbarLogic.h:313-320 (bound digit swallowed + enqueued)

Doc 07 lines 779/801/877/859 still list "digit in dialogue" as untested, and doc 07:196/344 asked for a conversation flag that was never built. - Fix: First run the PLAY row; if any `SWALLOW` appears in dialogue, add `inConversation` to KeyEvent (engine flag or dialog panel vtable in the panel list) and return pass for digits. Independent of the result, add a DEBUG-level gate line naming the top panel vtable so the dialogue case is visible in the log (gateLog already prints top=/topf48=).
- Test: PLAY row (PLAY_TEST_QUEUE.md): bind slot 1-3, enter a voiced conversation and a letterboxed cutscene dialogue, press 1, 2, 3 on reply menus and during an NPC line. Pass: `action_hotbar_log` shows `GATE open=0 why=other-panel-on-top` (or no `cap:` line) and the reply is selected; any `cap: ... SWALLOW` there is a FAIL. Unit test after the fix: decideKey with inConversation=true -> "pass(conversation)", no swallow.
- Engine question: Does the dialogue GUI panel appear in the panel list with ignore bits (0x600) while the HUD is still drawn? Never logged.

## V4-4 [med] CONFIRMED bug (editor save)
- Sources: h09-F2
- Where: ActionHotbar.cpp:1296-1297 (moveDuplicates + g_cfg.SetSlot mutate the live config); 1300 (Save); 1307-1308 (return false without rollback or refreshEffective)
- Defect: assignSlot edits g_cfg before Save and never reverts when Save fails. The failure does not change the file stamp, so no reload repairs g_cfg either. The bar and g_slotBound still show the old assignment while g_cfg holds the new one plus any duplicate it blanked.
- Scenario: Read-only or locked action_hotbar.ini: bind power P to slot 3 -> "Saving the config failed" -> bar unchanged. Later the lock clears and the player edits slot 7: Save serialises all of g_cfg, so slot 3 = P (and the slot the duplicate moved from = none) is written silently. recomputeBound at the next char change also makes digit 3 live.
- Fix: Copy the profile (`hb::Profile backup = d;` or a full Config copy), mutate, and on `!ok` restore it (`d = backup`) before returning false; call neither recomputeBound nor refreshEffective on the failed path.
- Test: pure test of a helper `applyAssign(Profile&, ...)` is awkward; instead add a hotbar_logic_test.cpp case that copies a Profile, runs moveDuplicates + SetSlot, restores the copy and checks equality. PLAY row: set action_hotbar.ini read-only, bind slot 3, expect the WARN `edit: assign ... ok=0`, clear read-only, bind slot 7, expect slot 3 still empty in the INI.
- Engine question: None.

## V4-5 [med] PLAUSIBLE edge-case (@lowhp target frozen while buffered)
- Sources: h08-F2
- Where: ActionHotbar.cpp:643-655 (idx chosen at drain time); ActionHotbar.cpp:611-617 (memberId, then PerformUseItem(... memberId, member+0x24)); queue_hud_src/QueueHud.cpp:2316-2330 (makeItemAction stores targetId and copies pos); queue_hud_src/QueueHud.cpp:1128-1134 (dispatch re-sends a.targetId/a.pos with no re-check)
- Defect: When queue-hud buffers the hotbar's PerformUseItem, the @lowhp choice is fixed at press time and replayed verbatim. Nothing re-evaluates HP, Down state, membership or position at dispatch. While the game is paused HP cannot change, so the pure pause case is benign; the real exposure is the busy/queued case (engine queue non-empty, up to 3 buffered per member).
- Scenario: Out of combat, Mira is lowest at 20%. Press the @lowhp medpac slot twice quickly: both presses pick Mira (the first heal is still buffered, HP unchanged), so the second medpac is dispatched at Mira after she was healed while Bastila is now the lowest; or a member goes Down/leaves between press and dispatch and the replay targets a stale id.
- Fix: Cheapest: in targetedUse count pending heals (queue-hud exposes buffered item targets) or refuse a new @lowhp press while queue-hud holds an item for the same target; better: let queue-hud store a "re-target at dispatch" flag (hotbar provides a callback `retargetLowHp(itemId) -> memberId`) and drop the action if CanUseItem(strict) fails. Cap: document the limitation in README target-modes section if not fixed.
- Test: pure vector in hotbar_logic_test.cpp for chooseTarget with a "pendingHeal[i]" adjustment (reduce missing HP of members with a buffered heal) once such a field exists. PLAY row: two members at low HP, press the @lowhp slot twice in one second with queue-hud on; pass: the two `target: PerformUseItem(... member N ...)` lines name different members.
- Engine question: Does queue-hud buffer item uses when the game is unpaused but the engine queue is non-empty (decideAction DECIDE_BUFFER with gateQ > 0)? Assumed from decideAction usage at QueueHud.cpp:2316.

## V4-7 [low] PLAUSIBLE edge-case (direct item routes skip the HUD usable flag)
- Sources: h08-F1, h08-F4
- Where: ActionHotbar.cpp:689-692 (UR_SelfDirect / UR_LowHpDirect taken without looking at e.flags); ActionHotbar.cpp:605-608 (refusal logs and returns true); HotbarConfig.h:85 (EntryUsable = bit 0); 07_force_power_hotbar_evidence/target_modes/decomp_751750.txt:84-124 (vanilla runs the item callback only when flags bit0 is set, else reports why-not bits 1-4)
- Defect: Only items use the direct routes (powers never do: useRoute requires K_Item), so FP exhaustion is NOT bypassed; Invoke=1 powers always run the vanilla why-not path. Items on @self/@lowhp skip the entry's bit0 check; they rely on CanUseItem(strict) alone (the same engine gate vanilla runs later in 0x77C780). For a CanUseItem refusal, keep consuming the key but show `ed.msg`/the existing tooltip line "Not usable right now" or play the vanilla refusal sound. Do not return false on refusal for @self with 2+ members: invokeEntry would arm the portrait-pick instead.
- Test: add a pure `hb::directRouteAllowed(route, flags)` and pin: flags=0 -> false, flags=1 -> true. PLAY row: find an item the HUD dims in the current state, bind it @self, press; pass: either the vanilla message appears or `target: self: CanUseItem refused` is paired with visible feedback.

## V4-8 [low] CONFIRMED edge-case (failed INI read followed by a Save)
- Sources: h07-F2, h07-F11
- Where: ActionHotbar.cpp:452-459 (checkConfig: filewatch::changed records the stamp before Load; failure only logs and returns); ActionHotbar.cpp:1281 + 1300 (assignSlot forces checkConfig then Saves g_cfg); HotbarConfig.h:320-328 (readFile never checks ferror); _shared_src/FileWatch.h:77-87
- Defect: When the reload fails (file deleted, locked, short read), the stamp is already consumed, so the previous in-memory config stays authoritative and the next assignSlot Save recreates/overwrites the file from it. Deleting the INI to reset the bars is therefore undone by the next edit. readFile also returns true after a failed fread, so an I/O error yields a truncated config that Load parses as complete.
- Scenario: User deletes action_hotbar.ini while playing to reset; the next slot assignment writes all old profiles back. Or the INI is briefly locked during a poll, the user hand-edits it, then assigns a slot in the editor: the hand edit is overwritten.
- Fix: In checkConfig, on `!c.Load` reset the poll (`g_cfgPoll.primed = false` or restore the previous stamp) so it retries, and set a `g_cfgStale` flag; assignSlot refuses (ed.msg + WARN) while stale. In readFile return `!ferror(f)`.
- Test: HotbarConfig round-trip test: readFile on a directory path returns false. PLAY row: delete action_hotbar.ini in game, open the editor, bind a slot; pass: log `cfg: cannot read` then either the refusal line or the template rewritten with only the new slot.
- Engine question: None.

## V4-12 [low] PLAUSIBLE edge-case (key state tracking after focus loss)
- Sources: h07-F5, h07-F6
- Where: ActionHotbar.cpp:1975-1986 (modifier resync only clears flags); HotbarLogic.h:310-317 (a later non-swallowed key-down does not clear downSwallowed)
- Defect: (a) If the Ctrl/Alt/Shift key-down happened while the game had no focus, g_ctrl stays false and the held modifier is ignored, so Ctrl+1 acts as plain 1 (swallowed, slot invoked instead of the game's binding). - Test: decideKey vector: downSwallowed=true, key-down not bound -> clearDown == true. PLAY: not worth a row.
- Engine question: Is GetAsyncKeyState trustworthy when the window just regained focus? Assumed yes.
