# V3 validated findings (sources: h01, h05, h11)

Key-question answer (engine evidence, all paths under patch_manager_mods/07_force_power_hotbar_evidence/target_modes/):
- 0x775700 (disasm_775700.txt 0x775725-0x775747) forwards its stack args to the builder 0x87A5C0 as: builder(spell, byte@+0x14, byte@+0x18, byte@+0x1C, int flag@+0x20, float* pos@+0x10, target@+0xC).
- The builder (decomp_87a5c0.txt:55, disasm_87a5c0.txt 0x87a5ff) calls `FUN_0044b8a0(pos,pos)` UNCONDITIONALLY (no NULL test; 0x44B8A0 is a 52-byte two-vector helper, almost certainly dot/length^2). So the pos pointer IS dereferenced on EVERY cast, object-target casts included. NULL is therefore NOT a safe value for the pos slot (likely crash).
- If that value is >= the double at 0x993768, message flag bit 2 is set and pos[0], pos[1], pos[2]+DAT_0098bb10 are serialized (decomp_87a5c0.txt:57-60,75-80). Server case 0x11 (decomp_65be70.txt ~1131-1151) then sets "has location" (local_184=1) and passes x,y,z with the target into AddCastSpellActions 0x565310.
- Flag slot (wrapper +0x20, builder param_5): nonzero adds bit 4; server then sets local_178=1 and SKIPS the 0x565310 cast branch (65be70 `if (local_178 == 0)`). This is the real root cause of QL9 ("buffered replays never fire"): the old replay passed a non-null pointer in this slot.
- All three vanilla callers (7791A0 x2 at 0x779368/0x779488, 899270 at 0x8992e9) pass a pointer to a ZEROED float[3] as pos and 0 as the flag (decomp_7791a0.txt:77, disasm_899270.txt:69-77). No caller ever passes a real ground point.
- Queue-hud's stack layout is positionally right (typedef QueueHud.cpp:82 puts arg 3 in the `targetId` slot, arg 7 in `pos`); only meaning/values are wrong.

## V3-1 [high] CONFIRMED bug
- Sources: h01-F1, h01-F2, h11-F1 (also h01-F3 typedef/doc part)
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1113-1129 (dispatchAction replay: `a.targetId` in the engine pos slot, `pp` in the flag slot); :2371-2382 and :2430-2431 (hook reads arg3 into `targetId`, derefs arg7 as a pointer, stores `posPtr ? posVal : nullptr`); :82 (typedef); patch_manager_mods/queue_hud_src/QueueHudLogic.h:626-637 (makeSpellAction), :650-652 (replayPos); patch_manager_mods/_shared_src/GameAddr.h:71; patch_manager_mods/30_queue_hud.md:78
- Defect: At capture `targetId` (ebp+0x10) is the caller's STACK ADDRESS of its zeroed float[3] (QL9 log shows tgt=0x00dbee74). It is stored raw and passed back as the pos pointer at replay, after that frame is gone, so the builder reads 3 floats of whatever now lives at that address (live frames of the current call chain). The real pos floats are never copied (the hook copies from ebp+0x20, the int flag, which is always 0, so `hasPos` is always false and `a.pos` stays zero). Flag slot: with default spell_replay_pos=1 the replay passes NULL (=0, correct only because hasPos is always false); with spell_replay_pos=0, or if a caller ever passes a nonzero flag, `pp`=&a.pos is a nonzero flag, setting bit 4 so the server skips the cast (the QL9 failure).
- Scenario: Pause, click a Force power (any object-target cast), unpause. Replay hands the builder a dead stack address. Any garbage dword that looks like a large float (e.g. 0x7F000000 kInvalidObjectId and client object ids 0x7Fxxxxxx are about 1.7e38 as floats; 0xFFFFFFFF is NaN) pushes |pos|^2 over the 0x993768 threshold, so the message carries a bogus location and the server queues the cast with hasLocation=1 (wrong or no cast, nondeterministic; denormal-looking dwords such as code/heap pointers and small ints read as ~0 and behave like vanilla). No harm has been observed in the repo logs; the defect is certain, the visible impact depends on what sits on the stack and on 0x565310's use of the location (unverified).
- Fix: (1) Retype PerformCastSpellFn to (creature; uint32 spell, uint32 targetClientId, const float* pos, int multiclass, int meta, int domain, int flag) and fix the GameAddr.h:71 / doc 30:78 wording. (2) Capture: read ebp+0x10 as a pointer and copy its 3 floats (saferead) into QueuedAction.pos; read ebp+0x20 as a plain int into a new `QueuedAction.flag`; keep arg2 as the target id and stop storing the raw pointer in `targetId` (use a distinct field or zero it; logs/trace at QueueHud.cpp:1840/1891/1951 print `targetId` for items only). (3) Replay: pass `a.pos` (a valid zeroed copy, exactly like vanilla's &zero) in the pos slot and `a.flag` as an int in the flag slot. NEVER pass NULL as pos (builder dereferences it). (4) Remove the `spell_replay_pos` key (or reduce it to a flag-only A/B) and `hasPos`; `replayPos` becomes trivial.
- Test: queue_hud_logic_test.cpp (replaces the checks at ~1430-1438): `makeSpellAction(..., pos={1,2,3}, flag=0)` -> stored pos == {1,2,3}, replay pos pointer == &a.pos and never nullptr, replay flag == 0; `makeSpellAction(..., posZero, flag=5)` -> replay flag 5; static_assert that no field of QueuedAction other than `pos` is ever passed as the pos pointer (assert on a small `buildReplayArgs(a)` helper returning {pos ptr, flag}). PLAY: pause, queue 2 powers (e.g. Force Heal on self, Force Push on an enemy at range), unpause; `queue_hud_log_check.py` SPELL_ARGS where=hook and where=replay show the same 3 pos floats (all 0), same flag, and the new fields; both casts execute, server cast seen once each, no `pos=` mismatch.
- Engine question: Exact threshold at DAT_00993768 and what 0x565310 does with hasLocation=1 plus an object target; whether 0x44B8A0 is dot(v,v) (inferred from call shape, 52 bytes, args (v,v)). None of this changes the fix.
