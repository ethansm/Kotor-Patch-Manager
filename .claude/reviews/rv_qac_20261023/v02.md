## V2-1 [high] PLAUSIBLE bug (combat-start double use)
- Sources: h03-F1
- Where: patch_manager_mods/queue_hud_src/QueueHud.cpp:1332-1342 (inEngine / headHeld / headValid); 1331 (h.sawExec computed, never used on the non-held path); QueueHudLogic.h:669-671,1476-1479 (150 ms debounce, 500 ms kMinActiveMs)
- Defect: At the edge, a non-held head (`buf.active && !inEngine`) is always re-sent (`headValid=true`, `headHeld=false`). Neither `buf.sawExecuting` nor `h.sawExec` is consulted, so a command that already ran and left the engine inside the not-yet-resolved window (gone < 150 ms, or active < 500 ms) is dispatched again. `inEngine` is also forced false when `gatherFor` fails at the edge (`gEdgeOk=false`), so a command that IS in the engine is re-sent too.
- Scenario: medpac/Force power executes, cur node and aa8/ab8 clear, combat flag rises within 150 ms of the node vanishing (or in the 1-2 frames between PerformUseItem and the server queueing it). Out-of-combat tick has not resolved `buf.active` yet; handoffTick sees `!inEngine`, sends it again: second medpac consumed or FP spent twice.
- Fix: At the edge: if `!gEdgeOk` treat the head as held (wait) not vanished; if `!inEngine && (buf.sawExecuting || h.sawExec)` set `headValid=false` (log DROP reason executed); if `!inEngine` and `now - buf.activeStartTick < kMinActiveMs` route through the headHeld wait path so a late-appearing entry is seen. Put the decision in a pure `edgeHeadAction(active, inEngine, sawExecuting, sawExec, ageMs, gatherOk)` in QueueHudLogic.h.
- Test: queue_hud_logic_test.cpp vectors: (active, !inEngine, sawExecuting) -> DROP_EXEC; (active, !inEngine, !sawExec, age 80 ms) -> WAIT; (active, !inEngine, age 900 ms, !sawExec) -> RESEND; (!gatherOk) -> WAIT. PLAY: trace_queue on, press a hotbar medpac then provoke combat within ~0.3 s; pass = exactly one `HANDOFF_ONE`/stack decrement, no second `dispatch`/`HANDOFF_ONE` for the same cmd.
- Engine question: how long after `PerformUseItem` the server queue/round shows the action, and whether the node/cur gap before debounce can coincide with the combat flag (not measured).

## V2-2 [high] PLAUSIBLE bug (held-head detach pops the head's own node)
- Sources: h03-F7 (plus h03-F9 side note)
- Where: QueueHud.cpp:1373-1376 (detachRound once per hand-off when `s.nrn > 0`); 1522-1536 (detachRound pops all `s.nrn` nodes, any subtype/owner); 1383 and 1210-1217 (engineHoldsAction counts list nodes subtype 9/10); QueueHudLogic.h:1211-1233 (reattachReady)
- Defect: `handoff_detach_held` assumes every pending round node at the edge is the player's new click. If the held head itself sits in the round list as a pending subtype 9/10 node (e.g. edge while paused, where nothing pops), it is detached too. Next frame `engineHoldsAction` is false (the same-frame check still uses the pre-detach `s`), `heldHeadAction(held=false, sawExec=false)` returns RESEND, the head is dispatched again, and the later reattach pushes the old head node back so it runs a second time (it needs only a following 0x3F).
- Scenario: auto-pause on combat start (or combat flag raised while paused) with a buffered medpac as active head: head's node is in the list, detach removes it, head re-sent, node reattached after the quiet period: two medpacs.
- Fix: Record the head's round node at dispatch (`activeAction` + ptr, or match `spellId`/`itemId` against `h.head`) and exclude it from detach; detach only nodes that do not match the head. If no player node remains, skip detach.
- Test: PLAY: pause, buffer medpac, trigger combat while paused (auto-pause on); pass = `ROUND_DETACH ... act=detach` n counts only non-head nodes and one item use total. Logic test: a new pure `detachableMask(rn[], n, head)`.
- Engine question: does the held head sit as a pending list node (not cur) at the edge, and does the combat-start wipe leave it (doc 29 D6 says ClearAllActions never empties `+0xB00`; the brief says 0x51CB10 does)? Unresolved.

## V2-3 [med] CONFIRMED bug (refused companion serverCast is re-sent, then lost)
- Sources: h04-F3
- Where: QueueHud.cpp:1067-1091 (serverCast returns bool; WARN at 1089); 1095-1105 (dispatchAction is void, result dropped); 1824-1840 (RI_OK re-inject, no spacing); QueueHudLogic.h:874-885 (reInjectWhy has no paused / time gate), 1476-1488 (UNSEEN, rule 3), 666 (kMaxReInjectCount=2)
- Defect: serverCast returns false on `no_server_creature` / `not_commandable` / `id_mask` / engine 0, but the caller ignores it and leaves `buf.active=true`. The follower still has 0x3D and no node, so `reInjectWhy` yields RI_OK on consecutive ticks: 2 more identical refused calls, then RI_MAX and ~650 ms later AV_UNSEEN resolves the command with no DROP line. Paused: with `pause_reinject=1` and `pause_eaten_wait=1` (ini defaults) it additionally waits, then re-sends up to 6 more times (250 ms apart) after unpause before GIVE_UP. A transient refusal (companion stunned / in a scripted action, `CrCommandable==0`) permanently loses the buffered power after about 3 attempts. Trace is WARN x3 plus two "re-injecting eaten" lines only.
- Scenario: leader switch leaves companion B with a buffered Force power while B is briefly non-commandable; power icon vanishes, nothing cast, no RESOLVE/DROP naming the cause.
- Fix: Make `dispatchAction` return bool. On refusal with a transient reason (`not_commandable`, `no_server_creature`) keep the command active but skip re-inject and verdict (new `buf.dispatchDeferred`), retry on a 250 ms cadence until a 5 s cap, then emit a DROP (DR_REFUSED) line. On permanent reasons (`id_mask`) drop at once.
- Test: queue_hud_logic_test.cpp: reInjectWhy/activeVerdict with `dispatchDeferred=true` -> no RI_OK, no UNSEEN before cap; cap -> GIVE_UP. PLAY: stun/cutscene a companion with a buffered power; pass = single `SRV_CAST ok=0` then `SRV_CAST ok=1` after recovery, or one DROP after 5 s.
- Engine question: does 0x57D8B0 return nonzero on success? FINDINGS.md only documents 0 on the commandable refusal (0057d8e3); if success can also return 0, `!r` is a false refusal and the re-inject would double a queued cast only when the node is not yet visible.

## V2-5 [med] PLAUSIBLE bug (any left click counts as "Cancel")
- Sources: h03-F3
- Where: QueueHud.cpp:2055 (`g_lastClickTick` on every LMB edge); 1380-1393 (held-head cancel clears the whole buffer); 1566-1573 (detachTick cancel); QueueHudLogic.h:159-165; 834/2063 (queue Cancel hidden in hard combat)
- Defect: `cancelClickRecent` has no spatial test. In hard combat the queue Cancel is hidden, so a click within 600 ms before a held head vanishes without exec evidence (or before the engine goes quiet with detached nodes) wipes the member's whole buffer (DR_CANCEL) and discards the detached node.
- Scenario: grenade head wiped by the combat-start wipe; player clicks an enemy 100-500 ms after the edge (the normal reaction). Head is not re-sent and every buffered command is cleared. The wipe normally lands within ~70 ms (doc 30 QL3), so the window is narrow but the held case (up to 3 s) widens it.
- Fix: Record a click only when the cursor is on the vanilla clear-all/clear-one controls or on queue-hud's Cancel rect (`guikit::hit`); store position with `g_lastClickTick`. Otherwise treat a vanished head as RESEND.
- Test: logic: `cancelClickRecent` unchanged; add `clickIsCancel(rect, x, y)`. PLAY: grenade combat trigger plus buffered medpac, click an enemy 200 ms after the edge; pass = `HANDOFF_HELD act=resend`, no `why=cancel_click`.
- Engine question: the vanilla combat Cancel control rects are not located in this code.

## V2-6 [med] CONFIRMED bug (unsent head lost at combat end)
- Sources: h03-F5, h04-F1 (log aspect only)
- Where: QueueHud.cpp:1333,1342 (head moved out of `buf` into `g_handoff[k].head`); 1361-1366 (owner hold B1); 1400 (midFlight stall); 1742-1743 (combat-end `endHandoff(DR_COMBAT_CLEAR)`); 1275-1278
- Defect: At the edge the active command exists only in `h.head`. If combat ends before it is sent (owner not in slot k after a leader switch, or midFlight stalls), `endHandoff` discards `h` and the command is gone, while the other buffered commands survive and dispatch. The DROP line is trace-only (on in the installed ini).
- Scenario: held grenade head for leader A, player switches leader to B in combat; hand-off for slot 0 holds (ownerSlot != k); last enemy dies; combat-end tick drops the head.
- Fix: On combat end, if `h.headValid && h.sent == 0 (head unsent)` restore it as `buf.active=true` with `markDispatched(0)` semantics changed to "not dispatched" (new flag `needsDispatch`) or as `buf.queue[0]` after growing the array by one; let the sequential dispatch path send it. Keep the DROP line for held heads that were really released.
- Test: logic test for a pure `restoreHead(h, buf)`; PLAY: leader switch during a held-head hand-off, kill the enemy; pass = head dispatched after combat (`dispatching buffered`), not `DROP why=combat_clear`.
- Engine question: None.

## V2-7 [med] CONFIRMED edge-case (detached nodes stranded at combat end)
- Sources: h03-F2
- Where: QueueHud.cpp:1686-1687 (detachTick only in the combat branch); 1742-1743 (non-combat hand-off end, no reattach/discard); 1539-1546 (discard only at "new_combat" 1686, cancel, timeout 600 s)
- Defect: Nodes taken out of the round list by `detachRound` are re-added only by `detachTick`, which does not run outside combat. If combat ends while `g_detached[k].n > 0` the player's Force power/item click never runs and nothing is logged until the next combat edge discards it ("new_combat", trace-gated). `detachRound`'s `d.n != 0` guard stays closed meanwhile.
- Scenario: player clicks a power while a held head is in flight, detach takes it, last enemy dies; combat ends before the 300 ms quiet window; power never fires.
- Fix: Run `detachTick` (or a reattach-or-discard with a default-level log line) from `tickItemQueues` before the non-combat return path while any `g_detached[k].n > 0`.
- Test: PLAY: grenade combat trigger + click a power, end combat immediately; pass = `ROUND_DETACH act=reattach` or an explicit discard log within 1 s of combat end.
- Engine question: None.
